# ADR-0148: Serious Run State Machine And Phase Barriers

## Status

Accepted

## Date

2026-05-14

## Context

Production diagnostics showed that PolicyOS can produce draft decision packets
before legal, data, method, grounding, conflict, privacy, security, ownership,
and scorecard checks have produced authority or blockers. This creates a gray
zone where downstream artifacts look final even when upstream evidence is
missing, skipped, generated by fallback, or later contradicted by runtime
quality reports.

The system needs an accepted runtime authority state machine, not only
post-hoc readiness checks. A checker that notices premature authority after the
fact is useful, but the architecture must also define when serious runs are
allowed to advance.

## Decision

1. Serious runs use these authority states:
   `initialized`, `intent_bound`, `evidence_emitting`, `blocked`,
   `ready_for_scorecard`, `scored`, `readiness_closed`, `approved`,
   `rejected`, and `published_blocked`.
2. `initialized` means the run exists but has not yet bound all
   authority-bearing inputs. It may not score, approve, or publish.
3. `intent_bound` means policy intent, tenant, requested profile, run id, and
   time context are recorded, and legal/data/method/provider/mode inputs are
   either bound or blocked.
4. `evidence_emitting` means runtime producers are emitting authority-bearing
   events and CAS artifacts.
5. `blocked` means a required invariant failed before scorecard readiness.
   Non-overridable blockers stop approval and publication. Overridable blockers
   require the override policy defined by the invariant registry.
6. `ready_for_scorecard` means the required runtime authority graph is closed
   enough to score and contains only permitted evidence classes, provenance
   kinds, refs, and same-input bindings.
7. `scored` means the scorecard has verified ref identity, payload identity,
   provenance, schema compatibility, and gate semantics.
8. `readiness_closed` means readiness has accepted, rejected, or blocked the
   run using persisted scorecard identity and the evidence authority graph.
9. `approved`, `rejected`, and `published_blocked` are terminal authority
   projections over the closed readiness result.
10. Phase barriers are mandatory for:
    policy intent canonicalization; Lex retrieval and conflict checks; Fabric
    source selection and data quality; Foundry method/input quality; Scientist
    workflow, skipped-node, and claim ledgers; grounding and citation
    faithfulness; privacy, security, licensing, retention, and export
    compliance; tenant ownership and CAS governance; replay, resilience, and
    performance readiness; human review and approval readiness; final/public
    artifact compilation.
11. A downstream authority surface must not be produced or accepted when an
    upstream required barrier is missing, failed, skipped without typed blocker,
    or produced from disallowed fallback evidence.
12. Draft decision packets may exist before `ready_for_scorecard`, but
    publishable/final decision artifacts, production approval, and closeout
    pass must not.

## Consequences

Positive:

- Runtime order becomes explicit and testable.
- Final artifacts cannot silently precede grounding, conflict, privacy,
  security, ownership, or scorecard authority.
- Skipped nodes must become typed blockers or profile-allowed skips before
  downstream surfaces can rely on them.
- Readiness can explain whether a run is blocked by missing inputs, failed
  evidence, premature compilation, or non-overridable policy.

Negative:

- Some current happy-path canaries will fail because draft artifacts are no
  longer enough.
- Orchestration code must distinguish draft, scoreable, approved, rejected, and
  publish-blocked states.
- Retry and resume behavior must preserve state transitions and barrier
  evidence instead of recomputing only final files.

## Concrete impact

This ADR does not define an implementation plan. It requires future
implementation work to introduce or update:

- serious-run state records;
- phase barrier ledger schemas;
- transition guards in runtime orchestration;
- scorecard/readiness checks for state and barrier identity;
- negative tests for premature final artifacts, skipped nodes without blockers,
  post-workflow evidence emitted after decision packet authority, and
  readiness accepting unclosed runtime states.
