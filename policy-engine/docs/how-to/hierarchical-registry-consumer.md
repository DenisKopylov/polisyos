# Configured hierarchical registry consumer

`HierarchicalPolicySearchAdapter` is an internal node adapter. A caller may supply an existing canonical `ParetoRegistry` to its constructor. The adapter forwards that instance to each existing coordinator construction port. It does not create a default registry, choose a namespace, or establish an objective basis.

Parameterized searches keep the coordinator's existing typed-vector evaluation and publication path. Parameterless searches publish each actual typed evaluation once through the same registry API and return its freshly read projection. With no evaluator, the empty history remains empty. Scalar-only observations do not become typed feasible measurements. A missing declared basis produces a candidate-only projection; missing usable coordinates produce null hypervolume with the existing unavailable assessment. A quantity computed over observed axes, including genuine zero, does not authorize a ranked export.

Pass caller identity in `initial_context` as `run_id`, `tenant_id`, and `cell_id`. The planning node supplies these values from its actual `RunContext`. When a raw tenant is present, the adapter derives `tenant_hash` with the existing anonymization helper, rejects a conflicting supplied hash or transfer context, and enters the existing security tenant scope for the entire call. The scope resets on normal exit or failure. This routing does not replace or grant `AccessScope`. Cell identity is forwarded to the evaluator; the current transfer contract has no cell coordinate or cell partition. With no raw tenant, the previous ambient-context behavior remains available and is not evidence of tenant appointment.

The report exporter still reconciles all typed source rows against the registry eligibility denominator. Omitted, conflicting, or unevaluated source rows prevent global rank. A configured consumer is distinct from the default planning node's producer appointment: the default constructor still has no registry. No ordinary factory or context field is invented by this change.

## A-owned structure-context dependency

The current coordinator's structure seed reader resolves `candidate_id` and default task family without receiving `initial_context`. Tenant routing is supplied by the existing security scope, but task family and source run identity can differ from the parameter reader. The separate `A-structure-context.patch` is a proposed supplier change, not applied D product code. It adds the existing optional context to `generate_structure_candidates` and `_transfer_seed_candidates`, using the existing resolver. Its target is the exact A-W01 coordinator blob recorded in the handoff. A/G must review, apply, and run the supplied native red recipe before claiming that context edge.

Default producer appointment and a complete objective-basis packet remain separate inputs: an actual configured caller, its registry root/namespace, full eligible source rows including unknown outcomes, and the ordered metric/split/direction/unit/definition-version basis with resolvable source bindings. A-W04's complete method-selection catalog is not this policy-candidate denominator. The adapter does not manufacture those fields from a first row or a display label.

The existing cold parameter generator retains its technical envelope in history. The policy DTO projection accepts only its exact empty `semantic={"interventions": []}` payload and dictionary `_strategy_metadata`; meaningful semantic content, malformed technical metadata, and unknown policy fields refuse. The original history remains available, and canonical policy hashes still identify the actual policy payload rather than technical proposal metadata.
