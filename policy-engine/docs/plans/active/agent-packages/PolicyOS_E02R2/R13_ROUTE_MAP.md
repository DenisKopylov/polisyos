## Served acquisition: authorized action to same-tenant N7 re-entry

The canonical route already exists. It is a later, explicit acquisition action after a generation run identifies a requirement gap; N6 does not fetch data merely because it ran.

1. **Persisted cycle and route.** The HTTP lifecycle compiles and runs the natural-language job and persists its recursive generation run (`runtime/http/services/control/run_lifecycle.py:3266-3379`). The route loop reads the tenant-scoped completed job and a unique costed cycle, then forms a verified route closure carrying the stable design-problem subject and cycle references (`runtime/quality/acquisition_route_loop.py:240-353`).
2. **Authority and journal.** `AcquisitionActionService.request_decision` persists a decision without executing its effect; `execute` reserves the external action and queues the job; `handle_job` reloads the persisted decision before invoking the bound effect (`runtime/http/services/acquisition_action_service.py:323-376,378-468,470-603`). The WDI port resolves the exact live catalog route against authority, provision, and registry (`runtime/http/services/acquisition_surface_execution.py:140-190`). It reserves the attempt and constructs the journal identity/path from tenant, cell, run, and route (`:389-402,663-678`). The journal covers the authorized request.
3. **Data Forge execution.** The port invokes `execute_live_catalog_acquisition` with that bound authority, route entry, constraints, journal, and the bridge-supplied ArtifactStore (`runtime/http/services/acquisition_surface_execution.py:404-466`). The executor validates source lane, license/profile, harness, and constraints, appends the request to the journal, performs ingestion through its `store_factory`, and emits typed live evidence in pending-passport state (`runtime/quality/acquisition_executor.py:716-899,977-997,985-1073`). `_owned_ingestion_store` checks the configured root but returns the supplied store instance; it does not rebuild an unguarded store.
4. **Overlay, passport, native epoch.** The production container installs `AcquisitionWorldGrowthBridge` when the world-growth configuration, source-authority owners, and epoch owner are present (`runtime/http/container.py:435-470`; bridge builder: `runtime/http/services/acquisition_surface_execution.py:697-760`). The bridge is given the exact `control_service._artifact_store`, event log, epoch owner, and PromotionRuntime; the container checks that `PromotionRuntime.store` is the same object as `runtime_api_context.store` (`runtime/http/container.py:233-259,351-364`). The port submits the typed evidence and receipt refs to `AcquisitionWorldGrowthBridge.admit` (`runtime/http/services/acquisition_surface_execution.py:453-466`). The bridge selects the exact tenant/cell/run/route/stable-subject closure (`runtime/quality/acquisition_world_growth.py:210-218`), calls native `admit_acquisition_with_production_semantic_epoch` (`:283-328`), resolves activation, checks passport route/source lane, and measures a positive native membership delta (`:509-552`). Missing or invalid authority is quarantined and does not grow the world.
5. **Persist and re-enter.** The bridge writes the runtime authority artifact through the same store, carrying tenant/cell/run/job closure, same-input closure, and event (`runtime/quality/acquisition_world_growth.py:871-935`). After the port reports `world_committed`, `AcquisitionActionService.handle_job` records `world_committed_reentry_pending` and calls re-entry (`runtime/http/services/acquisition_action_service.py:588-603`; port: `runtime/http/services/acquisition_surface_execution.py:540-567`). `AcquisitionWorldGrowthBridge.resume` revalidates native epoch, overlay, passport, and receipt, then calls the controller's active-acquisition re-entry method (`runtime/quality/acquisition_world_growth.py:740-824`; controller: `runtime/quality/generation_cycle.py:3822-3936`). The validated re-entry receipt/event is persisted through the same store (`runtime/quality/acquisition_world_growth.py:815-824,871-935`).

This is the one world-growth write path aligned with GY N13b: Data Forge overlay admission, passport, and native epoch qualification. It consumes an explicitly authorized/journaled request and retains tenant custody through re-entry. See `docs/plans/active/layer3-slices/GY-engine-subordination.md:2787-2844,5402-5405`. The plan records the earlier ACQ-01 outcome as `typed_deeper_terminal`, with no world-growth epoch (`:5828-5830`); this repair would fix the caller path, not claim the broader GY task complete.

## Stable subject and revised active basis (R12)

`GenerationCycleRecord.design_problem_ref` is the stable subject; optional `design_problem_basis_ref` records the problem snapshot active for that cycle (`runtime/quality/generation_cycle.py:1012-1024`). `_cycle_record` derives the basis from the actual problem used for that cycle and preserves a supplied stable ref (`:9024-9059`); `_cycle_basis_ref` prefers the basis (`:9078-9086`). The served route closure carries the root `compiled.design_problem_ref` and root `compiled.design_problem` (`runtime/quality/acquisition_route_loop.py:321-353`). The bridge currently passes that root problem to `reenter_after_active_acquisition_overlay` (`runtime/quality/acquisition_world_growth.py:795-799`).

The controller first checks the root problem ref against `original_run.design_problem_ref`; that is the stable-subject check and should pass. It then checks `_cycle_basis_ref(source_cycle) != problem_ref` (`runtime/quality/generation_cycle.py:3840-3849`). For an acquisition-required source cycle after cycle zero, the basis may already be a revised snapshot. This is the first identity mismatch: it compares the cycle's active basis to the original root problem ref.

The correct active-basis derivation is from the **previous** cycle, not from the source cycle's own revision request. The served bridge currently supplies the root `closure.design_problem`, so the re-entry owner must resolve the active problem from the persisted run history while independently retaining the root subject:

- For `source_cycle.cycle_index == 0`, the active problem is the closure's root DesignProblem.
- For `cycle_index > 0`, find the immediately preceding cycle in the same `original_run.cycles` and take that cycle's `revision_request.revised_problem`.
- Require `_problem_ref(active_problem) == _cycle_basis_ref(source_cycle)` and separately require `original_run.design_problem_ref` to remain the stable subject.
- Re-enter using `active_problem`, and pass `stable_design_problem_ref=original_run.design_problem_ref` into `_run_cycle`. The new cycle's basis should be the active problem ref while its stable subject remains the root ref.

Why this distinction matters: `run()` advances `current_problem` from the previous cycle's `revision_request.revised_problem` only when that previous cycle's VOI action is `advance` (`generation_cycle.py:3763-3780`). `_cycle_record` hashes the problem used in the cycle (`:9024-9059`); `_default_revision_request` creates the next problem with grammar/revision updates (`:8869-8906`). The source cycle's own `revision_request.revised_problem` is therefore the *next* problem, not its active basis. Fixing only the initial comparison would leave later currentness/receipt checks comparing or issuing the wrong identity (`generation_cycle.py:3987-3995`). The served movement consumer validates stable subject and cycle identity but does not independently compare the source/new active basis (`acquisition_movement.py:318-335,588-680`); its behavioral witness must carry both identities through bridge re-entry and movement, and reject foreign subject/basis cross-binding. Keep the correction in the existing controller re-entry owner and existing movement consumer; do not add a bridge↔controller owner.

## Canonical re-entry source-candidate identity (same R13 / ACQ-01 class)

The served re-entry receipt currently proves the identity of its own payload but does not prove that its source-candidate reference belongs to the route closure being consumed. `GenerationCycleRecord` carries `selected_candidate_ref` and `selected_candidate_content_hash` (`runtime/quality/generation_cycle.py:1027-1028`). The controller issues `AcquisitionOverlayReentryReceipt` with the source cycle's candidate reference, but omits its content hash (`:3993-4000`). `AcquisitionWorldGrowthBridge._validate_reentry` compares run, stable problem, cycle, overlay receipt, and admitted count (`runtime/quality/acquisition_world_growth.py:827-842`), but does not compare the receipt's candidate identity to the closure. There is a second, independent consumer: `AcquisitionMovementService` reloads the current closure and checks `reentry.source_candidate_ref` but not a content hash (`runtime/quality/acquisition_movement.py:318-335`). Both consumers can therefore accept a self-consistent receipt that names the same candidate ID with different candidate bytes. The receipt's self-hash (`generation_cycle.py:1187-1220`) only binds the fields present in the receipt; it does not bind them to either consumer's closure.

This is a same-class, deeper ACQ-01 route-binding defect under P40, not a new class and not the local-atom re-entry issue from R12. The canonical served path creates a fresh cycle through `reenter_after_active_acquisition_overlay` (`generation_cycle.py:3822-4018`); it does not consume or rebind the previous atom object. The local N7 arm's `isinstance(prior_atom, InterventionAtomBinding)` check is a separate reason to remove that arm from production. Do not claim that fixing canonical receipt binding closes that local atom-consumption gap.

There is a prerequisite to using the cycle's hash as a content identity. `_candidate_content_hash` prefers `atom.content_hash`, candidate/provenance hash fields, but falls back to `gy_content_hash(_json_ready(_candidate_id(candidate)))` (`generation_cycle.py:8338-8348`). The `GenerationCycleRecord` validator accepts a missing `candidate_binding` by returning early (`:1063-1079`); a SHA-shaped `selected_candidate_content_hash` therefore does not prove that candidate content was hashed. At source-cycle admission, recompute the digest from the canonical candidate payload or resolve and hash its content-addressed artifact, then independently compare that result with the cycle's selected hash and the candidate binding. Do not use an ID-only digest or a self-declared metadata field as the R13 lineage predicate. If the source content cannot be resolved and recomputed, leave candidate computation available with a typed unknown, but do not treat that cycle as having authority-grade candidate lineage for acquisition re-entry.

Minimal owner-first change: at source-cycle admission, require the independently recomputed content digest described above. Add `source_candidate_content_hash` to the existing `AcquisitionOverlayReentryReceipt`; have its canonical issuer copy the content-verified source-candidate ID/hash from `source_cycle`; and update both existing consumers—the bridge's `_validate_reentry` and `AcquisitionMovementService`—to require an exact ref-and-hash match against their re-resolved `VerifiedAcquisitionRouteClosure.source_cycle`. Keep this in existing candidate, receipt, bridge, and movement owners rather than creating a sibling lineage service. The property is that **every served re-entry consumer binds the receipt to the exact candidate bytes selected by the source cycle whose authorized acquisition route was admitted**. The digest predicate is `recomputed` from candidate content at source-cycle admission; the receipt's self-hash and matching string fields alone are not independent evidence.

The receipt is already versioned (`policyos.runtime.acquisition_overlay_reentry.v1` and `.v2`, `generation_cycle.py:1157-1162`).
