# R4 source map: GY-N6 validator scope mismatch

**Scope:** source-only diagnosis and checker design against the product code at `codex/e02-r2-partial-triage` (source blobs cited below). This docs-only correction does not change product source. No tests or native jobs were run; the proposed fix and probes remain unverified by execution.

## Finding and recommended checker repair

The checker opens its private verification session from the initial `DesignProblem`, but the `GenerationCycleController` calls N9 once after the cycle loop with `last_cycle_problem`, the active basis of the last cycle. When a cycle revises the problem, the stable namespace ID stays the same while the root-bound owner projection hash changes; the correct owner guard raises `confidence_ledger_scope_binding_mismatch`. This explains the reported checker crash without implying the scope check is defective.

Use a checker-local lazy adapter implementing the existing N9 call protocol. On the first `__call__(summaries=…, problem=…)`, derive the N9 binding and verification risk scope from that exact typed `problem`, open exactly one `_for_verification` session under the checker’s fresh temporary `state_root`, construct `CanonicalN9PromotionPort._for_verification(...)`, and delegate. Retain that exact `problem` and the opened session in replay context, and use both for `_embedded_promotion_comparison_admissions`. Cross-check the callback problem’s recomputed hash against the run’s final `design_problem_basis_ref` and, for a revised cycle, the prior cycle’s `revision_request.revised_problem` hash. Refuse a second callback with a distinct binding in this single-run fixture; the source controller has one post-loop promotion call.

This is a checker-local source-replay correction. The current checker creates a fresh `TemporaryDirectory` for each live verification run, so no initial scope root has been written when the lazy adapter opens its one session. It does not open a second scope or reset an existing scope, and it does not select production policy for continuity of durable risk spend across separate runs or changed projections. Keep all three scope/binding guards intact. A confirmed mismatch in live rederivation should be a typed `fail`; reserve `UNRUN`/exit 2 for an actual inability to inspect/rederive the source, not for this currently understood mismatch. Persisted receipt disagreement remains a typed `fail`, not a reason to restamp.

## Source trace

1. `ConfidenceRiskBudgetScope.scope_id` hashes `scope_owner_ref`, `authority_purpose`, `owner_scope_key`, and `epoch_ref`, but omits `owner_projection_hash`. The projection is nevertheless part of the full `risk_scope` and therefore of the immutable root binding. [confidence_ledger.py@c3775ce0a96966fcbc46fa243e5cc03f3a80c84b]
2. Session files are keyed from the stable scope ID, while root validation checks the full scope. Opening a different owner projection with the same stable ID against an already initialized state root is a binding collision (`ledger_scope_binding_mismatch`), not a fresh budget. [confidence_ledger.py@c3775ce0a96966fcbc46fa243e5cc03f3a80c84b]
3. The checker currently derives the initial problem/binding and opens `_for_verification` before controller construction. It then injects a static `_VerificationN9PromotionPort` holding that session. Its live fixture uses a fresh temporary state root per run. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160]
4. The existing verification port protocol is `__call__(summaries, problem)`. `_VerificationN9PromotionPort` recomputes the binding from that exact `problem`; `CanonicalN9PromotionPort._for_verification` accepts a verification-provenance session and constructs the private port. A checker-local adapter can therefore defer session construction until it sees the real active input and then delegate through the owner’s existing verification path. [promotion_sequence.py@dc8beab981b714e80e54bef22ba83bc66ab3ffd4]
5. `GenerationCycleController.run` initializes `current_problem` and `last_cycle_problem` from the input. After each cycle it assigns `last_cycle_problem = current_problem`; on `advance` it sets `current_problem = cycle.revision_request.revised_problem`. After the loop it makes one `_promote_completed_generation` call with `problem=last_cycle_problem`. The checker’s Lane-0 run enters this `contract_testing` path, which invokes the injected port once. [generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a]
6. The full revised problem is replayable from run history. `DesignRevisionRequest.revised_problem` is typed `DesignProblem`; `GenerationCycleRecord` stores that request. For a final cycle at index greater than zero, the immediately preceding cycle’s `revision_request.revised_problem` is the problem used by the final cycle. Recompute `_problem_ref`/the N9 binding and check it against the final cycle’s `design_problem_basis_ref`. For a single-cycle run the initial `_design_problem()` is the active basis. The adapter’s callback argument provides the exact live object; run-history reconstruction is an independent consistency check, not a guessed reconstruction. [generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a]
7. The checker currently passes its initial `problem` to `_embedded_promotion_comparison_admissions`, even though receipts from revised runs bind the active N9 problem. Use the adapter-retained active problem and same session there. The run does retain enough history to cross-check the active problem as described above; the earlier claim that the full revised snapshot was absent was incorrect. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160; generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a]
8. There are three relevant owner guards and all must remain:
   - `_run_n9_promotion_port_batch` compares the session’s full `risk_scope` with the scope recomputed from the active problem (`promotion_sequence.py`, approximately lines 3116–3134).
   - `_run_promotion_sequence_with_bound_session` independently repeats that full-scope comparison (`promotion_sequence.py`, approximately lines 4018–4028).
   - `CanonicalPromotionReceipt._promoted_requires_trace` checks the receipt’s projected `risk_scope` against the scope derived from its owner-projection problem binding (`promotion_sequence.py`, lines 2045–2054). This third check can keep a mutation test red when the two runner guards are removed, so it must be accounted for in the removal probe.
   [promotion_sequence.py@dc8beab981b714e80e54bef22ba83bc66ab3ffd4]
9. The reported crash escapes while rebuilding the live payload, before the checker’s narrow comparison-error handling. The CLI currently prints pass or the issue report and exits 0/1; it does not implement `UNRUN`/exit 2. Keep a narrowly typed `UNRUN` path for inspection failures if the checker boundary needs it, but do not translate the known correct scope guard into `UNRUN`. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160]

## Main/E02 provenance and scope boundary

- At main (`5fd3ebcc15637e98bbd4938de5d62ee5004504a`), controller promotion used the original problem after the loop, so the checker’s initial-problem session matched that route.
- E02 commit `ac2379319c3683bdd8943909851817eee8dc7a0a` (`fix(cyc): separate recursive subject and cycle basis`) added an explicit `design_problem_basis_ref` while keeping the subject ref stable.
- E02 commit `69dfb4439629f389a8bb1a45bfccb439d8686c83` (`fix(cyc): bind promotion to current basis`) changed promotion to use current candidate summaries and the last active problem/basis. The checker’s pre-loop session setup and initial-problem comparison input did not follow this change.
- Scope derivation and all three guards are existing owner behavior; the source delta exposing the checker mismatch is the generation-cycle current-basis path plus the unchanged verifier fixture. Main `generation_cycle.py@783793ef24227aa1e94e7473f91a9a35c7fe336a`; E02 head `generation_cycle.py@a17e52cff360f554478dd44844ea3ef27c62c043`; merged product code `generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a`. The checker source is `@b8134aeffe3b96760e7fd9663ae9670e85391160`.
- The proposed lazy session is scoped to the checker’s disposable verification namespace. It does not settle how a production durable N11 ledger should behave if a later run revises the same stable subject projection; that production continuity question and any governed transition remain outside this R4 checker repair. No durable ledger root, epoch, receipt, or authority artifact is to be reset or restamped.

## Test and probe plan

**Existing tests to replay after an implementation:**

- `tests/unit/runtime/quality/test_generation_cycle.py::test_generation_cycle_contract_mutations_turn_red` — the live two-cycle emission and its decisive mutation must complete and validate.
- `tests/unit/runtime/quality/test_generation_cycle.py::test_generation_cycle_contract_write_refuses_stale_comparison_admission` — preserving control: valid live owner replay still refuses a stale comparison admission with `generation_cycle_comparison_admission_manifest_drift`.
- `tests/repo_quality/tools/test_layer3_gy_generation_cycle_contract.py` — add checker regressions that assert the lazy adapter opens one verification session on the first active N9 callback, reuses that same session and exact problem for comparison admissions, checks the callback against the final basis and prior-cycle revised snapshot, and rejects a second distinct binding. Assert a confirmed persisted/live binding mismatch yields typed `fail`/exit 1; only an actual source-inspection inability yields typed `UNRUN`/exit 2 without traceback.

**Direct owner probe:** call the N9 owner with a verification session rooted at the initial problem and the final revised problem as its input. It must refuse at `_run_n9_promotion_port_batch` with the exact `confidence_ledger_scope_binding_mismatch` code before receipt construction. Do not weaken this assertion to any generic validation failure; the receipt-level third guard can fail later and mask a missing runner check.

**Property-wide removal probe:** keep the same deliberately mismatched initial session and revised active problem, retaining `scope_id`, `owner_projection_hash`, receipt markers, and error-code markers. In the mutation-only source variant remove the full-scope guard in `_run_n9_promotion_port_batch`, the repeated full-scope guard in `_run_promotion_sequence_with_bound_session`, **and** the `CanonicalPromotionReceipt._promoted_requires_trace` check binding the receipt projection to its problem. The behavioral assertion must then turn red by detecting an incorrectly accepted/misbound receipt or false-green replay. Removing only the first two is inconclusive because the receipt validator can mask their deletion; removing only one is inconclusive because a sibling check remains. Keep all three checks in production code.

**Property-preserving control:** with an unchanged problem projection, the lazy session scope, callback problem, final cycle basis, and receipt projection all agree; the three guards accept the exact owner-produced binding. Then mutate only the frozen comparison admission and retain the established stale-admission refusal. Also preserve the two-cycle mutation test’s prior behavior. This control permits ordinary correctly scoped candidate verification without relaxing binding or stale-comparison authority.

## P37 / P38

- **P37 predicates:** the callback problem’s content hash, N9 binding, and full expected risk scope are recomputed from the typed owner input. The final `design_problem_basis_ref` is recomputed from the final cycle’s active snapshot and independently reconciled against the prior cycle’s `revised_problem`; the lazy adapter’s retained callback input is also checked against it. Session-to-scope and receipt-to-owner-projection comparisons are recomputed by the N9 owners. `scope_id` is recomputed but proves only stable namespace identity; it deliberately omits `owner_projection_hash`. Production cross-run N11 spend continuity across revised projections is not established here and is not decided by this checker-local repair.
- **P38 property:** every live N9 verification receipt and comparison admission binds to the active problem snapshot actually passed to post-loop promotion. **Current implementation:** checker opens a session from the initial problem and also passes that initial problem to comparison admission, while the controller promotes with the last active problem. **Divergent case:** a two-cycle run shares stable subject/scope ID across its initial and revised problems but has a different final basis/projection hash; a gate keyed only to the stable ID would miss it, and the current static session fails the exact full-scope check. The lazy adapter binds to the active callback problem, with run history as an independent check.
- Relevant register patterns: P07 (replay), P29 (exercise the owner path), P31 (one invariant across all consumers), P32 (content-bound identity), P37 and P38. [policy-design-case-failure-patterns.md@7f4cc9ab9541a44c26e4648a2c08326e53743492]

## Limits
