# R4 source map: GY-N6 validator scope mismatch

**Scope:** source-only diagnosis at `codex/e02-r2-partial-triage` HEAD `a4ae728124ec5a9c5109a0664cd182428a006ddf`. No tests, native jobs, or writes to product code were run. This map records the reported crash and the source path that explains it; it is not a runtime receipt.

## Finding

The reported `confidence_ledger_scope_binding_mismatch` is explained by a stale verification fixture, exposed by E02's switch to promoting against the final active problem basis. The canonical N9 scope check is doing the right exact comparison. The checker creates one immutable verification session for the initial `DesignProblem`, but after a revision its private verification promotion port receives the revised `DesignProblem` and reuses that initial session. The expected scope's projection hash therefore differs from the session's bound projection hash.

This is not evidence to remove `problem_content_hash` from the risk scope or substitute the stable subject reference for the active problem basis. That would weaken N9's exact owner binding. Whether successive revised bases under one stable subject should share accumulated risk spend is a separate scope-identity question; this source diagnosis does not settle it.

## Call chain and mismatch

1. `N9DesignProblemBinding.from_problem(problem)` hashes the complete typed `DesignProblem.model_dump(mode="json")`; `confidence_risk_scope_for_problem(binding)` then binds the N9 scope to that problem id, content hash, model ref, and schema version. The canonical `CanonicalN9PromotionPort.__call__` derives a binding from its actual `problem` argument and opens the session for that same binding. That owner route is internally aligned. [promotion_sequence.py@5751f1634924bf549aa00f94417b4e9a72a50232]
2. The private `_VerificationN9PromotionPort.__call__` also derives the binding from its current `problem`, but it reuses the single session injected at construction. `_run_n9_promotion_port_batch` checks `session.risk_scope == confidence_risk_scope_for_problem(problem_binding)` and raises `ValueError("confidence_ledger_scope_binding_mismatch")` on disagreement. The bound sequence has a second exact scope check before executing a promotion. [promotion_sequence.py@5751f1634924bf549aa00f94417b4e9a72a50232]
3. The N6 checker creates `_design_problem()`, derives its binding, and opens one `_for_verification` session from that initial binding before constructing the controller and its verification port. That is suitable only while promotion is still bound to the initial problem. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160]
4. The Lane-0 revision changes `runtime_hints` (including the next grammar and revision record), so its revised problem has a different complete content hash. E02 also changed the controller to retain `last_cycle_problem`, pass that active problem into N9, and supply the last cycle's basis. The same checker port still holds the initial session. [generation_cycle.py@abb37214d5f87d1816add1625241e29b7de53c17]
5. There is a second stale-input seam after the promotion call: `_VerificationReplayContext` stores the initial `problem`, and `_embedded_promotion_comparison_admissions` receives that same initial problem. Once the session is aligned, committed-receipt comparison must also use the active problem and the session actually used by the verifier port, or the receipt's revised binding will fail replay against the initial problem.
6. `validate()` calls `_validate_committed_contract_text()`, which rebuilds the live payload before its narrow `ValueError` handler around canonical frozen-contract reconciliation. A mismatch thrown while building the expected live payload at that earlier step escapes; `main()` only formats a returned report. Thus the present path produces no checker verdict for this harness failure. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160]

## Narrow owner-correct repair sequence

1. Preserve `N9DesignProblemBinding` and `confidence_risk_scope_for_problem` unchanged. Do not rewrite ledger scope identity around `design_problem_ref`, omit the content hash, mutate a sealed session, or turn the equality check into a warning.
2. Make the private verification port obtain an immutable verification session for the exact active `DesignProblem` binding passed to its call, using the same isolated verification registry, CAS, and state namespace. A small factory/cache keyed by the recomputed scope is the narrow fit; it must return the same scope-bound session to subsequent replay consumers. This mirrors the canonical N9 owner's existing `binding -> session` route without granting verification authority.
3. Return or retain the actual active problem/session pair from the verifier port and put that pair in `_VerificationReplayContext`. Use it for embedded comparison admission and revalidation. Keep the run's stable subject identity and each cycle's explicit basis as separate values.
4. At the checker boundary, classify a confirmed mismatch in persisted promotion data as `fail` with a typed issue. A failure to complete rederivation because the checker context cannot be constructed is `UNRUN` with the failure named, and CLI exit 2. Do not turn either case into pass, and do not catch every exception as a semantic fail. Once this harness mismatch is removed, the existing contract can return its content verdict (the prior reported base result is a typed fail with three issues); no artifact should be restamped to avoid the verdict.

## P37 / P38

- **P37 predicates:** (a) the content hash of the typed problem is `recomputed` by `N9DesignProblemBinding.from_problem`; (b) the expected scope is `recomputed` by `confidence_risk_scope_for_problem`; (c) equality against the immutable session scope is `recomputed` by the N9 owner. However, the checker currently supplies a session constructed from the initial problem rather than the active problem, so its verification-context premise is stale. The mismatch is caught closed but is not mapped to a report. Do not call the scope predicate independently reconciled; no independent owner is consulted by that equality check.
- **P38 property:** the governed check must replay the promotion against the exact active problem basis and return a typed verdict. **Implementation:** it creates an initial-problem session, passes it into the private port, and allows the resulting `ValueError` to escape during live rederivation. **Divergent case:** an otherwise well-formed current two-cycle run whose second cycle revises `runtime_hints`; active-basis promotion is correct, but a stale fixture scope prevents any verdict. This is a real divergence between the checker contract and its actual behavior, not a reason to weaken the N9 binding.
- Relevant register patterns: P07 (historical/rule replay), P29 (recompute the live owner path), P31 (one scope invariant across both runner checks), P32 (exact content-bound identity), P37 and P38. The register requires a remove-property/keep-markers probe and requires naming what the predicate is derived from and where the implementation diverges.
