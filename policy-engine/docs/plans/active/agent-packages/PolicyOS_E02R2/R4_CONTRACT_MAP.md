# R4 source map: GY-N6 validator scope mismatch

**Scope:** source-only diagnosis against `codex/e02-r2-partial-triage` at `0e749d088`. This map-only correction does not change product source. No tests or native jobs were run; this is not a runtime receipt.

## Finding

The reported `confidence_ledger_scope_binding_mismatch` is explained by the checker opening one immutable verification session from the initial `DesignProblem`, while E02's N6 controller later promotes against the final active problem basis. The canonical N9 check correctly compares the complete risk-scope object, including its owner projection hash. This is not safely repairable by opening one session per revised basis: the scope ID is deliberately stable across revisions and all those sessions resolve to the same durable ledger namespace, whose root is already bound to the initial projection.

Do not remove the projection hash from N9's scope or weaken either exact-scope guard. Whether successive revised bases under one stable subject should share accumulated risk spend is an unresolved owner/principal decision. The repository evidence here establishes neither continuity policy nor authority to create a fresh ledger budget for each revised basis.

## Call chain and mismatch

1. `N9DesignProblemBinding.from_problem(problem)` hashes the complete typed problem. `confidence_risk_scope_for_problem(binding)` retains the stable owner key `design-problem:{design_problem_id}` and binds `owner_projection_hash` to the complete problem content hash. But `ConfidenceRiskBudgetScope.scope_id` excludes `owner_projection_hash`; it hashes owner, purpose, stable owner key, and epoch. Thus the stable subject chooses the budget namespace while the projection hash is part of that namespace's root binding. [promotion_sequence.py@dc8beab981b714e80e54bef22ba83bc66ab3ffd4; confidence_ledger.py@c3775ce0a96966fcbc46fa243e5cc03f3a80c84b]
2. `ConfidenceLedgerSession` derives `.head.json`, `.lock`, `.append.wal`, and `.scope.json` paths from `scope_id`. Its immutable root contains the full `risk_scope`; `_initialize_or_validate_root()` and `_load_state_locked()` reject a same-ID scope with a different projection as `ledger_scope_binding_mismatch`. Opening a revised-basis session in the same verification state root therefore does not create an independent session: it collides with the initial root. [confidence_ledger.py@c3775ce0a96966fcbc46fa243e5cc03f3a80c84b]
3. `_VerificationN9PromotionPort` is constructed around one session. Each call derives a fresh binding from the `problem` it receives, then `_run_n9_promotion_port_batch` compares the session's complete scope to that problem's derived scope. `_run_promotion_sequence_with_bound_session` independently repeats the exact check before executing the sequence. The mismatch is intentionally caught by both owner guards. [promotion_sequence.py@dc8beab981b714e80e54bef22ba83bc66ab3ffd4]
4. The checker creates `_design_problem()`, derives its binding, and opens one `_for_verification` session before constructing the private promotion port. E02's controller then retains `last_cycle_problem` and supplies it to promotion. A Lane-0 revision changes `runtime_hints`, so the active problem hash differs from the initial problem hash even though the stable subject stays the same. The initial session is reused against this active basis and fails the first exact-scope guard. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160; generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a]
5. The checker has a second binding defect: `_embedded_promotion_comparison_admissions()` receives the initial `problem`. Comparison admission verifies the supplied problem against each receipt's `design_problem_binding`; E02's final N9 receipt is produced from `last_cycle_problem`. Passing the initial problem is therefore wrong for a revised receipt. The run stores the initial `design_problem_ref` and per-cycle basis refs, but not the full revised `DesignProblem` snapshot needed by this comparison call. A stable subject ref cannot substitute for that typed active basis. Do not claim this seam is solved by changing the verification-session namespace; retaining or deriving the exact per-receipt basis remains a separate checker/artifact-design residual. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160; promotion_sequence.py@dc8beab981b714e80e54bef22ba83bc66ab3ffd4; generation_cycle.py@65d830f71dccd9c3b1e943e5e132678f7221ed8a]
6. `_validate_committed_contract_text()` rebuilds the live payload before its narrow handler for two comparison errors. The scope mismatch occurs during live owner rederivation, before a report exists, and escapes to `main()`. `main()` currently renders only `pass` versus other statuses and returns 0 for pass, 1 otherwise; it has no typed `UNRUN`/exit-2 path. [check_layer3_gy_generation_cycle_contract.py@b8134aeffe3b96760e7fd9663ae9670e85391160]

## Narrow checker repair and owner decision boundary

1. Keep `N9DesignProblemBinding`, `confidence_risk_scope_for_problem`, `ConfidenceRiskBudgetScope.scope_id`, immutable ledger-root binding, and both scope-equality guards unchanged. Do not add a per-revision factory/cache: because `scope_id` is stable, every such session targets the same head, WAL, and tombstone while its full root binding changes. Do not create a new namespace, reset a root, or silently choose whether risk spend follows a stable subject or each revised basis.
2. At the checker boundary, classify the exact live-rederivation scope-continuity failure as typed `UNRUN` (inspection could not establish a verdict) with a specific issue such as `verification_scope_continuity_requires_owner_decision`, and exit code 2. Limit this branch to the checker-owned live fixture's attempt to reuse the initial verification session for the active revised basis; do not convert arbitrary exceptions to `UNRUN`.
3. Keep persisted-artifact validation distinct. When replay confirms that a committed receipt's projection/root does not match its own bound N9 problem, return typed `fail` with the confirmed binding issue and exit code 1. The checker must not report `pass` or restamp receipts to make either condition disappear.
4. Fix the embedded-admission input only when the checker can supply the exact typed problem basis bound by each receipt. The current replay context retains only the initial problem, and the run has hashes for revised bases but not their full typed problem snapshots. Record this as unresolved until an owner-correct, replayable basis source exists; substituting the stable subject ref or guessed reconstruction is not sufficient.
5. Leave spend continuity unresolved for the principal/ledger owner: decide whether revisions under one stable problem subject share one budget or require separately named budget scopes and a governed transition. Until that decision and mechanism exist, the checker cannot claim successful live rederivation of revised-basis promotion. This residual is owner-decision blocked, not a reason to change ledger internals in this repair.

## P37 / P38

- **P37 predicates:** the full `DesignProblem` hash and expected risk-scope object are `recomputed`; each exact comparison with the immutable session scope is `recomputed` by the N9 owner. `scope_id` is also recomputed, but it deliberately omits `owner_projection_hash`, so it establishes the stable storage namespace only. The persisted root includes the full scope and rejects a changed projection under that same ID. Whether N11 spend should continue across revised projections is `not_established` and needs an owner/principal decision.
- **P38 property:** the checker must replay the owner behavior or return a typed non-verdict when its verification setup cannot establish the necessary session/basis relation. **Implementation:** it derives a session from the initial problem; E02's controller promotes with the active revised basis; both N9 guards correctly reject the scope mismatch; the checker lets that setup failure escape. **Divergent case:** the initial and revised problem share a `scope_id` because the stable owner key is unchanged, but their `owner_projection_hash` differs and the persisted root remains bound to the initial projection. A gate that compares only `scope_id` would miss the exact projection divergence; a checker that catches the current mismatch without a three-valued report crashes instead of returning `UNRUN`.
- Relevant register patterns: P07 (historical/rule replay), P29 (recompute the live owner path), P31 (one scope invariant across both runner checks), P32 (exact content-bound identity), P37 and P38. The register requires a remove-property/keep-markers probe and requires naming what the predicate is derived from and where the implementation diverges.
