## Conflict origins

### Epoch evidence — exact same bytes, different kind

`tests/_helpers/chronology_qualification.py:_put_statement` converts the typed statement to a raw mapping, canonicalizes it, and frames it (`:85-93`). `core/security/chronology_anchor.py:canonical_statement_bytes` performs the same three operations (`:471-476`). Thus the stored admission bytes and the later signed admission bytes are identical.

The fixture initially stores the `PredicatePolicyAdmissionStatement` using kind `fixture.predicate-policy-admission` (`tests/_helpers/chronology_qualification.py:1890-1904`). `_policy_configuration` reads that statement back (`tests/unit/runtime/quality/test_epoch_deployment.py:351-354`) and calls `FileSystemSignedArtifactEvidenceRepository.persist_signed` with the same canonical bytes and kind `policy.admission` (`:371-382,393`). `persist_signed` writes the subject through `store.put_bytes(blob_bytes, write_options)` (`core/artifacts/signed_evidence.py:140-152`). Since filesystem CAS validates the full existing profile and raises on mismatch (`core/artifacts/_manifest_lifecycle.py:63-108`; `core/artifacts/store.py:642-710`), this is a deterministic `kind` conflict.

The same `_policy_configuration` helper is used by the epoch deployment tests (`test_epoch_deployment.py:404-465`), the runtime deployment security test (`tests/unit/runtime/http/test_runtime_deployment_security.py:40-54`), and the promotion epoch deployment test (`tests/unit/runtime/quality/test_promotion_epoch_deployment.py:56-60`). The source evidence explains those R9 reds. The fixture should use an explicitly typed view, not alter its kind or add an envelope solely to evade the conflict.

### ProgramGraph — likely fixed-body / different-input collision; exact object unconfirmed

The failing test builds one filesystem CAS, one program graph, and intervention overrides with different rates (0.10 and 0.20), then runs individual, pairwise, and joint cases through a four-step horizon (`tests/unit/runtime/quality/test_joint_simulation_horizon.py:503-601,761-788`). `joint_simulation_horizon.py:1360-1393` calls `execute_program_graph` for each step and applies the returned state delta.

The executor assembles manifest inputs from program graph, execution plan, lowered IR, an optional parameter-override bundle, and each emitted patch-value artifact (`foundry/execute/_internal/graph/__init__.py:474-491`). The test supplies `parameter_overrides` but not `parameter_override_bundle_ref`, so the persisted input profile here includes patch-value IDs rather than a direct reference to the override mapping.

The strongest static collision candidate is `foundry.constraint_report`. The executor initializes a fixed empty report (`__init__.py:202-210`); this fixture's graph has only one mechanism node and no `check_constraints` node (`test_joint_simulation_horizon.py:543-565`), so the report is not recalculated. Because the fixture supplies a non-null empty constraint registry (`:600`), the executor still persists that report (`__init__.py:529-540`) with the per-run dynamic input list (`:474-491`). This gives the shape required for an `inputs` conflict: same report bytes, differing patch-input profiles. `foundry.state_delta` and `foundry.metrics` also persist against that input list (`:493-526`).

This is a likely diagnosis, not a measured artifact identity. No source-only read establishes the colliding ID or both exact `inputs` arrays. The baseline broker should capture the CAS ID, kind, and two manifest profiles for the actual failure before closure is claimed.

## Additive API and invariants

Recommended shape: retain `ArtifactID` as the content hash and add a typed `ArtifactViewRef(artifact_id, view_id)` with separate view-aware operations. A deterministic view ID must be recomputed from a canonical, versioned profile containing every persisted profile field: `byte_size`, kind, media type, schema, canon, inputs, producer, environment, governance, tenant context, same-input closure, authority marker, and persisted warnings (`core/artifacts/manifest.py:222-242`). `byte_size` is derivable from the blob but must still be reconciled with the manifest field in the profile key. Persisted warnings also belong in the key; the new view write contract must accept or deterministically produce them before key calculation. Content identity and integrity remain independently checked against the blob; `created_at` is descriptive and should not make otherwise identical views differ.

The view ID and any authority marker in the manifest are integrity bindings only. They do not prove an appointment, signer identity, trusted role, or current authority. Those are admitted separately by verification of the detached signature and verifier provenance. Likewise, a `tenant_context` value in the manifest is descriptive profile data, not the caller's custody. Each operation must resolve tenant and cell ownership from the runtime-bound store scope and check that ownership against the selected view.

Keep existing `ArtifactRef`, `InputRef`, `ArtifactManifest`, and legacy `put_bytes/get_manifest/verify_signature` semantics intact. `ArtifactRef` currently carries only content ID, kind, and media type (`core/artifacts/manifest.py:187-209`); existing `InputRef` carries only an artifact ID and role (`:187-197`). Making a legacy ref implicitly select among views would be ambiguous. Introduce a separate structural `ArtifactViewStore` protocol rather than requiring all legacy implementations to implement new methods immediately (`core/artifacts/protocol.py:26-78`). A view manifest must have typed view inputs when a parent profile matters; do not silently collapse those edges back to bare IDs.

The filesystem implementation should store one immutable blob and separate view manifests at deterministic view-specific paths under the existing artifact directory. It must verify that the reference's view ID recomputes from the complete stored profile before returning a manifest or signature. Reuse the existing CAS owner, artifact lock, atomic writer, and manifest-profile logic (`core/artifacts/store.py:642-726`, `core/artifacts/_manifest_lifecycle.py:63-108`); do not create a parallel store beside `FileSystemCAS`. Today `_iter_artifact_ids_lazy` enumerates `*.manifest.json` and accepts only a 64-hex basename (`store.py:1083-1107`). Preserve that legacy artifact-ID census; add `_iter_artifact_views_lazy`/`iter_artifact_views` over an explicitly recognized view layout. A view sidecar must not be mistaken for a new blob ID or silently disappear from view enumeration.

Kind-qualified IDs alone are insufficient: the observed ProgramGraph conflict is in `inputs`, and the full profile also carries tenant and authority facts. Hashing a profile into `ArtifactID` instead would change its stable `sha256:<64hex>` content-address ABI (`core/artifacts/ids.py:13-39`) and force broad path/reference migration. An explicit view ref preserves the blob identity and types the selected interpretation.

### Signatures, evidence records, and transfer

Current signature statements bind artifact ID, blob hash, and exact manifest hash (`core/artifacts/signing.py:67-100`). The signature sidecar path and operations are keyed only by artifact ID (`core/artifacts/_layout.py:25-27`, `_signature_ops.py:111-177`, `store.py:514-585`). Add view-specific snapshot, sidecar, sign, and verify operations; never overwrite or restamp a legacy signature. The exact manifest digest cryptographically binds the selected manifest, but the view ID itself is not a signature and does not establish authority. Resolution must select the manifest and signature for the same typed view, then separately verify signer, role, and provenance.

`SignedArtifactEvidenceRecord` v1 embeds `ArtifactRef` and hashes the exact manifest/signature bytes (`core/contracts/chronology.py:2372-2384`; `core/artifacts/signed_evidence.py:140-220`). It cannot select a second profile for the same ID. Add a versioned view-bearing record and reader; preserve v1 historical replay. Update the seven production consumers listed in the census table above. A view-aware write that is discarded back to a bare `ArtifactRef` before the consumer reads it does not close R9.

Transfer inventory v1 admits one `.manifest.json` and `.sig` per ID (`core/artifacts/_transfer_ops.py:30-34,72-95`), and import validates one profile per artifact (`core/artifacts/store.py:940-1027`). Add a new inventory version that exports the requested views and their signatures while transferring the shared blob once. Continue to parse and replay v1 bundles unchanged. Add explicit view enumeration separately; preserve `_iter_artifact_ids_lazy`'s legacy `*.manifest.json`/64-hex behavior and do not redefine `iter_artifact_ids` to imply one profile per view (`store.py:1083-1144`).

## Staged exclusive write leases

These are sequencing boundaries, not parallel write assignments. Freeze each interface before releasing the next lease.

1. **R10, then freeze.** R10 owns `core/artifacts/store.py`'s public `verify_signature` boundary and `tests/unit/core/phase0/test_store_signing.py`. R9 starts only after that commit is stable. New view signature methods must not change string-to-`ArtifactID` normalization.
2. **Core contract and filesystem API — one writer.** Lease `core/artifacts/manifest.py`, `protocol.py`, new view contract/type definitions, `_manifest_lifecycle.py`, `_layout.py`, and `store.py`, plus focused core artifact-store tests. Freeze the view ID and full-profile verification contract first.
3. **Signatures, ownership, transfer, signed-record version — one sequential writer.** Lease `signing.py`, `_signature_ops.py`, `_transfer_ops.py`, `ownership.py`, the relevant `store.py` methods, `signed_evidence.py`, and a new v2 record in `core/contracts/chronology.py`. This follows both R10 and the core API. Keep v1 serialization and parser behavior frozen.
4. **Backend and wrapper adapters — after the protocol is frozen.** S3, GCS, cache, async, tenant, namespace, and IR adapter work can use separate file/test leases once method signatures are stable. Tenant work follows the view ownership contract. Do not overlap edits to core protocol or shared test files.
5. **Consumer propagation — after view reads/signatures exist.** ProgramGraph needs typed refs through `foundry/execute/_internal/graph/__init__.py`, `foundry/execute/_internal/models/__init__.py`, `foundry/execute/_internal/patching/__init__.py`, and `runtime/quality/joint_simulation_horizon.py`. Epoch signed-record v2 needs its seven listed consumers. Projection CAS updates its selected-manifest capture. Freeze source before the whole-file replay.

## Behavioral removal probe and controls

**Removal probe:** write identical bytes under two profiles differing only in `inputs`, `byte_size` (using a malformed manifest for the negative), or persisted warnings; retain `ArtifactViewRef.view_id` and the manifest's declared view marker, then alter that profile field without changing the declared view ID. Resolution/verification must reject it. Separately remove the code that resolves manifests by view ID while keeping both refs and marker fields; the second view's lookup must turn red. A check that only sees a view marker, kind, or content hash is insufficient. For authority, keep the marker and view digest but remove or invalidate the detached signature/appointment: authority admission must fail. For custody, supply tenant A's view ref under tenant B's runtime scope while leaving all manifest claims intact: the owner check must fail.

**Profile-preserving controls:** repeated legacy writes with the same full profile remain idempotent; distinct payloads keep distinct content IDs; malformed IDs remain rejected; a view-aware write with identical bytes and two distinct full profiles succeeds, shares one content ID, returns different view IDs, and reads back the exact corresponding manifests and bytes. This is the candidate-band non-refusal control.

**Consumer and custody controls:** the ProgramGraph horizon witness preserves the expected outcomes and resolves the same-body/different-input constraint reports to their respective profiles. Two signatures over separate views verify independently; cross-selected signatures fail, while R10-normalized legacy signature verification continues to pass. Tenant A cannot resolve, verify, or sign Tenant B's view merely because both own the shared blob. Quota tests reserve the exact missing blob and view-sidecar bytes under a concurrent writer; insufficient quota fails before a view becomes readable, and failed publication releases the reservation without a partial view. Object-store retry tests force two writers to create the same blob/view and verify that the loser rereads and validates the winner's bytes/profile; conflicting profile publication must not overwrite. View export/import preserves every selected manifest/signature, and legacy v1 export/import remains replayable. Projection capture records the selected view bytes and rejects a changed selected manifest.

The relevant existing witnesses include `tests/unit/runtime/quality/test_joint_simulation_horizon.py::test_program_graph_plan_loops_real_shared_state_executor`, `tests/unit/runtime/quality/test_epoch_deployment.py`, `tests/unit/runtime/http/test_runtime_deployment_security.py`, `tests/unit/runtime/quality/test_promotion_epoch_deployment.py`, `tests/unit/core/phase0/test_store_signing.py`, `tests/unit/core/artifacts/test_signed_evidence.py`, `tests/unit/core/artifacts/backends/test_{s3_store,gcs_store,caching_store}.py`, `tests/unit/core/artifacts/test_async_store.py`, `tests/unit/core/security/test_namespace.py`, `tests/unit/runtime/quality/test_multi_tenant_shared_cas.py`, and the two non-data-acquisition projection suites. These are proposed witnesses; this note does not claim they were run.

## Principal decision boundary

R9 is explicitly a decision class. The technical recommendation is an additive, cross-backend `ArtifactViewRef` contract owned by the existing CAS interfaces, with versioned view manifests, view-level custody/signatures, and versioned signed-evidence/transfer records. Keep all v1 bytes and legacy behavior replayable.

The principal still decides whether PolicyOS admits multiple full semantic profiles for the same content ID as a core contract now, and whether that contract must be supported across S3/GCS and every custody/transfer consumer in this lane. A filesystem-only multi-view implementation would not close the class: cloud backends can currently return a ref whose requested profile differs from their stored manifest. If the decision keeps one profile per ID, callers must not receive refs claiming a second profile; the identified callers need an explicitly approved alternative that does not disguise lineage or authority. The choice between those contracts is not settled by this source review.
