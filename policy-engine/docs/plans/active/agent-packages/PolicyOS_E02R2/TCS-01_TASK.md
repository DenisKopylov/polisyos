# TCS-01 — tenant-bound served job consumers

## Property and scope

A served request under verified tenant and registry-resolved cell scope may project or consume a control job only when the canonical persisted job owner matches that scope. The class covers direct job-ID status, Lex pipeline-ID status, job-derived `/runs/{run_id}` projections, production-approval scorecard/packet inputs, and normative-evidence intake selected by job ID. The shared owner predicate must run before foreign fields are projected, Lex output paths are read or progress is written, approval evidence is selected, or normative artifacts/heads are resolved or admitted. Missing or unresolved legacy ownership is inaccessible to these tenant-bound consumers; it must not be inferred from the current caller. Newly produced same-tenant candidate work remains available.

This is a new E02-R2 task, not an E02 regression. It is distinct from R1/CYC-01 and R13/ACQ-01. The run's own owner check remains a preserving control, but it does not prove that a globally selected job belongs to the same tenant/cell. Classify EvaluationSafety's completed-job reader separately: it independently resolves and verifies immutable payload and terminal-manifest tenant/cell/run bindings; preserve those checks, do not route it through the outward status selector, and do not include `evaluation_safety.py` in this source lease. The intended audience for `/control/workers` and `/control/outbox` remains unresolved; do not call either a tenant leak or include them in this task.

## Owner and production path

Reuse the existing ControlPlaneStore and ControlPlaneService as the canonical owner. The production chain is authenticated request scope → route and authorization middleware → status/run/approval/evidence consumer → runtime-supplied, possibly guarded control-store proxy → canonical job/pipeline/run selector → projection or authority use. Current OPA tenant equality is based on caller scope; it does not establish the selected row's owner, and a run-owner check does not establish the selected job's owner.

Use one validated owner tuple at job admission: tenant from the verified effective actor and cell from the attested registry-resolved request route. The authenticated actor's optional cell claim, when present, must agree with the routed cell; a missing claim does not erase a verified routed cell, and a conflicting claim must be refused or reconciled before persistence. Create the immutable payload scope and canonical row fields from the same tuple. Carry it through existing owner components; do not infer ownership from path/header input, create a second owner registry, rebuild a store, or use a global selector as fallback after a scoped miss. If owner data is duplicated on the row and payload, enforce equality at admission without making the store rebuild/open another CAS. Historical rows with no independently reconciled owner remain inaccessible pending an authorized provenance-preserving transition. Internal candidate producers without verified tenant/cell route may retain their existing candidate posture, but their unknown owner cannot be projected to a tenant.

The default service uses GuardedDependencyProxy, which forwards arguments; prove scoped selection through that production proxy. Reuse one canonical persisted-owner predicate for every in-scope served selector. Keep EvaluationSafety's independent content verification and all internal worker/lifecycle readbacks under their existing contracts. Do not remove or bypass a reader by adjacency alone.

## Served witnesses

- Main negative: in one real app with two independently authenticated tenants and the same admin role/OPA composition, tenant B creates a job through the normal launch and worker path. B reads the returned ID successfully. Tenant A requests that known ID and receives an indistinguishable not-found/inaccessible result with no foreign status/progress fields and no mutation.
- Lex negative/control: B creates a pipeline through the ordinary producer path; A's read of the known pipeline ID is refused before output-directory progress collection or upsert, while B can read its own status.
- Run-detail negative/control: with a run owned by A but a selected job owned by B, A's run endpoint must not project B's diagnostics or policy-design fields; the same-owner run/job projection remains available. Preserve the existing run-owner check as a distinct control.
- Production-approval negative/control: a served approval/scorecard/packet request for A cannot select or consume B's job, even where the route already verified A's run. A valid same-owner approval continues to resolve and persist through the existing path.
- Normative-evidence negative/control: A's submission naming B's job is refused before artifact resolution, head admission, or mutation; a valid same-owner submission retains its current run-bound CAS/head behavior.
- Service permission negative: extend the existing RUNS_VIEW service-principal path to read an existing foreign job and prove path permission does not override stored row ownership.
- Guarded-store control: execute the tenant-filtered lookup through the actual production GuardedDependencyProxy; both a foreign tenant and a mismatched stored/routed cell must produce a scoped miss. Preserve same-tenant/same-cell success. This store-level cell negative does not assert unresolved registry reassignment semantics.
- Preserving controls: same-tenant job, Lex, run-detail, approval, and normative-evidence operations remain available; the Rego parity test remains only a path-permission control. Preserve EvaluationSafety's payload/terminal-manifest verification unchanged.
- Schema migration: exercise fresh SQLite schema, upgrade of a populated pre-owner SQLite schema, and repeated SQLite startup. Under the locked SQLite connection, inspect `PRAGMA table_info(control_jobs)` and issue `ALTER TABLE control_jobs ADD COLUMN tenant_id TEXT` and/or `cell_id TEXT` only for absent columns. For PostgreSQL, use `ALTER TABLE control_jobs ADD COLUMN IF NOT EXISTS tenant_id TEXT` and the corresponding `cell_id` statement. Both upgrades are nullable, leave historical rows `NULL`, add no inferred/default owner, preserve existing row data, and succeed on first and repeated startup. Run the Postgres layer when an authorized test environment is available; otherwise record it `UNRUN`.
