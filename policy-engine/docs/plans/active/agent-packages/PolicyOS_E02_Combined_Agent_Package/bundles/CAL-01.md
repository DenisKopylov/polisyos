## Поручение и минимальная приёмка

Сохранить отдельные наблюдения/источники одной даты либо явное преобразование владельца до компиляции target. Разрешить временные координаты, совместную сортировку values/masks/metadata и dtype до padding. Отличить наблюдаемый ноль, разрешённое заполнение и полное отсутствие данных.

**Различающие тесты и сохраняемое поведение.** Переименование observation ID не выбирает 10 вместо 20. Перестановка пар времени/значения сохраняет разрешённую интерполяцию; отсутствующий запрошенный time_column не становится позиционной осью. Integer/float при fill=0.5 дают одинаковое заполнение; empty+steps=3 не выглядит наблюдаемым рядом из нулей.

**Не считать исправлением.** Не выбирать автоматически max trust или среднее; не сортировать только время, не запрещать всякий endpoint-fill и не создавать фиктивную измеренную опору.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B176. Несколько наблюдений одной точки превращаются в одно по порядку идентификаторов

**Наблюдение.** `CalibrationTargetBundleCompiler.compile` сортирует записи по `(period_start, observation_id)`, группирует по семейству, метрике, scope и локатору, затем присваивает `values[idx]` и соответствующие metadata в цикле. Источник и единица измерения не входят в ключ таргета. Для нескольких наблюдений одного периода последняя запись перезаписывает прежнюю. Стабильная сортировка обеспечивает воспроизводимый выбор, но не обосновывает его содержательно. [C17.R03]

**Различающий результат.** Два источника с одной датой и таргетом, значениями 10 и 20 и trust 0,9/0,1 дали одну точку 20 с provenance последней записи. Изменение только `observation_id` поменяло результат на 10. Перестановка исходных строк результата не меняла — это положительный контроль существующей сортировки. Другая проверка передала 0,5 в долях и 50 в процентах с одинаковым metric ID; на этой границе они также стали одной точкой 50 без сохранённой единицы в target spec. [C17.P01–P04]

**Оптимальное направление исправления.** Сохранять отдельную ось наблюдений/источников либо разрешать объединение существующим владельцем преобразования до потери данных. Для нескольких независимых измерений допустимы отдельные residuals; для конфликтующих версий — явная политика версий/источников; для агрегата — определённая формула и полная lineage. Единицы и временные интервалы приводятся только по настоящему контракту. Для малого первого сценария достаточно адресно проверить однозначность таргет–период и оставить несовместимые записи доступными для ремонта. Нельзя автоматически брать «наибольший trust», среднее или первый ID как универсальное правило.

**Приёмка и граница.** Смена технических IDs не меняет наблюдаемую величину; каждая принятая строка либо представлена, либо имеет объяснённое исключение/преобразование. Настоящий `ObservationPanel` валидирует family/time grain, конечность и scope; это полезно, но не устанавливает единственность источника одной точки. DTO/registry в опыте заменены. Вышележащий resolver, гарантирующий однозначность и единицы, может исключить контрпример в конкретном маршруте; частота такого входа не измерена. [C17.R07]

## B177. Временная ось не проверяется, а отсутствие запрошенного столбца превращается в позиционный ряд

**Наблюдение.** Preflight передаёт `src_time` в `np.interp`/`searchsorted` без проверки порядка и соответствия пар. `extract_fabric_series` при отсутствующем явно названном `align.time_column` возвращает просто values. Дальнейший код может создать позиционную ось вместо запрошенного календарного времени. [C17.R01]

**Различающий результат.** Пары `(t,y)=(0,0),(1,10),(2,20)` на целевой оси `[0,5;1,5]` дают `[5;15]`. Те же пары в порядке `t=[2,0,1]` дают `[20;10]`. Совместная сортировка времени и значений восстанавливает `[5;15]`. Dataframe только со столбцом `y` при запросе `time_column='event_time'` возвращает bare-array `[10,20]` без ошибки о времени. При этом конфликт `steps=3` и оси длины 2 уже корректно отвергается. [C17.P05–P08]

**Оптимальное направление исправления.** Один раз до оптимизатора разрешить семантику оси: единицы, частоту, длину, конечность, порядок и правила одинаковых timestamp. При допустимом переупорядочивании сортировать одновременно values и все связанные маски/metadata; сортировка только времени неверна. Для повторов одной даты нужна содержательная политика, не слепое удаление дублей. Явно запрошенное, но отсутствующее поле — адресный mismatch. Позиционная ось остаётся допустимой для контракта, который действительно её задаёт.

**Приёмка и граница.** Перестановка тех же пар не меняет результат разрешённого выравнивания; отсутствующая календарная привязка не изображается установленной. Не надо запрещать любую интерполяцию и экстраполяцию: edge-fill прямо предусмотрен текущей конфигурацией и может быть осмысленным. Требование возрастающего `xp` документировано NumPy, а не является новым произвольным барьером. Опыт выполнен на полном preflight с настоящими NumPy/pandas/JAX и конфигурационными DTO-фикстурами, без реального Fabric. [C17.E01]

## B178. Дополнение ряда меняет дробный fill и создаёт наблюдаемые нули из пустого входа

**Наблюдение.** `_align_by_length` создаёт padding в исходном `values.dtype`. При целочисленном ряде дробный `fill_value` обрезается. Если values пуст, padding по умолчанию равен нулю. С явным числом steps `prepare_targets` поэтому возвращает непустой aligned-target, хотя исходных наблюдений нет; наличие ключа и ненулевая длина перестают доказывать наличие опоры. [C17.R01]

**Различающий результат.** Integer `[1]`, `steps=3`, `fill=0,5` дал `[1,0,0]`; float-вариант тех же значений — `[1;0,5;0,5]`. Пустой `raw_targets['y']` с `steps=3` стал `[0,0,0]`; loss нулевой модели равен 0, а mapping считается непустым. Обычное предусмотренное дополнение `[1,2]` крайним значением до `[1,2,2]` работает. Контроль с разрешением dtype до padding сохраняет 0,5, а пустую наблюдаемую опору выделяет отдельно. [C17.P09–P12]

**Оптимальное направление исправления.** Разрешать совместимый тип значений и fill до материализации. Одновременно разделить наблюдение, объявленное модельное заполнение и полное отсутствие данных. Использовать существующие маски coverage/provenance там, где это правильная форма входа; в raw-пути передавать достаточные сведения об опоре или возвращать адресный запрос на данные. Явная внешняя предпосылка о постоянном нуле может быть полезной, но остаётся предпосылкой, а не полученным эмпирическим рядом.

**Приёмка и граница.** Равнозначное численное представление integer/float не меняет выбранный fill; пустой ряд не получает видимость измеренной нулевой ошибки. Настоящие нули и предусмотренный endpoint-fill сохраняются. Отсутствие всех рядов без явного горизонта уже останавливается через `steps==0`; найден обход именно при явной длине и существующем пустом ключе. Проверена подготовка и вычисление loss, не положительный полный CalibrationReport.
