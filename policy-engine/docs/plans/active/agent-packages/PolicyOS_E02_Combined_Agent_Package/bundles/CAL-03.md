## Поручение и минимальная приёмка

Создавать свежий span на каждый restart либо один правильный внешний span. При выборе отдельно валидировать loss, отсутствие Hessian, известную вырожденность и удовлетворительную диагностику. Сохранять полезный ограниченный вариант, не приписывая ему прохождение фильтра.

**Различающие тесты и сохраняемое поведение.** Два старта с OTel и без него проходят; повтор одноразового context manager отсутствует. NaN-loss не выигрывает из-за порядка списка. condition=inf не считается отсутствием диагностики, finite-large и unknown имеют свои результаты. Проверка выбора на таблице кандидатов; один маленький настоящий Hessian в K4.

**Не считать исправлением.** Не выключать observability или multi-start, не запрещать все ill-conditioned модели и не исправлять уже правильную raw-Hessian диагностику вместо потребителя.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B183. Включение observability делает второй старт оптимизации неисполняемым

**Наблюдение.** `Calibrator.run` создаёт `span_cm` один раз перед multi-start, затем входит в тот же объект через `with span_cm` внутри каждого старта. В режиме без наблюдаемости используется повторно пригодный `nullcontext`. Стандартный контекст span в OpenTelemetry — одноразовый; его повторный вход не эквивалентен созданию нового span. [C17.R04]

**Различающий результат.** Настоящий установленный OpenTelemetry API выполнил первый вход, а второй дал `AttributeError: '_AgnosticContextManager' object has no attribute 'args'`. Свежий context-manager на каждый старт прошёл два раза. Повторный `nullcontext` тоже прошёл оба старта, объясняя, почему неисправность может не обнаруживаться без telemetry. Оптимизатор и настоящий provider/exporter не запускались: воспроизведён именно жизненный цикл контекста. [C17.P26–P28]

**Оптимальное направление исправления.** Один внешний span на исследование и отдельные свежие child-spans на старты либо фабрика контекстов на каждую итерацию. Сохранять идентичность старта, статус и уже выполненную работу. Не ограничивать multi-start единицей и не выключать наблюдаемость как постоянный ремонт. При ошибке дополнительного exporter должна действовать объявленная политика telemetry, не автоматический отказ всей науки или сокрытие обязательного аудита.

**Приёмка и граница.** Два старта с теми же входами проходят с telemetry и без неё; заголовочный span не используется повторно. Настоящее изменение цели между стартами по-прежнему требует своей привязки. Документация Python различает одноразовые и повторно используемые context managers; не каждый произвольный переданный пользователем tracer обязан воспроизвести проблему. Находка условна включённым HPC-observability, количеством стартов более одного и таким типом контекста, а не каждым запуском калибровки. [C17.E03]

## B195. Заведомо плохая обусловленность принимается как отсутствие диагностики

**Основание.** `_select_best_loss` фильтрует большие конечные condition numbers. Но при существующем Hessian с `inf` или NaN попадает в ветку «No Hessian info — accept by loss only». Известная вырожденность поэтому обходит фильтр, который действует для менее плохого конечного числа. Конечность самого `loss` до `min` также не установлена. `compute_hessian` уже корректно сохраняет `condition_number=inf` для вырожденного сырого Hessian; проблема находится в потребителе, а не в отсутствии диагностики. [C19.R01; C19.R07]

**Различающие проверки.** При threshold=10^8 вариант с loss=0,1 и condition=10^12 уступил варианту loss=0,5, condition=10. Замена первого condition на `inf` дала победу первому и строку `best_loss=0.1 (condition<1e+08)`. При loss NaN у первой записи `min` выбрал её; после перестановки впереди оказался действительный loss=0,5. Настоящий вычислитель Hessian на постоянной функции сохранил бесконечную обусловленность, несмотря на ремонт матрицы. C19-P01–P05.

**Почему важно.** Улучшенный restart может быть не выбран, а downstream получает неверное объяснение пригодности победителя. Это проявляется уже на двух стартовых состояниях.

**Рекомендуемое исправление.** Сначала проверять пригодность численного результата; отдельно различать действительную удовлетворительную диагностику, известное нарушение и отсутствие оценки. Допустимый режим выбора только по loss при отсутствующем Hessian сохраняется, но не маскирует известную вырожденность. Когда все варианты ограничены, можно вернуть лучший конечный диагностический результат с точными ограничениями; не нужно уничтожать уже выполненную работу. Ветка `best_identifiability` и одиночный проход также требуют согласованной обработки недопустимого loss.

**Приёмка.** Конечный пригодный кандидат не проигрывает NaN из-за порядка списка. Известная вырожденность не считается неизвестностью. Причина выбора соответствует реально применённой политике. Существующие тесты для конечного большого condition и выбранного числа идентифицированных параметров сохраняются. [C19.R08]

**Статус и предел.** Полный source-модуль selection исполнен с явными импортными фикстурами; реальные JAX/NumPy Hessian использованы в контроле. Полный multi-start optimizer не запускался. Не предлагается запрещать все ill-conditioned модели: их ограниченное исследовательское применение отличается от прохождения конкретного фильтра.
