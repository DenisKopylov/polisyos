## Поручение и минимальная приёмка

Согласовать возвращаемую ref с реальным first-writer manifest profile. Проверять existing bytes перед подтверждением повторного put; различить ошибку, quarantine и разрешённое восстановление. Ограничить lock registry без потери holders/waiters.

**Различающие тесты и сохраняемое поведение.** Повтор bytesA с profileB не выдаёт refB при сохранённом manifestA. Existing corrupt blob не подтверждается как successful put. Два управляемых writer сохраняют first-writer semantics. Малое число ключей и искусственный cap проверяют bound без массовых файлов.

**Не считать исправлением.** Не переписывать provenance ради dedup и не evict активный lock по LRU. Не придумывать историю восстановленного blob взамен реальной.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B150. Возвращаемая ссылка обещает профиль новой записи, а сохранённый манифест остаётся первым

**Основание и область:** `FileSystemCAS._put_blob_and_manifest_once` при существующем манифесте проверяет его content-identity, не соответствие новым `kind`, `media_type`, `schema` или lineage. `put_bytes` затем возвращает `ArtifactRef` с новыми `opts.kind/media_type`. `ManifestLifecycle` намеренно использует write-once. C14.R02–R04.

**Воспроизведение:** bytes `{}` сначала записаны как type-A/application-json с input A, затем как type-B/text-plain с input B. Content ID одинаков. Вторая ref называет type-B/text-plain, но чтение манифеста даёт type-A/application-json и input A. Первый манифест при этом корректно сохранён побайтно. Эквивалентный повтор с прежним профилем согласован. C14-P10–P12.

**Оптимальное исправление:** API подтверждает фактически сохранённую семантику. При повторе сравниваются именно существенные поля принятого persisted-profile; несовпадение возвращает адресный конфликт либо отдельный объект употребления/происхождения со ссылкой на общий blob. Для нового исследовательского события полезнее отдельная уже предусмотренная typed-запись, связывающая content и текущие входы/метод, чем дублирование крупных bytes. Физическую дедупликацию и первый манифест сохранять.

**Что не делать:** не переписывать старую историю, не дописывать произвольный run_id к каждому blob лишь ради другого hash и не утверждать, что байтовая идентичность установила одинаковое эмпирическое происхождение. В проекте есть frozen C4-профили и специализированная запись authority-артефактов; их строгие проверки могут уже закрывать отдельные пути. Полный C4-writer в C14 не исполнялся. C14.R07–R08.

**Приёмка и приоритет:** S/M. Ref и manifest не расходятся по обещанному профилю; повтор того же профиля не создаёт лишнюю копию. Разные события с одинаковым результатом сохраняют действительные источники. Это замечание generic-API и его потребителям, не предложение отменить намеренный first-writer ABI.

## B151. Повторная запись правильного результата подтверждает уже повреждённую копию

**Основание и область:** существующий blob не читается в `_put_blob_and_manifest_once`; манифест проверяется только на artifact_id и integrity.sha256. Полные digest и byte_size проверяются на чтении. Поэтому новый корректный расчёт способен закончиться успешной ref на повреждённое содержимое. C14.R02, C14.R04.

**Воспроизведение:** после исходной корректной записи blob локально повреждён. Повтор `put_bytes` с правильными bytes вернул ref, но последующий `get` отказал. Отдельно изменённый byte_size манифеста дал тот же результат: put подтвердил, read отверг. При отсутствующей sidecar существующий путь уже способен восстановить её — эта положительная ветвь сохранена как контроль. C14-P13–P15.

**Оптимальное исправление:** определить, что подтверждает put. Если он обещает доступный корректный объект, существующая копия должна быть проверена в согласованном снимке либо возвращён явный конфликт/повреждение. Разрешённое восстановление использует новые bytes, проверенные по ожидаемому digest, и отдельную атомарную публикацию; испорченная копия и событие ремонта сохраняются в карантине. Нельзя автоматически восстанавливать неизвестное происхождение манифеста только из тела blob.

**Баланс стоимости:** не дублировать проверку на каждом слое без необходимости — B152 устраняет повторную работу внутри одной операции. Но TTL-метка «проверено вчера» и `has()` не заменяют целостность реально используемых bytes при изменяемом filesystem. Контроль ремонта восстановил bytes с тем же digest и сохранил испорченную копию; конкурентная атомарность такого ремонта не заявлена. C14-P16.

**Приёмка и приоритет:** S/M для используемого CAS. Повреждение не превращается в успех записи; корректный retry либо восстанавливает доступный объект через разрешённый путь, либо даёт точную неисправность до downstream-работы. Read-time отказ уже правильный и не должен ослабляться. Реальная частота повреждений не измерена.

## B153. Реестр блокировок растёт по всем когда-либо записанным артефактам

**Основание и область:** экземпляр `FileSystemCAS` хранит `_artifact_locks: dict[str, Lock]`; `_artifact_lock` добавляет запись по новому ID, удаления не предусмотрено. Это per-instance процессное состояние. C14.R02.

**Воспроизведение:** запрос блокировок для 3000 разных ID оставил 3000 объектов после сборки мусора. Повтор одного ID правильно возвращал тот же lock и не увеличивал число записей. Этот опыт считает управляющие объекты, не RSS всей системы и не стоимость 3000 настоящих put. C14-P22–P23.

**Оптимальное исправление:** для простого умеренного потока — фиксированное striping-множество блокировок по стабильному hash. Оно ограничивает resident-state и сохраняет взаимное исключение одинакового ключа ценой возможной сериализации разных ключей. Для действительно высокой конкуренции — запись жизненного цикла lock с учётом держателей и ожидающих, освобождаемая только когда безопасно. Контроль с 64 полосами сохранял одинаковый lock для одинакового ключа; число 64 — пример, не новый постоянный лимит системы. C14-P24.

**Что не делать:** не применять обычное LRU-вытеснение к активному lock — это может создать два независимых замка для одного ключа. Не считать process-lock межпроцессной защитой; существующий `AtomicFileWriter.write_once` использует link/create-once и остаётся необходимым. Не нужен новый распределённый lock-service для первого локального результата. C14.R06.

**Приёмка и приоритет:** S, условная экономия для долгоживущего store с большим числом ID. Проверить одновременную запись одного ключа, ожидающих, разные scoped views и исключения. Короткий store на несколько артефактов не обязан сначала исправлять этот резерв. Отличие от B93 — здесь лишнее удержание замков, а там опасное вытеснение действующего ограничителя.

## K20. Content identity и контрольная сумма не являются сами по себе разрешением на reuse или closeout

Generation basis действительно строится из переданных bytes и версии правила; локально проверены current, changed content/model/rule, malformed digest и missing record. Но он не может самостоятельно установить полноту перечня, который передал caller. Generic manifest checker, в свою очередь, сохраняет поддержку пустого expected hash и не удостоверяет обязательность состава. Эти модули — полезные узкие primitives, **не obsolete helpers и не готовая полная replacement policy**. [E144, E146; r05-P34–P42]

В LA-039/LA-040/LA-041 их объединение должно сохранить различие: истинность hash, текущая принадлежность к поколению, эквивалентность запроса, целостность выходов и допустимость использования — разные утверждения. Ни одно из них не заменяется названием `current`, одним файлом manifest или удачным return code.
