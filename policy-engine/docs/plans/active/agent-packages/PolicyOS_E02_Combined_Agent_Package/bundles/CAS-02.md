## Поручение и минимальная приёмка

Импортировать в непубличное поколение и проверить связанный набор до publication. Directory export формирует точный новый inventory без хвоста прежнего запроса.

**Различающие тесты и сохраняемое поведение.** Bad import не повреждает доступный старый blob/manifest. ExportA затем B не включает остатки A в B. Сбой до публикации оставляет старое valid поколение. Несколько маленьких файлов/tar заменяют массовое копирование CAS.

**Не считать исправлением.** Не удалять рекурсивно пользовательскую папку. Staging не считается successful import; локальность bytes не отменяет проверку.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B148. Импорт меняет действующее хранилище раньше, чем проверяет входящий набор

**Основание и область:** `core/artifacts/_transfer_ops.py::import_subgraph` и `FileSystemCAS.import_subgraph`. Директория копируется через `shutil.copy2`, tar-члены — через `dst.open('wb')`. Проверка выполняется после копирования всех файлов. Она по умолчанию отключена, но даже явное `verify_integrity=True` не переносит проверку перед публикацией. C14.R01, C14.R02, C14.R04.

**Воспроизведение:** в двух опытах, с directory и tar, уже корректная пара blob/manifest заменена повреждёнными входящими bytes. Возвращён отчёт с одной неуспешной проверкой, но старые bytes не сохранились; чтение затем правильно выдало `ArtifactIntegrityError`. В отдельном случае одинаковые корректные bytes с другим producer/inputs прошли byte-integrity и заменили прежний манифест. Криптографическая подпись и реальный owner-контроль в опытах не исполнялись. C14-P01–P03.

**Оптимальное исправление:** импортировать в непубликуемое временное поколение; проверить комплектность, идентичность bytes, разрешённый профиль, подписи/владение там, где они обязательны, и конфликты с уже существующими артефактами. Затем публиковать через существующий immutable writer или одну проверенную границу поколения. Повтор идентичного артефакта допустим; другой манифест с тем же content ID требует явного решения существующего владельца, а не перезаписи «последний победил». Для крупных пакетов достаточно атомарности действительно необходимой замкнутой группы; не обязательно одной гигантской транзакции на весь архив.

**Что сохранить:** уже реализованный запрет абсолютных и выходящих за корень member-path, checksums, подписи, изоляцию tenant/cell и историю отказавшего импорта. Контроль со staging не публиковал повреждение и сохранил прежний результат; корректный импорт продолжал работать. Это контроль принципа, не готовый транзакционный importer. C14-P04–P06.

**Приёмка и приоритет:** S/M по используемому маршруту. Повреждённый пакет, обрыв чтения, конфликт манифеста и конкурирующая публикация не портят прежний читаемый объект. Результат отдельно описывает проверенное, опубликованное и отказавшее, не объединяя это в счётчик copied-files. Связь с B76: здесь первичная граница общего CAS-импорта, не checkpoint-sidecars.

## B149. Повторный экспорт в директорию включает остатки предыдущего запроса

**Основание и область:** directory-ветка `_transfer_ops.export_subgraph` создаёт или переиспользует каталог, копирует запрошенные файлы и заменяет `export_manifest.json`, но не определяет закрытый состав пакета. Manifest содержит числа, не перечень разрешённых members. Import обходит все подходящие файлы и пропускает export_manifest. C14.R01.

**Воспроизведение:** сначала экспортирован A, затем B в тот же каталог. Второй отчёт сообщил один экспортированный артефакт, а импорт из этой директории получил два: A остался от прежней операции. Контроль с новым каталогом поколения импортировал только B. Также после экспорта с manifests повторный вызов `include_manifests=False` не удалил старую sidecar. C14-P07–P09.

**Оптимальное исправление:** выдавать самостоятельный неизменяемый пакет в новом staging-каталоге и публиковать его после завершения; включать точный перечень файлов и их content bindings в manifest. При существующем destination — явно выбрать режим replacement-generation либо append-пакет с иным контрактом. Import читает именно принятый inventory, а лишние члены отвергает или изолирует по политике. Если требуется только один разовый перенос, новый уникальный каталог — уже дешёвый безопасный рабочий путь.

**Что не делать:** не удалять рекурсивно произвольный destination пользователя и не объявлять все файлы директории запрошенным подграфом. Не повышать «число скопированных сейчас» до «полного состава переданного». Правильный tar-пакет и чистая directory остаются доступными; найденное условие — reuse директории, не все экспорты.

**Приёмка и приоритет:** S/M. A→B через один логический output даёт опубликованный набор B без A либо явно документированный append A+B. Смена опций и ошибка второй записи не оставляют пакет, выдаваемый за завершённый. История предыдущего поколения доступна по своей ссылке, но не загрязняет новый запрос.
