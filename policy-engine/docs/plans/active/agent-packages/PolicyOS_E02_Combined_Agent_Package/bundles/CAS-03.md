## Поручение и минимальная приёмка

Переиспользовать один проверенный immutable bytes-view в конкретной integrity/signature операции. Локальные ошибки элементов возвращать в полном typed batch report. Ограничить inventory preparation и pending futures наряду с workers; cancellation сохраняет свой смысл.

**Различающие тесты и сохраняемое поведение.** Hash/read counters показывают одну пригодную подготовку без доверия чужой версии. Corrupt item не уничтожает уже готовые результаты остальных. Iterable из десятков entries имеет малый pending cap. Отмена останавливает новую работу и сохраняет фактические результаты.

**Не считать исправлением.** Не превращать общую ошибку доступа в per-item success, не поглощать BaseException, не называть полный N-элементный report константной памятью.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B152. Одна проверка целостности трижды хэширует те же bytes, а проверка подписи повторно читает их

**Основание и область:** `verify_filesystem_artifact` вычисляет digest, затем вызывает `verification_report_from_loaded_artifact`, который вычисляет digest и вызывает `validate_read_integrity`, снова вычисляющий digest. `_signature_ops.verify_signature` после этого вызывает `get_bytes`, выполняющий ещё одну проверку. C14.R02, C14.R04–R05.

**Воспроизведение:** обычная проверка неповреждённого payload вызвала SHA-256 три раза. Оркестрация проверки подписи вызвала четыре полных content-hash до входа в тестовый криптографический verifier, два чтения blob и три чтения манифеста. Обычный verified-read вызвал SHA-256 один раз. Это счётчики выполненных функций и I/O, не измеренный коэффициент ускорения. Настоящая Ed25519-проверка не выполнялась. C14-P17–P19.

**Оптимальное исправление:** один раз получить неизменяемые bytes и манифест, вычислить digest, проверить привязку/размер и построить report из этого же проверенного снимка. Оркестрация подписи использует тот же снимок, а не повторно открывает пути. Внутренний helper может принимать уже вычисленный digest только из доверенного локального вычисления; внешний заявленный checksum не является доказательством.

**Что сохранить:** алгоритм и полное покрытие hash, точные подписываемые bytes, проверку манифеста, ключа, отзыва и текущего доступа. Нет рекомендации кэшировать «подпись валидна» глобально по одному ID: trust/revocation имеют отдельный жизненный цикл. Контроль одного снимка сделал один content-hash и продолжал отвергать изменённые bytes и неверный размер. C14-P20–P21.

**Приёмка и приоритет:** S; хороший первый ремонт при использовании верификации. Счётчики подтверждают устранение повторов, тесты tamper дают прежние отказы, а cryptographic integration проверяет подпись того самого снимка. Возможное ускорение измеряется отдельно на реальных размерах, storage/cache и составе downstream-проверок.

## B154. Ошибка одного элемента прерывает выдачу полного отчёта пакетной проверки

**Основание и область:** `verify_all_signatures` вызывает callback через `executor.map` без поэлементного преобразования ошибки в результат. В `verify_signature` первичная `verify_integrity` расположена до защищённых блоков чтения sidecar. В `sign_all_artifacts` проверка `has_signature` для `only_unsigned` тоже находится до локального `try`. C14.R05.

**Воспроизведение:** callback для одного из трёх объектов выдал `PermissionError`; aggregate вообще не вернулся. Контроль с разрешённым поэлементным ERROR дал два valid и один error, не принимая отказавший объект. В signing аналогичная ошибка предварительного `has_signature` также вышла наружу. При повреждённом формате sidecar существующая обёртка уже корректно даёт ERROR — положительная обработка не игнорируется. Авторизация в опытах была тестовым отказом, не реальной проверкой tenant. C14-P25–P28.

**Оптимальное исправление:** определить классы отказов на границе одной операции. Локальную недоступность/невалидность представлять результатом этого элемента и продолжать независимую разрешённую работу, когда политика допускает частичный отчёт. Потеря общей авторизации, отмена, повреждение общего основания или broken executor могут требовать остановки; в таком случае сохранить уже полученные результаты и явное состояние aborted, а не выдавать пакет за полный.

**Что не делать:** не перехватывать всё и объявлять valid; не скрывать запрещённый объект и его отсутствие из полноты отчёта; не повторять криптографическую или внешнюю операцию слепо. Сам факт, что функция может бросить исключение, не универсальный баг: замечание касается неодинаковой обработки локальных ошибок и потери доступного агрегата.

**Приёмка и приоритет:** S/M для batch-ветки. Проверить локальный отказ, глобальный отказ, отмену и нормальный набор. Частичный отчёт не даёт права на публикацию, требующую всех подтверждений. Связь с B13 — новый конкретный интерфейс подписи, не повтор прежнего примера контроллера.

## B155. Число работников ограничено, но список заданий и очередь futures — нет

**Основание и область:** обе batch-обёртки сначала выполняют `ids = list(artifact_ids)`, затем `executor.map` без ограниченной очереди. `max_workers` ограничивает исполняющих работников, но не материализованный inventory и не весь набор отправленных futures. C14.R05, C14.E01.

**Воспроизведение:** на 40 ID при двух работниках и управляемой задержке функций весь источник потреблён и все 40 futures отправлены до завершения первого. Контроль со скользящим окном pending=4 потребил до разрешения работы четыре ID и затем обработал все сорок. Это счётчики очереди и чтения итератора, не измерение пикового RSS и не ускорение реальных подписей. C14-P29–P30.

**Оптимальное исправление:** читать inventory порциями и пополнять ограниченное окно по завершению работ; при закреплённой поддержке Python 3.14 можно использовать `map(buffersize=...)`, но ранний `list(...)` всё равно необходимо убрать или обосновать. В более ранней версии достаточно существующих futures/wait и небольшого окна. Документация отдельно указывает, что `chunksize` не меняет поведение ThreadPoolExecutor. C14.E01.

**Граница оптимизации:** если контракт требует вернуть подробности обо всех N артефактах одним объектом, результат по-прежнему занимает O(N). Для ограниченной памяти всей операции нужен потоковый/сегментный подробный отчёт с небольшим итогом, не незаметное усечение списка. Сначала достаточно убрать лишнюю материализацию и управлять pending; новый кластерный runtime не нужен.

**Приёмка и приоритет:** S/M, условно на объёме используемого batch. В окне не превышается принятая граница, отмена не продолжает допуск бесконечного inventory, результаты сохраняют идентичность и полноту. Ограничение по bytes может быть существеннее числа артефактов; большой blob и маленькая metadata не равнозначны по памяти. Для единичной проверки это не предварительный обязательный барьер.
