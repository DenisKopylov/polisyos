## Поручение и минимальная приёмка

Исключать волатильность по типизированным служебным полям, сохраняя предметные даты. Кодировать Python Random state по его версии. Для Sobol сохранить одну логическую последовательность и cursor/scramble при batch, cache и resume.

**Различающие тесты и сохраняемое поведение.** Разные starts_at в содержательном кандидате дают разные identities; audit timestamp не меняет предмет. JSON round-trip восстанавливает Random sequence. Один batch и несколько batches после restore дают один Sobol-префикс; несовместимый legacy checkpoint имеет точный исход.

**Не считать исправлением.** Не удалять рекурсивно любой *_at/*_ts, не превращать все lists в tuples, не считать новый seed от длины cache продолжением прежнего эксперимента.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B124. Эвристика «волатильных» полей удаляет содержательные даты внутри кандидата

**Основание и область:** `policy_candidate_hash`, `_strip_volatile_candidate_fields`, `update_legacy_pareto_front`; HA1–HA5. Полный `frontier.py` сверён по Git blob; helpers сериализации заменены явными детерминированными fixtures. [C11.R03]

**Проблема.** Удаление ключей `timestamp`, `*_at`, `*_ts`, `*_timestamp` и начинающихся с подчёркивания применяется рекурсивно к любому словарю, не только к транспортной оболочке. В generic-кандидате это может стереть предметную дату начала вмешательства или момент наблюдения. Два различных предметных входа затем получают одинаковый hash. При совпавшем hash frontier может заменить один результат другим вместо сохранения настоящего компромисса.

**Проверка.** Два dict-кандидата, отличающиеся только `semantic.interventions[0].starts_at`, стали одинаковыми уже после stripping. Для несравнимых векторов `(0,10)` и `(10,0)` осталось одно предложение. Изменение amount давало разные ключи; изменение верхнего provenance `created_at` правильно не меняло ключ. Независимое вычисление идентичности только явно выбранного предметного payload сохранило различие дат.

**Ограничение достижимости.** Даты и структура этого примера модельные. Не утверждается, что текущий канонический `PolicyCandidateSchema` содержит именно поле `starts_at` или что каждый producer использует fallback-hash: явный проверенный hash/metadata_hash может обходить эвристику. Тем не менее generic-API принимает такой payload, а потеря различия в helper воспроизводится точно; реальный маршрут требуется проверить отдельно.

**Рекомендуемое исправление.** Разделить предмет кандидата и оболочку исполнения по схеме, исключая только известные технические пути. Содержательное время, seed научной реплики и версии входов включать согласно контракту. Идентичности кандидата, его оценки и попытки исполнения не сливать в один случайный UUID.

**Приёмка.** Разные даты реального действия дают разные предметные ключи; только дата загрузки/trace не вызывает лишнее вычисление. Тестируется нормальная дедупликация одного и того же канонического входа и сохранение нескольких оценок/реплик. Перестановка полей JSON не меняет смысл, а временные данные не удаляются только по суффиксу имени.

## B125. Сериализуемое состояние стратегии не восстанавливает собственный Python RNG после JSON

**Основание и область:** `StrategyState.to_artifact/from_artifact`, `BaseSearchStrategy.get_state/set_state`; RG1–RG3. Полные `types.py` и `base.py` сверены по Git blob и исполнены с фикстурами зависимостей. [C11.R04, C11.R05]

**Проблема.** `random.Random.getstate()` даёт структурированный tuple. JSON сериализация превращает его вложенные tuples в lists; `from_artifact` декодирует bytes модели, но не восстанавливает представление Python RNG. Затем `_rng.setstate` получает несовместимый тип внутреннего вектора.

**Проверка.** Передача state напрямую в памяти сохранила следующую случайную точку. Настоящий `to_artifact → from_artifact → set_state` дал `TypeError: state vector must be a tuple`. Схемно-ограниченное восстановление только структуры Python RNG вернуло ровно ту же следующую точку. Версия опыта — Python 3.13.5; target-проект целиком не устанавливался.

**Рекомендуемое исправление.** Версионировать codec состояния каждого используемого генератора и восстанавливать проверенную структуру по его схеме. Для Python RNG это небольшая локальная нормализация необходимых контейнеров с проверкой версии, длины и типов. Не рекурсивно превращать все lists произвольного metadata в tuples и не десериализовать произвольные исполняемые объекты.

**Что сохранить.** Состояние модели, RNG и его идентичность должны иметь собственные правила совместимости. Возобновление с одним только seed обычно означает повтор начала, а не продолжение. Ошибка codec должна быть явной; новый случайный запуск — другая операция, не незаметный fallback под прежней меткой replay. [C11.E01]

**Приёмка.** Полный persisted round-trip каждого поддерживаемого strategy-state, а не только `get_state/set_state` в одной памяти. Восстановленная следующая последовательность совпадает; повреждённое/чужое состояние не принимается; случайный поток независимой реплики остаётся независимым.

## B126. Соболь-последовательность зависит от заполнения кэша и не включена в checkpoint

**Основание и область:** `BaseSearchStrategy._sobol_candidate/get_state`, `SearchSpace.sample_sobol`; SQ1–SQ4. Использовалась действительная ветвь SciPy при явно установленном `torch=None`; PyTorch/BoTorch не запускались. [C11.R04–R06]

**Проблема.** При расширении `_sobol_cache` создаётся новый sampler с seed, зависящим от текущей длины кэша, и запрашивается только недостающая часть. Следовательно, четыре последовательных запроса по одной точке используют разные scramble-seeds; один запрос четвёртого индекса создаёт четыре точки одного sampler. Сам `_sobol_cache` и позиция его потока не сохраняются в `StrategyState`.

**Проверка.** Четыре incremental-точки и четыре точки, подготовленные одним расширением, совпали только в первом элементе. После трёх вызовов get_state/set_state через память — без JSON-проблемы B125 — следующий Sobol-кандидат отличался от непрерывного исполнения. Реальный SciPy-контроль одного sampler с фиксированным seed и восстановленной позицией дал ту же точку. Сохранение старого cache отдельно также воспроизвело старый алгоритм; это контроль совместимости, не подтверждение свойств полноценной QMC-последовательности.

**Рекомендуемое исправление.** Для нового алгоритмического режима — одна идентичность sampler, scramble/seed, пространство, backend/version и курсор; последовательное продолжение либо восстановление через поддерживаемый fast-forward. Для уже существующих снимков — явная совместимая миграция или сохранение недостающего cache, а не подмена прежних результатов новой последовательностью.

**О численной гарантии.** В SciPy документированы особенности balanced выборок размера степени двойки. Исправление воспроизводимости не требует заставлять каждый поиск выполнять 2^m дорогих симуляций: можно честно поддерживать ограниченный префикс, не приписывая ему свойств полного balanced-дизайна. Реальная QMC-ошибка или улучшение качества оптимизации здесь не измерялись. [C11.E02]

**Приёмка.** Одинаковый логический индекс после 1+1+… и пакетной подготовки, до/после checkpoint и при чтении уже известной точки. Без смены объявленного algorithm-version исходное исследование не меняется из-за способа заполнения кэша.
