## Поручение и минимальная приёмка

Разделить предварительный допуск и привязку к уже скомпилированному DesignProblem. Провести один действительный CycleSubstrateContext через HTTP, рекурсию и N6; собрать сериализуемый запрос N5 из кандидата, WMR, атомов, горизонта и разрешённого ресурса. Согласовать три изменения в одном пакете: открытие входа без потребляемого контекста не является результатом.

**Различающие тесты и сохраняемое поведение.** Штатный вход без вручную собранного Python-context доходит до настоящего разрешённого N5. Изменение problem/model/catalog binding отвергается. Отсутствующие параметры не становятся нулями. В локальном тесте использовать настоящий builder/DTO и захват границы вызова; численный результат и CAS-readback проверяет K1.

**Не считать исправлением.** Не удалять ранний access-control для защищённых данных/действий; не выдавать fixture bundle за доступный источник; не строить второй world store.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B01. Контекст оценивания требуется до формирования оцениваемой задачи

*Источник карточки: A:B01. Унаследовано из прочитанной сводки A; не новый интеграционный прогон.*

**Происхождение и подтверждение:** P1; код, повторно прочитан в P3. В HTTP-композиции отсутствие `root_evaluation_context` отвергается до `build_design_problem_from_nl_request`. После компиляции отдельно проверяется привязка контекста данных к хэшу полученного `DesignProblem`. Требование заранее передать внутренний контекст может остановить обычный запрос ещё до содержательной работы. [A.R06: 450–565]

**Экономное расширение:** разделить общий предварительный допуск пользователя, ресурсов и инструментов и позднюю привязку оценивания к фактически полученному объекту. Для разрешённого чистого вычисления строить точный симуляционный контекст из реального результата N5; для действия с людьми или защищёнными данными сохранять необходимый допуск до действия. Уже существующий `simulation_value_execution_context` — точка переиспользования, не повод создавать второй EvalSafety. [A.R04: 1920–2200]

**Критерий:** обычный пользовательский вход без вручную созданного Python-контекста достигает разрешённого вычисления; чужой кандидат, чужая модель, неразрешённые данные и защищённое действие не проходят. Снятие одной ранней проверки без восстановления остальных привязок не считается исправлением.

**Ограничение и приоритет:** не доказана невозможность всех видов запуска; установлен порядок конкретной композиции. Высокое влияние, средняя интеграционная сложность. Зависит от B02–B03.

## B02. Контекст данных и модели не должен теряться при передаче между слоями

*Источник карточки: A:B02. Унаследовано из прочитанной сводки A; не новый интеграционный прогон.*

**Происхождение и подтверждение:** P1; статическое наблюдение о стандартной композиции. Нижележащий маршрут принимает `cycle_substrate_context`; N4 при его отсутствии возвращает `cycle_substrate_context_unavailable`. Поэтому снятие B01 само по себе не включает настоящий генератор. [A.R04: 1130–1235; A.R05: 600–705; A.R06]

**Экономное расширение:** после компиляции разрешить существующий `CycleSubstrateContext` через его владельцев и провести одну точную привязку через HTTP → рекурсию → лист N6 → N4/N5/N8. Использовать существующие сборщики и проверку идентичности, не создавать другой store или параллельное представление мира.

**Критерий:** один и тот же контекст действительно потреблён всеми стадиями; изменённый `DesignProblem`, другой WMR или иная версия каталога дают конкретный отказ. Отсутствующий настоящий источник остаётся отсутствующим, а не заполняется тестовым bundle.

**Ограничение и приоритет:** это не утверждение, что контексты нигде не строятся: в проекте есть отдельные подготовленные маршруты и контекстные вызовы. Высокое влияние; средняя сложность соединения. Проверять вместе с B01 и B03.

## B03. N5 ожидает готовый запрос вместо штатной сборки его входа

*Источник карточки: A:B03. Унаследовано из прочитанной сводки A; не новый интеграционный прогон.*

**Происхождение и подтверждение:** P1/P2; код. `JointSimulationPort` получает `joint_simulation_request_factory` или готовый `joint_simulation_request` из `runtime_hints`. Без них возможен корректный WMR, но возвращается `joint_simulation_request_missing`. Это разрыв сборки входа, а не отсутствие симуляторов. [A.R04: 1330–1503]

**Экономное расширение:** узкий сборщик из реального кандидата, связанных атомов вмешательства, WMR, требуемых исходов, горизонта, разрешённого бюджета и применимого существующего движка. Использовать `WorldModelSimulationInput` и входные привязки Foundry. У неизвестного параметра должен быть собственный пробел, а не молчаливое численное значение. [A.R08; A.R13]

**Критерий:** штатный запрос приводит к реальному вызову подходящего метода; изменение существенной привязки отвергается. Сохраняемая спецификация и серверное разрешение ссылок заменяют несериализуемый callable на пользовательском долговременном пути.

**Ограничение и приоритет:** не установлено отсутствие всех фабрик во всём репозитории. Нельзя обеспечить произвольную задачу универсальным заполнением полей. Высокое влияние, средняя сложность; это необходимая связка, а не новый движок.

## K02. foundry/data_plane и fabric/data_plane

Foundry input binding связывает внешние артефакты с runtime state и method contracts; Fabric отвечает за свой data-plane. Два файла в Foundry не делают intake устаревшим.

**Решение:** Сохранить input-binding границу; рассматривать дробление большого bindings.py как modularity-task, не как удаление legacy. [E33, E36]

## K17. Явно публичный OPA facade не обязан исчезать вместе со всеми aliases

`runtime/http/opa_input.py` — четыре явных reexports sealed runtime authorization objects у того же владельца. Собственной OPA-evaluation логики там нет, но narrow public import может быть нужной границей для consumers. Не установлены ни retirement-решение, ни эквивалентный обязательный публичный заменитель. Поэтому файл не добавлен в delete/retire manifest. Существование compatibility-фасада — сигнал выяснить его договор, не автоматическое доказательство legacy. Полные authorization/middleware implementations и их consumers здесь не аудированы. [E133]
