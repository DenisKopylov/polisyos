## Поручение и минимальная приёмка

Согласовать чтение/запись file-ledger на стабильном lockfile и атомарной публикации. Отделить отсутствующий новый ledger от повреждённого существующего. Сохранить ревизии, fsync и действующий owner.

**Различающие тесты и сохраняемое поведение.** Пауза writer после начала записи не даёт читателю blank=no-limits. Обрыв JSON и controlled crash между temp/write/replace оставляют valid old/new либо адресное восстановление, не обнуление расходов. Повтор чтения не списывает новую работу.

**Не считать исправлением.** Не создавать вторую SQLite/бюджетную подсистему, не блокировать на inode заменяемого snapshot и не принимать повреждение за свежий BudgetState.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B37. Бюджетный файл защищён при записи, но читатель может увидеть промежуточную пустоту

*Источник карточки: C02-04. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q05–C.Q07. **Свидетельство:** полное чтение основных методов ledger; B1–B4 на локальной файловой системе. **Достижимость:** используется FileBudgetLedger, чтение пересекается с записью либо запись прервана.

У FileBudgetLedger уже есть блокировка писателей, журнал ревизий, fsync и интерфейс через BudgetMiddleware. Поэтому проблема не в отсутствии бюджетной подсистемы. Однако `_persist_snapshot` делает ftruncate(0), затем запись, а `_load_snapshot` читает путь без согласованной file-lock. Пустое содержимое интерпретируется как отсутствие снимка; `load` возвращает `BudgetState()` без лимитов. BudgetState.remaining для неуказанного лимита возвращает None, и pre_check не трактует это как исчерпание.

В локальном опыте writer удерживал LOCK_EX и был остановлен в контролируемой точке после ftruncate. Незаблокированный читатель прочитал пустоту. Отдельный читатель с LOCK_SH|LOCK_NB корректно обнаружил занятость; после завершения записи прочитал полный новый снимок. Для искусственно оборванного JSON воспроизведён JSONDecodeError. Это не измерение частоты гонки и не имитация полного сбоя питания.

Проблема двойная: неполное состояние может остановить цикл исключением, а пустота может временно выглядеть как отсутствие ограничения. После сбоя пустой существовавший файл нельзя автоматически считать новым ledger с нулевым расходом.

**Разумное расширение.** Для текущего file-backed владельца согласовать чтение и запись; различить «ещё не создано» и «существующий снимок повреждён/оборван». Для устойчивого сохранения использовать полную запись временного файла с fsync и атомарную замену в той же файловой системе, затем синхронизацию директории и реальную процедуру восстановления. При replace замок следует держать на стабильном отдельном lockfile, а не на заменяемом inode данных. Один LOCK_SH у читателя уменьшает окно гонки, но не устраняет повреждение после аварии. [C.E01/C.E02]

Альтернативный путь — использовать подходящую существующую транзакционную реализацию хранения, не вводя новый сервис. Выбор нужно согласовать с действующими требованиями multi-host/ledger; просто поменять JSON на ещё одну параллельную SQLite-базу не является целью.

**Проверка:** конкурентное чтение не видит пустой частичный бюджет; авария между стадиями записи сохраняет проверяемое старое или новое состояние; повреждённый ledger не отменяет лимиты и не обнуляет расходы. Поздняя попытка не расходует бюджет второй раз под тем же идентификатором операции — это отдельное условие идемпотентности, не доказанное текущими опытами.
