## Поручение и минимальная приёмка

Дать heap детерминированный tie-breaker без сравнения payload. Убрать скрытый unbounded merge_log в пользу одного bounded collector с полными counts. Сохранить typed-empty UNION. Готовить index один раз и создавать log payload только при включённом уровне.

**Различающие тесты и сохраняемое поведение.** Обычный повтор ключа не падает.80 событий/cap=1 дают ограниченный пример и полный count. Empty valid UNION сохраняет columns/dtype. OVERLAY трёх столбцов не повторяет set_index трижды; NONE не создаёт лишних audit payload.

**Не считать исправлением.** Не отключать аудит, не обещать константную память для возвращаемых N строк и не заменять source failure успешным typed-empty.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B139. Повтор обычного ключа конфликта роняет ограниченный SUMMARY-журнал

**Основание и область:** `MergeLogCollector._sample` хранит heap-элементы `(-hash_value, MergeLogEntry)`. Dataclass записи не определяет полный порядок сравнения. Поля хэша: seed, row_key, column, два source ID и policy; значения наблюдений в него не входят. [C13.R01, C13.R02]

**Проблема.** Два разных конфликта в одной строковой группе между теми же источниками получают одинаковый приоритет выборки. При вставке второго элемента heap сравнивает сами объекты журнала и получает TypeError. Не нужна редкая коллизия SHA: равенство хэшируемого материала здесь нормальное следствие повторяющегося ключа. Аналогичная проблема возможна в других ветвях heap при совпавших приоритетах, но проверены конкретные вставки.

**Локальное свидетельство P05–P08.** Записи с одним ключом и значениями 10 и 11 получили одинаковый hash и TypeError. Цепочка `compose → JOIN → collector` с двумя строками слева и одной справа воспроизвела ошибку при SUMMARY. FULL на том же входе завершился, сохранив `[10, 11]` и две записи. Контроль с дополнительным детерминированным порядковым ключом сохранил обе записи без сравнения payload.

**Рекомендуемое исправление.** Установить полный порядок элементов heap: приоритет выборки, затем идентичность события или однозначный номер появления в объявленном стабильном потоке. Payload не должен быть последним сравниваемым полем. Когда требуется инвариантность к перестановке, простой счётчик входного порядка недостаточен — нужен соответствующий канонический event ID. Это обычный приём устойчивой очереди при равных приоритетах. [C13.E02]

**Приёмка.** Повторная группа, разные значения и одинаковый ключ не вызывают исключения; распределение ограниченной выборки, лимит, общие счётчики и воспроизводимость остаются определёнными. FULL, SUMMARY и NONE не меняют численный результат допустимой композиции. Отдельно проверить одинаковые payload и повтор одной и той же записи.

**Не делать и границы.** Не отключать аудит и не удалять повторяющиеся конфликты только ради обхода сравнения. Повторная строка может быть самостоятельным наблюдением, а ошибочная кратность должна диагностироваться отдельно по B140. Исправление не внедрено в репозиторий.

## B142. Корректный пустой UNION теряет схему и падает на заключительной сортировке

**Основание и область:** `_union` собирает список разрешённых строк, затем создаёт новый `DataFrame(resolved_rows)` и сортирует по ключам. При нуле строк колонки и их типы не переносятся. [C13.R01]

**Проблема.** Пустой результат после допустимого временного или предметного фильтра — нормальное состояние. Здесь оно превращается в KeyError и может остановить дальнейшую независимую работу. Это другой случай, чем отсутствующий список источников, ошибочный запрос или недоступное чтение.

**Локальное свидетельство P16–P18.** Один пустой вход с колонками `id:int64`, `x:float64` вызвал KeyError `id`. Контрольная пустая ветвь сохранила обе колонки и типы. UNION пустого и непустого входа с совместимой схемой правильно вернул одну строку.

**Рекомендуемое исправление.** После разрешения схемы явно вернуть типизированный пустой результат, не проходя реконструкцию из пустого списка. Для нескольких источников сохранить согласованную схему, не произвольно брать первую несовместимую. Оставить отдельно причину отсутствия наблюдений и состояние доставки.

**Приёмка.** Ноль подходящих строк возвращает пустой dataframe с ожидаемыми ключами, типами и происхождением запроса; следующие разрешённые этапы умеют корректно интерпретировать пустоту. Неуспешное чтение не получает такой же статус, как успешно прочитанный пустой источник.

**Не делать и границы.** Не добавлять фиктивную строку и не считать отсутствие наблюдений доказательством отсутствия эффекта. Проверку «нет ни одного источника» не удалять. Это небольшой локальный ремонт, а не ослабление предметной достаточности данных.

## B143. Ограниченный collector соседствует с неограниченным скрытым списком журналов

**Основание и область:** `_union` создаёт собственный `merge_log` и добавляет в него каждую запись resolver после передачи в `MergeLogCollector`. Этот локальный список не используется для возвращаемого результата compose. [C13.R01]

**Проблема.** SUMMARY или небольшой `audit_max_entries` ограничивают видимую выдачу, но дополнительный список удерживает все подробные объекты до окончания UNION. Ограничение кажется выполненным по итоговым полям, хотя память растёт с числом конфликтов и размером payload. Объекты не обязательно копируются дважды по содержимому, но лишняя ссылка не позволяет освободить те записи, которые collector уже не удерживает.

**Локальное свидетельство P19–P21.** На 80 конфликтах SUMMARY с размером выборки 1 выдал одну запись и правильный общий счётчик 80; локальный список содержал 80. FULL с лимитом 1 также удерживал 80, хотя collector выдал одну запись и указал 79 пропущенных. NONE не создавал этот список записей. Размер проверен через локальный trace-frame на возврате функции, без изменения её вычислительного тела.

**Рекомендуемое исправление.** Удалить неиспользуемую коллекцию либо сделать collector единственным владельцем оперативных записей. Счётчики, ограниченные примеры и обязательная полная история — разные представления. Когда полная история действительно обязательна, сохранять её потоково через существующее хранилище, а не незаметно удерживать в списке при режиме SUMMARY.

**Приёмка.** При большом числе конфликтов объём удерживаемых подробных записей соответствует заявленному режиму; полные счётчики не зависят от размера примера. Проверить не только длину возвращаемого списка, но и фактически живые объекты/память на выбранном сценарии.

**Не делать и границы.** Эта правка не делает весь UNION потоковым: pandas-таблицы и группировка по-прежнему требуют своего ресурса. Нельзя объявить общее потребление O(1) либо измеренный выигрыш времени по данному счётчику. Не пропускать обязательный аудит ради скорости.

## B144. OVERLAY повторно индексирует полный источник для каждого столбца и создаёт отключённые записи

**Основание и область:** внутри цикла по колонкам каждый вторичный dataframe снова получает `set_index`, затем выполняется reindex. При заполнении каждой ячейки создаётся MergeLogEntry даже при AuditLevel.NONE; collector немедленно его игнорирует. [C13.R01]

**Проблема.** Одинаковая структурная подготовка повторяется по ширине таблицы. При широком источнике это лишние построения индекса и потенциальные копии данных; при большом числе заполнений — Python-объекты журнала, которые не используются. Это издержки между существующими векторными операциями, не недостаток вычислительного метода.

**Локальное свидетельство P22–P24.** Для восьми колонок и десяти строк с одним вторичным источником посчитано девять `set_index` — один для primary и восемь для secondary — и 80 созданных записей при NONE. Контроль с одной подготовленной secondary-view выполнил два `set_index` суммарно и дал равный dataframe. Непустое primary-значение 999 осталось приоритетным.

**Рекомендуемое исправление.** Проверить и подготовить индекс каждого реально нужного источника один раз на данную композицию; переиспользовать выровненные представления или ограниченные блоки колонок. Подробную запись создавать лениво лишь для режима, который её требует. Если SUMMARY нуждается в полных счётчиках, считать маски векторно и отдельно материализовать выбранные примеры.

**Приёмка.** Результат, null-маски, порядок приоритетов, ключи и требуемый аудит совпадают с корректным эталоном; число подготовок не умножается на число колонок. Затем измерить время и пиковую память на реальном размере, не выводя коэффициент ускорения из отношения 9/2.

**Не делать и границы.** Не создавать глобальный кэш изменяемых dataframe без идентичности источника. Не копировать заранее все большие источники ради экономии одной операции. Дубликаты ключа предварительно разрешаются по B140; их нельзя «ускорить» произвольным удалением.
