## Поручение и минимальная приёмка

Разделить ticket identity, numerical reuse и calibration role. Full/split проверяют L2→L3 на одной границе до следующей стадии. Defer/freeze допускает только явно разрешённое продолжение с новым основанием.

**Различающие тесты и сохраняемое поведение.** Один candidate с разными contexts/roles не получает старый terminal. Full/split потребляют одну конфигурацию и transition decision. Без нового основания defer не запускает работу; с разрешённым изменением продолжается только нужный остаток.

**Не считать исправлением.** Не обходить freeze новым UUID, не повторять все стадии ради continuation и не считать уровень стадии доказательством допустимости использования.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B156. Кэш ticket объединяет разные контексты и калибровочные роли

Основание и область: `FunnelOrchestrator.submit`; ключом `_ticket_cache` служит только хэш candidate. При попадании контекст дополняется через `setdefault`, а уже terminal-ticket возвращается без нового исполнения. Sentinel-метаданные исключаются из хэшируемого payload и затем могут изменить роль того же ticket. Область — повторное использование экземпляра, в том числе split Stage A/B; нативный node, создающий новый orchestrator для каждого прохода, может избегать межзапусковой части риска. [C15.R01]

**Наблюдение:** C15-01: запрос A на dataset v1 со значением 10 исполнен, затем тот же кандидат в запросе B на v2 со значением 20 вернул 10; всего один вызов evaluator. Свежий экземпляр вернул 20. Точное повторение исходного запроса справедливо не вызывало новых вычислений. C15-04: sentinel с тем же предметом получил старый terminal-ticket, поменял его `is_sentinel` и не выполнил ни одной новой оценки.

**Рекомендуемое исправление:** разделить идентичность предмета-кандидата, действительного оценивания и организационной попытки. Ключ переиспользуемого научного результата должен включать эффективные ссылки на данные, модель и настройки, режим/схему оценки, область доступа и идентичность случайной реплики там, где она существенна. Новый запрос получает своё состояние ticket; совместимый неизменяемый результат можно присоединить с записью повторного использования. Калибровочное предъявление не меняет задним числом роль обычной попытки и не считается независимым наблюдением только из-за метки sentinel.

**Не исправлять** добавлением всех объектов `context`, случайного времени или UUID в общий ключ: это разрушает полезное переиспользование и не определяет семантику запроса. Не очищать весь кэш при каждом вызове. Для первого контролируемого запуска дешёвый обход — явно ограниченный временем одного запроса orchestrator при сохранении отдельного кэша артефактов.

**Приёмка:** одинаковый эффективный запрос переиспользует результат; новая версия входа не получает старый score; новый независимый контроль действительно исполняется; история обычной попытки не изменяется. Приоритет высокий на stateful-маршруте, сложность средняя. Связь: B60–B61, B118, B127; здесь другой владелец и непосредственная связь Stage A/B.

## B158. Разбиение Stage A/B меняет обязательный переход после L2

Основание и область: `advance` запрашивает VOI после L2/L3 только при наличии cheap-signal и если следующая стадия не превосходит текущий `execution_target`. Stage A устанавливает target=2. При следующем Stage B исполнение начинается уже с L3, а переход из L2 не переоценивается. [C15.R01]

**Наблюдение:** при одинаковых стадиях 2(signal), 3(без signal), 4 и scheduler=`defer` единый full-вызов выполнил только L2 и спросил scheduler один раз. Раздельные `as_stage_a_callable` и `as_stage_b_callable` выполнили все три стадии, не спросили scheduler ни разу и вернули `complete`. Контроль с разрешённым `advance` завершил единый маршрут через тот же набор стадий.

**Рекомендуемое исправление:** закрепить решение на ребре перехода, а не в хвосте вызова предыдущей стадии. До запуска следующей дорогостоящей работы должна существовать актуальная запись решения относительно её входов, бюджета и области. Частичная выдача может поставить паузу, но не устраняет этот переход. Решение не следует повторно списывать или рассчитывать только из-за формы API. При изменении основания требуется адресная ревалидация, а не слепое принятие старого решения.

**Не исправлять** обязательным повторным исполнением L2 при каждом Stage B, запретом split-API или отключением VOI. Burn-in-калибровка может иметь явно иной маршрут и должна сохранять собственные разрешения. Эвристическое решение не подменяет настоящий допуск владельца ресурсов.

**Приёмка:** единый и раздельный вызовы на неизменных входах дают одинаковый набор разрешённых вычислений, расходы и причины остановки. На изменённых входах фиксируется необходимое различие. Опыт использует scheduler-фикстуру, не доказывает обход внешнего бюджета или полномочий. Приоритет высокий, сложность небольшая/средняя; связь B120: допуск расхода не зависит от формы обращения.

## B159. Временное defer или freeze закрывает ticket без доступного продолжения

Основание и область: `defer`, `retry_cheaper` и `freeze_frontier` переводят ticket в `is_terminal=True`; `advance` работает лишь пока ticket не terminal. Повторное `submit` того же candidate возвращает прежний объект. В прочитанных публичных методах нет перехода возобновления после изменения условия. [C15.R01, R09]

**Наблюдение:** C15-11: scheduler сначала отложил работу после L2, затем разрешил её, но повторный `advance` не спросил его и не запустил L3/L4. C15-13: снятие freeze до первого вычисления тоже не открыло работу. Важный положительный контроль: остановка только по target=2 не terminal, и штатное последующее advance завершает оставшиеся уровни.

**Рекомендуемое исправление:** различать закрытую попытку, окончательное отклонение и ожидание устранимого условия. Добавить явное возобновление или новый ticket-преемник, связанный с прежним, по событию изменения бюджетного/данного/человеческого основания. Уже подтверждённые незатронутые стадии переиспользуются, новый переход проверяется заново. `retry_cheaper` должен адресовать иной разрешённый план, а не означать бесконечный повтор старого.

**Не исправлять** прямой установкой `is_terminal=False`, удалением истории, генерацией фиктивного изменённого candidate или снятием freeze без его действительного владельца. Терминальность конкретной попытки может быть осознанной политикой; тогда необходим открытый путь к корректному преемнику, а не молчаливое изменение её смысла.

**Приёмка:** повтор без новых оснований не расходует ресурс; разрешённое изменение создаёт проверяемое продолжение; постоянный blocker не исчезает; lineage и расходы сохраняются. Приоритет высокий для итеративного исследования; сложность средняя. Это расширение способности продолжать работу, не ослабление критерия её допустимости. Связь B09/B12/B118: содержательное продолжение, получение нового основания и отдельный запуск.
