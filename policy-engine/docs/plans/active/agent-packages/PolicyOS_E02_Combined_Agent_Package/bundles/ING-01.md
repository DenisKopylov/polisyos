## Поручение и минимальная приёмка

Нормализовать typed/dict dataset и передать действительный cursor в поддержанный ingestion API. Продвигать только подтверждённый dataset по границе источника, не по local now. Replay сохраняет свой режим после ошибки. Перед включением B79 совместно исправить B80 и проверить пригодность старых cursors.

**Различающие тесты и сохраняемое поведение.** A зафиксирован до 9, B failed: продвинут только A. Typed/dict manifests эквивалентны. Missing cursor явно означает полный режим. Missing/corrupt replay fixture не вызывает ordinary/live delegate; успешный replay сохраняет provenance.

**Не считать исправлением.** Не переименовывать неразрешённую живую загрузку вместо предотвращения действия; не пересылать неизвестный keyword и не применять общий datasets_fetched к каждому источнику.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B79. Инкрементальный маршрут находит курсор, но не передаёт его в загрузку

**Происхождение:** C07-01. **Основание:** тело `run_batch_incremental`, BI1–BI3. **Применимость:** вызов данного helper; независимая инкрементальная логика нижележащего connector может изменить конечное поведение. [C07.R01]

**Проблема.** Helper строит `incremental_cursors`, заполняя его из `CursorStore`, но вызывает `run_orchestrated_ingestion` без этого объекта и без изменения передаваемого manifest/request. Вычисленный здесь прогресс не влияет на делегированный запрос. Поэтому чтение и журналирование курсора сами по себе ещё не дают экономии повторной загрузки. Нельзя утверждать, что каждый connector обязательно загружает весь источник: у него может быть собственная логика. Установлена потеря именно сведений, разрешённых этим helper.

Есть дополнительный входной дефект: условное выражение в первой итерации возвращает пустые идентификаторы для несловарного dataset, хотя атрибутный manifest принимается окружающим кодом. В BI1 словарные datasets дали правильные lookup-пары, но делегат не получил watermark `9`. В BI2 атрибутные datasets вызвали два поиска `('', '')`, тогда как последующая запись использовала настоящие имена A и B.

**Рекомендуемое исправление.** Один раз нормализовать dataset к существующему типизированному представлению. Разрешённый курсор должен стать частью эффективного запроса источнику через поддерживаемый механизм incremental hints. Если на этой границе такого аргумента нет, нужно небольшое согласованное расширение запроса, а не передача произвольного неизвестного keyword. Сохранять snapshot/version, смысл границы и источник курсора. Внутренний ключ должен различать connector, dataset и нужную partition: одного одинакового имени dataset у разных источников недостаточно.

**Приёмка.** Настоящий connector получает объявленную нижнюю границу и возвращает допустимую дельту; атрибутный и словарный входы эквивалентны. Отсутствующий курсор допускает честно обозначенную полную загрузку. Источник без поддержки инкрементальности не выдаётся за поддерживающий её. Сравнить реальные объём I/O и состав результата, а не только запись «cursor found».

**Граница опыта.** Исполнено перенесённое тело с захватывающим делегатом, а не backend источника. BI3 — модель предлагаемой привязки, не патч upstream API. Производственная доля повторных загрузок не измерялась.

## B80. Общий успех одного dataset продвигает курсоры всех, причём до локального now

**Происхождение:** C07-02. **Основание:** завершение `run_batch_incremental`, BA1–BA3. **Приоритет:** высокий перед применением сохранённых курсоров для инкрементального чтения. [C07.R01]

**Проблема.** Условие `result.datasets_fetched > 0` открывает запись курсора для каждого dataset в manifest. Результат отдельного источника и подтверждённое покрытие здесь не проверяются. `watermark_value` задаётся через локальный `datetime.now(UTC)`, а watermark-policy определяется один раз из последнего запомненного connector-family. Один успех может тем самым продвинуть и неуспешный источник, назначить неподтверждённую верхнюю границу либо чужую семантику курсора.

В BA1 при двух datasets и фикстурном `datasets_fetched=1` записаны оба курсора с одинаковым текущим временем; policy вызвана только для beta. При нулевом общем результате запись не выполнялась — этот контроль сохранён. Это не свидетельство уже пропущенных реальных строк: показана логика helper на допустимом частичном результате.

**Рекомендуемое исправление.** Продвигать cursor по индивидуальному подтверждению фактической загрузки и фиксации результата: какой источник, какой запрос, какая непрерывно покрытая граница, какие артефакты сохранены. Timestamp выполнения не заменяет event-time/offset источника. Политика разрешается для конкретного dataset. При частичном успехе остальные курсоры остаются на прежней committed-позиции; агрегированный счётчик служит отчёту, не разрешению на продвижение.

**Почему B79 нельзя чинить отдельно.** Пока рассчитанный курсор не используется нижележащим запросом, ошибка B80 может быть скрыта повторной полной загрузкой. Подключение честной инкрементальности способно превратить старую ложную отметку в пропуск данных. Перед активацией B79 старые курсоры требуют проверки или явно консервативной миграции, а не автоматического доверия.

**Приёмка.** Источник A зафиксирован до 9, B не завершён: продвинут только A до 9. Искусственно задержавшаяся запись с event-time раньше локального now не исчезает. Для смешанных connector-family применяются их собственные правила; ошибка сохранения выходов не подтверждает прогресс источника. Повтор остаётся идемпотентным в объявленной области.

## B88. Replay после ошибки вызывает обычную загрузку вне симулятора и сохраняет метку replay

**Происхождение:** C07-10. **Основание:** полное тело run_replay_mode, RP1–RP3. **Приоритет:** высокий для воспроизводимых и ограниченных по сети запусков. [C07.R01: окно 335–555]

**Проблема.** Внутренняя coroutine выполняет загрузку под `async with simulator`. Когда она падает, контекст уже закрыт. Внешний широкий except вызывает обычный `run_orchestrated_ingestion` без того же симулятора, затем присваивает `result.mode_effective = 'replay'`. Таким образом, fallback изменяет доступную среду исполнения, но не отражает изменение в типе результата. Обещание helper «no network» не устанавливается этим маршрутом после ошибки.

В RP1 исполнено перенесённое тело с fixture imports: replay-попытка падает на «fixture missing», обычный делегат вызван один раз с simulator_active=False, результат помечен replay. **Никакого реального сетевого запроса не выполнялось.** Сам обычный делегат не обязан всегда обращаться в сеть — его dependencies могут ограничивать действие, — но эта replay-граница ограничение не сохраняет. Успешный replay-контроль не вызвал обычный fallback.

**Рекомендуемое исправление.** Режим воспроизведения — существенная часть запроса и допуска инструментов, а не только label. При отсутствии записи/повреждении симулятора вернуть точный недостающий вход либо использовать другой исполнитель, который читает тот же зафиксированный набор записей и сохраняет запрет сети. Разрешённый переход к новой живой загрузке оформлять отдельно: новый режим, действительное разрешение, иной provenance и отдельный результат; он не является воспроизведением прежнего эксперимента.

Не лечить ошибку только переименованием в `live`: сама сеть или передача данных может быть не разрешена. Не удалять failing fixture, не выполнять незаметный live refresh и не смешивать старые записи с новыми ответами под одним frozen-result.

**Приёмка.** На настоящем missing/corrupt fixture сетевой egress и ordinary delegate не запускаются без отдельного допуска; режим и provenance правдивы. Поддерживаемый fallback replay сохраняет те же bytes и request binding. Успешный replay остаётся дешёвым повторным исполнением. Тестовая фикстура в архиве проверяет границу вызова, а не настоящий aiohttp/APISimulator.
