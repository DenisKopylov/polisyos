## Поручение и минимальная приёмка

Уравнять live/persisted dedupe по объявленному горизонту. Ограничить входные batches; освобождать память настоящим spill/consumer, не бессодержательной паузой. Валидировать строки по versioned schema, не большинству пачки. Сделать bytes-учёт инкрементальным там, где это корректно.

**Различающие тесты и сохраняемое поведение.** При cap=2 последовательность a, b, c, a одинаково обрабатывается до и после restart. Optional note не меняет accepted set при batch=1/3. Длинная session и крупный chunk не меняют границы окна ради RAM. Малый threshold и счётчики сегментов/сериализации заменяют искусственный OOM.

**Не считать исправлением.** Не подменять 24-часовую гарантию count-horizon без решения; не терять научные строки из-за probabilistic false positives; не собирать весь chunk обратно и не заполнять missing нулём.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B83. Ограниченная очередь ключей соседствует с неограниченным и иначе восстанавливаемым множеством

**Происхождение:** C07-05. **Основание:** dedupe-loop и processing contract; DD1–DD3. [C07.R02: окна 570–1190; C07.R04]

**Проблема.** `dedupe_keys` имеет `deque(maxlen=...)`, но `dedupe_seen` только пополняется: ключ, вытесненный из deque, не удаляется из set. Membership проверяется по set, а checkpoint сохраняет только deque. Непрерывный процесс удерживает все увиденные уникальные ключи; после restart он помнит лишь хвост. Кроме потери ограниченности памяти, меняется поведение дедупликации от факта перезапуска. Объявленный `dedupe_window_seconds` не участвует в этом цикле; флаг `enabled` также не управляет самой проверкой, хотя эффективный контракт может его содержать.

В модели исходного loop при cap=3 и двадцати уникальных сообщениях deque имеет 3 элемента, set — 20. Для `a,b,c,a` при cap=2 непрерывный проход подавляет последнее a; перезапуск после c допускает его, поскольку a отсутствует в сохранённом хвосте. Официальная семантика `deque(maxlen)` автоматически удаляет только элементы самой deque, не связанного set. [C07.E01]

**Рекомендуемое исправление.** Один владелец dedupe-состояния с явно определённым временным/позиционным горизонтом, атомарным обновлением индекса и очереди и тем же persisted-представлением. Синхронное вытеснение deque/set — минимальный механизм для явно принятого count-horizon; оно не доказывает соблюдение 24-часового горизонта при большой частоте сообщений. Для более широкой гарантии нужны сохранённый индекс/сегменты либо честная ограниченная остановка, а не незаметное сокращение обещанного горизонта.

Не предлагать вероятностный фильтр как единственный источник решения о выбрасывании научных строк: false positive потеряет данные. Не склеивать разные события по идентификатору сущности, если источник различает версии/операции; сама семантика message ID требует контракта. Полный редизайн всех cache-слоёв не нужен.

**Приёмка.** При одинаковой политике uninterrupted/resumed дают одинаковое решение для пограничных повторов. Live memory и durable horizon измеряются отдельно; изменение cap не меняет гарантию без отражённого решения. TTL, disabled-режим и коллизии доменных ID проверяются как отдельные условия. DD3 — контроль ограниченного count-horizon, не реализация исходной 24-часовой политики.

## B84. Backpressure делает паузу, но не освобождает оконную память и не ограничивает входной блок

**Происхождение:** C07-06. **Основание:** основной stream-loop и accumulator.buffered_bytes; BP1–BP4. [C07.R02: окна 290–570 и 870–1190; C07.R04]

**Проблема.** При превышении лимита runtime вызывает pause → sleep → resume, но не удаляет, не выгружает и не передаёт дальше накопленный state окна. В этом же цикле нет другого потребителя, который освободил бы accumulator во время сна. Следующий poll продолжает добавление. Лимит проверяется до чтения chunk, а все очищенные batches этого chunk сначала вновь собираются в общий `clean_rows`. Даже `batch_size=1` не ограничивает суммарный размер блока. Ветка отдельно реализует FAIL_CLOSED; остальные объявленные стратегии в этом месте проходят через ту же паузу, без настоящего spill.

В модели с настоящим accumulator при лимите 5 сессионное окно выросло до 12 строк после семи пауз. Один блок из десяти строк прошёл предварительную проверку при cap=3, потому что буфер до блока был пуст. Это не измерение OOM в развёртывании, а контрпример к исполнению локального ограничения.

**Второй источник стоимости.** `buffered_bytes()` заново собирает список строк и JSON-сериализует каждую удерживаемую строку на каждой итерации. Для двадцати постепенно добавленных строк в незакрываемой сессии контроль насчитал 190 повторных оценок размера. При растущем буфере такая диагностика сама может дать квадратичную работу. Реальная доля CPU ещё не профилировалась.

**Рекомендуемое исправление.** Проверять допуск при поступлении ограниченных batches/строк, а давление связывать с реальным действием: обработка готового окна, spill неизменяемых сегментов, ожидание отдельного потребителя или точный отказ для неподдержанной ёмкости. Сохранять логическую границу окна: нельзя принудительно закрыть половину сессии ради уменьшения RSS и назвать это тем же исследованием. Где возможно, поддерживать размер инкрементально при добавлении/удалении, с отдельным учётом реальных затрат Python-объектов и внешних сегментов.

**Приёмка.** Длинная сессия или большой chunk не превышают принятый ресурс молча; состав и идентичность итогового окна не зависят от spill. Заявленный SPILL_TO_DISK действительно выгружает данные либо явно не поддерживается. В BP4 контроль сохраняет все 12 логических строк при peak live=5; это модель сегментации, не production disk implementation. Проверять время наблюдаемости, а не только throughput вычисления.

## B86. Размер технической пачки меняет, какие строки объявлены испорченными

**Происхождение:** C07-08. **Основание:** `_sanitize_stream_rows`, iter_record_batches и fields-only CDC; SM1–SM4. [C07.R01: окно 335–555; C07.R02: окно 870–1190; C07.R04]

**Проблема.** Sanitizer определяет ожидаемый набор полей голосованием внутри каждой текущей пачки, а несовпавшую структуру объявляет `poison_stream_message`. Он не получает объявленную схему с optional-полями. Поэтому один и тот же валидируемый поток обрабатывается по-разному при изменении только batch_size. Затем runtime считает схему объединением наблюдённых имён в чистом chunk: отсутствие optional-поля в следующем chunk может выглядеть как breaking schema change, хотя контракт источника не менялся. Изменение типов при прежних именах этой fields-only процедурой, наоборот, не устанавливается.

В SM1 три строки имеют `id,value`; у первых двух есть ещё `note`. При batch_size=1 приняты все три; при batch_size=3 — только первые две. В контрольной объявленной схеме `note` optional, и все три принимаются независимо от разбиения. Бесконечное значение настоящей метрики продолжает карантинироваться — устранение зависимости от пачки не означает отключение качества.

**Рекомендуемое исправление.** Нормализовать и валидировать по версионированной схеме источника/контракту измерений, различая required, optional, missing и null. Для источника с действительно неизвестной схемой неоднородность — диагностический результат и основание исследования, не автоматически доказанная испорченность меньшинства. При необходимости использовать явно объявленный schema-inference этап на фиксированном срезе, а не незаметно переучивать правило в каждой технической пачке.

Не заполнять все отсутствующие значения нулями ради единообразия. CDC должен различать версию контракта, видимые значения конкретного chunk и допустимую эволюцию. Сами имена полей не устанавливают полную семантическую совместимость.

**Приёмка.** Для фиксированного исходного набора и схемы batch_size не меняет accepted/rejected membership. Настоящее нарушение обязательного поля, типа или finite-метрики обнаруживается. Изменение optional coverage не выдаётся за удаление столбца из схемы. Область вывода условна для строго однородных источников, но зависимость helper от технической границы пачки воспроизведена непосредственно.
