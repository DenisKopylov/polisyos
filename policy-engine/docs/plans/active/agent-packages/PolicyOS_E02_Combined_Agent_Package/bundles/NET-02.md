## Поручение и минимальная приёмка

Разделить ёмкость единичного запроса и скорость refill. Привязать completion к generation допуска. Реестр освобождает только безопасное для восстановления состояние; active lease и cooldown не являются необязательным кэшем.

**Различающие тесты и сохраняемое поведение.** Rate=0.2/cap=1 разрешает один запрос и следующий через 5 по управляемым часам. Weighted request сверх capacity отвергается. Старый CLOSED-success не закрывает новый HALF_OPEN. TTL/pressure не сбрасывает Retry-After и не создаёт второй независимый регулятор.

**Не считать исправлением.** Не округлять rate до 1, не глотать любой CircuitLeaseError и не решать bounded-registry созданием огромного неограниченного словаря.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B91. Ограничение ниже одного запроса в секунду запрещает любой обычный запрос

**Происхождение:** C08-03. **Основание:** `RateLimiter`, `RateLimiterConfig`, `AdaptiveRateLimiter`, `with_rate_limit`; R1–R4. **Приоритет:** высокая локальная отдача для медленных внешних API. [C08.R02]

**Проблема.** По умолчанию ёмкость bucket задаётся равной rate_rps. Между тем обычное acquire требует 1 token и немедленно отвергает tokens > burst_size. Допустимая положительная скорость 0.2 запроса/с создаёт bucket 0.2; единичный запрос запрещён не на пять секунд, а постоянно. Положительность настройки проверена, но размер единицы операции с ёмкостью не согласован. Декоратор вызывает `limiter.acquire()` именно с единицей.

**Проверки.** R1: rate=0.2, default burst=0.2 → ValueError до ожидания. R2: при том же rate и явном burst=1 первый запрос проходит, следующий требует ровно 5 секунд по управляемым часам, после продвижения времени снова проходит. R3: rate=2 работает. R4: явно запрошенные 2 token при capacity=1 честно отвергаются.

**Рекомендуемое исправление.** Разделить размер разрешённой операции и среднюю скорость: для единичных запросов default capacity должен вмещать хотя бы один запрос, а скорость пополнения сохраняется 0.2. Существующая конфигурация burst=1 уже даёт минимальный локальный обход; декоратору требуется согласованное правило ёмкости. Для взвешенных операций поддержать явно известную допустимую единицу либо отказывать невозможной конфигурации заранее.

Не округлять rate вверх до 1: это нарушит лимит источника. Не убирать проверку tokens > capacity: ожидание тогда может стать бесконечным. Если источник запрещает начальный burst, стартовый баланс и pacing задаются отдельно от ёмкости. Retry-After и права обращения продолжают действовать.

**Приёмка.** Скорости 0.1, 0.2, 1 и >1; холодный старт; обычный и взвешенный запрос; явный cooldown; отмена ожидания. Проверить долгосрочную частоту и начальный burst по контракту источника, а не только отсутствие исключения. Конкретный production-коннектор с rate=0.2 здесь не выявлен: это воспроизведённый дефект поддерживаемой конфигурации общего механизма.

## B92. Поздний ответ прежнего поколения circuit breaker превращает успех в ошибку владения

**Происхождение:** C08-04. **Основание:** Fabric circuit-breaker lease и `execute`; C1–C5. **Приоритет:** высокий для перекрывающихся внешних запросов. [C08.R03]

**Проблема.** Попытка получает lease с состоянием начала. Но `record_success` и `record_failure` выбирают ветвь по текущему глобальному состоянию circuit. Если запрос начался в CLOSED, пока он выполнялся другой запрос открыл circuit, а после cooldown состояние стало HALF_OPEN, старый lease не содержит half-open token. Его завершение требует несуществующий token и вызывает CircuitLeaseError. Изменения поколения очищают набор tokens; поздние завершения прежних half-open probes требуют аналогичного различения.

**Проверки.** C1: тестовый producer завершил работу и вернул 42, но обёртка после перехода CLOSED→OPEN→HALF_OPEN подняла CircuitLeaseError. C2: исходная ошибка OSError замаскирована той же ошибкой владения. C3: настоящий probe текущего HALF_OPEN возвращает 42 и закрывает circuit. C4: существующий cancellation-path корректно освобождает его token. Последнее — важная уже имеющаяся защита, а не недостающая возможность.

**Рекомендуемое исправление.** Связать lease с поколением состояния защиты; завершать именно ту попытку, которая была допущена. Поздний результат сохраняет собственный успешный/ошибочный исход, но не становится голосом за восстановление нового поколения. Историческую метрику можно записать отдельно. Нельзя просто проглотить любой CircuitLeaseError: повторное завершение, чужой token и настоящее нарушение владения должны оставаться диагностируемыми.

Публикация полезного ответа и изменение автомата доступности — разные операции. Обёртка не должна интерпретировать собственную bookkeeping-ошибку как новую ошибку внешнего поставщика и повторно проводить неправильный lease через `record_failure`. Нужна идемпотентная финализация попытки, не ещё один circuit breaker.

**Приёмка.** Старый CLOSED-success, старый CLOSED-failure, поздний HALF_OPEN-token после открытия нового поколения; настоящий актуальный probe; cancellation; повторная финализация. Между сменой состояния и поздним ответом использовать управляемые события/часы, а не случайные sleeps. Проверенные тела используют fixture state-transition carrier и tracer; реальный HTTP-поставщик не вызывался.

## B93. LRU/TTL реестра стирает действующую защиту, а не только необязательный кэш

**Происхождение:** C08-05. **Основание:** полный `_bounded_registry.py` сверенный по Git blob, producers circuit/rate wrapper; E1–E3. **Приоритет:** зависит от числа активных ключей и длительности запросов/cooldown. [C08.R04, C08.R02, C08.R03]

**Проблема.** Реестр ограничен по размеру и времени последнего обращения, но хранимые объекты — stateful регуляторы. В них находятся token-баланс, Retry-After, текущий circuit и незавершённые leases. Вытеснение удаляет лишь запись из OrderedDict; выданный старый объект может продолжать жить у выполняющегося запроса. Следующее обращение создаёт новый объект для того же ключа с независимым свежим состоянием. Два регулятора одного источника перестают разделять лимит.

**Проверки.** E1: без вытеснения тот же ключ возвращает прежний объект и cooldown. E2: при фактическом default max_items=256 добавление 256 других ключей вытесняет A; следующее A получает новый bucket с 1 token и без прежнего запрета до t=300, тогда как старая ссылка ещё существует. E3: с тестовым TTL=1 после t=2 происходит то же при неистёкшем cooldown. Это реальное исполнение всего автономного registry-модуля, но объекты регуляторов и часы — fixtures; реальная нагрузка 257 источников не измерялась.

**Рекомендуемое исправление.** Разделить необязательный lookup-кэш и обязательное состояние управления нагрузкой. Не вытеснять живое состояние, пока оно влияет на допустимость вызовов: активная попытка, ненулевой cooldown, существенный balance/history. Освобождать только quiescent-объекты при семантически безопасном восстановлении. При нехватке памяти — ограничить допуск новых ключей либо сохранить компактное состояние у существующего владельца; не создавать безлимитную вторую карту.

Pinning только выполняющихся запросов недостаточен: неактивный объект всё ещё может содержать действующий Retry-After. Один общий замок вокруг словаря тоже не решает проблему — операции уже thread-safe, ошибочна семантика жизни значения. Увеличить 256 до огромного числа — отсрочить, а не устранить дефект.

**Приёмка.** Вытеснение под давлением памяти и TTL во время ожидания, cooldown и half-open; одинаковый ключ имеет один действительный регулятор или связанную сохранённую state-generation. Долговременные истории действительно ограничены. Отказ добавлять новый ключ должен быть понятным ресурсным результатом, не случайным отказом источника и не сбросом его защиты.
