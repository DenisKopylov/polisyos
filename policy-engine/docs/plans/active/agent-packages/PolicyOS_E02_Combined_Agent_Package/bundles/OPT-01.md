## B108. Допустимое альтернативное поле дефицита игнорируется при отсутствии основного

**Основание и область:** `BudgetDeficitObjective._extract_value` в `search/objective.py`; D01–D03. Это не общий диагноз всех objectives и не повтор B18 об исходе симулятора. Здесь уже передано настоящее значение в прямо предусмотренном альтернативном поле. [C10.R02]

**Проблема.** `results.get('gov_balance', 0.0)` возвращает ноль при отсутствии ключа. Ветвь чтения `budget_deficit` исполняется только при `balance is None`. Поэтому отсутствие `gov_balance` и его явный null, которые в данном fallback выглядят как два способа указать отсутствие основного измерения, приводят к разным численным целям. Пустой объект также даёт ноль.

**Локальное воспроизведение.** `{'budget_deficit':100}` даёт 0; добавление `gov_balance=None` даёт 100; `{'gov_balance':-100}` тоже даёт 100. В сравнении минимизируемого дефицита вариант с фактическим 100 получает балл 0 и обгоняет вариант с `gov_balance=-5`, получивший 5. Явный нулевой balance действительно остаётся нулём — его нельзя ошибочно заменить альтернативой через truthiness.

**Рекомендуемое решение.** На входной границе разрешить одно эффективное измерение по объявленным правилам presence/null/alias, знака и единиц. Когда основное значение отсутствует, использовать проверенное альтернативное; когда присутствует действительный ноль — сохранить его. Если оба отсутствуют, возвращать адресно отсутствующую метрику, а не экономически благоприятный ноль. Конфликт двух реально переданных значений требует явной политики, а не молчаливого предпочтения.

**Почему это экономно.** Достаточно небольшого общего extractor/adapter для данного контракта, а не новой функции благосостояния или изменения весов. Уже рассчитанный плохой исход перестаёт улучшаться из-за названия ключа. Недоступную метрику не следует автоматически наказывать произвольным числом: вариант может оставаться исследовательским, но не получать недоказанное преимущество.

**Приёмка и предел.** Эквивалентные кодировки balance/deficit дают одинаковый score; ноль не считается отсутствием; полностью отсутствующее, конфликтующее, non-finite и несовместимые единицы различены. Настоящие симуляционные producer и пользовательский search здесь не запускались.

## B109. Ускоренный Pareto-отбор сохраняет точку, уже доминируемую предыдущей группой

**Основание и область:** `_find_non_dominated_2d`, его использование в 3D и независимая проверка `_dominates_vector`; P01–P04. Полный `pareto.py` исполнен после совпадения Git blob. [C10.R01, C10.R09]

**Проблема.** Точки группируются по первой координате в убывающем порядке. Для последующей группы любая предыдущая группа уже строго лучше по первой координате. Но точка отбрасывается лишь при `second_value < max_second_from_previous_groups`, не при равенстве второй координаты. Это сохраняет доминируемую точку. 3D вызывает тот же 2D-helper для локального фронта, поэтому локальное расхождение переносится выше.

**Локальное воспроизведение.** Для максимизации `(2,1)` и `(1,1)` быстрый алгоритм возвращает обе точки, прямое определение доминирования — только первую. Для `(1,2,1)` и `(1,1,1)` в 3D также возвращаются обе. Полностью одинаковые `(2,1),(2,1)` должны остаться двумя равнозначными записями; существующий контроль это сохраняет. Перебор 81 упорядоченной пары на маленькой целочисленной сетке обнаружил расхождения; локальный контроль условия дал ноль расхождений на этой сетке.

**Рекомендуемое решение.** Отдельно отслеживать существование предыдущей группы и применять к ней слабое сравнение второй координаты: строгое улучшение первой уже обеспечено порядком групп. Внутри одной группы сохранять все настоящие равенства её максимума. Дополнить 3D теми же различающими тестами. Для отсутствующего предыдущего значения предпочтителен явный sentinel, не смешиваемый с числом неизвестной метрики.

**Чего не делать.** Не возвращать весь алгоритм к квадратичному сравнению на больших входах и не удалять все одинаковые точки по значениям. Независимый медленный oracle нужен в тестах; различные кандидаты с одинаковыми метриками имеют разные основания и историю. Изменение epsilon/округления — отдельная политика, не способ скрыть ошибку строгого сравнения.

**Приёмка и предел.** Согласовать быстрый и прямой фронт для 1–4 измерений, перестановок входа, равенств одной/всех координат и обоих направлений после нормализации. Приведённый тестовый patch использует простой конечный контроль, не предлагается как production-оптимизация. Неправильный конечный выбор пользователя не измерялся; доказано расхождение данного математического helper.

## B110. Название метрики не сохраняет идентичность координаты Pareto

**Основание и область:** `ParetoPromoter._objective_names`, `_vector_to_objectives`, `_reference_point`, `is_dominated`; I01–I02. [C10.R01, C10.R03]

**Проблема.** Координаты исходно определяются списком `PromotionPolicy`, каждая со своим split и направлением. Вектор хранит все позиции. Но преобразование в словарь использует только `primary_metric`. Две политики `score` для selection и holdout превращаются в один ключ, последняя запись заменяет первую. Дальнейшее `is_dominated` работает уже с сокращённым словарём. Аналогично теряется координата reference point.

**Локальное воспроизведение.** A имеет `(selection=10, holdout=1)`, B — `(selection=1, holdout=10)`. Векторы действительно выражают компромисс и исходный фронт содержит оба. Сериализованное представление хранит только `score=1` и `score=10`; после этого `is_dominated(A, front)` возвращает True. Прямая проверка исходных векторов доминирования не находит.

**Рекомендуемое решение.** Использовать полную стабильную идентичность координаты: как минимум metric + split, с привязкой к версии определения/единицам и выбранному направлению. Сохранять raw и нормализованное представление различимо. Либо передавать типизированный упорядоченный вектор вместе со схемой координат, либо словарь по однозначному ID. Случайное повторение одной и той же полной координаты отвергать при сборке.

**Минимальный безопасный шаг.** До миграции DTO запретить неоднозначные одноимённые координаты именно в этом формате; не запрещать содержательно правильное сравнение одной метрики на разных split вообще. Недостаточно добавить проверки только в `_vector_to_objectives`: сравнение, reference point, сохранение и чтение должны использовать одну схему.

**Приёмка и предел.** Фронт, его сериализация/round-trip и `is_dominated` дают одно отношение. Смена display-label не меняет решение; смена split не исчезает. Это локальная потеря семантики, а не доказательство, что все производственные policies сейчас имеют такие повторения.

## B111. Неизвестная или non-finite метрика проходит в численное сравнение без отдельного состояния

**Основание и область:** `BenchmarkEvaluation` допускает обычные float; Pareto переводит отсутствующие значения в бесконечный худший sentinel; registry проверяет `None`, но не finite. N01–N04. [C10.R01, C10.R03, C10.R07]

**Проблема.** В 2D NaN в первой координате не равен самому себе: формирование группы оставляет её пустой, следующий `max` вызывает ValueError. В 1D результат `max` с NaN зависит от порядка. Отсутствие координаты превращается в `-inf` после нормализации; та же величина попадает в reference point и может дать бесконечный hypervolume. Это не то же самое, что честно оставить неполный кандидат несравнимым.

**Локальное воспроизведение.** 2D-вызов с NaN выдаёт `max() arg is an empty sequence`. В 1D перестановка `[NaN,1]` в `[1,NaN]` меняет размер фронта с 0 на 1. В наборе `(1,1),(2,missing),(0,0)` hypervolume становится inf. Отдельный контроль generic registry на fixture-store допускает NaN при первом назначении; последующее чтение его JSON-представления не проходит DTO-validation.

**Существенная граница последнего опыта.** Fixture-store намеренно не является native CAS и не проверяет каноническую запись артефакта. Поэтому N04 не доказывает, что нечисловой отчёт проходит весь настоящий persistence-путь; это проверка самой численной границы registry. Для Pareto прямой API получает в памяти типизированные evaluation без такой предварительной записи.

**Рекомендуемое решение.** Перед численным сравнением разрешать каждую обязательную метрику: measured finite / missing / invalid / неприменимо. Сохранять неполные результаты отдельно и выдавать точный следующий запрос, не превращая unknown в лучшую или худшую бесконечность. При изменении множества сравниваемых координат создавать явно другую задачу сравнения. Проверять finite у порогов и индикаторов; не «лечить» NaN произвольным clipping или нулём.

**Экономная проходимость.** Один непригодный кандидат не должен ломать весь доступный поднабор корректных кандидатов, если политика допускает частичный фронт. Но такой поднабор маркируется как частичный; это не доказательство глобального превосходства над неоценёнными вариантами.

**Приёмка.** Перестановки не меняют конечный фронт; invalid сохраняет причину; reference point и hypervolume конечны или явно недоступны; генезис и смена чемпиона не публикуют неопределённое число. Проверить реальный CAS и существующие upstream guards, не дублируя их несовместимыми кодами.
