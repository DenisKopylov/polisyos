## Поручение и минимальная приёмка

Проверить candidate/evaluation/suite/split/loop и базу сравнения. Связать чтение предшественника, сравнение и публикацию head существующей атомарной операцией/lock. Дорогая оценка остаётся вне транзакции.

**Различающие тесты и сохраняемое поведение.** Чужая evaluation или другой suite не promote. Старый score=2 не переписывает уже опубликованный score=3. Сравнение против нового predecessor выполняется явно. Две управляемые локальные попытки проверяют гонку; новый comparison profile требует собственного перехода.

**Не считать исправлением.** Не считать atomic rename атомарным compare. Право записи не выводится из факта хорошего score.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B116. Технический champion может получить оценку другого кандидата или несопоставимого испытания

**Основание и область:** generic `ChampionRegistry.consider_promotion`, `BenchmarkEvaluation`, вызов из `SearchLoopRunner._evaluate_candidate`; C01–C04. Особый `claim_adjudication` путь не исполнялся. [C10.R03, C10.R07, C10.R11]

**Проблема.** API отдельно получает candidate_ref и evaluation_ref. Загруженная оценка содержит собственные candidate_ref, loop_id, suite_id/version и runtime split, но перед созданием pointer они не сопоставляются с эффективным запросом. Проверяются guardrails, promotable, sample count и число метрики; этого недостаточно для установления предмета доказательства. Текущий champion хранит suite_version, однако совместимость старой и новой базы сравнения также не проверяется в этой функции.

**Локальное воспроизведение.** Полный registry на fixture-store с настоящими временными JSON-файлами записал candidate B с evaluation, описывающей A. Отдельно прошла оценка из другого loop и смена suite/version при лучшем числе. Контроль `promotable=False` правильно отказал: защита не отсутствует целиком, она не закрывает идентичность. В нормальном caller candidate передаётся evaluator, но результат затем сохраняется и рассматривается без обнаруженной проверки соответствия внутри прочитанного участка.

**Рекомендуемое решение.** До использования числа связать candidate, evaluation и активную политику; подтвердить применимую версию suite, split, методику метрики и data basis. Не сравнивать два числа только потому, что ключ метрики одинаков. Для новой suite — переоценить текущий champion на новой базе либо явно начать новое сравнение; не запрещать развитие benchmark вообще.

**Сохранить границы полномочий.** Это проверка технической привязки, не добавление нового институционального допуска. Не следует ослаблять специализированные guards, выдавать подпись за валидность оценки или считать этот опыт обходом всех tenant/authentication/CAS-проверок. Fixture-store здесь не воспроизводит их.

**Приёмка.** Перепутанная пара A/B, чужой loop, неверный split и несовместимая suite не меняют pointer; одинаковая подтверждённая база допускает честное улучшение; ошибка возвращает конкретную несовместимость, а не общий low score. Проверить cache-replay оценки и штатный evaluator-to-registry путь.

## B117. Атомарная запись champion-файла не делает атомарным сравнение с предшественником

**Основание и область:** `get → compare → _write_pointer` и `_write_json`; R01–R02. Полный registry, настоящий файловый ввод-вывод и управляемая конкурентная последовательность. [C10.R07, C10.E02]

**Проблема.** Указатель читается, улучшение вычисляется, затем файл атомарно заменяется. Между чтением и записью другой вызов может установить более сильный вариант. Второй писатель не проверяет, что сравнивавшийся предшественник всё ещё актуален. Atomic replace защищает целостность одного файла, не изоляцию всей операции read–compare–publish.

**Локальное воспроизведение.** Исходный score=1. Писатель B со score=2 прочитал его и остановлен непосредственно перед записью. Писатель C со score=3 прочитал тот же 1 и опубликовал 3. После освобождения B записал 2. Обе операции вернули promoted=True, окончательный pointer содержит 2. При последовательном контроле C→B значение осталось 3, а B отвергнут. Синхронизация событий обеспечивает порядок; случайная гонка не используется как доказательство.

**Рекомендуемое решение.** Сделать conditional publish относительно конкретной версии predecessor под существующим владельцем: транзакция/compare-and-swap или подходящий стабильный lock вокруг чтения, сравнения и фиксации. На конфликте заново сравнить с актуальным pointer, а не слепо повторять старую запись. Дорогой benchmark исполняется вне критической секции; под ней остаётся короткая проверка неизменяемых артефактов и перехода.

**Два обязательных уточнения.** In-process lock недостаточен для нескольких процессов, если такой режим разрешён. Для специализированного claim-пути pointer и promotion_basis должны оставаться согласованными; просто добавить блокировку одной записи недостаточно. История конфликтовавшего кандидата/оценки сохраняется независимо от того, стал ли он текущим.

**Приёмка и предел.** Управляемая последовательность B/C не ухудшает лучший актуальный результат по одной принятой политике; conflicting predicate возвращается явно. Авария на границе публикации даёт старое или новое согласованное состояние. На production workload конкурентное обращение к этому registry не измерялось; карточка применима при разрешении нескольких писателей. Новый распределённый реестр ради одного локального сценария не нужен.
