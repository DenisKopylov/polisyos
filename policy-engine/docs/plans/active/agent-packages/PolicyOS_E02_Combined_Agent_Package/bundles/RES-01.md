## Поручение и минимальная приёмка

Сохранять original workflow fingerprint отдельно от остатка. Проверять доступность нужных output/state, а не кардинальность cache refs. Восстанавливать индекс по уникальным успешно проверенным точным refs; checkpoint-tail применять только при доказанной границе истории.

**Различающие тесты и сохраняемое поведение.** A→B→C переживает две остановки: A/B не запускаются заново. Полный valid-state без ненужного cache seed продолжает C; две копии A не покрывают B. 100 повторных точных refs не дают 100 повторных чтений; failed load не помечается проверенным. Changed functional input остаётся несовместимым.

**Не считать исправлением.** Не отключать fingerprint/scope guards, не выдавать allow_replay за реально возвращённые в план узлы, не dedupe только по idempotency_key.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B63. Восстановление кэша многократно читает одинаковые записи и их результаты

**Происхождение:** C05-07. **Основание:** WorkflowExecutor.execute, seed_from_trace/seed_from_entry_refs/load_entry; W1–W3. **Охват:** S для устранения повторных точных ссылок; M для checkpoint-tail восстановления. **Приоритет:** экономия восстановления при длинной истории/медленном CAS. [C05.N03, C05.N04]

**Проблема.** При execute создаётся новый NodeResultCache, затем читается весь trace, затем refs checkpoint. Каждая найденная запись вызывает load_entry: читается cache-entry, далее bytes его outcome, даже если та же точная запись уже была загружена. Общей дедупликации успешных проверок между двумя источниками нет. При первом настоящем get outcome снова читается. Поэтому «тёплое» возобновление само способно выполнить существенный объём повторного I/O и разбора данных прежде, чем дать полезный результат.

**Воспроизведение.** Счётная модель с 100 появлениями entry-A и одним entry-B выполнила 202 чтения «entry+outcome». Контроль, отмечающий только уже успешно проверенные точные refs, выполнил четыре и восстановил тот же индекс. Для ста действительно разных refs оба пути сделали 200 чтений: эффект не приписан всем workload. W3 проверяет, что временно нечитабельную запись нельзя отметить проверенной и затем навсегда пропускать. В опыте не запускался настоящий store и не отменялись его epoch/custody проверки.

**Рекомендуемое решение.** Первое дешёвое изменение — в рамках одной операции восстановления объединить точные refs trace/checkpoint и повторно использовать успешную проверку одной неизменяемой записи. Дедуплицировать не только по idempotency_key: две записи одного ключа могут иметь разное содержимое и требовать диагностики противоречия. Контекст доверия, доступ и область run остаются частью допустимости.

Следующий шаг — использовать проверенный checkpoint как границу и читать после него только нужный хвост журнала, а не пересобирать весь run каждый раз. Смещение/последовательность должны быть связаны с подлинной историей и актуальной попыткой; простое числовое offset без этой связи небезопасно. Ленивое чтение payload допустимо лишь там, где неизменяемый манифест уже однозначно определяет схему и все обязательные проверки всё равно выполняются до использования. Сегодня усиленная проверка output-aware результата действительно существует — её пропуск не является оптимизацией.

**Приёмка и границы.** Cold и restored-index дают одинаковое множество допустимых записей; точные дубли не вызывают повторного большого чтения; конфликтующий outcome, повреждённая эпоха и неверный run не становятся hits. Считать байты, число обращений и время до первого полезного шага, а не только hit-rate. Частота дубликатов, размер trace и реальная доля этого I/O в задержке PolicyOS здесь не измерены. Это адресная оптимизация существующего механизма, не новый сервис кэширования.

## B70. Первое восстановление меняет отпечаток workflow и может запретить второе

**Происхождение:** C06-01. **Основание:** `resume_from_checkpoint`, `_build_resume_workflow_spec`, `compute_workflow_fingerprint`, LocalWorkflowRunner, AsyncWorkflowExecutor и CASCheckpointHook; R70-1–R70-4. **Приоритет:** высокий для повторного восстановления; S–M. [C06.R01–R04]

**Проблема.** При resume исходный workflow сверяется с отпечатком контрольной точки, затем из него удаляются завершённые узлы и зависимости на них. Сокращённый workflow передаётся runner. AsyncWorkflowExecutor заново вычисляет fingerprint именно переданного остатка и передаёт его hook; hook сохраняет это значение в новой контрольной точке, одновременно объединяя список ранее завершённых узлов с новым прогрессом. Связь с исходным графом в этой передаче не сохраняется отдельным полем.

Для исходного A→B→C первая остановка после A оставляет B→C. Если после восстановления B выполнен и создана новая точка, её fingerprint относится к B→C, а completed_nodes уже содержит A и B. Следующий resume с исходным A→B→C попадает в WorkflowMismatchError. Передать вместо исходного только B→C тоже недостаточно: A теперь отсутствует в этом графе и отвергается проверкой completed_nodes. Это не смена научной задачи — изменение создаёт сама процедура продолжения.

**Проверка.** Исполнены извлечённые функции сокращения графа и построения fingerprint на Pydantic-оболочках. Канонический сериализатор проекта заменён явно указанной стабильной JSON-сериализацией; это не проверка всех правил PolicyOS canon. Различие содержательных payload и две ветви отказа воспроизведены. Контроли сохраняют одинаковый fingerprint при изменении только retry/timeout и различие при изменении функционального параметра. Полный двойной resume ещё должен быть выполнен в проектной среде.

**Рекомендуемое решение.** Сохранить неизменяемую идентичность исходного принятого workflow и отдельно представлять план оставшейся работы. Hook должен записывать исходный функциональный fingerprint вместе с доказуемой связью текущего плана исполнения с ним. Проверять завершённые появления узлов относительно исходного графа, а остаток выводить из него и подтверждённого прогресса. Можно передавать исходный граф с явным набором уже зафиксированных узлов либо оставить сокращённый граф и добавить origin-binding — выбирается вариант, лучше согласующийся с действующими владельцами.

**Чего не делать.** Не отключать сравнение fingerprint и не менять его задним числом на произвольный «ожидаемый». Настоящее изменение параметров, зависимостей, популяции или метода требует отдельной версии исследования и инвалидации затронутой работы; технический resume не должен легализовать такую смену.

**Приёмка.** A выполняется; первый сбой; resume выполняет B; второй сбой; второй resume выполняет C. A и B не вызываются снова, история связна. Изменённый настоящий запрос по-прежнему не принимается по старой точке. Дополнительно проверить повторное открытие уже полностью завершённого run. Имеющиеся тесты однократного resume и tenant/cell-защиты сохраняются, а не заменяются. [C06.R05]

## B71. Cache-seed остаётся обязательным даже для уже удалённых из плана узлов

**Происхождение:** C06-02. **Основание:** последовательность `resume_from_checkpoint`; R71-1–R71-4. **Приоритет:** высокий при полном восстановленном состоянии; S–M. [C06.R01, C06.R02]

**Проблема.** После materialize_checkpoint_state завершённые узлы удаляются из графа. Тем не менее стратегия `require_cache_seed` отвергает resume, если число cache_entry_refs меньше числа завершённых cacheable-узлов. В этом маршруте ссылки требуются как обязательное условие для операций, которые уже не будут исполняться. При полном допустимом снимке и доступных входах остатка отсутствие оптимизационной записи может стать искусственным препятствием.

Проверка к тому же кардинальная: два повторения ссылки на A проходят численный порог двух завершённых узлов, не доказывая покрытия B или читаемости результатов. Это не доказательство принятия испорченного полного checkpoint: его целостность проверяется отдельно. Это показывает, что число cache refs — неподходящий заменитель требуемого свойства.

**Связанный смысловой разрыв.** `allow_replay` ослабляет эту проверку и пишет предупреждение о возможном повторном запуске завершённых узлов, но `_build_resume_workflow_spec` в обоих режимах удаляет их одинаково. В рассматриваемой процедуре само название стратегии не возвращает эти узлы в план. Нельзя рекомендовать allow_replay как универсальный способ восстановить отсутствующее вычисление.

**Рекомендуемое решение.** Отдельно доказать достаточность и актуальность восстановленного состояния и всех артефактов, необходимых незавершённой части. Когда это доказано, cache-entry является ускорителем, а не новым обязательным свидетельством той же уже зафиксированной работы. Если конкретный результат действительно требуется восстановить через кэш или повтор, проверять связанный план восстановления по появлению узла, входам, версиям и результату; число ссылок не заменяет такую проверку.

При неполном состоянии и недоступном обязательном результате следует адресно восстановить данные или остановить зависимый шаг. Нельзя просто удалить guard, принять любые ссылки или считать полный JSON доказательством наличия всех внешних blobs. Scope, целостность, ограничения использования и исходная идентичность сохраняются.

**Приёмка.** Полный проверенный снимок с доступными входами C и без ненужных cache refs продолжает C; недостающий обязательный вход вызывает настоящий repair/отказ; дубликаты не засчитываются как независимое покрытие. Обе стратегии имеют точное документированное поведение. Локальные проверки воспроизводят предикат и проекцию графа, не весь protected-resume.
