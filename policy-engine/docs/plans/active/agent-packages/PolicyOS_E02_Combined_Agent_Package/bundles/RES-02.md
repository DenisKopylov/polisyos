## Поручение и минимальная приёмка

Уравнять смысл skip/ok в одиночном и параллельном пути. Определить commit/rollback действующего tier; сохранять state и complete-set одного рубежа вместе. Для нынешнего атомарного merge предпочтительна одна согласованная точка уровня, не N одинаковых snapshots с разным списком completed.

**Различающие тесты и сохраняемое поведение.** Независимый сосед не меняет skip в completed. A/B increment: остановка после первой публикации не применяет B дважды. A=ok/B=fail при fail_fast и continue даёт согласованные returned state, durable head и компенсацию. CAS-результат завершённого вычисления не уничтожается из-за rollback state.

**Не считать исправлением.** Не чинить только append-порядок; не смешивать наличие артефакта и принятую state-write; не объявлять skip успешным producer.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B72. Одиночный skip считается завершением, а параллельный — нет

**Происхождение:** C06-03. **Основание:** `_run_single_node` и `_execute_tiers` в AsyncWorkflowExecutor; R72-1–R72-4. **Приоритет:** высокий; S. [C06.R03]

**Проблема.** `_run_single_node` возвращает `node_failed = outcome.status == 'fail'`. Внешняя одиночная ветвь добавляет alias в completed_nodes всякий раз, когда node_failed ложен. Значит, `skip` попадает в успешно завершённые. Параллельная ветвь добавляет туда лишь записи `status == 'ok'`. Наличие другого независимого runnable-узла меняет смысл одного и того же skip.

Сам пропущенный узел checkpoint не создаёт. Но следующий успешный узел может сохранить уже загрязнённый completed_nodes. В дальнейшем пропущенная работа будет удалена из плана resume либо включена в знаменатель B71, хотя cache-entry для её успешного результата не производился. Это отдельная проблема от проекции stop→abstain из B29.

**Рекомендуемое решение.** В одиночном и параллельном маршрутах одинаково учитывать явно успешную фиксацию результата. Различать «попытка терминальна», «работа осмысленно не требуется по условию» и «заявленные выходы действительно произведены». Использовать существующие статусы и skip-blocker; не вводить новый vocabulary только ради исправления одного условия. Для зависимого шага проверять наличие именно нужных выходов, а не полагаться на отрицание fail.

Это не означает, что любой условный skip нужно автоматически повторять. Решение о повторе зависит от неизменности условия и состояния задачи. Но skip не должен молча превращаться в свидетельство выполненного вычисления.

**Приёмка.** Метаморфный тест: добавить независимый соседний узел, не меняя входов исследуемого узла. Его skip и дальнейший resume сохраняют один смысл в обеих ширинах. Ok добавляется в завершённые в обеих ветках; fail не добавляется. Тест выполняется на нативных статусах, а не с локальной заменой skip на ok.

**Граница.** Локально исполнено точное логическое условие обеих ветвей; частота таких одиночных skip в реальном workflow не измерена. Реальная достижимость полного отказа через checkpoint требует интеграционного контроля B70–B73.

## B73. Снимок параллельного уровня не совпадает с его отметками завершения и отката

**Происхождение:** C06-04. **Основание:** `_run_parallel_tier`, `_execute_tiers`, `_handle_checkpoint`, CASCheckpointHook; R73-1–R73-4. **Приоритет:** высокий до надёжного resume; M. [C06.R01, C06.R03]

**Первый механизм.** Все успешные результаты уровня сначала сливаются в state. Затем checkpoint создаётся последовательно для каждого успешного alias, а список checkpoint_completed растёт по одному элементу. Уже первая точка содержит эффекты всех успешных соседей, но отмечает завершённым только первого. Сбой между двумя записями оставляет несогласованный рубеж: данные B включены, а B по metadata ещё предстоит выполнить.

В модели A и B работают от одной базы; B увеличивает n с 0 до 1. Первая точка содержит n=1 и completed=[A]. Resume снова исполняет B и получает n=2. Внешний кэш не обязан предотвратить повтор: если B читает n, его ключ на восстановленном n=1 уже отличается от исходного ключа на n=0.

**Второй механизм.** Если один сосед успешен, а другой вернул fail, `_run_parallel_tier` может сохранить успешный state до возврата. Затем внешняя fail_fast-ветвь возвращает state к tier_savepoint, но опубликованная контрольная точка этим кодом обратно не согласуется. Текущий итог и durable head способны указывать на разные решения о фиксации. В той же последовательности `completed_before_tier` для compensation формируется после добавления успешных aliases; это также следует согласовать с реальным рубежом.

**Рекомендуемое решение.** Сначала определить принятое правило commit/rollback для уровня, затем фиксировать согласованный state вместе с полным набором действительно зафиксированных появлений узлов и их результатами. Для текущей схемы естественный экономный вариант — одна контрольная точка на атомарно сливаемый уровень, а отдельные node-events и результаты сохранить независимо. Для поузловой фиксации требуется состояние именно соответствующего префикса, а не уже общий финальный state.

При fail_fast, означающем откат всего уровня, новая успешная head не публикуется до решения об откате. При явно принятой политике частичной фиксации она должна одинаково отражаться в возвращаемом state, metadata и последующем resume. Ни одна политика не должна стирать уже сохранённый артефакт успешного вычисления: наличие артефакта и его включение в текущий рабочий state — разные факты.

**Дополнительная экономия.** Один checkpoint согласованного уровня вместо N одинаковых общих снимков уменьшает повторную сериализацию и обновление head. Это предполагаемая экономия числа операций; производительность настоящего CAS здесь не измерена.

**Приёмка.** Остановить процесс после первой возможной публикации уровня A/B: восстановленный state и complete-set совпадают по смыслу; инкремент B не применяется второй раз. Отдельно A=ok/B=fail при fail_fast и continue. Проверить compensation, output cache и seed refs; просто переставить один append недостаточно. Локальные R73 — модель порядка, не запуск полного executor.
