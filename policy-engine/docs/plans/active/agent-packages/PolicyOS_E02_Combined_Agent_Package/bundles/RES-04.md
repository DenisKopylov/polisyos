## Поручение и минимальная приёмка

Связать checkpoint с effective plan/inputs/params/seed и occurrence-prefix. Сохранить настоящие per-node results с исходной reproducibility. Публиковать JSON и sidecars как новое immutable поколение, используя однозначное кодирование путей.

**Различающие тесты и сохраняемое поведение.** Цепочка multiply/add: changed factor/input не принимает прежний результат 7 вместо холодный результат 10/9. Выходы 6/7 после resume остаются 6/7, исходный seed сохраняется. a_b и a→b сохраняют разные массивы; ошибка нового save после sidecar не портит старый snapshot. Tiny NumPy-файлы, без больших массивов.

**Не считать исправлением.** Не подставлять final_state в каждый исторический MethodResult, не переписывать старые массивы до публикации нового манифеста и не вводить второй канонизатор.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B74. Foundry checkpoint идентифицирует список методов, но не эффективное вычисление

**Происхождение:** C06-05. **Основание:** `_compute_chain_digest`, `CheckpointingChainExecutor.execute`, `ChainCheckpoint`; R74-1–R74-4. **Приоритет:** высокий при использовании этого resume-пути; M. [C06.R06]

**Проблема.** Digest строится только из упорядоченного списка FQN. Параметры узлов, params_per_node, seed, исходное состояние, slot bindings и эффективные зависимости в него не входят. При совпавшем digest исполнитель заменяет initial_state сохранённым intermediate_state и пропускает первые n_completed узлов. Соответствие completed_node_ids текущему префиксу отдельно не проверяется в этой ветви.

**Воспроизведение.** Исполнено извлечённое тело execute с простыми тестовыми MethodResult/registry/dispatcher. Цепочка «умножить на 2, прибавить 1» на x=3 имеет промежуточный результат 6. При изменении множителя на 3 холодный расчёт даёт 10, а resume по старой точке — 7. При изменении initial x на 4 холодный результат 9, resume — 7. Новый граф с теми же FQN и другими UUID принимает старые ID завершённого префикса. Смена порядка FQN корректно отвергается — существующий digest не бесполезен, но его область слишком узка для полного обещания совместимости.

**Рекомендуемое решение.** Использовать существующую функциональную идентичность скомпилированного плана и эффективных входов: параметры после разрешения defaults/overrides, slot bindings, зависимости, версии методов и модельного контекста, исходные артефакты, смысл случайного seed/повторения. Не выдумывать второй несовместимый канонизатор, а согласовать checkpoint с действующими контрактами composer/dispatcher. Идентичность появления узла и его место в сохранённом рубеже должны быть проверяемы.

Изменение только расписания или допустимого operational-timeout не обязано уничтожать численный reuse; изменение научного параметра обязано инвалидировать зависимую работу. В сложном случае следует повторно использовать незатронутые предки по графу зависимостей, а не отвергать весь корпус и не принимать весь прежний результат. Полный хэш огромного input не нужно вычислять заново, если есть настоящая связанная immutable artifact identity.

**Приёмка.** Тёплый и холодный результат совпадают для одного эффективного запроса. Смена параметра, seed, входного снимка, порядка/семантики binding либо версии метода либо отвергает старую точку, либо даёт явный план частичного пересчёта. Неверный completed-prefix не принимается. Это тест данного Foundry executor, не утверждение о неправильности всех кэшей и всех других checkpoint-контуров.

## B75. При восстановлении итоговый state выдаётся за результат каждого прежнего узла

**Происхождение:** C06-06. **Основание:** восстановление stub_result и последующая сборка ChainExecutionResult; R75-1–R75-3. **Приоритет:** высокий перед использованием per-node history; M. [C06.R06, C06.R10]

**Проблема.** Checkpoint хранит общий intermediate_state, список методов/UUID и timing. На resume для каждого прежнего узла создаётся MethodResult с `output=dict(state)`, где state — один и тот же итог всего сохранённого префикса. Исходные результаты отдельных методов не восстанавливаются. ReproducibilityInfo также создаётся заново по нынешнему runtime и переданному сейчас seed, а не по сохранённым условиям той попытки.

В тестовой цепочке настоящие выходы двух узлов равны 6 и 7; восстановленные MethodResult содержат 7 и 7. Настоящих новых dispatch-вызовов не было. Сохранённый расчёт выполнялся с seed=7, а при resume с seed=99 восстановленные metadata записали 99 и fingerprint тестового текущего окружения. Итоговый state при неизменном запросе при этом остаётся верным — проблема относится к потере и последующему восстановлению истории.

**Важный существующий сигнал.** Код добавляет warning и note `restored_from_checkpoint`. Поэтому не утверждается, что восстановление вообще скрыто. Но предупреждение не возвращает отсутствующий исходный output и не делает нынешний fingerprint историческим. А построитель общего reproducibility_contract читает данные из этих MethodResult; конкретный последующий authority-потребитель и ложная публикация не воспроизведены.

**Рекомендуемое решение.** Сохранять ссылки на настоящие per-node MethodResult, их исходные inputs, outputs и reproducibility metadata. Общий resume-state хранить отдельно. Если старый формат не содержит node-output, возвращать явную неполноту истории, не подставляя финальное состояние как произведённое каждым методом. Данные нового сеанса чтения — отдельная запись replay, не переписывание оригинального исполнения. Ранее полученные warnings, ошибки, артефакты и ограничения не должны исчезать.

**Почему это связано с производительностью.** Имея точные выходы и зависимости, можно повторно использовать отдельный дорогой шаг и пересчитать только следующий. Общий state без верной истории провоцирует либо небезопасный reuse, либо дорогое повторение всего префикса. Нативные immutable refs предпочтительнее многократной сериализации одинакового полного state.

**Приёмка.** После resume выход A остаётся 6, B — 7; исходные seed/runtime/версия сохраняются; новый replay не записывается как новое независимое вычисление. Для legacy-точки без этих данных отсутствующее явно отсутствует. Доступ к final_state остаётся возможным в его подтверждённой области.

## B76. Идентичность sidecar-файлов не обеспечивает целостность всего checkpoint

**Происхождение:** C06-07. **Основание:** `_serialise_state`, save/load, атомарные файловые helpers; R76-1–R76-4. **Приоритет:** высокий для численных checkpoint; S–M. [C06.R06, C06.E01]

**Коллизия внутри одного снимка.** Имя массива строится конкатенацией stem и имён ключей через `_`. Пути `['a_b']` и `['a','b']` получают одинаковое имя `stem_a_b.npy`. При объединении sidecars последняя запись заменяет первую, а обе ссылки указывают на один файл. В настоящем локальном save/load двух массивов [1] и [2] прочитаны [2] и [2]. Это не коллизия SHA-256 и не теоретически редкое событие: это неоднозначное кодирование пути.

**Смешение поколений при сбое.** Save атомарно заменяет каждый sidecar по отдельности, затем сериализует и публикует JSON. Если запись идёт по тому же checkpoint path, старые sidecars могут быть заменены до успешной публикации нового JSON. В тесте новая запись массива [2] состоялась, а JSON-сериализация другого значения в списке завершилась ошибкой. Старый JSON остался побайтово прежним, но при чтении прежнего checkpoint вернулся новый массив [2] вместо [1]. Сценарий использует намеренно неподдерживаемое новое значение для проверки отказоустойчивости; ошибка нового save не должна портить ранее валидный снимок.

Внешний `_save_checkpoint` использует секунды времени, сокращённый digest и индекс узла для имени. Поэтому повторная запись того же шага в тот же каталог не имеет универсальной гарантии уникального поколения. При разных путях снимков отрицательный контроль сохранил старый массив. Произошедшая production-порча не заявляется.

**Рекомендуемое решение.** Адресовать массивы по однозначному структурному пути плюс поколению или по настоящему content-addressed ref. Опубликовать сначала весь новый неизменяемый набор данных, проверить его, затем атомарно переключить единственный manifest/head. Не перезаписывать файлы, на которые ещё ссылается предыдущий manifest. Использовать существующий CAS, когда этот путь допустим, либо отдельный generation-directory; валидировать также shape/dtype/content и безопасный путь разрешения sidecar.

Атомарная замена отдельного файла не является транзакцией над JSON и всеми массивами. fsync и rename уже используются — их не надо изобретать заново; нужно правильно определить объект публикации. Garbage collection удаляет только действительно недостижимые поколения после фиксации, а не при неудачной попытке сохранения.

**Приёмка.** Плоский ключ с подчёркиванием и вложенный путь сохраняют разные массивы; перестановка ключей не меняет данные. Сбой после записи любого sidecar оставляет доступным полный старый либо полный новый снимок, не смесь. Контроль включает одновременные писатели, повтор того же шага, отсутствие и повреждение файла. Тесты C06 исполнили извлечённые методы save/load с реальными JSON/NumPy/filesystem, но не весь проектный ArtifactStore.
