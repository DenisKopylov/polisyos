## Поручение и минимальная приёмка

Один раз разрешать эффективный deadline и передавать остаток вниз. Сохранить contextvars при разрешённом thread fallback. Убрать циклическое ожидание вложенной работы в том же исчерпанном pool через существующие async-входы. Различить отмену ожидания, завершение и право поздней записи. LA-057 — двухэлементная типовая очистка до behavioral patch, без изменения type parameters и без общего TypeVar-codemod.

**Различающие тесты и сохраняемое поведение.** Одинаковые direct/async/thread входы имеют согласованный timeout/context; A затем B не протекают через worker. Малый saturated pool с управляемыми событиями не блокирует собственную inner task. Noncooperative timeout явно оставляет диагностируемую незавершённость, не разрешает поздний актуальный commit. Проверить get_type_hints с корректными namespaces, четыре function-local T, ContextVar, cancellation/finally, direct/star/reflection imports; отдельный малый процесс до/внутри loop.

**Не считать исправлением.** Не повышать max_workers/timeout как ремонт, не убирать timeout, не подставлять actor/tenant из слов агента. Native macOS процессные варианты — RUN-02, не считать Linux fork проверенным на Mac.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B14. Таймаут ожидания не равен остановке вычислителя

*Источник карточки: A:B14. Унаследовано из прочитанной сводки A; не новый интеграционный прогон.*

**Происхождение и подтверждение:** P1; точная копия проектного async_tools.py из предыдущего пакета и два коротких искусственных опыта. Кооперативная coroutine прервалась около 10,5 мс при лимите 10 мс; синхронная блокировка внутри coroutine вернула результат около 80,4 мс. Это не замер времени PolicyOS. Отмена Future также не прекращает уже исполняющийся поток. [A.R10; A.H1; A.E02]

**Экономное расширение:** выделить тяжёлые некооперативные вызовы в подходящую имеющуюся границу исполнителя; различать дедлайн задачи, ожидание результата, отмену и фактическое завершение. Переиспользовать retry/timeout-инфраструктуру Scientist только после проверки её транспортной и процессной семантики — см. B24.

**Критерий:** превышенный лимит не оставляет скрытую работу, которая меняет состояние после отказа. Успевший вычислитель не убивается только из-за неправильного ожидания передачи результата. Сохранение и очистка проверяются отдельно.

**Ограничение и приоритет:** наличие небезопасного поведения в любом production-окружении не утверждается. Существенная поправка P3: существующий process wrapper не является автоматически готовым безопасным решением. Средняя сложность; актуально и для одного локального прогона.

## B40. Незаданный timeout наверху превращается в скрытый предел внизу

*Источник карточки: C02-07. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q09/C.Q10. **Свидетельство:** переход по исходникам; полный проверенный async_tools; T1/T2. **Достижимость:** синхронный узел исполняется через execute_with_retry_async без timeout_s.

Для синхронного узла ветка `_invoke()` при timeout_s=None вызывает `run_blocking_async(node.execute, ctx, state)`. У helper None означает `_DEFAULT_TIMEOUT_SECONDS`; без переменной окружения это 30 секунд. Для настоящего execute_async используется иной путь, а sync-wrapper без timeout вызывает execute непосредственно. Поэтому одинаково незаданный верхний параметр не означает одинаковый эффективный предел.

В опыте использован полный проектный async_tools_source.py с Git blob SHA-1 `01981db2ccbbb39ab54d2afa6ef3dafafcb0e3c0`. При разрешённой тестовой настройке helper default=0.1 секунды функция длительностью 0.25 секунды получила TimeoutError при async-делегировании; прямой вызов завершился. Сам блокирующий код закончил работу позже таймаута. Полный retry-wrapper в опыт не импортировался; его делегирование установлено чтением. Исходный default=30 подтверждён кодом, но 30-секундный опыт не проводился.

**Разумное расширение.** На уровне владельца запуска один раз разрешать эффективный deadline из политики, бюджета и явного запроса, затем передавать оставшееся время вниз. Различать «не указано, применить default» и другие разрешённые режимы. Делать эффективный предел видимым в trace. Не отменять ограничения и не повышать глобально 30 до огромного числа.

Остановка ожидания не гарантирует остановку синхронной работы в потоке. Принудительное прерывание требует подходящего исполнителя и отмены последующих записей. Это связано с прежними B14/B24, но новая находка — именно появление неявного deadline при смене формы вызова. [C.E04]

**Взаимодействие с B39.** Helper выдаёт обычный TimeoutError, который относится к OSError и попадает в широкую exception-ветку retry. Если блокирующая работа ещё не остановилась, повтор способен запустить вторую копию. В локальном T3 полный проверенный helper соединён с моделью retry-loop: первая функция намеренно ожидала начала второй; после таймаута и backoff=0.1 секунды одновременно работали две попытки. Обе завершились после снятия барьера. Это реальный локальный опыт с потоками, но не запуск проектной retry-обёртки и не измерение частоты такого наложения в приложении. Перед новым запуском нужна согласованная семантика отмены/завершения старого и допустимости повтора, а не одно только увеличение лимита.

**Проверка:** объявленный достаточный бюджет не обрезается неучтённым helper-default; короткий лимит действительно соблюдается по согласованной семантике; время очереди/инициализации учитывается явно; после объявленной отмены нет недопустимой актуальной записи позднего результата. Для CPU-методов безопасность process-boundary проверяется отдельно.

## B69. Вложенные sync/async-мосты могут исчерпать собственный общий пул

*Восстановленный источник: Library-S02/U47. Уровень подтверждения не повышен.*

**Происхождение:** C03-06. Исторический C03 альтернативной Library-ветки; не новый C05.

**Приоритет:** Высокий при подтверждённой вложенности на выбранном пути. **Охват:** S–M.

**Наблюдение.** При вызове run_coro_sync из работающего event loop новый loop выполняется в общем ThreadPoolExecutor, а вызывающий поток ждёт Future.result. run_blocking_async посылает внутреннюю синхронную работу в тот же пул. Если все его потоки уже заняты внешними мостами, внутренние работы не могут начаться: поток нужен именно тому, чего ждут занятые потоки.

**Новый опыт.** Выполнен полный проектный async_tools.py, сверенный по Git blob SHA-1. В тестовой конфигурации с четырьмя потоками четыре внешних вызова достигли внутренней точки, но число начатых элементарных вычислений оставалось нулём. Все четыре закончились TimeoutError. Прямой асинхронный контроль без вложенного блокирующего моста на том же пуле вернул четыре результата 42. Пул 4 — явно выбранный тест, совпадающий с допустимым минимумом формулы проекта; текущая ёмкость реального развёртывания не установлена.

**Минимальное расширение.** На внутренних путях сохранять async-вызов до асинхронного владельца, не проходя обратно через блокирующую sync-обёртку. Если синхронная граница действительно необходима, её ожидание не должно занимать единственный пул, необходимый вложенной работе. Использовать существующие async-точки входа; раздельные исполнительные ресурсы допустимы лишь после проверки их владения и завершения. Повышение max_workers не устраняет класс цикла ожидания.

**Приёмочная проверка.** При ограниченной ёмкости вложенная разрешённая операция доходит до вычисления либо явно отвергает неподдержанную re-entrancy до занятия всех ресурсов. Отмена освобождает ожидания, не повреждает артефакты, новые задачи не остаются навсегда в очереди. Контроль проверяет доступную ёмкость, а не высокую общую производительность.

**Граница.** Точный helper исполнен, но достижимость именно такого вложенного насыщения из главного N6 не установлена. В соседних модулях импорты обоих мостов и async/sync обёртки присутствуют; одного импорта недостаточно для утверждения об обязательном тупике. Это подтверждённый механизм при описанной композиции, а не диагноз всех запусков PolicyOS.

## B95. Включение thread-timeout теряет текущий контекст исполнения

**Происхождение:** C08-07. **Основание:** `_execute_with_timeout_sync` и путь без fork; X1–X3. **Приоритет:** высокий при использовании этого fallback; охват локальный. [C08.R07, C08.R08]

**Проблема.** В non-fork ветви `get_shared_executor().submit(node.execute, ctx, state)` передаёт явные аргументы, но не текущий contextvars.Context. Без timeout прямой вызов его видит. `run_blocking_async` и running-loop путь `run_coro_sync`, напротив, уже используют `copy_context().run`. Следовательно, правильный общий шаблон в проекте имеется, но обходится внутри вложенной timeout-обёртки.

**Проверки.** X1: прямой узел читает ContextVar=`request-A`; выбранное thread-fallback тело на том же запросе читает None. X2/X3: явный copy_context переносит A и затем B, не оставляя значение в исходном контексте потока после завершения. Это реальный ThreadPoolExecutor/contextvars с тестовым маркером, не опыт с настоящими пользовательскими полномочиями. Утрата маркера не объявлена доказанным обходом security: защищённый потребитель может корректно отказать.

**Рекомендуемое исправление.** На границе отправки в поток захватить фактический текущий контекст и выполнить узел в нём либо использовать уже согласованный helper без повторной вложенности. Копия context дешёвая, но она не даёт новых прав и не продлевает истёкший lease. Длительная операция продолжает применять необходимые актуальные проверки полномочий у владельца. Межпроцессная граница требует собственного явного trusted-context envelope, а не автоматической передачи всего процесса.

Не убирать timeout, чтобы восстановить контекст. Не подставлять tenant/actor по запросу агента и не брать «последний» контекст из глобальной переменной. Сохранить ранее найденные ограничения отмены и собственного общего пула B14/B69: исправление контекста не делает зависший поток прерываемым.

**Приёмка.** Direct/thread/fork и async-пути сравниваются на заявленных свойствах контекста; повторная работа другого запроса не получает старые значения. Проба принудительно выбирала thread-ветвь, потому что текущий Linux допускает fork; не утверждается, что эта ветвь является стандартной на каждом развёртывании.

## LA-057. Common async bridge: прежний модульный TypeVar больше не участвует в четырёх generic-функциях

**D — прямая очистка одного остаточного объявления и ставшего ненужным import-name**

**Точная область:** `src/polisyos/common/async_tools.py`:

```python
from typing import TYPE_CHECKING, TypeVar  # убрать только TypeVar
T = TypeVar("T")                           # убрать это объявление
```

`TYPE_CHECKING` и import Awaitable/Callable под ним остаются. `TypeVar` в других модулях не входит в scope.

**Что установлено.** Полный файл использует `[T]` непосредственно в четырёх generic declarations: `_await_awaitable`, `_run_coro_in_fresh_loop`, `run_coro_sync`, `run_blocking_async`. Их собственные type parameters не являются прежним модульным `T`. Scope-aware проверка полного AST этого файла не нашла unshadowed Name-load модульного `T` за пределами функций с локальным параметром. Это конечный **one-module census**, не нулевой внешний граф импортов. [E229; r09-P23]

В локальном исполнении Python 3.13.5 у каждой из четырёх функций `__type_params__[0]` отличен от старого `module.T`. `typing.get_type_hints` с явными annotation namespaces возвращает собственный параметр функции и до, и после удаления. После очистки нет module attributes `T`/`TypeVar`; формы resolved annotations совпали. Здесь проверялась не строка `T` в исходнике, а действительное разрешение параметра типа. [r09-P24]

**Почему это legacy.** Новая форма объявления generic уже введена в рабочие функции, а прежнее модульное объявление TypeVar осталось рядом. Никакая coroutine/executor-обязанность за ним в проверенном файле не закреплена. Требуется удалить остаток прошлого способа типизации, не создавать shared types module для одного ненужного имени.

**Что сохранить.** Все functions/class-free execution bodies, `get_shared_executor`, ранние env defaults, context propagation, atexit shutdown, cooperative timeout, cancellation и очистку pending tasks. Файл — работающий sync/async bridge, не placeholder. Даже его возвращаемые ошибки и поведение уже запущенного event loop сохраняются.

**Фактическое удаление ограничено in-memory AST.** Удалены ровно assignment на строке 17 и `TypeVar` из typing import. Полные AST всех функций вместе с атрибутами строк остались неизменными; изменённый модуль компилируется. Настоящие sync вызовы, sync-over-running-loop, blocking executor и ContextVar дали одинаковые значения. Cooperative timeout вызвал одинаковую ошибку и `finally`; оставленная дочерняя task была отменена и очищена; ValueError и zero-timeout rejection сохранились. Executor instances завершены в конце диагностики. Репозиторий не редактировался. [r09-P23–P28]

**Что ещё блокирует безусловное удаление.** В самом `async_tools.py` нет restrictive `__all__`; external `from ... import T`, star import или reflection могут видеть incidental names. Root Common экспортирует модуль `async_tools`, но не отдельное `T`. Адресный GitHub поиск `async_tools.T` не нашёл совпадений, однако он не проверяет все прямые импорты, aliases или динамические обращения. Нужен конечный scan именно этих consumers и typing/tooling конфигураций, не всего научного pipeline. [E230–E231; r09-P29]

**Куда перенести.** Никуда: при отсутствии поддержанного внешнего договора удалить два остатка. При найденном явном consumer сначала выяснить, действительно ли он использует это generic identity, и мигрировать его отдельно; не превращать служебное имя в новый глобальный публичный тип ради сохранения файла.

**Приёмка в проекте.** Exact imports/aliases/star consumers, full module TypeVar scope, supported Python typecheck, существующие async_tools tests, запуск до/внутри event loop, context and cancellation, packaging. Ненулевой внешний потребитель переводит соответствующий объект из direct cleanup в compatibility-задачу; локальные пробы не отменяют этот критерий.

**Приоритет:** дешёвая небольшая очистка, без обещаний ускорения и без зависимости от DDM-миграции. **Основания:** E229–E231; r09-P23–P29.

## K36. Async bridge работает; маленькая типовая очистка не отменяет его исполнительный контракт

Нативные coroutine, executor и ContextVar проверки дали совпадающие результаты до/после in-memory cleanup. Это защищает ограниченную LA-057, но не аттестует все комбинации event-loop affinity, fork, nested executor saturation или подавления cancellation. Cooperative cancellation не превращается в доказанный hard real-time deadline. Удаляется только ненужный типовой residue; остальные функции не названы legacy из-за сложности или размера. [E229–E230; r09-P23–P29]
