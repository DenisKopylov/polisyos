## Поручение и минимальная приёмка

Нормализовать возвращённые и поднятые ошибки до retry-решения. Каждую разрешённую попытку начинать с новой изолированной ветви одного логического baseline; continuation по checkpoint считать отдельным договором.

**Различающие тесты и сохраняемое поведение.** Постоянный дефект return/raise имеет одинаковое число попыток; временная ошибка допускает ограниченный retry. x+=1→ошибка→успех даёт x=1, не 2. Старые расходы и история сохраняются; чистый producing-copy узел работает как раньше.

**Не считать исправлением.** Не запрещать ошибки только по имени класса, не обнулять стоимость failed-attempt и не считать rollback памяти отменой внешнего эффекта.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B39. Retry-политика зависит от формы ошибки, а не от её содержания

*Источник карточки: C02-06. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q09. **Свидетельство:** обе обёртки sync/async; локальная модель R1–R4. **Достижимость:** настроено max_retries>0.

Когда узел возвращает NodeOutcome со status=fail, обе обёртки вызывают `_should_retry(error, policy)`, который проверяет retry_on. Когда узел выбрасывает исключение из `_RETRY_RUNTIME_ERRORS`, наличие оставшихся попыток достаточно для повтора, независимо от retry_on. Среди этих исключений есть ValueError, TypeError и ValidationError.

В локальной модели при max_retries=2, retry_on=[]: возвращённый отказ остановился после одного вызова, поднятый ValueError дал три вызова. Это не проверка полного retry-wrapper: паузы, журнал и настоящие NodeOutcome не создавались. Контроль max_retries=0 сохранил одну попытку; контроль разрешённой временной ошибки завершился на второй.

**Почему это мешает полезному циклу.** Неизменный вход с детерминированно неверной схемой не становится корректнее от повторного запуска. Он расходует лимит, задерживает другие кандидаты и прячет правильное следующее действие — исправление входа, выбор другого метода либо условный результат с пробелом.

**Разумное расширение.** Нормализовать исключения и возвращаемые ошибки в одну классификацию до решения о retry. Различать временный транспортный сбой, непригодный вход/контракт, недостаток основания, недоступный метод и неопределённое состояние внешнего действия. Повтор первых допускается по политике; постоянный дефект маршрутизируется в ремонт/перепланирование. Не запрещать все ValueError по имени: классификация должна учитывать действительного владельца и причину.

**Проверка:** одинаковый тип постоянного дефекта имеет одинаковое число попыток независимо от return/raise. Разрешённый временный сбой допускает ограниченный повтор. Внешнее действие после неопределённого ответа не выполняется повторно без гарантии его допустимости. Значение max_retries=0 по умолчанию уже ограничивает данный риск; это не объявляется дефектом всех запусков.

## B96. Retry повторяет узел на состоянии, уже изменённом неудавшейся попыткой

**Происхождение:** C08-08. **Основание:** повторные вызовы в sync/async retry используют тот же state; I1–I4. **Приоритет:** для узлов, допускающих мутацию полученной ветви до ошибки. [C08.R07, C08.R06]

**Проблема.** Executor может изолировать узел от общего ExperimentState один раз. Но retry-loop затем повторно передаёт эту же ветвь каждому вызову. Если узел корректно пишет в объявленную область и после частичной записи получает временную ошибку, следующая попытка начинает не с первоначального входа, а с изменённого. Это отдельный уровень изоляции от B59: даже глубокая копия перед всей серией retries не решит отсутствие новой ветви между её попытками.

**Проверки.** I1: извлечённая sync retry-функция с отключённой задержкой и fixture-node делает x+=1, первая попытка падает, вторая успешна. Итог x=2 вместо эффекта одного успешного исполнения x=1. I4 повторяет механизм на уменьшенной модели genuine execute_async. I2 — свежая ветвь одного baseline на каждую попытку — даёт 1. I3 — узел, самостоятельно всегда создающий новый результат из неизменяемого входа, — уже даёт 1 на текущей обёртке. Поэтому неверно считать все методы повреждаемыми.

**Рекомендуемое исправление.** У повторов одной вычислительной попытки должен быть неизменный логический вход. Перед каждым разрешённым повтором создавать новую ветвь от него по действительным write-paths и публиковать только принятый результат. Использовать существующее bounded branching после исправления B59 либо неизменяемое представление входа; не копировать без необходимости весь мировой корпус. Работа, которая намеренно продолжает частичный алгоритм, должна иметь отдельный continuation-contract и проверенный checkpoint, а не маскироваться под retry.

Изоляция памяти не откатывает сеть, платежи, внешние записи или файл: для них сохраняются идемпотентность, сведения о фактически выполненном действии и запрет слепого повтора при неизвестном исходе. Цена первой неудачной попытки тоже не обнуляется откатом состояния. Новый UUID/seed сам по себе не делает повтор отдельным допустимым научным экспериментом.

**Приёмка.** Мутация→ошибка→повтор; возвращённый fail и исключение; чистый производящий копию узел; отмена; разрешённое продолжение с checkpoint. Итог одного успешного расчёта совпадает с cold-контролем, история неудачных попыток и реальные расходы сохраняются. Полный workflow и внешние побочные эффекты не испытывались.
