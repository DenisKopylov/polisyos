## Поручение и минимальная приёмка

Проверять происхождение реально обнаруженного набора, а не запрещать cardinality=1. Применять обязательные свойства до top-k. Сохранять requested modalities даже при отсутствии поддерживающего метода.

**Различающие тесты и сохраняемое поведение.** Genuine singleton выбирается, фиктивный вне каталога — нет. Добавление non-value методов не прячет value-метод. Panel-запрос не становится пустым требованием при tabular-only каталоге; разрешённый adapter имеет реальный producer.

**Не считать исправлением.** Не добавлять фиктивный второй метод, не повышать top-k вместо ремонта порядка, не смягчать обязательные требования пересечением с каталогом.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B34. Единственный корректно обнаруженный метод принимается за hardcode

*Источник карточки: C02-01. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q01, C.Q02. **Свидетельство:** код; локальные контроли S1-1–S1-3. **Достижимость:** автоматический выбор при полном value-denominator из одного элемента.

В `MethodSelectionReceipt._verify_selection_trace()` стоит проверка:

```python
if self.selection_authority == "foundry_registry_advisor" and len(self.denominator) <= 1:
    raise ValueError("value_method_selection_fixed_default")
```

Для явно запрошенного метода используется иной источник выбора — `requested_registry_method`, — на который это условие не распространяется. Поэтому одинаковый одиночный элемент может быть допустим для явного запроса, но недопустим для автоматического выбора. В локальном опыте эти две ветки расходятся именно по этому условию. Остальные предикаты receipt в опыте не выполнялись.

**Важное уточнение:** здесь denominator — весь обнаруженный набор методов с подтверждённым владельцем value-проекции, а не число подходящих вариантов после всех фильтров. Один подходящий метод среди большого denominator не обязательно вызывает этот отказ. Нынешняя численность полного value-набора в данном проходе не измерялась.

**Почему ограничение избыточно.** Кардинальность не устанавливает происхождение выбора. Честно обнаруженный singleton не становится hardcode; два фиктивно добавленных метода не доказывают честность процедуры. Так проверка заменяет нужное свойство косвенным признаком.

**Разумное расширение.** Разрешить singleton при доказанной связи с действительным каталогом, корректной применимости и честном полном составе рассмотренного набора. Сохранить обязательность source/contract/context bindings и запрет подменять полный denominator удобным подмножеством. Итог формулируется «единственный доступный в этой области», а не «лучший среди всех возможных методов».

**Проверка:** один реально зарегистрированный допустимый метод выбирается; тот же метод вне объявленного набора отвергается; скрытие других обязательных членов набора по-прежнему выявляется. Добавление фиктивного второго элемента не служит обходом проверки.

**Стоимость и граница:** очень небольшое условие, но смысл анти-hardcode проверки нужно заменить доказательством происхождения. Не повод ограничивать большую систему одним методом.

## B35. Top-k применяется раньше фильтра по обязательному типу результата

*Источник карточки: C02-02. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q01–C.Q03. **Свидетельство:** межфункциональное чтение; искусственный упорядоченный набор S2-1/S2-2. **Достижимость:** `route_constraint=None` и методы других типов попадают в верх списка.

`_value_method_advisor_query` устанавливает `limit=max(1,min(8,len(value_entries)))`. В `advise_methods` ранжируется каталог, затем берётся верхняя часть `scored_entries[:limit]`. Уже после этого `select_value_method_for_problem` оставляет из рекомендаций только элементы value-denominator. Без route_constraint исключение всех non-value методов заранее не задано.

В контрольном наборе `[diagnostic.a, diagnostic.b, value.m1, value.m2]` при limit=2 текущий порядок даёт пустой список. Отбор value-методов до ограничения оставляет оба. Это не реальное ранжирование Foundry: порядок является заданным искусственным входом, демонстрирующим следствие композиции.

**Особенно существенное следствие:** расширение общего каталога может ухудшить доступ к существующим нужным методам. Новые методы других типов занимают короткий рекомендательный список; система сообщает отсутствие подходящего результата, хотя методы ниже доступны.

**Разумное расширение.** Обязательные свойства результата и применимость должны ограничивать множество до top-k. Альтернатива — ленивое продолжение чтения ранжированного списка до исчерпания допустимого бюджета, с явной неполнотой. Не решать это увеличением 8 до большого числа: дефект порядка останется.

**Имеющийся правильный шаблон:** `select_method_for_input_contract` получает eligible-множество, ранжирует только его с `limit=None`, затем выбирает. У ветки с route_constraint есть собственное предварительное исключение несовместимых методов; это важный контроль, а не повод считать все маршруты сломанными. [C.Q02]

**Проверка:** добавление новых non-value методов не скрывает подходящие value-методы; отсутствие всех подходящих методов остаётся настоящим отказом; журнал сохраняет причины исключений и область поиска. Ранговое предпочтение не создаёт доказательной силы.

## B36. Обязательное требование исчезает, если каталог не умеет его удовлетворить

*Источник карточки: C02-03. Унаследовано из полного C02/r01; 25 исторических локальных записей.*

**Источник:** C.Q03/C.Q04. **Свидетельство:** код; S3-1/S3-2. **Достижимость:** явно заданная `value_required_data_modalities` содержит модальность, которой нет среди value_entries.

В `_value_selection_criteria` выполняется пересечение requested modalities с объединением модальностей доступных методов. Потом `_rank_entries_with_scores` проверяет лишь это сокращённое множество.

Пример: требуется panel, каталог содержит только tabular. После пересечения обязательное множество пусто; проверка модальности не исключает tabular-метод. При добавлении любого panel-метода требование внезапно возвращается. Таким образом, одно и то же входное требование меняет силу от состава каталога.

**Это не доказательство уже опубликованного неверного причинного результата.** Рассмотрен этап выбора; downstream может остановиться, в частности нынешний N8 имеет собственный недостроенный положительный путь. Но отсроченный отказ хуже для диагностики: настоящая причина уже потеряна.

**Разумное расширение.** Сохранять обязательный запрос неизменным. Если его нельзя выполнить, возвращать точный пробел: нет подходящего метода, нет разрешённого преобразования или нужно уточнить само требование. Предпочтения можно смягчать; жёсткие требования нельзя молча переименовывать в предпочтения. Поддерживаемые aliases/совместимость следует разрешать явным типизированным преобразованием, не простым пересечением строк.

**Почему это расширяет цикл, хотя добавляет точность отказа.** Контроллер получает адресное действие для ремонта или перехода к допустимой альтернативе вместо более позднего непонятного падения. Обычный scalar/табличный результат не выдается за выполненную panel-задачу.

**Проверка:** запрос panel не превращается в пустой; подходящий метод проходит; несовместимый — нет; разрешённое преобразование имеет настоящего производителя, входы и проверяемый выход. Изменение каталога не переписывает исходный запрос.
