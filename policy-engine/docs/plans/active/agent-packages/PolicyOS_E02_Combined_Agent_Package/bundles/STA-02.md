## Поручение и минимальная приёмка

Разрешать effective-input и immutable source snapshot до внешнего reuse; привязать настоящий read к тому же снимку. Внутреннее exists→ok заменить проверкой доступности/пригодности bundle. Сохранить presence/null по действительному контракту и version ключа.

**Различающие тесты и сохраняемое поведение.** Старый bundle на новом target_context/required_parameters не даёт пустой ok. Смена bytes по тому же SKG path меняет actual snapshot/key, замороженный снимок остаётся reusable. Missing threshold, null, zero, false и empty-list различаются там, где это различает метод.

**Не считать исправлением.** Не читать version отдельно от живых данных без связи; не хэшировать всю базу на каждом запросе при готовом owner-ref; не включать весь state в key.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B60. Наличие старой ссылки на параметры прекращает проверку нового запроса

**Происхождение:** C05-04. **Основание:** ResolveParametersNode.execute и его state_reads; E1–E4. **Охват:** S–M. **Приоритет:** высокий при повторном исследовании с изменившимся контекстом. [C05.N05, C05.N03]

**Проблема.** Первое условие execute: если ARTIFACT_CONTEXT_ADAPTIVE_PARAMETER_BUNDLE_REF уже есть в artifacts_index, сразу вернуть `NodeOutcome(status='ok', state=state)`. До чтения реального bundle, сопоставления target_context, required_parameters, графа и версии источника дело не доходит. Наличие имени артефакта подменяет его пригодность для конкретного следующего запроса.

**Почему внешнего кэша недостаточно.** В state_reads перечислены target_context, required_parameters и граф. Поэтому их изменение может правильно дать cache-miss. Но затем исполнившийся узел сам возвращает прежний state по проверке наличия ссылки. При последующем сохранении успешного outcome старое состояние может закрепиться уже под новым ключом. Этот составной риск следует из двух прочитанных участков; полное такое выполнение через DTO и CAS не запускалось.

**Локальное свидетельство.** Перенесённое начальное условие возвратило ok и выполнило ноль загрузок при новом контексте, расширенном наборе требуемых параметров и ссылке, для которой фикстура не предоставляла никаких bytes. Это не тест валидности вымышленных ArtifactRef: строковые метки в опыте обозначают расположение ссылки; проверено именно отсутствие её чтения в данном предикате. Контроль без ссылки достиг точки необходимости реального разрешения.

**Рекомендуемое решение.** Использовать существующий bundle как кандидат на reuse: загрузить его через штатного владельца, проверить целостность и привязки к фактическому запросу, модели и снимку. Только после этого принять reuse. При частично покрытых required_parameters сохранить пригодные компоненты и доразрешить недостающие, если их контракты допускают композицию. При несовместимости построить новую версию; старую оставить исторической. Одна проверка полного набора bindings может обслуживать и внешний кэш, и внутренний быстрый путь — не нужны два независимых определения «актуальности».

**Приёмка.** Тот же связанный запрос переиспользуется без повторного дорогостоящего выбора; изменённый контекст/граф/список параметров вызывает ровно нужную работу; недоступная ссылка не даёт ok только своим присутствием. Перенесённый извне bundle принимается лишь при его действительных основаниях. Удалять все прежние артефакты на каждом шаге — не рекомендуемая стратегия.

## B61. Путь к изменяемой базе данных не идентифицирует её содержимое для кэша

**Происхождение:** C05-05. **Основание:** объявленные чтения ResolveParametersNode, общий idempotency payload, чтение версии SKG после разрешения; P1–P3. **Охват:** M. **Приоритет:** высокий только при разрешённом обновлении источника по прежнему адресу. [C05.N03, C05.N04, C05.N05, C05.E02]

**Проблема.** В ключ попадают значения `params.skg_db_path` и `params.skg_index_dir`, но не снимок базы, который будет фактически потреблён. Внутри execute узел открывает SKGQuery по пути, делает выбор, а latest_skg_version_id/skg_snapshot_ref узнаёт и сохраняет уже после него. Если база обновилась по тому же адресу внутри того же run и прочие state_reads не изменились, внешний ключ не замечает новых bytes и может вернуть старый результат до входа в узел.

**Воспроизведение.** Временный файл переписан с «version-one» на «version-two» по тому же пути: хэш содержимого различается, модель ключа по объявленным state-полям — нет. Добавленный явно связанный snapshot_ref различает версии. Контроль одного и того же замороженного снимка сохраняет reuse. Это файловый контрпример и примитивная модель ключа, не запись в настоящую SKG и не измерение поведения её владельца версий.

**Рекомендуемое решение.** Перед решением о reuse разрешать существующую неизменяемую версию/снимок источника и связывать с ней как ключ, так и настоящее чтение. Предпочтение — уже имеющиеся source-owner refs, а не повторный полный hash огромной базы на каждом обращении. Для файла без версионирующего владельца сначала нужен действительно стабильный снимок либо контролируемый digest. Только mtime или строковое название версии недостаточны. Нельзя прочитать version_id, отпустить защиту, а потом читать другую живую версию по тому же пути: это оставляет гонку между проверкой и потреблением.

**Связь с B60.** Устранение одного слоя не закрывает другой: правильный внешний miss ещё может попасть в старый внутренний exists→ok, а проверка внутреннего bundle не вызывается при внешнем hit. Поэтому эта пара требует одного согласованного понятия фактических входных оснований.

**Приёмка и границы.** Изменённая фактически используемая версия меняет ключ и результат; новая непотребляемая база не инвалидирует всё исследование; сохранённый снимок остаётся воспроизводимым. Если действующий режим уже гарантирует неизменность всей базы на протяжении run и перевыпускает run при обновлении, этот конкретный риск не реализуется. Такой режим следует подтвердить, а не объявлять все нынешние hits неверными. Не предлагается снимать существующую run-scope границу ради межпользовательского reuse.

## B62. Ключ объединяет отсутствие поля и явно переданный null

**Происхождение:** C05-06. **Основание:** _resolve_path/extract_state_slice; M1–M3. **Охват:** S–M из-за версии контракта ключа. **Приоритет:** условный, где метод различает эти входы. [C05.N03, C05.N07]

**Проблема.** `_resolve_path` возвращает None и для отсутствующего атрибута/ключа, и для явно записанного None. В state_reads_snapshot оба случая становятся одинаковым null. Однако в Python `params.get('threshold', 5)` даёт 5 при отсутствии и None при явном значении. Для метода, различающего значение по умолчанию и явно отключённое/неизвестное значение, это разные запросы.

**Воспроизведение.** Два разрешённых Pydantic-словаря, пустой и `{threshold:None}`, получают одинаковую модель payload по объявленному чтению, хотя холодная тестовая функция возвращает соответственно 5 и None. Явный ноль уже различается текущей процедурой — это положительный контроль, а не заявление, что все falsy-значения слиты.

**Рекомендуемое решение.** Либо до хэширования нормализовать входы по настоящему контракту метода в полный эффективный запрос, если отсутствие и null действительно эквивалентны, либо сохранить присутствие явно: например, представление пути с признаками present/value. Не применять одну глобальную трактовку null ко всем методам. Изменить версию idempotency-контракта и обеспечить безопасное чтение старых записей; не переприсваивать старым bytes новый смысл.

**Приёмка.** Если семантика различается, отсутствующий ключ и null не дают общий hit; если она объявленно совпадает, нормализованные эффективные входы переиспользуются. Ложное, ноль, пустой список, отсутствие промежуточного контейнера и null на листе проверяются отдельно. Это не повод включать в ключ весь state: достаточно точного представления действительно читаемой области.

**Граница.** Конкретный production-узел, уже выдавший неправильный результат из-за такого совпадения, не установлен. Это прямое свойство ключа и контрпример к его универсальности; на методах, намеренно считающих missing и None одинаковыми, проблема не проявляется. В пробах не импортировался проектный canonical serializer: он не может восстановить уже утраченное различие при одинаковом payload.
