## Поручение и минимальная приёмка

Один direction/severity используется поиском, worst-case и отчётом. Attempted/valid/violating/missing считаются до presentation dedupe/top-k. Ограниченные примеры хранятся отдельно от полных счётчиков.

**Различающие тесты и сохраняемое поведение.** Для 10 нарушенных сценариев top_k1/10 не меняет score. Десять проявлений одной проблемы не становятся одним нарушением. Lower-tail значения 10/−5 при пороге 0 выбирают−5; cost-профиль проверяет обратное направление. Empty не выглядит установленной устойчивостью.

**Не считать исправлением.** Не подменять долю обследованного множества генеральной вероятностью; не хранить все payload ради целочисленного счётчика.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B106. Ограничение списка замечаний меняет численную оценку устойчивости

**Основание и область:** окончание `run_stress_test`, после dedupe и `collect_top_k`; S/M. [C09.R07]

**Проблема.** Список уязвимостей сначала дедуплицируется и обрезается, затем `robustness_score` вычисляется как `1 - len(vulnerabilities) / total_evaluated`. Ограничение представления таким образом меняет количественный итог одного и того же испытания. Число уникальных описаний также смешивается с числом неудачных сценариев, хотя это разные единицы счёта.

**Локальный опыт R1–R3.** На десяти неудачных сценариях с разными замечаниями три исходных выражения дали score 0,9 при cap=1 и 0 при cap=10. В другом контроле десять проявлений одной проблемы после dedupe дают тот же эффект. Это модель точно прочитанного порядка выражений, не запуск полного stress-runner и не частота отказов продукта.

**Рекомендуемое решение.** До презентационного dedupe/cap фиксировать счётчики испытанных сценариев, наблюдавшихся нарушений, нечисленных/неполученных результатов и полноту проверки. Отдельно хранить уникальные issue-группы и отобранные примеры. Формулу и единицу `robustness_score` определить явно; исходные occurrence-count не выводить из короткого списка. Не хранить все большие сообщения ради счётчика: достаточно потоковой статистики и ссылок на ограниченные примеры.

**Приёмка.** Изменение `collect_top_k` не изменяет итог той же серии. Десять проявлений одной проблемы и одно проявление не смешиваются. При нулевом количестве оценённых сценариев или непроверенных условиях score не должен выглядеть установленной устойчивостью. При адаптивном/раннем прекращении доля в обследованном наборе не является автоматически вероятностью отказа во всём пространстве.

## B107. Стресс-поиск выбирает максимум показателя, чьи низкие значения признаны уязвимостью

**Основание и область:** `run_stress_test`, `_detect_objective_vulnerability` и negated search bookkeeping; высокий при lower-tail objective, M. [C09.R07]

**Проблема.** Уязвимость в рассмотренном детекторе устанавливается при `objective <= threshold`. Однако `worst_case_objective` начинается с минус бесконечности и обновляется по `objective > worst_case_objective`. Поисковая история дополнительно минимизирует `-objective`, то есть предпочитает большие исходные значения. Поэтому поле «худший случай» и направление поиска не согласованы с собственным тестом нарушения. Для других целевых смыслов направление должно разрешаться явно, а не универсально инвертироваться.

**Локальный опыт W1–W3.** При значениях 10 и −5 и нижнем пороге 0 детектор признаёт −5 уязвимостью, но предикат отчёта сохраняет «худший» 10. Минимизация отрицательного значения также выбирает 10. Контроль через одну явно заданную severity `max(0, threshold-value)` выбирает −5. Это исполнение прочитанных выражений на модельных данных, а не реальная оптимизация и не проверка всех CompositeObjective.

**Рекомендуемое решение.** Одна разрешённая семантика нарушения/нежелательности для направления поиска, остановки и полей отчёта. Для lower-tail utility это может быть минимизация utility либо максимизация величины нарушения; для затрат направление обратное. Повторно использовать существующий objective/direction-контракт, не добавлять конкурирующий optimizer. Сохранить исходное значение вместе с преобразованной поисковой оценкой.

**Приёмка.** Табличные контрпримеры для maximize-utility и minimize-cost, порога в обе стороны, отрицательных значений, отсутствующих/нечисленных результатов. Запись worst-case совпадает с определённым нарушением. Эта правка должна идти вместе с B106: правильный экстремум ещё не означает правильно посчитанную полноту/устойчивость.
