## Поручение и минимальная приёмка

Согласовать ObjectiveValue constructor, направление и отбор normalized scores. Перед численным reuse проверить space/bounds/split/units/origin; похожесть пригодна для идей, не заменяет binding. Обратный мост сохраняет реального кандидата, оценку и происхождение.

**Различающие тесты и сохраняемое поведение.** Найденные строки не исчезают из-за constructor mismatch. При minimize=1 отбирается раньше 9 по объявленной квоте. Несовместимая оценка остаётся proposal/ограничением, не GP training. Нет zero SHA, фиктивного holdout или params в metrics. Native DTO проверки обязательны.

**Не считать исправлением.** Не активировать B128 отдельно так, чтобы ожили неподтверждённые численные данные B131/B132. Не создавать evidence по одной текстовой похожести.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B128. При восстановлении найденных оценок несовместимый конструктор молча удаляет все строки

**Основание и область:** `TransferLearningManager.get_warm_start_evaluations` создаёт `ObjectiveValue(name="transferred", value=...)`, но настоящий тип требует `raw_value` и `direction`. Конструкция находится внутри `except Exception: continue`. `WarmStartBridge.load_warm_start` получает пустой список без различения пустой истории и ошибки адаптера. Применимо к данному transfer API после успешного чтения истории; это не утверждение об отсутствии всех warm-start-механизмов системы. [C12.R01, C12.R02, C12.R06]

**Локальный результат:** найден один подходящий запуск; его артефакт содержит две допустимые записи; обычная связка bridge → manager вернула ноль. Прямой вызов настоящей сигнатуры с `value` дал `TypeError`. Контрольный конструктор с `raw_value` и направлением смог создать объект. Последний контроль доказывает совместимость формы, а не содержательную допустимость переноса. P01–P03.

**Потеря:** накопленные и уже оплаченные наблюдения выглядят отсутствующими. Новый поиск может повторять начальные вычисления, хотя исходная история доступна. Замена исключения новым пустым статусом без исправления формы не расширит путь.

**Рекомендуемое решение:** использовать явный типизированный адаптер между сохранённой оценкой и текущим Evaluation. Сохранить исходные имена, направления, значения, идентичность эксперимента и допустимый статус; для исторического нормализованного scalar требуется однозначная конвенция, а не произвольное восстановление raw-метрики. Ошибку схемы возвращать адресно, с идентичностью записи и причиной. Совместимые записи могут продолжать путь, если это допускает политика частичного корпуса; исключённые не считать отсутствовавшими. Не строить новый transfer-engine.

**Приёмка:** реальный сохранённый Evaluation проходит существующий мост без ручного monkeypatch; несовместимая запись различается с действительно пустой историей; количество принятых, отклонённых и недоступных записей согласовано. Конструктор нельзя исправлять отдельно от B130–B132: сейчас эта ошибка маскирует последующие дефекты отбора и смысла.

**Приоритет и оговорка:** высокий для использующего этот API warm-start; размер связующей правки небольшой, но нельзя ограничиться переименованием аргумента и объявить весь перенос доказанным. Защищённые публикации не проверялись и из результата не выводятся.

## B130. Ограниченный перенос выбирает худшие нормализованные оценки вместо лучших

**Основание и область:** `get_warm_start_evaluations` сортирует `scalar_score` по убыванию и берёт начало списка. Стандартный search-путь нормализует score к минимизации; Bayesian-подготовка использует отрицательный score для максимизируемого GP-выхода. Следовательно, для такого допустимого корпуса порядок отбора обратен заявленному «best evaluations». [C12.R01, C12.R06, C12.R08]

**Локальный результат:** на оценках 1, 2, 9 при `max_evals=1` выбран score 9, а контроль по конвенции минимизации выбирает 1. Чтобы достигнуть этой ветви за B128, только несовместимый конструктор ObjectiveValue временно заменён интерфейсной прокладкой; остальной полный source не изменён. Это masked downstream finding, а не заявление, что текущая сломанная сборка уже выдаёт 9. P08–P09.

**Дополнительный расход возможностей:** floor-квота `max_evals // n_runs` не перераспределяется после короткой истории одного источника. На двух историях с общим числом допустимых записей 4 и лимитом 4 возвращены 3. Это вторичное наблюдение той же процедуры формирования ограниченного корпуса, не отдельная карточка. P10.

**Рекомендуемое решение:** отбирать по объявленной нормализации/направлению, не по универсальному `reverse=True`. При неустановленной сопоставимости разных запусков ранжировать внутри совместимых групп. Разнообразные и неудачные наблюдения могут быть полезны модели: явная политика корпуса должна отличать «best», diversity и learning examples. Не отбрасывать плохие результаты лишь ради красивой метрики. После покрытия источников доступную остаточную квоту перераспределять только по действительно допустимым данным.

**Приёмка:** минимум и максимум исходных целей после нормализации приводят к правильному порядку; полные равенства не создают ложных различий; ограничение объёма не превышается, а свободная квота заполняется согласно объявленной политике. Миграция старого корпуса должна установить значение scalar, не угадывать его по имени.

**Приоритет и оговорка:** локально дешёвая правка, но исполнять совместно с B128/B131. Ускорение GP или выигрыш решения не измерены.

## B131. Похожесть запуска подменяет достаточную привязку переносимой численной оценки

**Основание и область:** `RunFingerprint.space_hash` существует, но `find_similar_runs` проверяет только совпадение множеств имён целей. `get_warm_start_evaluations` уже не получает целевой fingerprint, чтобы сопоставить пространство. При регистрации проекция Evaluation сохраняет params, normalized coordinates, scalar и два статуса, но отбрасывает objectives, provenance_ref и metadata. Поэтому имеющиеся у входа сведения о split, единицах и происхождении не проходят этот контракт. [C12.R01, C12.R02, C12.R07]

**Локальный результат:** история `old-bounds` найдена для `new-bounds` при одинаковом имени score. У входного Evaluation заданы provenance и metadata раздела/единиц; их нет в сохранённой строке. Другие имена целей корректно отфильтрованы — механизм не лишён всех ограничений. P11–P13.

**Потеря:** смысл сохранённой координаты 0,5 зависит от исходного пространства. Имена целей сами по себе не устанавливают одинаковые единицы, direction, estimand, набор данных или разрешённый training split. После устранения B128 такая история способна перейти дальше как обычная успешная оценка. Фактическое загрязнение нативного GP/holdout не запускалось.

**Рекомендуемое решение:** развести discovery аналогий, предложение начальных кандидатов и перенос численных наблюдений в обучающий корпус. Первый может быть широким; второй допускает повторное оценивание на целевой задаче; третий требует сохранённых идентичностей и проверяемой совместимости или явного преобразования. Передать уже существующие версии пространства, источников, метрик и ссылки на оценки. Сходство не выдаёт права доступа и не делает hidden holdout обучающим материалом.

**Приёмка:** различающиеся пространства не считаются численно тождественными; разрешённый адаптер преобразует действительные параметры; несовместимая оценка остаётся доступной как идея с ограничением. Новая версия данных может требовать переоценки, но не полного запрета межзадачного обучения. Проверить tenant/split у действительного владельца, а не доверять тексту метаданных.

**Приоритет и оговорка:** существенная содержательная часть ремонта. Не требовать одинакового space_hash для любых аналогий — это неоправданно сузит потенциал. Для прямого повторного использования чисел либо установить строгую совместимость, либо оставить явную неизвестность.

## B132. Обратный warm-start-мост создаёт фиктивный benchmark вместо сохранения происхождения

**Основание и область:** `WarmStartBridge.evaluations_to_benchmarks` присваивает всем кандидатам `sha256:` из 64 нулей, копирует `ev.params` в metrics, записывает `scalar_score` под именем raw primary metric и помещает один набор значений одновременно в selection и holdout. Исходный candidate_id остаётся только в metadata. `promotable=False` и статус warm_start явно сохранены. [C12.R02]

**Локальный результат:** две разные оценки получили один нулевой ArtifactRef. Для параметра x=0,2 и минимизационного scalar=-0,9 обе группы метрик содержали `{x: 0.2, score: -0.9}`. Обе записи остались nonpromotable, а отдельные source_candidate_id в metadata сохранились. P14–P17.

**Потеря:** параметр не становится измеренной метрикой; минимизационный scalar не обязательно равен исходной метрике; одно измерение не становится двумя независимо выделенными разделами испытания. Нулевая ссылка не обеспечивает загрузку реального кандидата. Эти неоднозначности мешают последующему сопоставлению и безопасному переиспользованию даже без защищённой публикации.

**Рекомендуемое решение:** сохранять переносимые записи в их настоящем обучающем/историческом контракте. BenchmarkEvaluation создавать лишь при наличии действительного кандидата, версии испытания и измерений нужного split. Использовать подлинную ArtifactRef либо явно указать, что адресуемого артефакта нет; метаданные происхождения сохраняются отдельно. Разрешённая повторная оценка на целевой suite создаёт новые benchmark-результаты, а не переименовывает старый scalar.

**Приёмка:** разные кандидаты сохраняют разные настоящие ссылки; координаты не попадают в метрики; direction round-trip не меняет смысл; отсутствующий holdout остаётся отсутствующим; nonpromotable продолжает действовать. Прежние placeholder-записи не повышать автоматически при миграции.

**Приоритет и оговорка:** высокий для реально вызываемого обратного преобразования; его распространённость в production не установлена. Контроль подтверждает существующую защиту nonpromotable; обход полномочий не заявлен. Это другой переход, чем B113, где benchmark превращался в фиктивные координаты модели.
