## Поручение и минимальная приёмка

Различить explicit value и default при разрешении task_family/domain. Одинаковые фильтры действуют на local и transferred lessons до/после материализации. Last-access не обновляет время проверки evidence; учёт чтения ограничен.

**Различающие тесты и сохраняемое поведение.** Переданный typed context не заменяется policy/isolated defaults. Source_run/trust/threshold одинаковы в обеих ветвях. Два чтения старого урока не повышают confidence без новой проверки; настоящее подтверждение имеет свои ссылки/время.

**Не считать исправлением.** Не менять tenant/права через default override. Не переписывать весь CAS snapshot при каждом чтении и не стирать исторический след.

**Цикл работы:** зафиксировать actual scope и нужный characterization; оформить equivalent move и намеренный behavior fix раздельно; выполнить указанные малые tests через I1; независимый reviewer проверяет actual owner; передать commit, path map и остатки. CLI/test selectors разрешаются по настоящему checkout до запуска, не выдумываются из названия находки.

## B135. Переданный типизированный контекст теряет task_family и domain при разрешении значений

**Основание и область:** `resolve_transfer_context` успешно извлекает вложенный TransferContext, но для task_family до обращения к base уже ставит truthy fallback policy/discovery. Domain из base вообще не входит в выражение выбора; вместо него появляется isolated-домен. При этом run_id, tenant_hash и timestamp из base могут сохраняться. [C12.R04]

**Локальный результат:** вложенный `TransferContext(task_family='discovery', domain='education', run_id='r')` — и объект, и соответствующий словарь — разрешились как `policy / isolated::r / r`. Повторение task_family/domain отдельными явными аргументами восстанавливает правильный результат. P26–P28.

**Потеря:** вызывающий код уже передал нужную область, но поиск уроков и перенос могут попасть в другой namespace либо получить нулевую совместимость. Это не «не хватает контекста», а потеря существующего контекста на адаптере.

**Рекомендуемое решение:** установить явный приоритет источников, сохраняя значения base, когда не задано разрешённое переопределение. Подстановка defaults выполняется только после попытки взять все допустимые содержательные значения. Конфликт явного и вложенного контекста различается, а не маскируется. Для tenant/полномочий по-прежнему приоритет действительного execution-owner; агентный словарь не создаёт право доступа. Не объединять различные домены лишь ради успешного поиска.

**Приёмка:** вложенный объект, сериализованный объект и равнозначные явные поля ведут к одному эффективному предметному контексту; настоящее разрешённое override работает; невалидный base имеет адресный результат; isolated-fallback остаётся для действительно неизвестной области.

**Приоритет и оговорка:** дешёвый локальный ремонт существующего resolver. Security-импорт в опыте возвращал None; реальные tenant-разрешения не проверялись, и обход из этой ошибки не выводится.

## B136. Ограничения запроса к урокам действуют локально, но теряются на ветви переноса

**Основание и область:** `_query_local` проверяет trust_levels, min_confidence и source_run_id. `_entry_matches`/`_revalidate_transfer`, используемые find/materialize, не обеспечивают этих же проверок. `query_with_transfer` добавляет материализованные карточки без финальной проверки всей семантики LessonQuery. Перенос при этом может сам изменить trust_level. Legacy controller действительно вызывает query_with_transfer с min_confidence=0,5 при наличии lesson_registry; это связывает API с условным потребителем, но не доказывает полную проходимость GY. [C12.R05, C12.R09]

**Локальный результат:** запрос `min_confidence=0.8`, `trust_levels=[LOCAL]` вернул перенесённую карточку с confidence=0,2 и trust=TRANSFERRED. Тот же слабый пример в local-ветви отвергнут. Контроль с несовместимой stage тоже отвергнут; явно разрешающий слабые transferred-hints запрос получил допустимый результат. Исполнена цепочка выбранных тел query → find → materialize с фикстурами хранения, а не вся инфраструктура. P29–P32.

**Потеря:** расширение поиска на чужую историю незаметно смягчает фильтр пользователя. Система может расходовать следующие итерации на материал, который сама локальная ветвь считает неподходящим. Наличие карточки не означает её применение как полномочного доказательства — такое применение здесь не испытывалось.

**Рекомендуемое решение:** единый явный предикат выдачи для local и transferred, с отдельной проверкой до дорогой материализации и после преобразования значимых статусов. При необходимости ослабления фильтра вернуть отдельное предложение расширить поиск или отдельную не соответствующую запросу группу, а не включать её в подходящие результаты. Фильтры доступа/tenant проверяет владелец; совпадение labels этого не заменяет. Адресную применимость/разрешённый перенос сохранить.

**Приёмка:** переданный threshold и trust-filter соблюдаются независимо от маршрута; локальный промах не меняет требования; действительно допустимая transferred-карточка возвращается; несоответствующая не материализуется зря. Проверить source_run_id и политику частичного ответа, не только два численных примера.

**Приоритет и оговорка:** небольшая согласующая работа вокруг существующих predicates. Это не предложение запретить cross-domain transfer; контроль уже показывает полезный разрешённый вариант.

## B137. Обычное чтение старого урока восстанавливает уверенность без новой проверки

**Основание и область:** `_materialize_query_card` определяет возраст через `entry.last_accessed_at` или last_seen и при превышении TTL понижает confidence до 0,5 и trust до LOW_CONFIDENCE. `_query_local` после выдачи обновляет last_accessed_at и сохраняет индекс. Исходная карточка с прежними confidence/trust остаётся неизменной. При следующем чтении age мал, и прежние значения вновь возвращаются. [C12.R05]

**Локальный результат:** для карточки возрастом 100 дней при TTL=90 первый широкий запрос вернул `0.5 / low_confidence`; немедленный второй с `min_confidence=0.8, trust=LOCAL` вернул `0.9 / local`. Источник и его created_at не изменялись. Без предшествующего широкого чтения строгий запрос правильно отвергался. Контроль отдельного evidence-clock сохраняет понижение. P33–P35.

**Потеря:** популярность начинает действовать как подтверждение актуальности. Повторные чтения могут поддерживать старое основание без наблюдений или ревалидации. Кроме того, успешное чтение вызывает `_persist_index`: полный изменённый snapshot пишется в файл и CAS. Это установленный путь вызовов, не измеренная деградация скорости на большом реестре. [C12.R05]

**Рекомендуемое решение:** различить clock использования для retention/LRU и clock действительной проверки/версии доказательства. Чтение может продлить доступность кэша, но не уверенность и не срок эмпирической применимости. Использовать существующую запись проверки и происхождение; если требуется новая семантика last_verified, она должна быть явно определена, а не автоматически заполнена now. Счётчики доступа можно обновлять отдельно или пакетно, не публикуя новый полный доказательный snapshot при каждом чтении. Старые пригодные идеи сохранять с их ограниченным статусом, не удалять историю.

**Приёмка:** любое число обычных чтений не повышает доверие; настоящая разрешённая ревалидация создаёт новую версию с новыми основаниями; повторный холодный и тёплый запрос дают одинаковую содержательную степень актуальности. Retention может учитывать популярность, evidence sufficiency — нет. Проверить восстановление после restart и перенос, а не только пару запросов в одной памяти.

**Приоритет и оговорка:** высокий для использующего age-demotion реестра. Число 0,9 здесь внутренний confidence урока, не измеренная вероятность истинности. Нельзя объявлять весь урок ложным по календарному возрасту: политика доказательной актуальности зависит от природы его основания.
