# PolicyOS — исполнительская редакция аудита S02/r19-E01

**19 сентября 2026 года · 225 B-карточек → 84 рабочих пакета · 8 отдельных S-пакетов развития**

**Основной режим: Sol + 14 Luna = 9 исполнителей + 3 проверяющих + 2 интегратора.** Допустимый диапазон — 12–16 Luna. Локальные тестовые процессы ограничиваются независимо от числа агентов.

## 1. Что представляет собой эта редакция

Это готовое распределение работы по полному `PolicyOS_All_Findings_S02_r19(2).md`, а не новый аудит исходников. Диагнозы, предлагаемые исправления, контрпримеры, оговорки и источники всех B01–B225 сохранены дословно и перенесены под соответствующие пакеты. Восемь S-направлений вынесены отдельно: они не переименованы в баги. Исторический контекст, планы T1–T21, результаты прежних опытов и source ledger сохранены в заключительной части. Точный исходный файл включён в комплект отдельно; его SHA-256: `9c98584cbfa72996b058abf127f6c689f919a3421cdd563a82c84a7324ab39b5`.

База исходного аудита — `5fd3ebcc15637e98bbd4938de5d62ee5004504a8`. **В этой редакции актуальный HEAD репозитория не проверялся, PolicyOS не запускался, исправления не внедрялись.** Пути взяты из source ledger r19; это точные адреса рассмотренной версии, а не обещание неизменности будущего checkout. Распределение, зависимости и ресурсный режим ниже — новые инженерные решения по организации работы. Они не повышают доказанность исторических находок.

Названия Sol/Luna обозначают выбранные пользователем роли. План не устанавливает их фактические API-имена, сравнительное качество или поддерживаемые параметры Codex. Расчёт сделан для удалённого выполнения моделей через выбранный клиент; локальный inference больших моделей на Mac не включён.

**Состав доступного основания.** В E01 включён переданный Markdown r19. Прежние исследовательские ZIP, probes и полные Git blobs, на которые ссылается его историческая доставка, в этом поручении не предоставлялись и не включены как будто прочитанные/проверенные файлы. Их можно использовать только после фактического получения; для приёмки достаточно самостоятельно построить малый native test из точного counterexample карточки. Архивные команды и заявления о прежней доставке — история источника, не новое поручение исполнителю.

## 2. Команда и границы ролей

| Режим | Исполнители кода | Независимые проверяющие | Интеграторы | Всего Luna |
|---|---:|---:|---:|---:|
| Начальный / меньше готовых пакетов | 8 | 2 | 2 | 12 |
| **Основной** | **9** | **3** | **2** | **14** |
| Расширенный при свободной очереди | 10 | 4 | 2 | 16 |

**Sol** выбирает следующий готовый пакет, утверждает точную область записи, разрешает межконтрактные решения и принимает итог. Он ведёт один короткий ledger состояния и не делегирует каждому агенту повторный аудит всего репозитория. Главная цель — проверенный работающий путь и последовательное закрытие конкретных ограничений, не заполнение всех свободных slots.

**Исполнитель** получает один пакет, один branch/worktree и конкретный base SHA. Он проверяет актуальность карточек в своей области, пишет минимальное согласованное исправление и регрессии. Ему не нужно самостоятельно управлять всей тестовой машиной или ждать тяжёлого milestone, чтобы передать готовый patch. Следующий пакет получает новый агент либо новая короткая сессия с точным handoff; приоритет — сохранение воспроизводимого состояния, а не непрерывность одного огромного чата.

**Проверяющий** не является автором принимаемого patch. Он изучает исходный counterexample, diff и фактические результаты, добавляет различающий негатив/метаморфный тест, проверяет producer→carrier→consumer. Независимость здесь процедурная: другой агент и отдельное задание, не независимая модель ошибок или внешняя экспертиза. Проверяющий не делает параллельную альтернативную реализацию того же контракта без решения Sol.

**Интегратор I1 — ветка и очередь проверок.** Единственный владелец integration branch, merge queue, общей очереди локальных тестов, подготовки окружения и сводных milestone runs. Он сериализует публикацию, не обязательно всё написание кода. Его маленькие integration-fixes проходят review другим агентом.

**Интегратор I2 — межконтрактная согласованность.** Прослеживает соседние consumers, версии и activation prerequisites; готовит cross-boundary tests и независимый review изменений общих DTO. По умолчанию не конкурирует с implementer за production-файл. Ему можно поручить минимальный glue patch с отдельным явным write-set.

Третий/четвёртый reviewer при наличии slots распределяется по текущей потребности: lifecycle/storage, численная семантика, compatibility/causal boundaries. **Это роли потока, не 84 постоянных агента и не 84 одновременно открытых worktree.**

## 3. Режим MacBook Air M2 / 16 GB: простые правила вместо постоянного мониторинга

Параметры машины даны пользователем: MacBook Air M2 2022, 16 GB RAM, macOS Tahoe26.6.2. Следующие числа — **стартовая политика организации**, не измеренный оптимум и не гарантия конкретного RSS или скорости на этом Mac.

| Класс работы | Когда | Одновременный локальный допуск |
|---|---|---|
| **E — чтение/редактирование** | Постоянно | В пределах 8–10 implementers; локальные просмотры/поиск точечные |
| **L — лёгкая проверка** | На каждом пакете | **Не более двух тестовых заданий суммарно по всем worktree** |
| **N — небольшой native/numerical тест** | По необходимости конкретного пакета | **Один; на время его исполнения другие L/N не запускаются** |
| **C — укрупнённая приёмка milestone** | K1–K6, по одному окну на крупный результат | **Один последовательный набор; другие тестовые задания ждут, агенты продолжают читать/писать/review** |

L — отдельные выбранные тесты на маленьких DTO, словарях, локальных файлах, управляемых clocks/events; targeted lint/format. По умолчанию один последовательный pytest-процесс на задание. N — маленький настоящий NumPy/SciPy/JAX/GP/HNSW/процессный путь, тяжёлые импорты или сборка которого уже могут заметно занимать машину. **Маленький input не автоматически означает L:** объём импорта и setup тоже учитывается. В таблице пакета указан наиболее требовательный ожидаемый локальный класс, а не запрет писать дешёвые unit-тесты до него.

**Без церемоний.** I1 один раз подготавливает очередь и общий launcher. Проверенный класс задания повторно не обсуждается. Исполнитель передаёт точную команду, branch SHA и класс, после чего занимается следующим полезным шагом. Никто не запускает `top`, memory pressure или повторную проверку всего окружения перед каждой правкой. Отдельный мониторинг не является deliverable этого ремонта.

**Очередь глобальная, не по агентам.** Два L slots означают два задания на весь Mac, а не по два на каждого из 14 агентов. Не запускать скрытые background pytest, full-test watchers, несколько coverage suites, `-n auto`, многопроцессные benchmark grids или полные build/install параллельно с N/C. Независимые compile/typecheck сборки также занимают слот, если становятся заметной нагрузкой. Размер одного задания включает его дочерние процессы и native thread pools.

**Параллелизм внутри теста разрешён, когда это и есть предмет проверки.** Для гонки достаточно двух участников и управляемого barrier; для fail-fast — четырёх маленьких coroutines. Их нельзя отключить глобальным `workers=1`, иначе тест перестанет проверять исходную ошибку. Это один контролируемый тестовый job, а не дополнительный свободный пул.

**Native threads.** Для тестовых команд на OpenBLAS/OpenMP начать с `OPENBLAS_NUM_THREADS=1` и `OMP_NUM_THREADS=1` до импорта библиотек. OpenBLAS различает эти настройки по типу сборки [EXT-01]. Они не доказывают ограничение каждого Apple Accelerate/JAX/native runtime. Не добавлять наугад XLA-флаги. Для имеющего собственный cap estimator передавать его штатным API; один уровень вычислительной параллельности за раз. **Это тестовый launch profile, не изменение production defaults и не сокращение научных folds/replications.**

**Размеры стендов — ориентиры подготовки, не новые свойства продукта.** Обычно достаточно 2–5 узлов workflow/графа, нескольких десятков строк, двух источников, двух попыток, матриц 2×2/4×4. Для исходного механизма B24 сохраняется тест 1MiB; B211 —400 строк без гигантского N×N; B216 — полный конечный набор 2400 малых запросов. Монте-Карло на простых функциях — десятки/сотни draws; дорогое обучение целой модели не заменяет counterexample. Для statistical calibration малый стенд проверяет механизм, **не доказывает номинальное покрытие или качество inference в общем случае**.

**Без слепой экономии.** Если именно реальный JIT, native index, сериализация или concurrency необходимы для доказательства исправления, выполнить один маленький такой тест в N. Не заменять его фикстурой только ради зелёной отметки. Если зависимость не установлена, исполнитель сдаёт patch и точный deferred-native item; статус не повышается до полного принятия. I1 объединяет одинаковые setup/import потребности в очереди, а не заставляет каждого агента устанавливать окружение.

**Реакция только на симптом.** При OOM, зависшем принадлежащем тесту процессе, устойчивой потере отзывчивости или просьбе пользователя I1 прекращает новые тестовые запуски, завершает/останавливает только известное собственное задание и понижает допуск. Уже написанный код и остальные агенты не останавливаются. Один необычно тяжёлый тест переводится в N/C или делится без ослабления проверяемого свойства; его не повторяют циклически. Профиль 2×L /1×N не повышается автоматически до числа CPU-ядер.

## 4. Окружение и изоляция: сделать один раз

I1 выполняет короткий SETUP-01 перед первой выдачей: фиксирует checkout HEAD, читает действующие repository/AGENTS инструкции, проверяет project Python/lock/extras, выбирает native macOS arm64 окружение и сохраняет реальные команды выбранных проверок. Исторический Python3.13.5/Linux из probes не заменяет требуемый проектом runtime. Установка зависимостей — одна последовательная операция; не 16 одновременных `sync/install`.

Для независимых изменений использовать отдельные linked worktree/branches одного repository, а не 16 полных clones [EXT-02]. Не предполагается, что subagent автоматически получает отдельную файловую систему. Sol явно назначает каждому его working directory. После сохранённого commit и handoff освобождать ненужный worktree штатным способом; не удалять грязные пользовательские изменения и не применять общий `reset --hard`.

Зависимости можно разделять как неизменяемое окружение только при **правильной привязке импортов к тестируемому worktree**. Общая editable install, указывающая на другой checkout, недопустима. I1 фиксирует project-supported способ выбора source path; после создания/смены worktree и перед его первым native тестом подтверждает путь импортируемого изменённого модуля. Не делать это перед каждым тестом. Если проект требует отдельной install metadata, создать минимальное корректное окружение только там, где нужно, не менять глобальную editable install во время чужих тестов. Механика imports зависит от pytest/import mode [EXT-03].

У каждого test job свои temporary directory, выходы, локальный CAS/SQLite state и при необходимости порт. Нельзя использовать рабочий пользовательский CAS/DB как fault-injection стенд. Не запускать несколько локальных сервисных кластеров, Docker/Ray/Temporal ради unrelated unit checks. Непроверенные Linux-specific способы запуска фиксируются отдельно и не объявляются покрытыми macOS.

## 5. Как Sol выдаёт следующий пакет

**Первый набор из девяти исполнителей:** CYC-01, SEL-01, STA-01, ING-01, DOE-01, OPT-01, CAS-01, CAL-01, GRF-01. По статической карте r19 они не пересекаются production write-set и не имеют неисполненных bundle dependencies. Для начальных восьми оставить CAL-01 в ближайшей очереди; десятым можно выдать LLM-01, если review/test queue не перегружена. Это заранее подготовленный старт, а не требование заново декомпозировать 225 пунктов.

После первого набора **нет глобальных волн ожидания всех девяти**. Освободился слот → Sol выбирает следующий ready пакет по условиям:

1. Его необходимые входные контракты уже приняты на текущей integration branch; либо I2 подтвердил, что существующий контракт их уже обеспечивает.
2. Его фактический write-set не пересекает активные writers; значимая semantic boundary не находится в несовместимом изменении.
3. Есть точный base SHA, отдельный working directory и reviewer неавтор.
4. Пакет продвигает выбранный сквозной путь или даёт независимый локальный результат; наличие свободного slot не является достаточной причиной начинать большой refactor.

Приоритет при прочих равных: исправление, открывающее действительный positive route; затем сохранность/ложный численный успех; затем ускорение того же уже правильного расчёта. При занятом `generation_cycle.py` Sol выдаёт свободный CAS/DoE/graph/data пакет, не размножает writers центрального файла. Карта конфликтов и dependency graph поставлены в JSON; **related finding не является автоматически hard dependency**.

`depends_on` в пакете задаёт выбранную стартовую последовательность согласования контрактов. Это инженерный план E01, не доказанная зависимость файлов актуального HEAD. Он не требует бессмысленно чинить уже исправленную карточку: найденное подтверждённое существующее решение удовлетворяет соответствующую зависимость. I2 может сузить ненужное ребро после локального чтения и записать краткую причину; нельзя снимать ребро только ради занятых slots. Read-only подготовка и тестовый дизайн последующего пакета допустимы заранее, но production запись — после допуска.

**Умеренный WIP.** Ориентир — не более четырёх завершённых patches, ожидающих первого независимого review. При накоплении очереди свободные агенты становятся reviewers/готовят тесты и interface notes; Sol не создаёт ещё десяток writers ради активности. Не устанавливается численная квота закрытий или искусственный срок на пакет.

## 6. Три разные зависимости — не смешивать

**Implementation dependency:** следующий пакет потребляет изменённый carrier/API/семантику предыдущего. Его production patch основывается на принятой версии.

**Write conflict:** два пакета меняют один файл или один согласуемый контракт. Это причина выдать их последовательно, но не доказательство, что все результаты одного логически необходимы другому. Даже при отсутствии текстового конфликта I2 проверяет совместимость семантики. По умолчанию один active writer на production-файл; разрешить непересекающиеся функции можно только после явного разделения и проверки общей границы.

**Activation/acceptance prerequisite:** local patch можно написать и проверить раньше, но нельзя объявить новый пользовательский маршрут готовым до совместной проверки. Примеры из источника: подключение B04/B08 должно сохранять B18–B22; B79 активируется только с правильным B80; быстрый delta B189 не включается как готовый путь без корректного B190. Это не повод останавливать весь проект или объявлять все 225 обязательными до первого результата.

Особые общие границы: effective plan/occurrence; state writes и checkpoint cut; immutable artifact/profile; causal query и graph version; uncertainty carrier и independence. Изменение общего DTO или schema version согласует I2 до передачи downstream. Tests-only agent тоже не редактирует тот же файл одновременно с implementer: даёт отдельный test patch на зафиксированном commit или согласованный файл.

## 7. Жизненный цикл пакета и минимальная приёмка

**Короткий запуск, не повторный аудит.** Прочитать собственные B-карточки и перечисленные producer/carrier/consumer. На текущем base определить: механизм ещё есть, уже исправлен, условен или требуемая среда недоступна. Достаточно точного локального чтения и минимального native counterexample; не требуются production incident или полный UI запуск, чтобы исправить дефект поддержанного API. Если воспроизведение не получилось, объяснить конкретное отличие; не объявлять finding ложным только по отсутствию нужной зависимости.

Для актуального дефекта: регрессия на исходном поведении → минимальное согласованное исправление → та же регрессия и сохраняемые негативные контроли → независимый review → targeted consumer check на принимаемом commit. Содержательная проверка должна падать при устранении исправляемого свойства; достаточно адресного revert/mutation одного изменения в изолированной проверке, **не полного mutation-testing репозитория**. Не менять ожидаемый результат теста под удобный patch.

Если source допускает несколько решений, исполнитель выбирает простейшее совместимое с текущими owners и заданной областью. Реализованный честный capability-result может устранить ложное обещание, но не считается реализованным отсутствующим методом: например, отказ от притворной RBC не означает появление RBC. Отдельно фиксировать «корректность режима восстановлена» и «функция ещё не реализована».

**Состояния работы:** `planned → active → patch_ready → reviewed → merged_local → accepted_checkpoint`. `merged_local` допускает только названную integration branch, не production release. Альтернативные исходы: `already_resolved`, `not_reproduced`, `conditional_not_used`, `blocked_environment`, `decision_needed`, `deferred_native`, `resolved_by_explicit_limitation`. Любой из последних исходов имеет причину и не превращается в «225 bugs fixed». У каждой B-карточки может быть свой статус внутри одного пакета.

Приёмочный handoff содержит: bundle ID; B-ID и исход каждого; base/patch commit; точный список изменённых файлов; суть исправления и неизменные ограничения; команды/exit codes/лог; новые или изменённые tests; native vs fixture границы; deferred проверки с checkpoint/владельцем; исход независимого review; миграцию старых bytes/contracts, если нужна. Краткий структурированный результат важнее длинного самоотчёта. Полные логи сохраняются отдельно, не пересылаются всем агентам в контекст.

I1 переносит patch на текущую integration branch последовательно. Если изменились его write/read-contract dependencies, выполняется адресный повтор затронутых проверок. Не нужен автоматический полный CI после каждого rebase. Нельзя принимать чужой test log от старого SHA как проверку нового merge. Пока тест читает worktree, в нём не меняют checkout, зависимости или файлы.

## 8. Шесть укрупнённых проверок K1–K6

Это **шесть запланированных окон**, а не шесть обязательных полных CI. Внутри каждого последовательно выполняются маленькие реальные маршруты, выбранные consumer suites и только относящиеся performance checks. Упавший тест повторяется адресно после исправления; не весь window автоматически. Дешёвые seam tests на bundle boundary выполняются раньше, поэтому большой batch не маскирует недели непроверенной разработки.

| Окно | Результат | T-сценарии источника | Ограниченная нагрузка |
|---|---|---|---|
| **K1** | Настоящий условный N5→N8, читаемый результат, вторая итерация, малая композиция | T1, T2, T4; применимая часть T3 | Один выбранный метод,2–3 узла,2 кандидата; CAS readback, отрицательные controls |
| **K2** | Сохранность, два resume, ресурсы, ingestion и artifact transfer | T3, T5–T8, T13–T14 | Два worker/connector, маленькие files/arrays, одна контролируемая ошибка в каждой границе |
| **K3** | Поиск учится на правильной истории; funnel и backtest сохраняют запрос | T9–T12, T15–T16 | Малый DoE, tiny GP/index, короткая история,2 folds; никакого массового поиска |
| **K4** | Одна и та же калибровочная цель и закон uncertainty | T17–T19 | Один механизм,2 старта,2–4 параметра, короткий scan; небольшие Hessian/covariance и draws |
| **K5** | Граф, причинный запрос, оценка и inference не подменяются labels | T20–T21 | Малые panels/SCM;200 ADMG/2400 запросов; bounded statistical smoke отдельно от утверждения о покрытии |
| **K6** | Согласованная поставка на фиксированном integration SHA | Повтор краткого T1/T2/T3 и второго отличающегося случая; выбранные regressions K1–K5 | Один последовательный набор применимых suite; остальная platform validation явно перечислена |

Окна не задают обязательного порядка **написания** всех подсистем. Графовые пакеты могут идти одновременно с runtime, а K5 запускается по готовности своего блока. K6 выполняется последним. Нельзя ждать всего K2 ради маленького CAS readback, необходимого уже K1; такой readback — N-проверка своего пакета. Аналогично, общий DTO проверяется на native constructor при merge, а не только на последнем milestone.

**Performance:** одинаковые inputs, outputs, precision, seeds и intended work. В L обычно достаточно call counts, числа построенных rows/futures и удерживаемых bytes. В C — короткий controlled before/after на выбранном workload с сохранённым baseline. Не сравнивать рабочую новую версию с падающей старой как численный speedup. JAX cold compilation и warm execution раздельны; asynchronous completion надо дождаться и сравнивать одинаковые dtype [EXT-04]. Не включать coverage/профайлер на каждом patch и не увеличивать benchmark до предела 16 GB.

Если полноценная статистическая calibration или platform suite не помещается в разумный локальный стенд, сохранить точное непроверенное обязательство; не ослаблять критерий и не присваивать статистическую аттестацию. Доступный working route можно поставить с явно ограниченной областью, но не с выдуманной полнотой.

## 9. S-направления: не потерять улучшения и не расширить ремонт бесконтрольно

EVO-01–EVO-08 сохраняют S01–S08 как отдельную очередь. По умолчанию Sol сначала исполняет B-пакеты и bounded K-приёмку. S03/S07/S08 частично выражены уже в выборе условного результата, независимых полезных выходов и второго случая; это не автоматическое закрытие исходного архитектурного предложения. Новые функции S01/S02/S04/S05/S06 запускаются после явного выбора объёма пользователем/принятым project decision и могут быть дополнительно раздроблены. Их отсутствие не блокирует исправление локальных B-дефектов.

## 10. Что именно выдавать агенту

Исполнителю: `TEAM_RULES.md`, один `bundles/<ID>.md`, назначенные base SHA / branch / worktree. В его packet уже находятся исходные карточки, адреса owners, связанные B-ID и relevant source ledger. **Не требовать перечитать весь основной документ каждому из 84 исполнителей.**

Проверяющему: тот же packet, зафиксированный patch commit, logs и `REVIEWER_PROMPT.md`. I2 дополнительно получает `CROSS_BOUNDARY_MATRIX.md`. Sol — `SOL_ORCHESTRATOR.md`, `bundle_manifest.json`, `dependency_graph.json` и один короткий обновляемый ledger. Поставленный manifest — плановые данные, не конфигурация Codex и не автоматически созданные repository roles/gates.

Команды тестов до чтения actual checkout не выдумываются. В packet указан **предлагаемый новый** файл regression tests и исходные существующие tests, если они названы в r19. Исполнитель выбирает точный test node ID; pytest позволяет запускать отдельные nodes [EXT-05]. Полная collection всего репозитория не является обязательным preflight каждого пакета. Не переносить готовые архивные probes как единственное доказательство: они часто исполняли extracted bodies с fixtures, а не native API.

## 11. Основания технических указаний E01

Следующие официальные справки использованы только для организации исполнения; они не подтверждают findings PolicyOS и не заменяют project lock/runtime. Ресурсные caps2×L/1×N и размер команды — авторский стартовый профиль для данного поручения.

- **EXT-01 — OpenBLAS runtime variables:** https://www.openmathlib.org/OpenBLAS/docs/runtime_variables/ — OPENBLAS_NUM_THREADS и OMP_NUM_THREADS зависят от типа сборки.
- **EXT-02 — Git worktree:** https://git-scm.com/docs/git-worktree/2.52.0 — отдельные working trees одного repository, своё HEAD/index, совместные repository данные.
- **EXT-03 — pytest import mechanisms:** https://pytest.org/en/stable/explanation/pythonpath.html — режимы импорта и разрешение source path.
- **EXT-04 — JAX benchmarking:** https://docs.jax.dev/en/latest/benchmarking.html — compilation, asynchronous dispatch и сопоставимая precision.
- **EXT-05 — pytest invocation:** https://pytest.org/en/stable/how-to/usage.html — выбор test node IDs и python -m pytest; повторные pytest.main в одном процессе не предназначены для перечитывания изменённого кода.
