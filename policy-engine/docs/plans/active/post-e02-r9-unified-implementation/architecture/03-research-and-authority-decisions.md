## FA1: four independently reviewable implementation contracts

Canonical specification: `docs/superpowers/specs/2026-09-10-producers-foundry-authority.md`, GY §8.5 GY-FA1 and DEBT GY-DEF22. GYD-15 coordinates four direct writer assignments from root after source rebind; no subordinate agent creates children. They can develop independently once their shared evidence consumption interface is pinned. Their exact new filenames are chosen adjacent to the current Foundry/runtime authority owner, not predeclared as existing files.

1. **Cutoff control.** Identify an owner independent of the source writer that admits the runtime subtree/candidate basis and enforces its immutability or explicit invalidation. Producer records the exact admitted set and enforcement context; real runtime reader checks that control, not a self-reported path list. Falsifier: source writer adds/replaces a member while keeping declaration/hash fields; admission fails. A race after check must not commit authority on the old cut.
2. **Resolution receipt store.** Reuse CAS/store and exact resolution readers. A non-test caller resolves a scoped admitted receipt by content and owner identity; caller-supplied path/hash cannot select a fabricated self-issued receipt. Falsifier: swap producer/scope/member at the same locator; fresh consumer refuses. Preserve historical receipt resolution without inferring current admission.
3. **Platform/toolchain admission.** Bind actual executable/toolchain/dependency profile to a competent, independent admission mechanism. Distinguish observed runtime fingerprint from authority to rely on it. Falsifier: altered interpreter, plugin or code closure with unchanged manifest markers fails the actual consumer. Environment absent or unverified remains limited; no hardcoded trusted-machine label.
4. **Production-data trust.** Bind exact data root, acquisition/provenance/permission and use scope through the existing source/rights owner. A data mount, checksum or successful parse is not trusted production data. Falsifier: replace source/root/purpose or use a revoked generation while keeping declared trust; runtime authority refuses. No production scan is needed to design the contract; authentic input validation stays in the permitted local environment during execution.

The four outputs compose conjunctively for a runtime-authority claim; each remains independently diagnosable. Missing one does not block candidate observation, but cannot yield an authority receipt. Include the existing refusal path, real caller, persisted readback, API/audit projection and removal control for each. If an independent control cannot be implemented in the selected deployment, record the precise unsupported authority claim and a reviewed alternative, rather than forge independence through another agent's name.

## No recurring abstract clarification loop

Before escalating, the executor must inspect existing owners, accepted E02 outputs, original criteria and admissible alternative inputs; develop the smallest sound implementation or a bounded research proposal. An escalation lists what was actually tried, exact unresolved proposition, recommended option, rejected alternatives, effect on dependent tasks, migration and a decisive experiment/oracle. It does not ask G to select a generic technology or approve an empty concept. Missing institutional authority is requested as an exact original act/competence/scope/time packet; G's architecture choice cannot manufacture it.
