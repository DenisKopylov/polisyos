## Safe topology and authority

Use depth `0=root`, `1=lead`, `2=leaf`; reject depth 3. Root may assign work directly at either worker role. A lead is a root-assigned planner/owner for a bounded slice. It can prepare a decomposition and use only the child seats that root reserved in a grant. The root admission journal must record a child identity and task before creation, either from an exact child manifest or a pre-authorized slot grant with bounded task classes and paths. This leaves room to decompose work without giving a lead independent program-wide dispatch authority.

Nested spawn is available only when both the execution runtime permits it and root enables it for that assignment. Missing or ambiguous runtime permission means direct-root dispatch only. Prompt text or a manifest boolean cannot manufacture runtime permission. Delegation cannot bypass the actual E02 acceptance gate, P0 source/obligation rebind, or the existing requirement that an owner task be ready before a lease is issued.

A child grant is a finite, revocable lease. Bind it to `grant_id`, `agent_id`, `parent_id`, depth, task IDs/source obligations, branch/base and upstream identities, exact read/write sets, resource keys and vector budget, maximum child seats, expiry/renewal rule, and required output receipt. A child lease must be a subset of its lead's and root's authority. Neither a lead nor a child may widen a write set, resource budget, source claim, or task scope; it returns the proposed change to root.

Count one global pool across the whole tree. The 100-agent ceiling includes root and every direct and nested agent. Reserve a seat before runtime creation; starting, running, output-pending, and cancellation-pending agents consume seats until terminal state is confirmed. Completed work releases an agent seat, but its output and audit trail remain in custody. Per-lead allocations can only be sub-budgets whose sum is bounded by root's pool. CPU, RAM, disk, browser, fixed-port, database, and provider limits are also global resource tickets; no lead gets a fresh copy of the same limit.

Use the existing Wave 0 task/lease registry and append-only journal as the root-owned admission and resource ledger, adding ancestry/grant/status fields there. Avoid a new standalone agent-management subsystem. On parent failure, expiry, or root revocation, the grant cannot mint more children. Root freezes new dispatch under it and either explicitly reissues a narrowed lease or cancels descendants. Until cancellation/termination is confirmed, descendants continue to consume seats and any held write/resource locks; do not replace them and oversubscribe. Root reads the exact tree/branch and outputs before reassignment, consistent with the current history rules.

Child output stays a candidate. The root-owned record must retain the leaf's source/base identity, exact paths and output commit/hash, complete deciding output and limitations, and parent/grant ancestry. A lead relays the child's evidence without dropping negatives or changing its status; root checks readback before integration. Leads can plan, sequence, and explain their slices, but they cannot accept a capability, close an original obligation, approve a release, or integrate a branch on root's behalf.

An independent reviewer must sit outside the author's delegation subtree. For a leaf authored under lead A, neither lead A nor a sibling/descendant under A can count as its independent reviewer. Root assigns the review to a direct reviewer or a separate non-author branch. The reviewer reads the exact frozen candidate and returns its own disposition; the authoring parent cannot promote the reviewer's conclusion into acceptance. Root remains accountable for integration and final acceptance boundaries.

## Main bottlenecks and failure probes

The first bottleneck remains root's source rebind, admission, lease reconciliation, and serial integration. Leads reduce root's task-decomposition load only if their slices are already bounded and their outputs are concise, source-pinned, and easy to audit. Otherwise the extra handoff adds coordination latency and creates context loss, hidden blockers, duplicate work, and review cost. Root's attention and the count of independently reviewable claims may saturate before the global seat cap.

The next bottlenecks are owner boundaries and review capacity: there is still one canonical writer per API/schema/generator/shared artifact; authors cannot review their own family; and compatible changes still integrate through root. Shared WMR/DuckDB state, Playwright, Storybook, fixed ports, provider quotas, CPU/RAM/disk, and the one expensive closeout wave remain globally contended. Nested agents multiply demand on these same pools; they do not create capacity. External issuers, readiness dependencies, and a single-source or backend requirement can keep substantial work blocked regardless of agent count.

Admission should exercise properties, not flags. P37/P38 probes for the future dispatcher:

1. Attempt child spawn when runtime permission is absent, unknown, or revoked while a prompt says it is allowed; dispatch must stay direct-only.
2. Give four leads individual-looking limits that would allow 100 children each; the root ledger must reject any launch that would exceed 100 active agents including root and all descendants. This distinguishes the global property from a per-branch counter.
3. Attempt a third edge (`root → lead → leaf → grandchild`); the root admission check must reject it even when the parent has free seats.
4. Let a lead or leaf fail with children active; root must retain their identities and output receipts, prevent new overlapping writers while old cancellation is unconfirmed, and require a fresh root lease before resuming.
5. Have an authoring lead assign review to its own sibling leaf; the independence check must reject it. A separate root-assigned reviewer must be accepted against the same frozen source.
6. Have a leaf return a green summary while omitting a negative result or exact source/output identity; root readback must keep the work unaccepted.
7. Have a child request a shared schema or resource outside its lease; the write/resource gate must deny it before execution or write, not merely flag it in a final prompt.
