# R9 red-team delta: AP05 / AP07 / AP16

Read-only review of the current task/workstream/route changes. This assesses planned scope, not implementation: AP05, AP07 and AP16 remain `UNRUN` in `inventory/r9-obligations.json`; no runtime or semantic test was executed.

## AP05 — outbound query privacy

**Prior gap substantially closed; one predicate-binding condition remains (Medium, same class one level deeper).** The canonical row is `policy-engine/docs/research/universal-policy-design/external-foundations/acquisition/05-implementation-and-review.md#AP05` (line 60). `CAP-01` in `workstreams/01-acquisition.md` now owns outbound query privacy and requires binding sensitivity/purpose, exact projected query, provider/recipient and permitted logs before egress. Its `positive`, `adversarial`, `removal` and `surface` fields require a permitted query to reach only its admitted recipient, a marked-confidential query to be denied despite an allowed hostname, a controlled provider/log sink to observe the removal failure, and an opaque audit decision. Route AP05 is `CAP-02,CAP-01`; the full original scenario remains controlling.

The remaining ambiguity is the authorization predicate's owner/basis. `CAP-01.requires_other_mechanisms` names the A0 source denominator/actual caller and existing registry/connector ownership, but not who supplies the source/query-disclosure permission or how an unknown sensitivity/recipient scope is treated. A caller-provided “permitted” marker alone would still authorize the wrong property. At A0 bind this to the selected provider/source/use contract or accountable source/custodian evidence; if the basis is unavailable, refuse egress or record the profile as unclaimed. This stays within AP05's source-domain query check and does not require inventing a privacy law or a new privacy service.

## AP07 — query-only handling and cumulative disclosure

**Composition-owner gap is closed at plan scope; query-only no-persistence remains a separate conditional gap (High when that profile is claimed; new class relative to the earlier composition-accounting finding).** The source is `.../acquisition/05-implementation-and-review.md#AP07` (line 62), with the governing owner rule in `.../acquisition/03-storage-and-reuse.md#§2-§6`. `LIF-05` now owns source/custodian-defined protected units, overlap/aliases/lineage, recipient cooperation scope, atomic reserve/commit, indeterminate holds after possible output, replay-vs-fresh-draw treatment, and a marker-preserving removal probe. `CAP-03` and `CAP-06` depend on `LIF-05`; `workstreams/02-lifecycle.md#R11` explicitly makes them consumers of one LIF-05 transition, not alternate counters. If the applicable source composition law is unavailable, the affected path is refused/unclaimed. This correctly avoids a universal epsilon, a generic privacy rule, or a second ledger.

The full AP07 row also requires the **query-only** profile to keep restricted raw material out of CAS, logs, browser state and provider temporary storage, and to make revoke-before-resume block fetch/cache/export. The revised `CAP-03`/`CAP-06` `positive`, `adversarial` and `removal` fields cover purpose rights, remote receipts, restoration and composition, but do not name this query-only sink set or the revoke-before-resume sequence; `LIF-05` focuses on enrolled managed copies, restore and deletion outcomes. The route's “full original scenario remains controlling” prevents silently dropping the obligation, but these task fields do not yet bind a test to it. Add the query-only negative to the existing CAP/LIF owners: enumerate the actual selected-profile sinks, prove no raw persistence while an allowed output/receipt remains consumable, and revoke between initial admission and resume to prove fetch/cache/export stay blocked. Do not create another service; use the selected source's permission and the existing provider/storage owners, or leave that profile unclaimed.

## Pattern disposition

AP05 is the P37/P38 seam: property = only owner-authorized query disclosure; present task gate = sensitivity/purpose and query-projection admission; divergent case = an ungrounded caller “permitted” assertion passes for a query whose provider disclosure the accountable owner has not authorized. AP07's residual is P38: property = query-only raw bytes never persist in the selected sinks; present task gate = grant/composition plus managed-copy lifecycle; divergent case = composition admission succeeds while raw bytes remain in browser/provider temporary state. The AP07 residual is a new class relative to the earlier shared-composition accounting finding under P40, so close it by widening the existing CAP/LIF acceptance to the selected sink set, not by creating a second ledger. AP16's newly named positive, adverse and removal paths close the earlier bootstrap/recovery gap at plan scope.
