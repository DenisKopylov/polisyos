# Red architecture review — post-E02 R9 program

**Disposition:** do not dispatch owner-writing implementation slices yet. The integration-boundaries document states the right single-writer rules, but the workstream manifests still assign overlapping mechanisms and leave the selected public consumer unresolved. Preserve the explicit gate: implementation starts only after G records actual E02 acceptance and W0 rebinds the accepted tree, source/input/backend scope, and owner paths. This review is a planning correction, not E02 acceptance or capability evidence.

## Findings

### 1. One mechanism has multiple writer assignments

The integration table says CAP-02 owns capture protocol while LIF-03 alone owns cursor/frontier fencing; CAP-04 emits source-specific change events while LIF-02 owns dependency enrollment, replay, and publication fencing; CAP-03 wires admission to LIF-01; OPS owns deployment/backend topology; LIF-05 owns rights-sensitive copy and restore behavior (`architecture/01-integration-boundaries.md`, rows at lines 31–35).

The work packages contradict those allocations:

- CAP-02 proposes the expected-head cursor fence and includes `cursor_store.py` as a writer path; LIF-03 proposes `compare_and_commit_partition_state` in that same owner and calls CAP receipt consumption read-only. This is a direct duplicate cursor writer.
- CAP-04 is titled and scoped as enrollment plus fresh projection, and lists the same Claim Ledger, Decision Validity, cascade, and publisher paths as LIF-02. Its deliverable includes the event-to-fenced-projection bridge, while the integration table reserves enrollment/currentness/publication to LIF-02.
- CNT-03 independently owns exact capture and purpose-bounded reuse through `acquisition_executor.py`, `acquisition_planner.py`, `acquisition_epoch_admission.py`, tenant CAS, lineage, access control, and retention. Those overlap CAP-02/CAP-03’s shared capture/admission chain; the integration table says CNT supplies case evidence and CAP owns the acquisition bridge.
- CAP-06 proposes a “scoped backend owner,” while OPS proposes adapter-specific S3/GCS tenant/cell ownership and LIF-05 owns copy placement/restore. The integration table assigns CAP-06 wiring only and OPS deployment/backup topology.

**Required correction:** assign one canonical writer per mechanism in the task manifests, not only in the architecture prose. Keep CAP-02 on transport/representation protocol and have it call the cursor owner; LIF-03 alone writes the frontier fence. CAP-04 emits source-specific events; LIF-02 alone enrolls dependencies, replays, fences and publishes. CNT-03 should supply selected-case definitions, grants and consumer evidence to CAP’s interface, not modify shared acquisition owners. CAP-06 should own provider request/receipt semantics only; OPS/backend owners own adapter parity and LIF-05 owns governed copies/restore. Give the shared artifacts canonical lock IDs so the scheduler cannot mistake aliases for disjoint resources.

**Pattern:** P27/P02. **Capability state until repaired:** `implemented_but_not_orchestrated` is not a task-allocation answer; the conflicting planned writer is `not_established` at W0.

### 2. The CAP-04/LIF-02 handoff can become a cross-workstream cycle

The explicit local dependency lists in the three task manifests appear acyclic. The cross-workstream responsibilities are not. LIF-02 consumes admitted source events and owns the fresh currentness fence. CAP-04’s current scope requires that same enrollment and fenced projection for its own source-update capability to pass. Thus CAP-04 can wait for LIF-02’s projection, while LIF-02’s integration proof waits for the CAP-04 event producer. The integration table already describes the intended one-way edge—CAP emits, LIF consumes—but the acquisition memo and CAP-04 row do not preserve that boundary.

**Required correction:** make the handoff directional and explicit: CAP-04 can finish its producer-side contract/receipt against a selected fixture; LIF-02 consumes that event and owns enrollment/replay/currentness/publication; LIF-09 (or the selected vertical’s final acceptance task) proves the composed path. Do not make either local owner wait for the other’s whole capability closure. Record this as a cross-workstream edge in the authoritative task graph.

**Pattern:** P01/P02/P27/P38. This is an ownership/readiness cycle, not a cycle in the local `depends_on_local` edges.

### 3. Two CodeC owner inventories need correction before dispatch

**CNT-02 points at the wrong source-catalog owners.** `semantic-grounds-tasks.json` labels `fabric/catalog/registry.py` and `fabric/catalog/search.py` as verified existing owners for source-library metadata. Bounded `git show C` checks find `DataContractRegistry` in the former and `MetricSearcher` in the latter. The relevant CodeC source-catalog owners are `fabric/catalog/discovery.py::SemanticDatasetCatalog` and `data_forge/domains/catalog/registry.py::CatalogSourceRegistryEntry` (also named by the acquisition memo). Replace the CNT-02 owner list with those exact source owners, or explain a distinct responsibility for the two other modules; do not use their current “verified_existing” label as evidence of a source registry/search owner.

**The acquisition caller is located, though the full generic reuse chain remains a separate question.** The acquisition memo says W0/A0 must locate the actual caller after its proposed `runtime/quality/acquisition_action_service.py` path did not resolve. `runtime/http/services/acquisition_action_service.py` is already listed in CNT-01/CNT-09 and exists at CodeC: its `AcquisitionActionService` builds the production WDI execution port, resolves the route closure, requires the production bridge, enqueues the job, and invokes `port.execute`; the port calls `execute_live_catalog_acquisition` (CodeC symbols in lines 314–364, 452–538, 546–553, 726–753; `acquisition_surface_execution.py` lines 334, 430–476). Narrow the unresolved claim to whatever is still unproven—e.g. the generic planner closed-loop caller or a second-use exact-body consumer. Do not schedule a broad “find the caller” task or describe the caller as absent. This bounded check proves only the CodeC route; rebind it after E02 acceptance as required.

**Pattern:** P27/P35/P41. The path/name mismatch is a source-inventory defect, not proof that the complete capability is closed.

### 4. The real downstream/public consumer is still unassigned

The runtime diagram ends in generic “Policy / scientific consumer” and “Atlas and MACHINE projection.” CAP-01/CAP-03/CAP-04 surfaces say “user/audit/API” or “Audit/API.” CNT-09 lists existing backend paths but its proposed deliverable still says to join the result to the “selected Atlas/API/UI owner”; the integration table likewise says “Assigned UI owner” without naming one. No task currently binds the chosen receipt/status to an exact public/API route, DTO/OpenAPI/client, browser/MACHINE projection, or declares that surface out of scope.

**Required correction:** at W0 name the selected consumer by path and symbol, the actual API/client/UI/MACHINE surface owner, audience gate, and the negative behavior that surface must show. If the pilot has no permitted public projection, state `surface_out_of_scope` with owner, reason and trigger. Until then mark the selected vertical `consumer_missing` / `surface_missing`; generic audit/API wording is not an acceptance target.

**Pattern:** P01/P03/P05/P29/P32. This is a bounded plan omission; it is not a claim that no consumer exists anywhere in the repository.

### 5. The 100-direct-agent schedule is not yet executable and serializes independent work

README line 32 states up to 100 direct helpers, one orchestrator, and no child agents. At this reviewed snapshot, it links to `execution/02-parallel-execution.md` and `execution/03-waves.md`, but those files are absent from the plan directory; only execution/01 and execution/04 are present. The semantic-grounds prose says W1–W4 can proceed in parallel after W0, but the task graph serializes CNT-04 and CNT-05 behind CNT-03, CNT-06 behind CNT-05, and CNT-07 behind CNT-03/04/05. Some of those are valid composed-proof prerequisites, but the manifest does not distinguish them from prerequisites to begin owner-local work.

**Required correction:** restore the two linked schedule documents or remove the links, and publish an executable direct-agent assignment/lease plan. Separate `owner-local implementation readiness` from `vertical/composed acceptance readiness`: after E02 acceptance and W0 rebind, independent legal, measurement, causal, testimony, API and review/oracle work can proceed on named owner paths with fixtures while acquisition is in flight; only end-to-end acceptance waits for the real receipt and all required owner outputs. Keep one writer per canonical owner and serialize only shared resources. The orchestration level remains one root with at most 100 direct agents; no lane lead should create descendants. Keep CNT-09/LIF-09 as composition gates, not global gates on unrelated owner work.

**Pattern:** P02/P13/P27/P39. The E02 acceptance gate itself remains in force; do not use parallelism to bypass it.

### 6. Resource locks are not canonical, and rollback can retain prohibited bytes

The same contention domains have different lock labels: CAP-02 uses “CAS/root” and “cursor head/lease”; LIF-03 uses “CursorStore partition head” and “Artifact manifest/root publication”; CNT-03 uses “Same source/CAS generation.” With 100 direct agents, a lease checker matching these task-level strings can schedule concurrent writers to the same CAS root/cursor/source generation. Normalize resource identities (for example source/profile generation, tenant/cell CAS root, connector/partition cursor head, control outbox/effect inbox) and require exact lock-key acquisition at dispatch.

Separately, CAP-02’s rollback says “retain bytes, journals and receipts,” and CAP-03 says to preserve bytes/history when promotion is disabled. That is unconditional even when a right is revoked or its retention basis excludes recovery copies. LIF-05 correctly requires actual copy inventory and rights-aware restore/delete outcomes; OPS requires reconciling post-backup revocations. Retain the audit event/receipt separately from the raw payload. Quarantine first; retain raw bytes only when the applicable grant explicitly covers recovery/retention, otherwise route deletion/backup reconciliation through LIF-05’s actual copy owner and report its bounded outcome. Also define the predicate behind LIF-05’s “restore prior authorized head if safe” so operational rollback cannot restore an older authority head over a newer right/revocation event; OPS already says never restore older decision/history over a newer revocation.

**Pattern:** P05/P07/P08/P37/P38. Before claiming a hard resource cap, keep the OPS/LIF-06 state `absent/unallocated` until a selected owner, canonical lock/reservation mechanism, and measured enforcement exist.

## Parallelization and gate summary

There is no reason to weaken actual E02 acceptance or W0 source/owner rebind. After those gates, do not serialize all implementation behind a single end-to-end data path. Allocate direct agents to independent owner-local work, source/case evidence, negative-oracle design, and distinct consumer surfaces; give each a non-overlapping path lease and canonical resource locks. Hold shared semantic owners to one writer. Run selected vertical acceptance only when its actual producer, persisted receipt, bridge and consumer are all available. Any external-input absence should block only the affected claim/use and remain a typed limitation, consistent with the charter.

## Pattern pass

Relevant IDs: P01/P02/P03, P05/P07/P08, P10/P13/P14/P15, P27/P29/P31/P32, P35/P37/P38/P39/P41. Existing anti-patterns found: plan-by-plan duplicate mechanism ownership; a cross-workstream producer/consumer readiness loop; source-owner paths mislabeled as verified; generic surface placeholder; over-serial task prerequisites; noncanonical resource locks; and rollback wording that does not condition payload retention on rights. Target pattern: one canonical owner per mechanism, directional persisted handoffs, exact selected consumer, one-level direct dispatch with owner/resource leases, and rights-aware rollback that preserves audit history without assuming payload retention. Missing capability labels at this snapshot: selected public `consumer_missing` / `surface_missing`; CAP-04→LIF-02 `bridge_missing` until the producer/consumer contract is directional; resource enforcement `absent/unallocated` until W0 identifies an existing enforcing owner.
