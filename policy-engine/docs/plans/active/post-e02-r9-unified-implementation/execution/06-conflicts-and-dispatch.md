## Admission algorithm for future root

1. Resolve the actual original predicate and task stage; materialize selected case/profile witness and execution requirements.
2. Name one canonical writer for each exact source path, semantic rule and generated family. Resolve all path aliases to repository-relative canonical paths. Read-only anchors carry no write permission.
3. Construct the ready set from the stage graph. Remove tasks whose actual write sets are unknown or conflict with an active lease. Different task IDs, branches or lead parents do not make a conflict disappear.
4. Admit only the subset fitting global agent capacity, CPU/RAM/disk/provider tickets and review/integration throughput. Retain OS/control/recovery reserve. Off-path read-only work stays runnable when safe.
5. Record why each pending item waits: producer/output, owner decision, exact write conflict, resource, review, or genuine external input. Do not queue all streams behind one busy browser/store.
6. After owner delivery, read back its commit/tree, independent review and bound outputs; release only confirmed-inactive leases and recompute affected readiness. Parent/lease expiry does not terminate a process.

Example: CAP-01 selection service, LIF-03 cursor protocol and a CNT legal-content researcher can prepare together once exact writes are disjoint. CAP-03's edit to the same service waits for CAP-01's lease, while its separate consumer/test preparation may proceed on an explicitly leased interface-bound slice. UI-06 and UI-08 may design separate components simultaneously, but the shared cycle projection and generated family go through their one owner. Verifiers reading an immutable WMR snapshot need no WMR write lease.

The programme provides up to100 subagent seats including nested leaves, not100 independent source owners. Its largest static ready level is a logical upper bound only. Exact runnable width and calendar critical path remain **not_established** until P0 leases, selected branches, representative durations and actual machine budgets exist. The plan does not promise linear speedup or a fixed number of simultaneous heavy checks.

## Negative admission examples

Reject two differently named tasks with the same normalized file; two leads asking for the same generated family; a write hidden behind a read-only anchor; a source change that invalidates a prepared consumer interface; and a child quota that duplicates the parent/global allowance. Permit two read-only reviewers on one immutable candidate, and disjoint source changes that do not share a resource. These are procedure predicates for future execution; no product scheduling implementation is requested here.
