## Decision and deployment ladder

Deploy by one measured trust boundary at a time. A deployment profile is accepted only when the effective posture, running components, authorization chain, stores, and recovery path agree. A backend enum, environment variable, chart, or successful process start is configuration evidence; it does not prove a working worker, tenant isolation, remote-store parity, source permission, or custody.

1. **A0 commissioning, before any input.** Pin exact source/build/lock and selected profile. Name one policy question, one source, the permitted data/use, owner, actors, audience, retention, region, trust root, and decision authority. Name the operator and deputy, the pilot stop time/run count, and owner-approved SLO/RPO/RTO and spend limits. If any protected premise is unknown, carry it as a declared limitation and do not claim protected execution. This is a commissioning gate, not a new legal authority.
2. **Finite local candidate pilot.** Use loopback-only API, embedded `ControlWorker`, SQLite, and filesystem CAS for a non-sensitive candidate journey. Before first input, the operator commissions the finite source/use scope, maximum workload or run count, expiry, cost ceiling, and stop conditions; this plan sets no fixed numeric cap. Exercise a bounded single-response acquisition, quarantine its receipt, then separately verify admission and a fresh read; if rights and commissioned scope allow, perform a second permitted reuse run. This is a candidate-only pilot, with no public/currentness claim. Do not use real sensitive/private input until the selected profile, authentication, source grant, secret handling, egress, retention, and restore checks are accepted. Paid provider use waits for a real provider-account spend ceiling or an explicitly approved per-operation ceiling with unknown account-wide spend declared.
3. **Single organization/private server cell.** Only after external-worker composition and readiness are real: one API behind TLS, one PostgreSQL control store, one separately supervised worker process, and a supported filesystem CAS volume. Use the existing cell/authz/OPA owners. Keep the first cell a single failure domain and document that fact. Fail closed on a missing/weak effective profile, unavailable runner, unapplied migration, DB/CAS mismatch, missing source rights, or stale trust. Do not call the topology HA.
4. **Hybrid private-source worker.** Only after A4 rights/secret handling and A5 external dispatch/receipt/cancel are proven. Run the worker inside the source custodian's network; credentials and raw input stay there. A server-issued scoped lease authorizes one job, and the worker emits only a specifically permitted result/receipt. Prove limits on logs, temp, caches, crash dumps, retries, and downstream copies. Network reachability or an API token is not a source grant.
5. **Distributed or cloud cell.** Only when a measured single cell cannot meet its declared service target and the additional failure domains are justified. Split API replicas and fixed worker pools by measured resource class. A remote S3/GCS/cache backend is eligible only after tenant/cell ownership, object identity, bounded read, write/read/delete lifecycle, cache isolation, concurrent access, backup, and restore conformance passes for the exact adapter/configuration. Keep raw/private source data at its custodian when policy requires it. Kubernetes, HPA, and quotas are optional placement controls; no default manifest or `s3`/`gcs` enum establishes capacity or parity.
6. **Air-gap, conditional.** Consider only for a named institution that can operate local identity, clock, models/methods, update verification, key succession, and recovery. Import signed, versioned bundles through an independently authenticated trust path with anti-rollback. Prove zero hidden egress. State an `as_of` validity bound where external freshness cannot be checked; do not silently present offline history as current.

Each transition is a go/no-go dossier with the exact build/profile/config digest, operators and audiences, data/source grants, secret and provider principals, stores and all copies, measured workload, measured service/capacity profile, backup/restore proof, negative authorization cases, rollback and duty handoff. A vendor's example settings can inform setup; only tests on the selected deployment establish its properties.

## Operations required at every tier

**Resource isolation and cost.** Do not translate `agentparallel100` into 100 production jobs or assume developer/reviewer parallelism is runtime capacity. GY's one-process E2 sweep is repository-closeout tooling, not a service scheduler. Start with fixed, separately measured lanes for network fetch, interactive/API work, CPU-heavy analysis, high-RSS/native-thread work, model/GPU work, indexing, and restore. Bound each lane's process concurrency, CPU, RSS, scratch/disk, bytes in/out, open files, native threads, queue age, retries, and drain time. Add a shared cross-process admission owner before claiming a global cap; a per-process semaphore or job lease is not shared admission. Kubernetes requests/limits and namespace quotas constrain platform resources, but memory-limit OOM and namespace totals do not bound application work or an external provider account. See [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) and [ResourceQuota](https://kubernetes.io/docs/concepts/policy/resource-quotas/).

For each chosen workload, record a baseline and accepted maximum for peak RSS, CPU time, scratch high-water, input/output and spill bytes, IO, thread count, queue delay, stage wall time, retry/cancel count, DB/CAS latency, and provider attempts/charges. Include cold/warm runs, skewed/large records, slow source, concurrent tenants, retry after timeout, worker restart, and restore. Declare the tested environment and sample window; repeat after material image, model, data shape, or backend change. If a cap is exceeded, defer, reject, partition, or use a bounded algorithm; never weaken admissibility to meet throughput. Track storage, compute, and confidentiality budgets separately. A timeout is not proof that the remote provider did not charge.

**Verification sequencing ([GY §3.5.7](../../layer3-slices/GY-engine-subordination.md#357-compute-economics-gates-the-gy-n4-lesson-extended-by-the-gy-n11--binding-for-every-task-with-expensive-shared-state-a-live-provider-or-content-bound-artifacts-restored-rev-15-e11e14--gy-infra-2-added-rev-20); [Atlas Execution Doctrine](../../POLICYOS_ATLAS_SURFACE_IMPLEMENTATION_MASTER_PLAN.md#execution-doctrine-every-slice-obey-these)).** Before any live provider call, run the parse/validate near-valid gauntlet, recorded-input replay, and scripted end-to-end smoke; record the effective config and change one variable per expensive attempt (GY E7/E8). Freeze implementation, obtain all independent reviews against that exact source, batch accepted blocking repairs, then pay the full expensive receipt/restore/load wave once (E11). Name the shared DB/CAS/pilot/provider resources and serialize only their writers; independent logic checks and read-only inspection need not wait behind them (E13). Measure each suite once before setting its timeout, re-review only the fix delta after a full first review, and report long-run status only when evidence changes (E14). Keep the review chain intact: these economics sequence verification and do not remove any property check. Any new dashboard must ship its machine twin with parity, enforce audience server-side, and show currentness/as-of; markers do not grant authorization or readiness.

**SLO, RPO, and RTO.** Repository runtime SLO seeds (`ops/components/runtime/slo.yaml`, `ops/observability/slo/runtime.yaml`) include p95 API under 1 second, error ratio under 1%, and a 28-day window; the runtime contract is `report_only`. These are not measured pilot/service commitments. The service owner must set targets before rollout and measure the selected profile against a representative window. Define RPO over admitted events, job/control state, CAS references, and rights/revocation history together. Define RTO as time from restore start until a fresh protected read is again permitted after reconciliation, not process startup. Restore from an actual backup into quarantine, measure elapsed time and lost/replayed state, and compare with the signed targets. PostgreSQL PITR requires a matching base backup and WAL/timeline scope; use its supported [backup/restore](https://www.postgresql.org/docs/current/backup.html) and [continuous-archiving/PITR](https://www.postgresql.org/docs/current/continuous-archiving.html) procedures. SQLite WAL requires the WAL-aware backup method and colocated files/processes; do not put a WAL database on a network filesystem ([SQLite WAL](https://www.sqlite.org/wal.html)). No measured evidence means RPO/RTO is not established.

**Migrations and rollback.** Treat SQL control store, runtime-state, and CAS as separate persistence owners. Preserve existing forward order and checks in [`ops/migrations/db/README.md`](../../../../../ops/migrations/db/README.md): 001 tenant columns, 002 backfill, 003 RLS enable, 004 roles/grants; `003_rls_disable_rollback.sql` is emergency rollback only after enablement. Add explicit versioned control-store schema migration before relying on Postgres. Keep N-1 readers where replay/audit/idempotency require them per [`ops/migrations/runtime_state/README.md`](../../../../../ops/migrations/runtime_state/README.md). Use expand → dual-compatible read/write → verify → contract, with dry-run evidence and owner-approved rollback. Do not treat a DB snapshot as a transaction with CAS. Roll back the exact application/config artifact pair; preserve the failed head and evidence. Restore to quarantine, check CAS manifest/hash and control references, then reconcile all rights changes/retractions and histories outside the snapshot before any protected fresh read. Existing [migration/promotion](../../../../runbooks/migration-release-promotion.md), [replay/restore](../../../../runbooks/replay-or-restore.md), and [canary rollback](../../../../runbooks/canary-rollback-or-promotion-failure.md) runbooks remain owner paths.

**Trust, secrets, and custody.** Provision the first trust root through independent authenticated authority. Record release digest, signing role, threshold, validity, generation, and recovery custodian. Succession requires an authenticated successor transition; compromise recovery must not rely on the same compromised key. Anti-rollback state must survive the real restore closure. The [TUF specification](https://theupdateframework.github.io/specification/v1.0.37/index.html) is a design reference for root bootstrap/rotation/recovery, not a PolicyOS dependency or a source of legal authority. Keep source credentials out of logs, environment dumps, LLM context, manifests, and receipts. Scope secret resolution to connector, dataset/query, purpose, actor, cell/region, recipient, and short validity; re-check rights on every retry/resume. Separate source credentials, PolicyOS identity, and provider billing principal. A provider key rotation does not reset account spend.

Name an accountable duty owner and deputy for each signed claim's currentness watch, correction/revocation escalation, and service recovery. Before the first public currentness claim, activate the existing scoped watch, deadline, owner, and fail-limited reaction. Before shutdown or custody transfer, either transfer the duty with authenticated acceptance or issue the claim owner's signed validity cutoff. Keep historical verification distinct from a claim that remains current. At retirement, stop new admissions, revoke credentials, drain/cancel jobs, reconcile unknown remote effects, export required audit/claim history, and record custody transfer/cutoff; do not promise revocation of copies outside PolicyOS custody.

## Finite pilot stop, rollback, and handoff

The pilot ends at the operator-commissioned workload, expiry, budget, or scope boundary, or on a property failure: unknown effective profile; missing/expired rights; foreign/absent authorization projection differs; secrets appear in logs or payloads; worker lease/heartbeat becomes stale; measured resource or provider allowance is exceeded/unknown; restore or fresh-read reconciliation differs. If its duty owner or deputy is unavailable, gate the affected currentness-sensitive claim or operation and hand off that duty; continue independent work only under its own commissioned scope. Freeze admissions for the affected source/operation, revoke its specific credentials, cancel/drain related workers, preserve job/outbox/receipt/CAS hashes and the failed release/config digest, and reconcile remote effects before retry. Roll back the affected artifact/config pair to the recorded last-known-good release as described in the canary runbook. Never restore an older decision/history over a newer revocation. At retirement, transfer the duty with authenticated acceptance or issue the affected claim's bounded validity/custody cutoff through its existing owner; unrelated cells or tasks need not stop when their trust and duties remain independent.

## R11 selected-environment refinements
