# Окна связанной приёмки и порядок интеграции

**Маршрут исполненияv3:** последовательность лейнов, параллельные группы внутри них и точные deferred-acceptance triggers заданы в [09_Исполнение/План_исполнения.md](../09_Исполнение/План_исполнения.md). Ниже сохранены CP как окна доказательства способности, а не дополнительный конфликтующий календарь.

CP — окна принятия связанного результата, не отдельные runtime-состояния и не требование полного CI после каждого пакета. Исторические predecessor edges уточняются по уже работающим контрактам: выполненный owner удовлетворяет зависимости без нового кода. CP6 завершает поставку, но не запрещает раннюю независимую квалификацию.

## Практический порядок

1. Зафиксировать baseline и поддержанный профиль, source/test identity и разрешённый test principal. Отсутствующая credential — setup refusal, не ошибка модели
2. Воспроизводимые локальные исправления выполнять параллельно только при непересекающихся owners; общие файлы интегрировать последовательно
3. Квалифицировать существующие положительные пути и исправления общими вариантами, не переписывая работающий код
4. Недостающие положительные способности и compatibility decisions выполнять отдельными ограниченными шагами, сохраняя уже доступный кандидатный результат
5. Принять затронутые CP и сквозные истории; затем package/generated-client/installed checks CP6. Нативный FAIL не скрывать положительным fixture
