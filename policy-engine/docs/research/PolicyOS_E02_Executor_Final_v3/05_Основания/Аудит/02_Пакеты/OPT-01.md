# OPT-01 — метрика, полная координата и строгий Pareto
## C18 · выпуск v016 · 31 октября 2026 года

**Исходные IDs:** B108, B109, B110, B111. **Очередь:** LANE-02. **Срез:** `20d9009be21097bfbdc38a546a15cc60213b8ace`. Репозиторий, проектные тесты, настройки и зависимости не изменены. Следующий пакет — OPT-02 / B112, B113, B127.

## Решение

**Частичная оценка; полного закрытия нет.** Первоначальная ошибка ускоренного строгого доминирования не воспроизводится на исследованной конечной области. Полные типизированные координаты и явная полнота переданного набора уже реализованы. Текущий fiscal objective сознательно не превращает наблюдение balance-stock в установленный period deficit только по имени; это развитие смысла исходного ремонта, не повод возвращать старую подмену. [S01–S05]

**C18-R01:** `is_dominated` проверяет внутреннюю целостность чужого complete-front, но не совпадение его координат с активным promoter. При несовместимой метрике/split/unit/direction несовпадение ключей превращается в False, то есть в содержательный отрицательный ответ вместо неподтверждённости сравнения. [P11–P13]

**C18-R02:** promoter сохраняет ссылки на изменяемые PromotionPolicy, но координатную схему вычисляет только при создании. Поздняя мутация direction/split меняет потребляемое число и победителя под прежней схемой. Выданная схема также разделяется с владельцем; изменение старого результата меняет следующий результат. Это один класс aliasing эффективного договора. [P14–P18]

Исполнены **30 ограниченных наблюдений**, в том числе 17 988 малых сравнений с независимым oracle внутри P04. MATCH включает обнаруженные дефекты, не означает product PASS. Полный target `pareto.py` сверён по Git blob; настоящие Pydantic-модели target использованы с явно заменёнными инфраструктурными типами. Штатные pytest/PolicyOS/CAS/HTTP/LLM/ObjectiveStack — **UNRUN**.

## 1. Требование и смысл для универсального проектирования политики

[Исходный OPT-01](../05_Источники/OPT-01_исходные_строки.txt) требует не подменять отсутствующее число нулём, сохранять полную координату и сравнивать допустимые величины по строгому Pareto-отношению. Разные кандидаты с равными значениями остаются разными кандидатами; разная выборка или единица не исчезает при сериализации. Квадратичный oracle — средство малого теста, не новый production-алгоритм.

Рабочая установка LLM сохраняется: модель может предложить цели, гипотезы, критерии и следующий эксперимент. Вычислительный слой обязан исполнять именно выбранное сравнение. Наличие хорошего Pareto-фронта само по себе не доказывает эмпирическую истинность, общественное предпочтение или право публикации. Отсутствие универсального алгоритма назначения целей не записывается дефектом OPT-01.

Особенно важно различать: предметную постановку координаты; получение значения в этой координате; вычисление доминирования; полноту обследованного набора; и последующее право использовать вывод. Исправный слой одного вида не замещает другие. Типизированная единица в policy — ещё не измеренная единица источника.

## 3. B109: исходная математическая ошибка устранена

`_find_non_dominated_2d` хранит `max_second_from_previous_groups` как optional-значение. При уже существующей строго лучшей первой координате вторая проверяется через `<=`. Поэтому `(2,1)` удаляет `(1,1)`, а не сохраняется рядом с ней. Внутри одной группы одинаковые максимальные значения сохраняют все отдельные идентичности. 3D использует тот же исправленный локальный 2D-отбор и skyline. [S01:489–643]

| Проверка | Результат |
|---|---|
| `(2,1)` против `(1,1)` | Только первая точка |
| `(1,2,1)` против `(1,1,1)` | Только первая точка |
| Два разных candidate refs с `(2,1)` | Оба refs сохранены |
| Разные направления benefit/cost | Знак нормализован до сравнения |
| Selection/holdout tradeoff `(10,1)` и `(1,10)` | Оба остались и после настоящего Pydantic JSON-round-trip |

P04 независимо сравнил target с простым определением «не хуже по всем координатам и строго лучше хотя бы по одной». На сетке `{-1,0,1}` проверены все упорядоченные пары в 1–4 измерениях. Дополнительно проверены все знаковые направления, перестановки осей и обратный порядок строк на конечных наборах из семи точек с фиксированным RNG. Всего **17 988 сравнений**, расхождений нет. Это ограниченный вычислительный corpus, не формальное доказательство на всех float и не 17 988 закрытых критериев. [P01–P06]

Контроль удаления свойства заменил только `<=` на `<` в отдельной памяти audit harness. Исходный контрпример снова сохранил обе точки и разошёлся с oracle. Production source не изменялся. Не нужно заменять быстрый алгоритм медленным или удалять все равные точки. [P28]

## 4. C18-R01 — чужая схема даёт ложную определённость отрицательного ответа

### Порядок перехода

`is_dominated` строит вектор по текущему promoter, проверяет complete-схему front и внутренние соответствия keys/value/reference. Затем `_dominates` получает словари разных coordinate IDs; при несовпадении ключей он возвращает False. Если input assessment чужого front complete, внешний метод также возвращает False. Проверки `active IDs == front IDs` в этой цепочке нет. [S01:385–407,473–487]

### Различающий опыт

Исходный front: holdout `score`, maximize, unit не задана; значение известного члена 2. Запрашиваемый кандидат содержит `score=1` и в selection, и в holdout. Владелец с той же схемой вернул **True**. Затем persisted front перечитан через настоящий `ParetoFront.model_validate_json`, а изменён только контракт спрашивающего promoter:

| Изменение active promoter | Координаты совпадают? | Получен ответ |
|---|---:|---:|
| Selection вместо holdout | Нет | False |
| Явная единица usd вместо отсутствующей | Нет | False |
| Minimize вместо maximize | Нет | False |
| Другая metric | Нет | False |

Нужный исход здесь — явная несовместимость или неустановленность отношения, **не принудительное True**. False не должен выдавать результат сравнения, которого не было. Изменение только порядка эквивалентных осей сохранило нормальное сравнение — порядок списков сам по себе не является новым предметом. [P11,P13]

**Severity: medium, conditional; confidence: high локально.** Триггер — публичный локальный API с front, произведённым другим comparison contract. Не установлены production-частота, ошибочное продвижение или внешняя публикация. Поиск `is_dominated` показал определение и тесты, но не заменяет конечный caller census. Рассмотренный registry-consumer создаёт свежий promoter и вызывает compute_front; этот факт ограничивает перенос находки на него. [S06]

**Минимальное направление:** перед Boolean-ответом сопоставить полную каноническую схему front с эффективной схемой owner. При реально разрешённом преобразовании оно должно иметь явного владельца; не переименовывать IDs и не сравнивать лишь display-labels. Audit-only контроль сравнения множества canonical IDs отверг несоответствие и сохранил обычное True. Это проверка направления, не patch и не доказательство всех будущих schema migrations. [P12]

## 5. C18-R02 — изменяемая policy переопределяет вычисление без новой схемы

В конструкторе `self._policies = list(policies)` копирует только контейнер. Конкретные PromotionPolicy остаются теми же изменяемыми Pydantic-объектами. Схема и IDs вычисляются один раз; `_assess_objective_vector` позднее читает исходные mutable policy, сохраняя ранее построенные coordinate IDs. [S01:271–301,439–464; S02]

### Контрпример direction

Первоначальная policy — maximize `score`. Кандидат A имеет 2, B — 1: выбран A. После изменения **переданного caller-объекта** `policy.direction = MINIMIZE` тот же promoter выбрал B и записал нормализованное число −1. При этом в выданной coordinate schema по-прежнему `direction=maximize` и прежний hash. Настоящий Pydantic JSON-readback такой внутренне сформированный результат принял. [P14]

### Контрпример split и обратная связь от результата

Изменение caller policy с selection на holdout привело к чтению значения 9 из holdout под старым coordinate ID selection, где фактическое значение было 2. Это тот же механизм, не ещё один отдельный дефект. [P15]

Есть и выходной alias: `front.coordinate_schema` — объект, разделяемый с promoter. Мутация статуса схемы уже выданного front в `legacy_limited` меняет статус следующего свежего front того же owner. Поэтому недостаточно изолировать только список входных policies; договор выдаваемого snapshot тоже должен быть согласован. [P18]

Дополнительный контроль: `member.evaluation` сохраняет сам исходный BenchmarkEvaluation. Мутация внешнего input после compute меняет встроенный evaluation в выдаваемом JSON, оставляя canonical numeric value прежним. В опыте coordinate осталась 2, evaluation стала 100. Неизменяемые CAS-bytes здесь не затрагивались. Это граница согласованности mutable результата, не свидетельство изменения сохранённого внешнего артефакта. [P17]

**Severity: medium, conditional; confidence: high локально.** Триггер — повторное использование owner с изменяемым общим config или изменение уже возвращённой схемы. Исследованный registry создаёт owner внутри вызова, поэтому такой lifecycle для него не продемонстрирован. Неверный защищённый результат не заявлен.

**Минимальное направление:** неизменяемый или адресно скопированный небольшой эффективный comparison contract и независимая выдаваемая схема. Чтение значений и маркировка результата должны использовать один снимок договора. Разрешённая смена цели создаёт новое согласованное основание. Не требуется deepcopy всех моделей, datasets и сервисов. Audit-only копирование policies при создании сохранило прежнюю семантику при поздней caller-мутации; это направляющий контроль. [P16]

## 6. B111: неполнота уже не спрятана в числовом sentinel

В compute_front missing и nonfinite исключаются до сортировки, с сохранением input index, candidate ref и конкретных отсутствующих/нечисловых координат. Если хоть одна пригодная строка есть, полезный фронт может остаться, но input assessment становится partial. Пустой и полностью непригодный набор дают no_usable_inputs и incomplete schema, не произвольную бесконечность. [S01:98–152,303–383; P07,P09]

Важно: complete означает только полноту **переданной последовательности**, не полноту всех потенциальных политик. Источник и основание формирования этой последовательности — отдельная обязанность владельца.

В частичном наборе фактически наблюдённый доминирующий кандидат может доказать True. Но отсутствие такого свидетеля не доказывает False, когда другие переданные кандидаты не были оценены: `is_dominated` выдаёт адресный отказ. Неизвестный queried-кандидат тоже не превращается в недоминируемый. Эти положительные механизмы сохраняются. [P08,P10]

Настоящие Pydantic target DTO сохранили omissions после JSON. Подмена hash схемы, удаление coordinate-value, duplicate полной координаты и несогласованные coverage counts отвергаются. Перестановки finite/invalid rows не поменяли численный front. Это не замена проверки источника измерения или настоящего CAS. [P19–P22,P29–P30]

## 7. B108: текущий смысл точнее исходного равенства balance/deficit

Прочитаны действительные producer и source-reconciliation branches, а также регрессионные tests. Они уже не применяют `get('gov_balance', 0)` и не теряют direct deficit при отсутствующем основном ключе. Для допустимого прямого deficit требуются явно связанные единицы; действительный ноль сохраняется. Primary null в fiscal aliases трактуется как отсутствие, а malformed non-null — как invalid. Conflicting aliases и противоречивые значения/units в root и вложенных источниках не исчезают при выборе удобного контейнера. [S03,S05]

При этом balance-stock в одиночку теперь ограничен как `budget_deficit_period_flow_source_not_established`, даже при подходящем названии unit. SourceMetricObservation также разводит наблюдённый stock и ещё не доказанное objective-mapping. Старое требование «эквивалентные balance/deficit кодировки всегда одинаковы» нельзя исполнять так, чтобы снова молча объявить запас периодным потоком. Текущие тесты это различие намеренно закрепляют.

Этот фрагмент **не исполнялся в текущем аудите**: B108 имеет source/test-design assessment, в отличие от исполненной Pareto-части. Не заявлены настоящее фискальное измерение, его нормировка или прохождение source→consumer. Для последующей приёмки нужны действительный law/adapter и две предметно эквивалентные кодировки именно одной величины, а не просто два похожих ключа.

Остаётся точная методологическая граница для владельца: cross-family конфликт всё ещё проверяется через условное преобразование balance. Нельзя автоматически переносить это правило на входы, где stock и period deficit законно различны. Здесь оно записано как необходимость определить поддержанный входной профиль, не как ещё один воспроизведённый production-баг.

## 8. Дополнительные границы без смешения с основными находками

**C18-G01 — display collision.** Каноническая координата безопасно хэшируется, но legacy-label строится конкатенацией `::`. При необычном metric-name, буквально совпавшем с display-name другой координаты, три canonical values дали две display values. Canonical relation и IDs сохранились. Нужно квалифицировать отображение/старых читателей; не называть это потерей координаты действительного Pareto-алгоритма. [P23]

**C18-G02 — координатная декларация не доказывает источник split/unit.** BenchmarkEvaluation читает selection отдельно, а прочие split-значения через общий holdout dict. В опыте runtime_split был holdout, а policy hidden_holdout всё равно получила число и hidden-label. Это измерено только на локальном механическом adapter. Требуется фактический upstream split contract; обход скрытого holdout, права или прикладной ошибки не установлен. [P24; S02]

**C18-G03 — hypervolume выше 2D не точная мера объединения.** В source это прямо названо rough approximation: произведение диапазонов. На трёх точках `(10,1,1)`, `(1,10,1)`, `(1,1,10)` и нулевой reference reported indicator равен 1000; точный объём объединения трёх прямоугольников равен `10+10+10−1−1−1+1=28`. Добавленная нулевая точка задаёт reference, а сама доминируется. Отбор членов правильный. Для 2D отдельный rectangle-union oracle дал точное совпадение 8. Не нужно переписывать comparator ради этого индикатора; нельзя выдавать bbox-proxy за exact hypervolume или сравнивать поколения с неявно разными references. [P25–P27; S01:671–725]

Finite check для reference и результата существует. Глобальная numerical robustness, измерение качества оптимизации и реальная производительность не тестировались.

## 9. Потребители, тесты и запрет необоснованного расширения scope

В прочитанном `ParetoRegistry` действительные objective maps переводятся в evaluations, создаётся новый promoter, compute_front возвращает membership и coverage. При отображении назад сохраняются input_count/assessed_count, missing и nonfinite IDs. File persistence проверяет finite каналы и индикаторы. Это полезный существующий consumer, не повод создавать второй registry. [S06:1510–1663]

Исторический task B109/P27 отделяет исходную comparator-проверку от расширенной задачи зарегистрированного served provider. Его прежний census нельзя цитировать как новое доказательство отсутствия provider на текущем SHA. Здесь полная registered chain не запускалась и текущая полнота injections не устанавливалась. Два слоя не объединены в безусловный blocker всего B109. [S07]

Прочитанные окна `test_pareto.py` уже содержат slow oracle, адресные 2D/3D regression cases, equal identities, направления, split/unit/hash tamper, JSON и partial front. Не нужно заводить дублирующий framework. В рассмотренных окнах нет различающих случаев foreign complete-schema и изменения caller policy после сборки; это не заявление об отсутствии такого теста во всём репозитории. Все существующие проектные tests в данном выпуске — UNRUN. [S04]
