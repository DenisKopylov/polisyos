## 1. Итог

**Три первоначальных изменения присутствуют:** реальный одиночный элемент больше не запрещён только по cardinality; value/обязательная применимость отбираются до top-k; requested modalities не сокращаются пересечением с доступным каталогом. Их не нужно реализовывать заново.

**Два локальных остатка:** C11-R01 — opaque candidate/atom ID может добавить ложное обязательное `panel` и остановить пригодный выбор; C11-R02 — объяснение проигрыша может противоречить фактическому лексикографическому порядку. Отдельно остаются квалификация происхождения полного набора и адресные причины исключения до ранжирования. Они не объявлены обходом полномочий или новым глобальным отсутствием реестра.

| ID | Что сохранять | Точный остаток | Вывод этого прохода |
|---|---|---|---|
| B34 | Singleton без фиктивного второго метода; реальный output-owner; canonical denominator; context/content binding | Действительный полный scoped intake и потребитель, отрицательный контроль согласованно усечённого набора | Основной запрет снят; native/source-origin приёмка не завершена |
| B35 | Value/hard filter перед top-k; полная value-проекция отдельно от eligible trace; инвариантность нерелевантному расширению | Точное объяснение rank и исключений; штатный selector/consumer | Порядок исправлен; два участка диагностики ограничены |
| B36 | Неизменные explicit modalities; отказ malformed present; explicit method не обходит hard требования | C11-R01: lexical proposal из ID не должен становиться обязательным условием; настоящий adapter только при подтверждённой необходимости | Прежнее пересечение устранено, осталась иная потеря смысла |

## 2. Основание и содержательная цель

Исходный E02 требует оценивать происхождение реально обнаруженного набора, а не его размер; отбирать обязательные свойства до усечения; сохранять требуемую модальность, даже когда её некому обеспечить. Он запрещает фиктивный второй метод, увеличение top-k вместо исправления порядка и молчаливое ослабление запроса. LK06 сохраняет существующие MethodRegistry/view/runtime роли, а не поручает создать ещё один registry. [E02: 1443–1582]

Смысл пакета — не доказать универсальную оптимальность выбранного метода, а довести корректно поставленный вопрос до реально подходящего доступного метода и вернуть понятную причину, если это невозможно. LLM может предложить метод/гипотезу, предметные требования и допустимое преобразование. Алгоритмическая часть должна сохранять эти различия, а не заново получать жёсткое условие из технического имени или исправлять вопрос под имеющийся каталог.

Это не запрет полезной эвристики: она может влиять на предложения и порядок исследования. Проблема начинается, когда её результат без отдельного основания становится обязательным предметным условием.

## 3. Действительная цепочка и владельцы

Основной путь `select_value_method_for_problem` остаётся в `foundry/methods/selection/advisor.py`. `MethodSelectionReceipt` и `MethodSelectionAlternative` теперь физически находятся в лёгком `selection/receipt.py`; advisor импортирует те же объекты. Для исторического чтения сохранён прежний `__module__`. Проверять только прежнее расположение валидатора было бы ошибкой. [C11-S01/S02]

Последовательность текущего value-пути: форма advisory manifest → registry bootstrap → catalog snapshot → методы с настоящей owner-backed value-проекцией → route constraint → required modalities → эффективный контекст и query → hard eligibility → advisor/rank/top-k либо разрешённый explicit request → receipt. Полный value-denominator строится отдельно от отфильтрованного множества.

`_catalog_entry_is_value_method` разрешает реальный класс, сверяет MethodSignature, native value capability, выходной slot, contract ID и owner. Одной надписи «value» в имени/тегах недостаточно. Наш harness заменяет этот внешний capability-owner явной фикстурой; его истинность не выводится из P04. Сам владелец прочитан по исходнику, а соответствующие настоящие негативные тесты — отдельно. [C11-S01: 1470–1520; C11-S03]

В реальном FoundryValuePort до выбора загружается `ValueDataProfile` от владельца; после выбора receipt проходит модельную проверку и сравнение с заново вычисленным selection context на тех же owner rows. Также сохраняются candidate/world/EvalSafety/estimand проверки. Таким образом, здесь существует действительный consumer, а не только библиотечная функция без вызовов. Однако весь этот путь не исполнен в текущей среде. [C11-S06: 6500–6860]

## 4. B34 — singleton исправлен, но checksum не равен происхождению

### 4.1. Что уже подтверждено

В полном текущем receipt нет blanket-условия `len(denominator)<=1`. Проверяются каноничность и непустота набора, членство выбранного метода и trace, ровно одна selected-row, отсутствие дублей, последовательные ранги, конечные scores и content hash. Явный запрос имеет собственное `requested_registry_method` и `advisor_score=None`, не придуманное ранжирование. [C11-S02]

P01 провёл одноэлементный fixture-каталог через исходную selector-логику и полный текущий Pydantic receipt. P02 отказал незарегистрированному явному методу; P03 сохранил причину неготового backend. P22–P25/P27/P28 отдельно проверили hash drift, чужой trace с пересчитанным hash, чужой context, сдвиг ranks, пустой denominator и NaN-score. P34 выполнил JSON→Pydantic round-trip. Последний не равен CAS-readback новым процессом.

Полные bytes `receipt.py` независимо совпали с Git blob `534196e115cc485392382fcf8e9fb370c28dd4db`. Pydantic использовался настоящий, версия 2.13.5. Заменён только общий `artifact_self_identity_projection` на объявленную проекцию без `content_hash`; проектный пакет целиком не импортировался.

### 4.2. C11-G01 — точная граница подтверждения полноты

Receipt в одиночку устанавливает внутреннюю согласованность переданных полей, но не восстанавливает внешний полный каталог. P26 согласованно сократил denominator и trace до выбранного метода, пересчитал self hash и оставил прежний expected context hash. Модель и equality-метод приняли такой объект. **Это характеристика границы DTO, не установленный путь внесения подделки через штатный API и не обход защищённого N8.**

В реальном catalog-owner уже есть более сильная граница: `registry_report` связывает точный набор и content binding, а `require_bound_discovery=True` дополнительно требует связанный manifest, успешный intake и согласованные members. Default construction без report и этот профиль не тождественны. Прочитанный value-selector вызывает обычный builder без этих аргументов; это не доказывает отсутствие внешне закреплённого контекста во всех путях композиции. [C11-S04]

Существующий singleton-тест использует настоящую registry entry, но подменяет builder сокращённым snapshot. Он хорошо проверяет отсутствие cardinality-запрета и реальные output-contracts, однако сам по себе не является доказательством полного одноэлементного независимого discovery. Нужен точный положительный intake и различающий отрицательный сценарий скрытого члена на фактическом принимающем владельце. Не назначать второй каталог, новую подпись или обязательный второй метод.

Отдельный analyst-facing API может намеренно требовать два сопоставимых результата для cross-method consensus. Это другая цель. B34 не требует снять такое условие и не приравнивает выбор единственного метода для исследования к готовому консенсусу методов. [C11-S01: 730–1010; C11-S03]

## 5. B35 — eligibility до top-k работает; причины надо сохранять точно

### 5.1. Исправленное устройство

`eligible_value_entries` получается из owner-backed value-набора по runnable/route/required modalities до `advise_methods`. Advisor получает только этот subset. Receipt затем использует исходный value-каталог, поэтому отбор применимости не выдаётся за полный обнаруженный denominator. Сам top-k остаётся ограниченным; необязательное расширение его размера не требуется. [C11-S01: 1260–1450]

P05 добавил 20 нерелевантных diagnostic entries с большими controlled scores. Выбор, receipt и контекстная value-проекция не изменились, advisor получил только допустимые value entries. P06 с 12 допустимыми методами сохранил 12 членов denominator и 12 trace rows при limit=8. P35 изменил значимое содержимое value-entry и получил новый context hash. В проверке rank использует исходное тело, но числа scores, truthfulness-depth mapping, history и упаковка advisory payload контролируются фикстурами; реальное качество ranking не измерено.

### 5.2. C11-R02 — объяснение противоречит первичному ключу ранга

**Серьёзность:** низкая для самого выбора, средняя для диагностики и автоматического ремонта, если consumer использует эту причину. **Уверенность:** высокая в исходном builder и выполненном локальном контроле; частота на настоящем score profile не измерена.

`_rank_entries_with_scores` сортирует по `(-truthfulness_depth, -score_rest, fqn)`. Поэтому scalar score не всегда объясняет проигрыш. Но `_build_value_method_selection_receipt` назначает каждому проигравшему одну из двух причин: scalar tie либо `advisor_score_below_selected_on_owner_data_shape`. Другой первый ключ в объяснении не отражён. [C11-S01: 1520–1595, 1930–2010]

P29: у выбранного A более высокий truthfulness tier и score=10; у B более низкий tier и score=100. Исходный rank корректно для своей принятой политики выбирает A. В receipt B получает «балл ниже выбранного», хотя 100 больше 10. P30 подтверждает, что при одинаковом tier и действительно меньшем score эта причина правильна.

Минимальный ремонт — выводить loss reason из реально различившего ключа/решения ранжирования, сохраняя текущую политику и сырые значения. Не требуется менять порядок truthfulness/score или выравнивать scores ради правильной надписи. LLM, читающая обратную связь, должна исправлять настоящий недостаток, а не пытаться повысить уже больший балл.

### 5.3. C11-G02 — фильтр исключает правильно, но не оставляет адресный журнал

P31: при required panel каталог содержит A(tabular) и B(panel). A сохраняется в полном denominator; в `ranked_alternatives` и `score_trace` находится только B. Возвращаемая структура не содержит per-member причины hard-исключения A. Это отличается от причины проигрыша уже ранжированного метода.

Исходный B35 прямо требует журнал причин исключений и область поиска. В данном returned trace эта часть ограничена. Можно сохранить детерминированный disposition по существующему набору: un-runnable, route mismatch, modality gap и т. д., не выдавая неранжированному методу фиктивный numeric score. В соседнем `select_method_for_input_contract` уже есть candidate disposition/reasons; это образец ответственности, не поручение копировать второй loop. Полный UI/audit consumer этого набора в проходе не проверен. [C11-S01: 650–730, 1810–1840]

## 6. B36 — запрос не ослабляется каталогом, но дополняется текстом идентификатора

### 6.1. Защищаемое поведение

`_value_selection_criteria` больше не пересекает requested modalities с capabilities доступных методов. Явные hints проверяются на форму; неподдержанный raw manifest не становится пустым hint. Автоматический и explicit method пути проходят тот же hard predicate. P07–P15 различили panel без поддержки, появление реального по fixture capability panel-метода, несовместимый explicit request, корректный explicit request без fake advisor score, route exclusion, malformed hints и flat advisory grammar.

Такой строгий отказ полезен: отсутствие исполнителя не переписывает задачу. Исправление R01 ниже не должно вернуть прежнее ослабление или разрешить явному имени метода обходить настоящие требования.

### 6.2. C11-R01 — техническое имя меняет обязательную модальность

**Серьёзность:** средняя для пути выбора; может закрыть реально доступное вычисление либо направить поиск на неподходящую структуру данных. **Уверенность:** высокая на прочитанных/исполненных функциях. Полный user HTTP-путь, частота и конечное решение не измерены.

`_candidate_selection_signal` собирает candidate_id, id, diversity_key и поля атома, включая intervention_id. `_required_modalities` ищет в этой строке подстроку `panel` и добавляет обязательный `panel` к явному запросу. Это не preference и не отдельное предложение: итог немедленно участвует в subset-предикате eligibility. [C11-S01: 1730–1770, 1835–1870, 1930–1960]

| Условия fixture-каталога и запроса | Наблюдение |
|---|---|
| Один runnable value method поддерживает tabular; явно required=tabular; ID=`case-alpha` | selected |
| Те же inputs, меняется только ID на `case-panel-alpha` | blocked; required становится `(tabular,panel)` |
| Меняется только `atom.intervention_id` с аналогичной подстрокой | тот же ложный hard blocker |
| Подходящий tabular method задан явно | не обходит ложное добавленное условие |
| Candidate signal содержит `no_panel_data` | подстрока всё равно добавляет panel |

P16 — контроль нейтрального переименования: alpha→beta не меняет selected, хотя context hash закономерно меняется по текущей схеме. Следовательно, дефект не в самом изменении идентичности контекста, а в изменении предметного hard requirement.

P17–P20 — один механизм, а не четыре независимых бага. Полный selector body доведён до receipt/blocked return; registry, dataset ownership и scoring представлены явными фикстурами. Это stronger-than-string-only routing witness, но не native интеграция. Публичная функция принимает такой candidate mapping; достижимость соответствующего имени в каждом типизированном producer пока не проверена.

### 6.3. Минимальное направление ремонта

Разделить техническую идентичность и содержательные признаки. Opaque ID не порождает обязательную модальность. Явные требования и типизированная характеристика owner-data проходят своим существующим каналом; lexical clue остаётся candidate proposal/предпочтением, пока не получено основание поднять его до hard constraint. Истинное panel-требование должно сохраниться независимо от имени кандидата и состава каталога.

P21 — только контроль направления: исключение identity-полей из сигнала устранило данный контрпример, а явно заданный panel по-прежнему отказал tabular-методу. Это не готовый патч и не решение отрицаний/произвольной интерпретации diversity_key. Замена substring одним regex не завершает контракт.

Сходный класс «opaque identifier → обязательный предмет» ранее проверялся в REQ-01, но там другой owner и другая capability. Общий защищаемый инвариант стоит применять к переходам интерпретации; текущий C11 не объявляет весь код повторно просканированным. Новый NLP framework, второй compiler или каталог не требуются.

Установка о LLM не снимает эту задачу: если LLM уже сформулировала явное содержательное требование, инфраструктура не должна подменить его техническим названием. Предложение LLM при этом тоже не превращается автоматически в подтверждённую структуру реальных данных.

## 7. Преобразование данных: не приписывать способности декларации

Соседний checker содержит реальные типы планов unit/shape/type conversion и различает несовместимость. Прочитанные декларации сами по себе не являются материализующим producer panel→tabular и не означают, что такое преобразование сохраняет смысл заданного estimand. [C11-S05]

В этом пакете не установлен необходимый новый конкретный modality adapter. Поэтому нет безусловного backlog «построить универсальный конвертер». Если в разрешённом сценарии нужен adapter, его реальный output должен удовлетворять прежнему требованию либо новая согласованная постановка должна быть обозначена отдельно. Пересечение строк требований с capabilities не является таким преобразованием.

## 9. Практическая очередь завершения

| Приоритет | Работа у действующего владельца | Различающий результат |
|---|---|---|
| 1 | Отделение IDs/proposals от hard modalities | Переименование не меняет применимость; настоящий panel остаётся обязательным, explicit method не обходит его |
| 2 | Верное объяснение ranking и hard exclusions | Consumer видит фактическую первую причину проигрыша/исключения, а не ложный scalar или отсутствующую запись |
| 3 | Source-qualified singleton и полный denominator | Установленный scoped singleton проходит; сокрытие нужного члена или замена контекста не принимаются реальным consumer |
| 4 | Один настоящий selector → owner rows → receipt → downstream | Пригодный метод действительно потреблён, невозможность остаётся адресной; чужое основание не переиспользуется |
