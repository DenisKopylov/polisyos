# Точечные предлагаемые уточнения к v2

Это отдельные предложения к согласованной редакции. Ни исходная v2, ни продукт не изменены. Применять синхронно к каноническому тексту и его производным копиям; затем обновить hashes и проверить trace parity. Идентификаторы REQ/TEST/binding сохраняются.

## FAC-01: UDF-02, TEST-UDF-02-01

JSON exact legacy bytes, NPZ arrays/nnz/hashsize, Parquet rows/schema/index=False. Отказ до успешного replace сохраняет prior file и удаляет собственный оставшийся temp. Если replace уже успешен, новые bytes видимы; ошибка directory fsync не доказывает durability и не обещает восстановление prior file; фаза/исход различимы в existing error/reporting evidence. No output PASS до reader.

При подготовке следующего выпуска заменить oracle в packet MD и companion JSON, затем обновить его точные производные записи в индексе требований/связях при наличии. Согласовать setup: отдельно отказ до успешного replace и directory-fsync failure после успешного replace. Не требовать нового error framework: использовать текущий способ различения/доказательства фазы.

Будущая приёмка: первая инъекция сохраняет old bytes и удаляет собственный оставшийся temp; вторая наблюдает new visible bytes, failure phase и отсутствие ложного durability/rollback claim. Не считать это уже выполненным native test.

## FAC-02: E02-I07-C-B01, concrete_obligation

Paired time/value/mask/metadata порядок и finite source/target axes проходят compiler/preflight до фактического calibration consumer; duplicate source timestamps отклоняются без объявленной содержательной duplicate policy, а explicit target axis проверяется по declared coordinate/model contract без скрытой сортировки или dedup user-requested order.

Обновить канонический JSON binding и его MD-представление. Не менять source/target semantics незаметно в остальных ТЗ. Для interpolation-query profile с допустимыми повторными запросами проверить source[0,1,2], values[0,10,20], target[.5,.5,1.5] → [5,5,15] в заданном порядке. Это иллюстративная независимая арифметика, не выполненный NumPy/JAX тест. Для модели, требующей unique/strictly increasing target, явно назвать отдельное предусловие и отрицательную проверку. Duplicate source без объявленной политики по-прежнему отклоняется.

## CM-001: необязательное уточнение общей карты

Сохранить FIT-01; SCM-часть краткой строки уточнить так:

SCM-03 — closure/prepared-plan и canonical stream coordinates; SCM-02 — conditional-row/PSD и refit qualification; SCM-01 — twin consumer и native selected fit→query acceptance. Подробное распределение и порядок shared edits: LANE-05 и §7 SCM-01/02/03.

Проверка документарная: общая строка и подробные разделы одинаково направляют исполнителя к владельцу смысла/consumer/приёмки. Новый runtime test, реорганизация кода и перенос владельцев не нужны. Если SCM-03 имеет отдельную implementation role для worker, назвать её отдельно от acceptance owner.
