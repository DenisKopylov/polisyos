# Порядок исполнения: последовательно по лейнам, параллельно внутри

## Current LANE-01 additions (14 November)

The user authorized the seven useful growth extensions recorded in the root work plan: explicit input maps, durable method dataflow, persistent model scalars, step-qualified period inputs, entity vectors, selected-input feedback and certified derivation composition. These are shared mechanism improvements within the active LANE-01 workstream, not new original lanes or replacement requirements. Keep the 11/66/64 denominator and all late-consumer windows. Their actual producer/consumer and identity/time/dynamics rules must be independently reviewed; unsupported or unverified combinations remain explicit. The root plan holds current ownership and results; do not create parallel planning packages.

## Основное правило

Один активный **implementation lane** в каждый момент. Внутри него несколько отдельных рабочих направлений; в каждом списке пакеты идут слева направо. Разные направления могут готовить анализ, тесты и непересекающиеся patches параллельно. Это не разрешение одновременно менять общий файл или семантический owner: перед запуском каждому worker выдать фактический write-set lease на текущем commit. Здесь write-set lease — организационное назначение единственного writer и разрешённых файлов в рабочем реестре, не новый runtime lock/lease subsystem. Непересекающиеся строки одного файла не делают две независимые правки автоматически безопасными.

**Рекомендуемый маршрут:** 06 → 08 → 07 → 04 → 10 → 05 → 09 → 01 → 03 → 02 → 11 → 12. Номера исходных лейнов и принадлежность всех127 пакетов сохраняются. Это dependency-informed порядок реализации, не ранжирование важности и не изменение исходных CP.

Не превращать references/co-review в ложный hard predecessor: уже работающий и квалифицированный owner удовлетворяет зависимости без нового patch. Обратное тоже верно: существование имени/import не доказывает контракт. До начала зависимого кода проверить реальный owner/caller и выбранный профиль.

## Почему нельзя требовать полный PASS каждого лейна перед следующим

RES-03 из06 требует настоящих CMP-01 из04 и CYC-02 из01; CAL-01 из07 получает конечное свидетельство у CAL-02/06 из10; CYC-05 из01 нуждается в final build evidence из12. При этом сами consumers нуждаются в runtime/data primitives ранних лейнов. Поэтому строгое «сначала закрыть все claims06, затем открыть08» создаёт искусственное круговое ожидание.

Разделены два события: **локальный этап реализации/регрессий завершён** и **сквозная способность принята**. Для перехода вперёд допустимо оставить конкретный late-consumer test в NOT_RUN/BLOCKED с owner, trigger и требуемым endpoint по реестру ниже. Запрещено объявлять такой пакет полностью принятым или подменять отсутствующий consumer stub-ответом. Если для самого кода недостаёт actual primitive/contract, блокируется этот конкретный implementation step; он не объявляется готовым и переносится в явное последовательное corrective window после появления владельца. Одновременно два лейна не открываются.

## Вход и выход каждого этапа

**Вход:** exact HEAD/lock/profile; актуальный caller/owner census; решения DEC, необходимые выбранному шагу; известные source/test baselines; разрешённые test principal/assets. При новом HEAD провести impact reconciliation, а не механически восстановить уже исправленный дефект.

**Выход для перехода:** все запланированные локальные patches либо квалифицированные no-change dispositions имеют review; preservation выполнено; доступные local и shared проверки реально исполнены; существенный FAIL не скрыт; deferred items содержат точную причину, owner, trigger и затронутый claim. Если недостающая capability блокирует следующий лейн, переход к этому consumer запрещён. Независимый следующий шаг допускается с явным ограничением scope.

**Финальная приёмка:** все применимые REQ/TEST/bindings имеют актуальное evidence, нет необходимой незакрытой способности или скрытого SKIP; финальные package/client и cross-lane consumer checks выполнены на согласованном source/artifact. Предметная научная/институциональная квалификация остаётся отдельной и не выдумывается из software PASS.

## Практика параллелизма

- За каждым shared file/contract один интегратор. Остальные готовят отдельные regressions/design deltas, но не конкурирующие варианты helper/lock/registry
- Каждый patch имеет base SHA, write set, dependencies и merge order. После merge на новом HEAD повторить затронутые локальные и shared negatives. Не запускать тесты на worktree, который другой worker меняет
- Default resource envelope из v2: максимум два лёгких test jobs; один native/numerical/embedding/GP/SALib/process-heavy job без других test jobs. Документарная работа может идти рядом. Увеличение только после явной оценки ресурсов
- Shared test fixture/harness один на capability; local numerical oracles не отменяются. Дублирование evidence не независимая реплика
- Установки, credentials, deployment и реальные protected external actions требуют соответствующих разрешений. Комплект не выдаёт новые полномочия
- Native guard assets отсутствуют → точный NOT_QUALIFIED/BLOCKED, а не forced fake encoder/transport/backend success
