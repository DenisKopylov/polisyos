# PolicyOS E02 — финальный комплект заданий v3

**Готов для передачи исполнителю.** Лейны выполняются последовательно по маршруту09, внутри активного лейна — по разрешённым параллельным группам. Код продукта не изменён; будущие продуктовые тесты **NOT_RUN**.

## Начать исполнение

1. **НАЧАТЬ_ЗДЕСЬ.md** — готовый стартовый prompt исполнителю
2. **09_Исполнение/План_исполнения.md** — последовательность лейнов, внутрилейн группы, shared writers и окна отложенной приёмки
3. **09_Исполнение/Состояние_исполнения.json** — заполняемый реестр выполнения и свидетельств
4. **00_Общее/Правила_исполнения_и_приёмки.md**, карта общих владельцев и реестр ограниченных решений
5. Обзор активного лейна из01, его задания из02, интеграционные сценарии03 и точные связи04

**Номер лейна — идентификатор способности, не номер очереди исполнения.** Межлейновые зависимости требуют порядка из09. Завершение локальной реализации не равно окончательному PASS сквозной способности: некоторые реальные consumer/build/generated-client проверки доступны позже. Для них указаны owner, trigger возврата и необходимое evidence. Это не разрешение подменить отсутствующую реализацию моками.

## Что окончательно уточнено

После двух раундов review применены последние три согласованных уточнения:
- UDF-02: pre-replace failure и post-replace directory-fsync failure имеют разные допустимые исходы; откат опубликованных bytes не обещается
- CAL-01/I07-C: source duplicate policy отделена от admissibility target axis конкретной модели; общий binding не вводит случайный запрет
- SCM: краткая общая карта синхронизирована с подробными ролями closure/coordinates, conditioning/refit и native fit→query acceptance

Другие v2 решения, включая обоснованный выбор библиотек, независимые численные oracles и свободное расширение через контракты/профили, сохранены. Точный diff и новые проверки находятся в06.

## Приоритет и история

Корневые00–04 — действующие заданияv3.09 определяет план координации и последовательность, но не отменяет требования к способности/приёмке. Если фактический HEAD изменил зависимости, исполнителю нужно переоценить расписание и явно записать основание, сохранив обязательства.

05 — исходный план, аудит и design decisions.07 — исторический технический review v1→v2.08 — source-led reviewv2, найденные замечания уже внесены в текущие задания. Старые snapshots/proposed replacements внутри истории **не являются альтернативными действующими ТЗ**.06 содержит текущую QA_v3 и отдельно обозначенные исторические проверкиv2.

Основание анализа кода: commit20d9009be21097bfbdc38a546a15cc60213b8ace. Перед реализацией проверить текущий checkout; этот архив не утверждает совпадение с будущимHEAD. Open DEC, доступность native backend, эмпирическая и институциональная квалификация разрешаются в ходе исполнения до зависимых claims, а не выдумываются при упаковке.

Целостность всего финального комплекта: MANIFEST.json и SHA256SUMS.txt. Начать можно с любого исполнителя, которому доступны репозиторий и выбранная среда; архив не предоставляет новых полномочий на push/merge/deploy или доступ к секретам.

Для проверки целостности после распаковки: `python Проверить_комплект.py` из любой директории. Скрипт использует только Python standard library, не запускает продукт и не устанавливает зависимости. Он проверяет hashes/IDs/структуру очереди, но не заменяет инженерную приёмку. Заполняемый реестр09 изменять в рабочей копии: после правок его hash закономерно отличается от неизменённого исходного выпуска.
