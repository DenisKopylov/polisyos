# PolicyOS Development Programs

## Proposed direction

Develop PolicyOS along seven subject-matter trajectories grouped into three families: **usable foundations**, **models and new knowledge about the world**, and **executable policy and choice**. Fund small, complete increments that change the answer to a concrete question and reach a real consumer. Data Forge, Fabric, Foundry, Scientist, Runtime, and Atlas remain the implementation owners.

The initial portfolio should be small: one candidate for the active slice and one prepared source profile. Start with an inexpensive check of the existing path for choosing a final set of measures. If a repaired native alternative-preservation path already retains all actions, scores, and the required downstream use, that is reuse and demonstration, not a reason to commission new code. Direct the next investment to the first genuinely missing class of questions. The Ukrainian Spending profile remains limited to metadata and source semantics: actual rows and an end-to-end link from contracts to payments have not been confirmed. Count shared setup and verification once where the work truly overlaps.

This is a research proposal for discussion. It does not make architectural decisions, change the official status of work, or authorize implementation, data acquisition, spending, or publication of protected findings.

In the machine-readable catalog, new addresses use the `DEV` prefix—for example, `DEV-E1`, with the shorter `E1` label in prose. These are navigation identifiers for this proposal, not official task IDs or decisions.

Seven trajectories do not mean seven teams or seven simultaneous launches. A numerical experiment, training in a research procedure, human competence, and a bounded answer from a data owner each need their own conditions before they qualify as separate investments. Until then, their concrete work belongs in an increment of the main trajectory and should not receive a second budget.

Result provenance and freshness, independent verification, and operational guarantees remain shared conditions with separate owners and costs. They do not form a new universal program layer. Legal applicability, financing for Ukrainian projects, and company knowledge for business agents remain explicitly selectable application branches with their own consumers and constraints.

## Why this grouping

Grouping by technical layers helps allocate code, but lets each layer finish without producing a useful answer. A complete stack for every industry gives a quick demonstration but multiplies sources of truth, repeats verification, and makes the next case expensive. One universal “evidence lifecycle platform” simplifies the diagram but hides the differences between extraction, causal identification, forecasting, normative choice, and human understanding.

The selected structure preserves durable scientific questions while allowing small end-to-end deliveries. Check its boundaries with a second, substantively different case: if central owners must be rewritten or the earlier verification does not transfer, revisit the boundary. Do not derive the number of programs from the number of GV areas, modules, old phases, or research tasks.

## Where to start

### First profile: a jointly admissible set of measures

A fully specified finite model contains three abstract measures, two outcomes, a monetary constraint, and a shared resource. It answers: which sets are admissible, which are non-dominated, and how does an explicit choice of values change the preference? Its coefficients are model values; the result is not presented as the effect of a real reform.

An existing foundation is available: Scientist preserves candidate identity, score vectors, and references in ParetoRegistry, while the controller reads the stored frontier. Use this path first. Do not declare Foundry NSGA2 the sole optimizer: its output preserves one selected action vector and retains the other alternatives only in objective coordinates. Whether a bridge is needed depends on the selected consumer.

The reference answer is an exhaustive evaluation of the eight sets with an explicitly stated selection function. First check whether the existing path preserves the actual actions, constraints, and scores through reload. If so, classify the result as reuse; otherwise, estimate only the concrete missing function. No new simulator is needed. For the scenario in which E02 repairs are complete, use the exact B109–B111 results for the required path. If that work is delayed, a separate finite-model demonstration through an existing supported owner and profile remains possible, or an explicitly separate analytical reference result, without claiming that the whole user journey is ready.

### Second profile: contract amounts and observable counterparties

For one preselected buyer, period, and set of documents, the Spending profile asks: what contract amount and what degree of counterparty identification does this exact set support? Which parts are observations, and which result from a transformation rule?

The existing normalizer divides each contract amount equally among its listed suppliers, then aggregates rows by buyer, supplier, and period. That allocation is not an observed payment to each supplier. A contract, obligation, transaction, and performance report also remain distinct objects. The first result is therefore a checkable description of the source and its limitations; it does not establish actual budget execution, a causal effect, or the existence of funding.

The reference is a manual calculation from original document identifiers that preserves currency, dates, and uncertain identity. Separate checks distinguish a contract with multiple suppliers, a hidden identifier, and a duplicate document. Reuse existing Data Forge builders, normalizers, and artifact reads. The metadata check confirmed that an old observation panel exists, but did not confirm that its rows were read, that it has the required units, or that a compatible reader run completed. Retained D0 failed after retained D5 completed, so they do not establish a coherent successful release. The first result here is a prepared source-semantics profile; access to a real bounded input and a final consumer remain conditions for a future empirical demonstration.

See the [initial portfolio](first_portfolio.md) for the detailed specification, alternative observation profile, and conditions for changing the order.

### Conditions for changing the order

- If a usable numerical result already exists but a consumer loses its meaning, first complete the narrow path that carries that result into use.
- If a mature forecast and an independent observation of its consequence are available, M2 may start before a data-acquisition campaign: a useful O1 diagnosis need not wait for O3.
- If the main constraint is a missing measurement or causal premise, prioritize E2 over a new optimizer.
- If a fixed finite set of measures cannot answer the needed question, open a bounded adaptive-rule path under P2; clarify its carrier and consumer first.
- If a complete repeated calculation is genuinely expensive, select one numerical acceleration or reuse method that preserves the question.
- If no available source supports the claimed result, retain the useful model or source work and leave the missing empirical result open.

## What changed after reading the source

PolicyOS already has a ledger, Research DAG, VOI mechanism, memory, verification tools, publication for different audiences, PER_CELL and household-cell materialization, ObservationRecord, measurement-weighted calibration, Ukrainian D0–D5 builders, and legal temporal structures. Planning those again would be a mistake.

The main gains lie elsewhere: suitable real inputs, correct scientific meaning, preservation of the complete action or rule, a concrete consumer, and independent verification. Some gaps are small code changes. Others need a new measurement profile, a discriminating experiment, or a mathematical formulation. The existence of a mechanism does not make this work routine interface wiring.

Several boundaries matter especially:

- DP computes the complete rule inside the method, but the named output preserves the value function and one random trajectory. Keep the small adaptive increment budget paused until the preserved rule and its consumer are clarified.
- C7 returns a relative partial hazard. An absolute event probability over a horizon needs its own premise and output quantity.
- The measurement-aware adapter is actually applied, but its quality multipliers are not a general model of censoring, measurement error, or causal identification.
- The Ukrainian synthetic producer creates proxy household cells; the existence of links and aggregation does not prove that joint household composition is preserved.
- A real observation panel and a separate demonstration-method contract may be different artifacts. In the inspected D2 producer, some numerical contracts are built from synthetic sequences.
- A signature, correct link, literal match, or successful delivery does not replace semantic, scientific, or institutional adequacy.

## How to read effort estimates

All ranges are hypothetical normalized effort units, **not forecasts of PolicyOS coding-agent time for Denis**. They separately account for input research, architectural and scientific decisions, code, integration, independent verification, external waits, and operations. Do not add ranges across cards to estimate the cost of PolicyOS.

Earlier broad estimates for adaptivity and the human interface were revised to match their exact scope. With tools ready, a narrow CB2 slice is conditionally estimated at 5–15 normalized days; human research is excluded. The 20–40-day estimate for a small adaptive rule remains paused because its assumed ready carrier and consumer have not been established. For a process with definitions and a QueueDES profile already in place, the conditional 20–40 days cover only a narrow comparison; building a full observation model and reusable process class needs a separate estimate.

Verification for each first increment is already included in its cost. Do not add a separate “general scientific evaluation” budget on top of the same reference answers, corpus, and control cases. Give research into evaluation itself a separate budget only when the question is genuinely new.
