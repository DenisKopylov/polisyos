# Распределение облачных тестов E02

Дата: 4 октября 2026 года. Получатель: Денис и локальные исполнители E02. Тариф: Pro $200.

**Актуальное распределение от 5 октября:** [полный прогон F01–F15](full-run/README.md) заменяет поэтапный dispatch ниже. Он включает повтор всех четырёх пилотов, 560 текущих Python-файлов, 1 514 исторических запусков и отдельные native/gate команды с бюджетом около 3–4 часов на VM. Ниже сохранён первоначальный план и его исходные матрицы.

**Организация работы с кодом:** [E02: шесть предметных групп и интегратор](execution-organization/README.md), с полной картой владельцев 127 пакетов и 282 ID, распределением локальных/облачных проверок и правилами передачи результатов.

Этот документ распределяет сбор фактического поведения E02 между облачными задачами, чтобы исследование и исправление кода продолжались локально. **Для первого сбора рекомендованы 20 задач Q01–Q20 на одном актуальном срезе: сначала четыре пилота, затем десять одновременно работающих VM.** Историческое сравнение четырёх ревизий отдельно распределено по C01–C20; его использовать для требуемого E02R2 replay и атрибуции, а не автоматически добавлять к первому исследованию. Отдельные смысловые проверки запускать по готовности входов. Число задач, параллельных VM и процессов внутри VM — три разных величины.

Это план запуска. В ходе его подготовки облачные задачи и продуктовые тесты не запускались. Оценки времени не являются облачными измерениями. Наличие маршрута проверки для каждой записи не означает, что её требование уже проверено или исполнено.

## Что уже установлено

Исследование кода и пакетов привязано к `69780761ae091d8fcc6ab8778c7f5f7227eeef0b` в рабочем дереве `main`. Ветка этого чата — `docs/raw-evidence-ignore`, исходный HEAD `78187878ee188ff6d27442ba1498bd094da9785b`; она содержит более раннее состояние. Поэтому команды ниже выполняются в облачной копии нужного SHA, а не произвольно в каталоге этого чата.

**E02 имеет 282 исходные записи, а не 282 самостоятельных запуска:** 225 B и 57 LA распределены между 127 рабочими пакетами. В `source/card_index.json` также есть восемь S-направлений; они не добавляются к знаменателю 282. Из 127 объявленных тестовых путей существуют 85. Это полный обход манифеста и исходных индексов, выполненный корневым агентом; знаменатели и проверка распределения сохранены в `verification.json`.

Текущий `residual_ledger.json` сохраняет 9 `closed`, 260 `partial`, 12 `held`, 1 `open`. Здесь эти статусы воспроизведены как содержимое реестра, а не переаттестованы тестами. Для каждой записи следует читать её `residual`; `p_triage.next_step` использовать только там, где triage заполнен. Полный обход реестра показывает 117 заполненных triage и 165 null. Исходное поле `initial_status: planned` не описывает текущее состояние. В частности, B09 требует второго обслуживаемого N5, который потребляет действительно изменившийся допущенный basis; смена UUID или времени не заменяет этот свидетель.

**Есть готовый знаменатель регрессионного сравнения:** подготовленная E02R2 матрица включает 483 уникальных Python-файла × четыре ревизии = 1 932 ячейки. Полная проверка каждого `SHA:path` через Git подтверждает 1 518 существующих и 414 отсутствующих файлов. Четыре существующие ячейки имеют установленное ограничение безопасности, поэтому план содержит 1 514 предлагаемых запусков, а не 1 932 тестовых процесса. Матрица до этого не запускалась как единая волна.

Последний тестовый cut `0213101b6d124e6f855b1aff7c442bb0912a61c2` и исследованный `main` отличаются двадцатью документационными путями. Полный diff показывает ноль изменений в `src/`, `tests/`, `tools/` и перечисленных конфигурациях Python/pytest/pnpm. Это позволяет использовать кодовую карту, но не переносить результаты документационных валидаторов: они также читают документы.

У исходного Combined package есть checksum drift: `SHA256SUMS` ожидает для `EXECUTION_GUIDE.md` digest `fd934552…49fb87`, а bytes на research SHA дают `4b4a6689…c04d0f`. Это воспроизведено чтением обоих owner-файлов через Git, без исправления пакета. Перед использованием его собственного admission verifier потребуется согласованный package manifest; данное распределение проверяется независимо по полным исходным множествам.

## Лимиты и размер облачной машины

Короткий ответ уменьшает только часть расхода: в токены входят запрос, контекст, прочитанные файлы, результаты инструментов и ответ. Официальная документация не устанавливает для этого проекта универсальный множитель «облако дороже локальной работы». Экономия в предложенном формате достигается короткими заданиями, фиксированными командами и сохранением больших логов в файлы. Конкретный расход включённых лимитов нужно измерить на пилоте. [OpenAI Pricing](https://learn.chatgpt.com/docs/pricing)

Снять usage перед и после пилота вместе с elapsed и числом выполненных ячеек; учесть остальные активные чаты, поскольку лимиты общие для аккаунта. Полученная дельта остаётся оценкой при параллельной работе. Агент запускает подготовленный runner одной командой и читает компактный итог; повторное исследование кода и разбор каждого падения остаются локальной работой.

Текущие спецификации для Pro — 4 vCPU, 16 GiB RAM и 32 GiB диска на облачную задачу. Опубликованное окружение даёт каждой задаче собственное рабочее пространство. Это спецификация сервиса, а не измерение уже выделенной VM: фактические CPU/RAM/free disk фиксируются перед запуском. [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments)

Не выбирать число VM по желанию держать CPU на 100%. Цель — число полезных проверенных ячеек в минуту при воспроизводимых входах. Начать с одного pytest-процесса на VM и численных thread limits = 1; пилот отдельно сравнивает два изолированных процесса. Повышать до четырёх можно только по измерению throughput, памяти и отсутствия конфликтов. Native/JAX, один DuckDB writer, один CAS/canonical head и один фиксированный серверный порт сериализуются в пределах своего ресурса.

| Режим | Параллельные VM | Процессы на VM | Назначение |
| --- | ---: | ---: | --- |
| Пилот | 4 | 1; отдельное сравнение с 2 | Проверить Linux setup, сбор результатов, cold/warm время и расход лимитов |
| Основная волна | 10 | 1 по умолчанию | После четырёх пилотов — очереди из десяти и шести частей; измеренный безопасный режим применяется отдельно |
| Ускоренная волна | 15 | После пилота | Если одновременно доступно столько задач и перенос результатов устойчив |
| 20 или 30 VM | Пока не рекомендовано | Не установлено | Сначала измерить реальные места, расход и выигрыш; доступность не предполагается |

Локальный семиединичный Mac-бюджет E02 продолжает применяться к локальным процессам. Он не является описанием суммарной мощности независимых облачных VM. Облачный ресурсный контракт должен явно заменить адреса, OS-метрики и правила очереди прежнего Mac-harness; старый bound manifest нельзя выдать за уже допущенный облачный запуск.

## Проверки сверх основной матрицы

Регрессионная матрица показывает поведение существующих проверок, но не исчерпывает дискриминаторы карточек. Дополнительные задачи имеют собственные входы и не получают фиктивно равного времени ради таблицы. Подробная привязка пакетов и конкретных команд находится в [bundle-catalog.md](bundle-catalog.md); маршруты всех B/LA — в [coverage.csv](coverage.csv).

D01–D04 — четыре семейства работ, не четыре заранее равные готовые задачи. После подготовки inputs/проб их конкретные целые файлы и неделимые normal/removal/restore triads распределяются по измеренным блокам около 25 минут в разведочном режиме или 90 минут в историческом. Известный длинный gate/triad выделяется отдельно. До этих измерений число D-запусков и равенство их длительности `not_established`.

Для D04 protected handwritten schema, DDM R2 и различные calibration роли сохраняют свои действительные discriminator tests.

Если требуемый положительный producer/bridge или diagnostic probe отсутствует, результат задачи — точный reproducer и `producer_missing`, `bridge_missing`, `artifact_missing` или `semantic_test_missing`, согласно фактическому разрыву. Не поручать облачному исполнителю придумывать производственную authority, signer, epoch или допустимость.

## Пилот и выравнивание времени

Для рекомендованного режима Q пилоты указаны выше. Если выбран сразу исторический режим C, его первые четыре полные части — **C15, C03, C07, C01**. В них включены recursive epoch gate, generation cycle, native fit, calibration, CAS и прочие назначенные файлы; все части также содержат смешанный фон из остальных областей. После пилота выбранного режима остаются шестнадцать частей: первая очередь из десяти, вторая из шести. Отдельных повторных пилотных заданий для той же матрицы не требуется.

Дополнительно в одном пилоте коротко сравнить один и два независимых Python-процесса на непересекающихся sandbox roots, используя два малых файла из его собственного списка. Это отдельно обозначенный повтор для измерения throughput, не новая evidence-ячейка. Пилотные ячейки с тем же SHA/lock/env/test blob принимаются в общий результат и повторяются только при изменении входов.

Замерять installation/setup, collection/import, test execution и export отдельно. Для планирования брать wall time целого файла; pytest `--durations` не учитывает все imports и setup. После пилота заменить предварительные веса median cold/warm wall time с той же VM/OS/profile. Учитывать максимум по историческим ревизиям, а не считать одинаковые пути одинаковыми тестами.

Пересчитать оставшуюся очередь методом longest processing time: сначала самые дорогие пары/связанные файлы, каждый следующий — в совместимую часть с наименьшей суммой. Файл × четыре ревизии сохранять вместе для простой атрибуции; если он один превышает целевую длительность, выделить его отдельно, не резать произвольным selector. Близкие веса — свойство планового распределения, а не доказательство равного реального времени. Не дополнять быстро завершившуюся задачу лишними повторами ради загрузки CPU.

## Подготовка окружения

Использовать опубликованное Linux-окружение с Python 3.14.x, Node 22.x и uv 0.9.21. Baseline contributor rules и фактические lockfiles читаются из pinned источников. Python-профили runtime/research и Node-профиль готовятся один раз в окружении; каждую ревизию тестировать на явно записанном dependency profile. Для причинной атрибуции изменения кода нельзя незаметно менять зависимости между endpoints.

```bash
# В policy-engine/ выбранной cloud-копии. Это provisioning, не тестовый результат.
UV_NO_BUILD_PACKAGE=pillow uv sync --frozen --extra lint --extra test --extra runtime
corepack pnpm install --frozen-lockfile
```

Core JAX уже входит в базовые dependencies; `ml`, `sensitivity`, `analytics`, `bayesian`, `optimization-advanced`, `vector-search` и другие extras выбираются по назначенным импортам и tests. Research/native extras добавлять по реальным требованиям выбранных файлов; не устанавливать `all` в каждой задаче. В свежей Node-копии pnpm links обязательны до TypeScript scanners. Для `hnswlib` нужен C/C++ compiler. Python-version markers исключают EconML/DoWhy из части extras на 3.14; такую поверхность нельзя аттестовать importorskip. `Dockerfile.reproducible` на исследованном cut использует Python 3.11 и не является готовым образом этого плана. Linux DuckDB extensions устанавливаются/проверяются как Linux payload; macOS arm64 кэш не переносится. pytest, conftest, lockfiles, installed packages и загруженные module origins входят в receipt. SKIP/importorskip из-за отсутствующего обязательного extra не закрывает назначенный дискриминатор.

Репозиторий требует минимум 20 GiB свободного диска перед новым environment/install/build. У Pro default disk 32 GiB; доступный остаток после профиля надо измерить. Если floor не соблюдается, это ограничение окружения: сократить независимый profile или использовать больший runner, а не снижать floor молча. Четыре checkout и сборка могут оказаться слишком велики для одной default VM.

Все четыре commit objects должны быть действительно доступны в cloud Git checkout; одного имени ветки или локального наличия SHA недостаточно. Не менять целевую ревизию при недоступном object. Для repo-quality проверить также sixteen foreign-document inputs прежнего freeze: source cut содержал их вне tracked tree, и одного Git clone недостаточно для восстановления этих входов. Они получают отдельный manifest/transfer receipt, либо соответствующая ячейка остаётся UNRUN.

`production_data`, local scratch evidence, расширения и секреты не появляются в облаке от самого клонирования Git. Требуемые данные передаются через явно разрешённый артефактный канал с manifest/hash; при отсутствии входа ставится `UNRUN/environment_unavailable`. Запрет копирования production data для safety-skipped `test_data_state_substrate.py` сохраняется во всех четырёх ревизиях.

Облачная Linux-проверка не аттестует Apple Metal, macOS, настоящий PostgreSQL без сервиса, live HTTP без сетевого допуска, LLM-вызов без разрешённого профиля или UI браузерного продукта. Эти поверхности имеют отдельный environment matrix и не заменяются фикстурным PASS.

## Команды и формат результатов

Базовая команда одной предлагаемой ячейки, `cwd = <checkout>/policy-engine`. В режиме Q `<TEST>` берётся из назначенной записи **jobs-current.json**, cut — `research_main`; в режиме C — из **jobs.json** и её `run_refs`. В команде убирается только префикс `policy-engine/`. `<CELL>` включает mode, job ID, полный SHA, SHA256 полного test path и уникальный attempt ID; это отличает одинаковые basename и повтор измерения. До dispatch создаются выходной каталог и отдельный basetemp; существующий output не перезаписывается.

```bash
.venv/bin/python -m pytest -c pytest.ini <TEST> \
  -o cache_dir=_build/cloud-e02/<CELL>/pytest-cache \
  --benchmark-storage=file://./_build/cloud-e02/<CELL>/benchmarks \
  --basetemp=_build/cloud-e02/<CELL>/tmp \
  --junitxml=_build/cloud-e02/<CELL>/junit.xml --durations=20 -ra
```

На ревизии, где доступен соответствующий интерфейс, переиспользовать `tools.quality.testing.run_timed_suite` с `--capture-pytest-workload` и `--receipt-output`: он связывает реально собранные nodes, байты тестов и config с временем того же дочернего процесса. Это ещё не producer загруженных module-origin receipts и не полный Linux-порт Mac executor. Для старых cuts инструмент не предполагается доступным; runner/instrumentation должны иметь собственный pinned origin, не подмешивая новый product source в старый `PYTHONPATH`.

Каждый запуск сохраняет `stdout.log`, `stderr.log`, JUnit, timing/resource JSON, import-origin JSON и source/env/request manifest. Сводка должна содержать job/cell, SHA, test blob, argv/cwd, env/lock digest, collected identities, counts PASS/FAIL/ERROR/SKIP, exit, termination reason, wall/CPU/RSS, refs на входы и SHA256 каждого output. Exit 0 без полного collected/JUnit receipt не доказывает, что выполнен нужный набор; collection error, timeout и убийство по ресурсу остаются отдельными исходами.

Большие логи сохраняются в архиве `raw/`, а в чат возвращается 10–20 строк и ссылки на скачиваемые файлы. Один текстовый PASS-summary не заменяет raw evidence. До освобождения VM локальный получатель скачивает результат и проверяет hashes, полноту ячеек и module origins. Если облачная поверхность не позволяет выгрузить raw files, пилот ещё не завершён; VM-state не используется как единственный архив.

### Задание облачному исполнителю

> Выполни только назначенную задачу Qxx из jobs-current.json (первый сбор) либо Cxx из jobs.json (историческое сравнение) на указанных immutable SHA и подготовленном Linux profile. Выбранный режим указан в dispatch; второй автоматически не запускай. Не исправляй код, тесты, snapshots, lockfiles, canonical artifacts или authority. Не запускай другие задачи, рекурсивных агентов или повторные full suites. Проверь входные hashes и наличие всех назначенных путей. Существующие разрешённые ячейки выполни целыми файлами, отдельным процессом, сохраняя полный вывод/JUnit/origins/timing в уникальные каталоги. Для MISSING, safety UNRUN и environment-unavailable сохрани причину. При падении продолжай независимые ячейки, если ресурсы и custody исправны; не исследуй и не лечи причину. Не печатай весь лог в контекст. Верни короткую сводку, hashes, список незавершённых ячеек и доступные архивы результатов. Ошибка проверки входов прекращает только зависимую часть.

## Использование фактов локальными исполнителями

Локальному исполнителю передаются карточка B/LA, текущий residual, связанные результаты C/D, exact failing identity и raw log. Он сначала воспроизводит затронутый путь, затем проводит wire-existing → extend → consolidate → build-new. После изменения отправляет в облако только blast-radius delta; CP1–CP6 проводятся на принятом integration SHA по соответствующим свойствам, а полная дорогая wave резервируется для closeout.

P41: красный исход считается inherited только после точного replay на базе, предшествующей собственным изменениям slice, и проверки полного input denominator. Исторические четыре cuts дают материал для атрибуции, но не являются автоматическим доказательством нужной slice base. Если test bodies, dependencies, loaded owners или semantic identities различаются, comparison получает `not_established` с конкретной причиной.

План не переводит ни одну B/LA запись в closed. Для закрытия нужна индивидуальная связка discriminator → реальный producer → persisted artifact/event → bridge → consumer → внешняя/audit поверхность или явный out_of_scope → отрицательная проверка.

## Проверка плана и ограничения

Pattern pass: P01/P02 — у каждой записи есть маршрут к runtime/evidence, а missing bridges названы; P29/P32/P37/P38 — сравниваются действительные nodes и свойства, не слова PASS или имена полей; P35 — полные множества 282/127 и 483×4 пересчитаны; P41 — refs, test bodies и среда не смешиваются. Сохраняемые ограничения: cloud executor bridge и Linux environment/transfer verification ещё не исполнены; отсутствующие discriminator probes имеют `semantic_test_missing`. Отсутствие проверки не является отрицательным результатом продукта.

`coverage.csv` даёт полный finding → bundle → candidate regression route, а каталог сохраняет действительный discriminator owner-пакета и дополнительные пробы. Это плановая трассировка: точное соответствие каждого finding реально собранному node и достаточность его runtime evidence пока `not_established`. В частности, наличие пути, конструктора DTO, import identity или mocked producer не закрывает этот разрыв. Предлагаемые relocation paths перепроверяются на dispatch SHA; старый список перемещений не считается фактом выполненного cutover.

До массового запуска необходимы успешный environment/transfer pilot, проверенный Linux resource adapter и frozen argv/inputs. Это технические входы запуска, не новое разрешение на планирование. Никакой облачный runtime или cost receipt в данном документе не заявлен.

Источники: пакет `PolicyOS_E02_Combined_Agent_Package` (`bundle_manifest`, индексы B/LA, bundle IDs и LK/CP); E02R2 `residual_ledger.json` (индивидуальные B/LA findings), `BASELINES.md`, `HANDOFF_EVIDENCE.json`; failure register P01/P02/P29/P32/P35/P37/P38/P41. Все локальные source pins и решающие результаты проверки перечислены в `verification.json`. Raw matrix не встроена вторым многомегабайтным представлением: jobs-current.json содержит первый актуальный сбор, jobs.json — независимое историческое распределение.
