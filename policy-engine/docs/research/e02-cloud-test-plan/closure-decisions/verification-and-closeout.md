## Принцип приёмки по строке матрицы

Для новой функциональной приёмки зафиксировать exact candidate commit/tree и source/module origins; воспроизвести дискриминатор исходной карточки положительным случаем; сравнить с независимым oracle; добавить отрицательный/adversarial случай и «удалить runtime property, сохранить маркеры»; дойти до настоящего consumer либо fresh-process persisted readback, если именно это часть свойства. Для истинно локального свойства использовать фактический публичный caller и не добавлять несуществующий persistence контракт. Поле, имя метода, hash-синтаксис, caller-provided flag и зелёный exit-code не заменяют реальное условие. Каждый result должен сохранять stdout, stderr, код выхода, wall time, точную среду, HEAD/tree, selectors и необходимые artifact refs; большие deciding logs идут в ignored `raw/` и цитируются SHA-256.

Это **не** означает four-base replay и production corpus для каждой строки. Production input требуется только если содержание конкретного source criterion зависит от реальной истории, owner-issued source, настоящей measurement law, сервиса/профиля или заявленной политики; тогда перечислить ровно минимальные входы и owner. Если их нет — `UNRUN` и точная причина/команда, которая разрешит вопрос. Нельзя превращать синтетический fixture в factual evidence, но и нельзя объявлять отсутствующий optional backend product failure.

**B151 / CAS-01 пример:** проверить на exact candidate corrupt-put/retry-control: после повреждения сохранённых bytes совпадающая повторная запись не должна ложно принять corrupt payload; независимый byte/hash/readback oracle подтверждает реальное содержимое; первый write и валидный retry — положительные controls; fresh-reader consumer видит точный исход. Отсутствие исторической P41 матрицы не мешает доказать эту новую функциональную характеристику. P41 нужен только если кто-то утверждает, что уже существующая красная проверка была унаследована: replay ровно на literal slice base, той же командой/средой, с полным gate-input denominator и нулевым пересечением входных путей с изменёнными путями. Иначе attribution остаётся `not_established`.

Для P40 повторный результат классифицируется как новый класс или тот же класс уровнем глубже. На втором результате одного класса остановить patch-ladder: расширить invariant на необходимый объём либо назвать ограниченный остаток, минимальную отсутствующую способность и falsifier. Для P37/P38 записать, что predicate решает, чем код его измеряет, и конкретный расходящийся случай; внешне supplied fact маркируется отдельно и не повышается до recomputed.

### Первичные технические источники

- [BoTorch 0.18.1 models](https://botorch.readthedocs.io/en/v0.18.1/models.html): `condition_on_observations` добавляет наблюдения к существующей модели; это не подтверждает конкретный source owner's restore/fit semantics без readback конкретной модели.
- [JAX higher-order derivatives](https://docs.jax.dev/en/latest/higher-order.html): Hessian вычисляется через производные; численно вычисленный inverse curvature сам по себе не становится inferential covariance для любого loss.
- [SALib Morris sampler source docs](https://salib.readthedocs.io/en/latest/_modules/SALib/sample/morris/morris.html): Morris траектории/число уровней — часть метода и требуют whole-trajectory denominator, а не top-k summary.
- [NetworkX DAG predicate](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.dag.is_directed_acyclic_graph.html): графовая проверка относится к конкретному объекту directed graph; conversion/readback формата проверяется separately.
- [DoWhy refutation guide](https://www.pywhy.org/dowhy/v0.14/user_guide/refuting_causal_estimates/index.html): refutation анализируется поверх идентифицированного/оценённого estimate, не заменяет assumptions или native backend input admission.
- [EconML DML specification](https://econml.azurewebsites.net/spec/estimation/dml.html): DML требует cross-fitting / nuisance models и target-effect semantics; callable/marker fixture не доказывает native estimate.
