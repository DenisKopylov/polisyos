# G — Непрерывная интеграция и независимая приёмка

Перед любой работой полностью прочитай как обязательные task instructions `policy-engine/docs/research/e02-cloud-test-plan/execution-prompts/HANDOFF.md` и корневой `AGENTS.md`. Ты — локальный интегратор G. Стартуй немного раньше A–F и работай параллельно до closeout. Активно заполняй до 20 прямых субагентов; при сомнении делегируй отдельную полезную проверку. Единственный publisher интеграционной ветки — G. Параллельно веди разные поступившие slices и раздельные вопросы: ancestry/receipt/input identity; owner/diff/companions; runtime property; independent oracle/adversarial discriminator; consumer/API/surface; deciding outputs/limitations. Пример для большой очереди — три slices по шесть вопросов и два помощника по dependencies/local-check queue; перераспределяй роли по реальной сложности, не создавай шесть reviews каждой мелкой правки. До первых handoffs картируй consumers и готовь defining checks. Автор не рецензирует собственный код как независимый reviewer; helpers не пишут в integration branch и не создают своих субагентов. Прочитай `policy-engine/docs/research/e02-cloud-test-plan/execution-organization/README.md` и полный result pack. До использования результатов запусти `python3 policy-engine/docs/research/e02-cloud-test-plan/results/import_results.py --check`, затем проверь `verification.json`; результат importer — фактическая проверка целостности входов, чтение JSON само по себе её не заменяет. После этого используй `python3 policy-engine/docs/research/e02-cloud-test-plan/results/query.py --failures-only --limit 30` и точечные запросы, не выводя ownership из коротких summaries. G не получает bundle/findings как самостоятельный code owner.

Создай локальную ветку `codex/e02-integration` от записанного published base SHA. G — единственный publisher этой ветки. На каждый поступивший slice fetch-ь точный remote topic head/PR из Git; прочитай committed `policy-engine/docs/research/e02-cloud-test-plan/implementation-handoffs/<unit>/<slice>.json`, проверь base/candidate/tree SHAs, ancestry, полный diff footprint включая tests/companions, canonical writer, property witness, negative control, decisive output и limitations. Каждый reviewer читает immutable candidate SHA/tree, а тестирующий получает изолированный checkout и локальный compute slot. Не регулируй число тяжёлых прогонов B/D/E/F в облаке; ограничивай только совместную нагрузку локальных A/C/G. Review старого head пригоден только для неизменившейся части: при новых commits перепроверь delta, её dependencies и evidence, без полного повторного review всего пакета. Review входящих PR/коммитов идёт параллельно; принятые commits добавляй в интеграционную ветку последовательно и append-only, сохраняя оригинальную историю. При конфликте верни поправку каноническому владельцу. Не переписывай upstream историю.

Публикуй интеграционные checkpoints как `codex/e02-integration`; A–F узнают их через fetch, поэтому не предполагается никакой автоматической связи между чатами. Помогай согласовать 4 declared implementation edges из плана и фактические consumer impacts. Приёмка кода отдельно от closure finding: локальные production-dependent проверки ставь только там, где этого требует criterion, на read-only data и exact candidate. Не переноси dataset в cloud и не требуй его повсеместно.

Не запускай broad regression после каждого merge. Повторяй affected consumer/defining-property checks после изменившегося upstream contract, сохраняя точные receipts; общий дорогой replay и data-dependent closeout проведи один раз после freeze integration SHA. Финальный отчёт различает accepted commits, findings closed/limited/held, unavailable inputs, skipped backends и remaining verification. Пуш в `main` не разрешён; будущая main публикация требует отдельной явной авторизации.
