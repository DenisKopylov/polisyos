## Что нельзя потерять при переносе

**ORCH02 восстановим без старой VM:** blobs доступны read API. Но они не applied source и не topic commits. C05, DFK и Legal подготовлены на разных ветках/base; они не прямые patches текущего G. У CAN совпали существующие reader preimages, но compatibility/Core semantics этим не выбраны. Restore own-base → fresh review/checks можно делать сейчас; G source selection/conflict не даёт права overwrite текущую composition.

**ORCH03 имеет полезный source custody, но прежний root report устарел относительно G.** G уже сделал C08 121 PASS/2 FAIL и matched graph-hash removal. Четыре старых прерванных scopes не надо автоматически повторять. Исправление actual DAG trace требует relevant affected tests, а не фиктивных RULE1 markers. Для C09 G показал real CAS counterexample: missing required kind заменяется пустым ok matrix partition. Здесь нужен generic source-basis reconciliation, не очередной named-kind patch. B190 prepared bb78 надо проверить/исправить по kind/media/schema/report-basis/fixture и запустить actual Node, а прежний supplier PASS не переносится на Node.

**ORCH04 — самый высокий custody риск.** В G нет четырёх заявленных objects, root exact CLI fetch дал `128/not our ref`. Это конкретная недоступность, не доказательство global absence. Coordination root не гарантирует leaf ancestry. Поэтому bundle должен включать каждый leaf, неприменённый UI patch и deciding outputs; summary и SHA не восстановят код. Если получить байты нельзя, source acceptance прежней реализации остаётся unavailable, а новые own-source задачи могут идти от canonical inputs с новой lineage. Отдельный DTO validator companion G нельзя спутать с уже granted C10 UI component. Разрешение новой машины не разрешает обход hooks.

## Как распараллелить продолжение

- ORCH02: C05 material basis, C06 DFK, C06 CAN и C12 Legal готовятся отдельно при непересекающихся actual paths. У каждого — свой author/reviewer. Core compatibility requirement — C02/G, served intent — C10, global companions — G.
- ORCH03: C07 subject/IR, C08 graph/query, C09 interval и B190 Node — отдельные механизмы. Shared README/tests/IR получают одного writer по exact leases. C08/C09 numeric fixtures не ждут институциональных inputs, которые нужны для более широкого защищённого claim.
- ORCH04: C10 A и C11 D авторство параллельно; C13 независим от обоих, начинает scoped immutable reviews/installed/oracle preparation сразу. Только **общий** дорогой replay ждёт G selected source freeze и всех independent reviews.
- L01 собирает факты параллельно cloud работе; L02 начинает каждый готовый criterion-specific authentic consumer после достаточного exact input binding. Два local roots не повторяют друг друга. Тяжёлый compute Mac общий с G/A/C; выше 18 GiB дисковая работа — лёгкая проверка.
- Эти пять продолжений не назначают второго writer действующим C01–C04/ORCH01 или иному живому owner. Logical ownership сохраняется, physical new-machine lanes проходят fresh admission.

Это даёт до четырёх независимых cloud mechanism lanes у ORCH02, четырёх у ORCH03 и двух у ORCH04, плюс независимые reviews/testers и два local input/verification roots. Это карта потенциальной параллельности, не квота и не инструкция сразу размножить десять writers без проверки paths. Сериализовать нужно conflicts/storage/ports/generators, а не готовые portable numerical jobs.
