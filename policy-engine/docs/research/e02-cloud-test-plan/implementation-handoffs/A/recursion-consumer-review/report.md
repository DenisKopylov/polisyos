## What the served path can and cannot do

A6 requires an actual graph with two meaningful children, a stop after child one that preserves its output and an incomplete/frontier record, and a one-child completion control (`closure-decisions/A.md:94–100`; B15 source excerpt in `CYC-05.md:46–63`). In the pinned source, `POST /api/v1/control/runs/nl` reaches the HTTP recursive compiler (`routes/control.py:369–404`). The HTTP budget is currently `max_depth=0`, `max_nodes=1`, and at most three N6 cycles per leaf; `requested_max_iterations`, the effective value, recursive projection, and clamp reason are retained in `RecursiveBudgetResolution` (`services/control/generation_cycle.py:129–179`, `1253–1279`). That makes the leaf-cycle clamp observable, but it does not admit a multi-node graph.

The `RecursiveDesignGraph` schema and `derive_recursive_design_graph` builder already carry node refs and edges, but the builder only binds supplied refs; its authority boundary explicitly forbids using a replay graph as decomposition-validity evidence without a coupling graph (`design_axes/coupling_composition.py:228–242,404–435`). The ordinary HTTP compiler calls the builder with `module_refs=()` and `parent_child_edges=()`, then invokes the controller with only `{root_ref: problem}` (`services/control/generation_cycle.py:1137–1153`). This is an A-owned producer/bridge implementation gap: the CYC-05 criterion specifies two meaningfully defined children and their relationships, and its candidate write paths are A's HTTP/compiler/lifecycle/controller modules (`CYC-05.md:11–19,21–30,55–60`). No separate scientific-owner contract is blocking that implementation. A real provider still must derive distinct child problems and bindings from admitted, protected owner context and actual coupling evidence; the harness must not fabricate them.

The controller validates the entire node denominator before routing. If `len(node_refs) > max_nodes`, it raises `recursive_node_budget_exhausted` before starting a leaf; it also requires `problems_by_node` to cover exactly the graph (`recursive_generation_cycle.py:816–824`). It awaits each child before the parent (`:1222–1247`). Therefore `max_nodes=2` on root+two children does **not** stop after child one; it rejects the graph before either child. Raising `max_nodes` to three admits the whole graph but is not an execution-progress cap.

The persisted `RecursiveGenerationCycleRun` is a complete-graph artifact: `nodes` must equal the graph's node set and edges, and each leaf must carry a `cycle_run` (`recursive_generation_cycle.py:219–255, 346–416`). It has no unexecuted-child/frontier/checkpoint representation. A child-two exception after child one would also prevent assembly of this final run; the in-memory first result is not the required persisted partial artifact. Thus the missing property is a genuine stoppable, persisted frontier with preserved child output, not another cap field.

The CYC-05 unit fixture is not a served producer witness and was not run. It calls `WorkspaceLoop.decompose_fixture` with the same fixture ID twice, constructs child `DesignProblem`s inside the test, uses `authority_scope="contract_testing"`, and directly invokes recursive N5 (`tests/unit/remediation/test_cyc_05.py:509–563, 572–622, 626–679`). ## Can the admitted candidate context seed children?

At the current follow-up SHA, the protected context is more than empty metadata: `CycleSubstrateContext` content-binds the parent problem hash, selected registry-entry hashes, WMR hash, and candidate-lever rows. Each `CandidateLeverEvidence` row carries its source refs, selected-entry hash, target concept, and parent-context binding; `_validate_problem_world_match` checks the parent `DesignProblem`'s candidate-lever target slots against the WMR slot map (`cycle_substrate.py:711–729, 766–789, 830–881, 1313–1337`). It can seed an A-owned **candidate search partition** only after a producer proves a one-to-one join from each selected `DesignProblem` lever to its admitted evidence and L6-resolved target slot. The current context validator does not establish that cross-object join: `CandidateLeverEvidence.target_concept` is not a typed `target_slot`, and the problem/world check only proves the problem's slots occur in the WMR. A missing or ambiguous join must therefore stop child production. The ordinary configured-profile test helper has no candidate-lever evidence (`tests/_helpers/controlled_candidate_profile.py:215–222`), so that fixture cannot serve as the two-child positive input.

It is not yet a typed policy-dependency partition. `DesignProblem` has one problem frame and a `CandidateLeverSpace` whose levers name operator, instrument, and target slot; it has no child or inter-lever relation field (`design_problem.py:205–235, 256–307`). `SubstrateRegistryEntry` binds source/family/layer, provenance, authority, trust, coverage, and version, but no lever-to-lever dependencies (`substrate_registry.py:139–176`). The WMR binds exact slot paths and references to model, program-graph, NCM, and SKG-prior artifacts; those references do not themselves state which policy levers compose, conflict, or are alternatives (`pdc/_impl/world_model_record.py:219–227, 252–289`; `:87–120,172–181`). The candidate context therefore proves each lever's source/slot binding, not the relationship among levers.

The smallest honest producer can be A-owned: after the exact candidate/evidence/target join succeeds, derive deterministic child `DesignProblem` projections from the parent by putting one or more real lever candidates in each nonempty child and preserving the shared objective, constraints, population, jurisdiction, outcome, rule version, and time basis. Persist a parent-bound partition record that names the exact child problem refs and each child's exact lever/source-entry refs. Its relation must be typed as `candidate_search_partition` (or an equivalent non-causal relation); validate that child subsets are unique, disjoint, and their union equals the complete parent lever denominator. Mark the artifact `candidate_only` and explicitly deny decomposition-validity, modularity, causal-independence, and whole-design authority. If the denominator cannot produce at least two nonempty children, fail closed to the one-child path/limited result instead of cloning a child. This is an A frame-grammar decision, not an external scientific-owner contract.

That producer alone does not yet close B15 through the existing controller. Each child hash differs from the parent, while the current `CycleSubstrateContext` is exactly bound to one `design_problem_ref`; child contexts need an A-owned, content-bound projection from the admitted parent context, or a source-backed reissue, not a copied parent context (`recursive_generation_cycle.py:1112–1127`). Existing `JointSimulationRequest` builders are leaf builders and do not pass a coupling graph (`generation_cycle.py:3507–3533, 3775–3787`); there is no child-output-to-parent-request builder. Reuse `derive_recursive_design_graph`, the controller, and `compose_subdesigns`, but add the protected child-context/partition bridge and assemble parent N5 only from the actual child-produced intervention bindings. Unknown coupling must remain entangled/limited; do not turn a candidate graph into observed S5 evidence. In fact `classify_coupling` currently accepts `evidence_state="candidate"` as observed whenever discovery refs and edges are present (`coupling_composition.py:480–505`), so candidate graphs must not be passed to that authority path without first fixing/guarding this discriminator.

If A instead intends B15's children to represent semantic policy subdesigns with `depends_on`, `alternative_to`, `conflicts_with`, or composition relations, those relations are a missing input contract: the current admitted candidate context has no such pairwise/partition semantics. A may define a candidate-only relation grammar and producer; it must not infer relation types from lever names, shared context membership, or world-slot proximity.
