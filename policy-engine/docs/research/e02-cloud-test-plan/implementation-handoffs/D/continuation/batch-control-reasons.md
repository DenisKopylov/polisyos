# Empty-batch control reasons and acknowledged state

The original B119 clause applies to `run`/`_generate_candidates` when an actual batch port returns `[]`. Existing bounded exhaustion and transient-empty transitions remain. StopIteration, a declared ValueError refusal, and concurrent.futures.CancelledError already preserve their original exception object, accepted partial history, and cost view through the public service. The ordinary Bayesian adapter's numerical fallback is unchanged.

The service now includes asyncio.CancelledError in its existing ask rollback and failed-run boundaries. A cancelled ask restores the generator and pending/run state before rethrowing the same object. If restoring the generator itself refuses, publication is blocked: the live cursor is not claimed to have been restored. Reopen the last acknowledged checkpoint with the same configured store, generator, objectives, stopping rules and context. Its immutable bytes and accepted history remain available.

A failed run records the original reason in a new failure checkpoint when publication succeeds. If checkpoint publication also fails, the service keeps the original exception rather than replacing it with a secondary write error, and blocks subsequent publication. That branch does not claim a successfully persisted failure reason. A fresh service must read the last acknowledged reference before continuing. No checkpoint schema/version, cancellation authority, numerical method or retry policy is introduced.

The defining fixture separately records caller-declared context cost 7.5 and actual local settlement custody. In the latter, one supported transport response with a declared request ID/cost passes through LLMBudgetEnforcer and FileBudgetLedger; the nonzero 1.25 spend receipt and fresh snapshots remain identical across refusal/cancellation. This is a measured local producer/settlement path, not independent external billing truth. Partial scientific iterations and empty generation attempts remain separate.
