## Compatibility law versus decisions G/C02 must make

### Already-established constraints

The canonical `CAN-01` source, `policy-engine/docs/plans/active/agent-packages/PolicyOS_E02_Combined_Agent_Package/bundles/CAN-01.md` (from the original pinned plan), already requires preserving historical bytes, hashes, exception identity, depth and the intentionally distinct Core/IR typed-tag profiles. It expressly forbids silently widening the IR decoder or treating Core as the one correct profile. Current IR acceptance of only `datetime`, `date`, `decimal`, `bytes`, and `float`, with Core-only tags rejected, is therefore the correct bounded behavior. Do not “fix” this candidate by broadening IR tags. The default shared-subset producer/read path above is independently evidenced.

### Decisions that remain open at G/C02

1. **Profile-less history:** the old helper decoded bytes without consulting a manifest. This candidate deliberately raises `unsupported_ir_canon_profile` before bytes for `canon=None`. The exact IR API therefore changes for historical/raw Core JSON blobs lacking a canon profile. The candidate has no migration or synthesis rule and no census establishing whether such artifacts occur in deployed data. G/C02 must ratify the fail-closed refusal/rollout or define an existing, source-qualified compatibility route. Do not manufacture a default profile, rewrite bytes/CAS identities, or infer that the history is unused.
2. **Shared `polisyos.canon.json@0.2.0` identity:** Core and IR publish that same name/version while Core accepts three tags IR rejects. Existing law requires the divergence remain explicit and not silently widen IR; G/C02 must decide whether the current shared-subset contract is sufficient for intended cross-use or whether profile identity/version/capability binding must distinguish them. This is a compatibility contract decision, not a defect in the strict decoder.
3. **Profile declaration versus producer conformance:** an actual `FileSystemCAS.put_bytes` witness stores raw JSON `{"fraction":1.5}` with `forbid_floats=true`; the current IR decoder returns a Python float. `max_depth` and tag handling are consumed, but a manifest profile does not prove which encoder emitted the bytes or that every serialization flag was followed. The same default materialized manifest is also unable to prove that all nine canon members existed in the original raw sidecar: Core `get_manifest()` validates/deserializes into `CanonInfo` fields with defaults before the IR reader receives it. The bounded source claim must remain “strictly validates the presented Core/IR manifest view and decodes with its depth/tag rules,” not “proves raw sidecar completeness, emitter identity, or serialization conformance.” If those stronger properties are required, G/C02 must select an existing trusted producer/content-binding or raw-manifest-view capability; the current `ArtifactStore` reader protocol does not expose original manifest bytes.
4. **Existing Core Mapping options seam:** unchanged `core/artifacts/ir_adapter.py::_coerce_write_options` reconstructs only a subset of existing `ArtifactWriteOptions`; the independent actual-CAS control shows typed options preserve one warning while an equivalent Mapping silently drops it. The same constructor omits `tenant_context`, `same_input_closure`, `authority`, and `warnings`. This is a separate existing Core adapter issue, not caused or repaired by C06-CAN. G/C02 should own a separate narrow companion: preserve the full current typed metadata contract for Mapping input or reject unsupported fields explicitly. Do not attribute this finding to the four-path reader patch.
