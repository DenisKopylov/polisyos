## Alternatives (reuse → extend → consolidate → build)

**A. Keep the full singleton v1 denominator.** Reuse current behavior and documents. This is safest if every registered profile is intentionally global policy input. It also means an unselected private profile can keep an otherwise selected run `not_established`, and any presentation-only/unselected edit invalidates its receipts. Do not claim a selected-profile positive under this contract.

**B. Extend to a recomputed selected effective scope v2 — recommended.** Reuse the existing registry/resolvers, catalog source YAML, persisted database bindings/candidate rows, normalized Core plans, actual fixed/dynamic connector profile resolution, `GenerationBasis`, stage/Core receipts, publisher and fresh readers. Extend the versioned currentness object to carry a live-recomputed scope and selected profile status/material. A selected set is complete only if recomputed from the actual producer path: include relevant run/source inputs, persisted bindings and plans before dispatch (including failed/deferred plans that can affect selection), and the profile the actual connector will use even when YAML is profileless. Reconcile actual resolved use with that set. Never accept caller-declared `profile_ids` as the denominator. Consolidate the same scope and selected safe material identity through run signature, Core checkpoint/resume, stage and publish receipts, and Fabric/read-api/shadow/quality consumers. Currentness consumers recompute and compare the live complete scope; they do not trust saved scope declarations. Keep G-only `_resources` and all 13 distinct supplier blobs unchanged.

Under B: selected safe public profile material changing under the same ID invalidates reuse/checkpoints/receipts; changing a truly unselected profile has no effect; selected headers/credentials/environment auth or unresolved/malformed selected inputs remain `not_established`/refused; missing DB is not an empty denominator; an unknown actual resolved profile cannot be omitted. The controlled witness is only source-bound local currentness, not production currentness.

**C. Dual-version compatibility.** New executions emit v2; v1 retains its exact full-singleton meaning and can be current only when its old complete basis is recomputed exactly. Where that cannot be proved, report `legacy_unknown` and require a fresh producer run. This preserves more old behavior but has a longer-lived dual reader and must never reinterpret a v1 full-registry map as a selected-use receipt.

**D. Build a new global profile owner/revision service.** Consider only if the contract is that every global registry mutation must invalidate every consumer. No existing source owner exposes a verifiable non-secret revision for private values, and D01 says not to create another global registry/hash/schema. This is not needed for the selected-scope mechanism and would not make secret equality knowable without a real owner-backed revision.

## Recommended v1/v2 migration and boundaries

If G selects B, keep existing v1 records intact as historical data, classify them as `legacy_unknown` for selected-scope currentness, and require the ordinary producer to create a v2 receipt. Do not backfill v2 scope from current configuration and stamp old outputs. A present malformed v2 object, missing v2 scope, missing database, unknown selected profile, or mismatch between persisted and recomputed scope fails closed; it is not absence/default. Preserve existing public read API/facade exports and typed refusal/status meanings. An older reader must reject an unsupported v2 as unavailable rather than treat it as v1.

The v2 `established` status is limited to the exact local selected source/config/database/run and its bound outputs at the recorded basis time. It does not establish remote data freshness, legal or institutional currentness, production profile/custody, permission, issuer authority, or scientific adequacy. No header, credential, environment token, or secret digest is persisted. A selected private input remains `excluded_present`/`not_established` until a real owner supplies a verifiable non-secret revision contract; none is invented here. Keep historical profileless Core support only when the actual fixed transport profile and its safe material are bound.

For P37/P38, the predicate must be `recomputed` at producer and reader boundaries, with actual open DB/source/plan relationships independently reconciled where existing owners allow it. A saved selector, `scope` field, profile ID, marker, or matching digest alone is `consumer_asserted` and cannot turn the currentness gate green. The intended property is the complete consumed profile basis; testing only declared IDs diverges when a failed/deferred plan or fixed connector resolves a profile outside that declaration.

## Discriminators before any closure proposal

1. With selected profile A and unrelated private profile B present, changing B must not change the selected v2 basis **only if** a source/caller census and actual plans show B cannot be consumed by this run. Add an out-of-scope actual use and verify the live scope expands or refuses.
2. Change selected public material (for example base URL) under the same ID and `none` coverage. Core resume/checkpoint, report/publish receipt, and fresh consumer must become stale/refuse until a new ordinary producer completes.
3. Change a selected profile from no excluded input to private/header/auth present. Status becomes `not_established`; no currentness or FetchPlan is admitted. Do not compare or emit secret values.
4. Change and remove an actual persisted selected DB binding while leaving completion markers or a matching forged receipt intact. Recomputed producer/reader scope must detect both; missing DB is not an empty scope.
5. Include actual fixed transport profile material for profileless source/plan; include failed/deferred pre-dispatch plan profiles. Remove scope equality or selected-material propagation while keeping marker fields, and the negative must fail.
6. Preserve v1 historical bytes but demonstrate v1 → `legacy_unknown`; malformed/missing v2 fields refuse. Produce one genuine controlled ordinary QC + benchmark + publish → fresh RetrievalService/read-api positive under unchanged native thresholds. Keep this positive separate from the full 13-supplier denominator and from production currentness.

P40 bucket: this remains the SAME effective-profile-basis/currentness class, one level deeper at scope completeness and propagation. Widen one mechanism through every persistence/cache/publisher/consumer boundary; do not patch only the v2 return object or one profile fixture. Full 13-supplier pathwise composition remains an independent source/input requirement and is not satisfied by this semantic choice.
