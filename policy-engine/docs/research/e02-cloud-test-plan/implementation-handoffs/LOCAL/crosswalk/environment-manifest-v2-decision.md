## P40 classification and property

This is `SAME_CLASS_DEEPER` for the P37/P38 environment-completeness class. The property is a truthful, source-bound description of the runtime that actually executed each selected command. The v1 implementation instead requires every loaded import row to have a path and nonempty `package_version`, while its completeness basis is a claimed input list and a field-shaped environment hash. It cannot state the observed but ownerless `_virtualenv` file, a namespace/container with children whose origins were not captured, or loaded non-filesystem modules without inventing path/version values. A divergent case is this exact V5 capture: serializing a fake nonempty version would satisfy v1’s string predicate while the process capture reports that no exact installed distribution owns `_virtualenv.py`. The fix is a generic typed origin/status model and recomputed source/input/output binding, not exceptions for these module names.

This follows the failure/repair register’s P29, P37, P38, P39, and P40: recompute from retained evidence; classify gate predicates; test property rather than a field/prefix; keep mandatory records outside mechanism budgets; and widen on the second same-class escape. The current adapter is a research prototype and has not been admitted by the committed `git show` oracle.

## G alternatives

1. **Keep v1 as the only admission profile and cite partial captures as separate evidence.** This preserves the strict complete-profile guard and needs no schema migration. It cannot carry typed partial runtime scope through the handoff, and therefore cannot claim a complete profile or support a profile-dependent `VERIFIED` evaluation.
2. **Recommended: add a discriminated v2 environment observation and handoff route.** Keep v1 unchanged for complete historical profiles. Add a v2 observation with explicit `complete`, `partial`, and `not_established` states and typed origin kinds. A handoff schema v3 should use a tagged choice between a complete v1 backend profile and a partial v2 observation ref, so incomplete context is never coerced into `backend_id`/`profile_id`/`environment_sha256`. The v2 route carries evidence and limitations; it does not authorize a profile-dependent verified result by itself.
3. **Rejected: stringify unresolved versions as placeholders and pass v1.** That turns `"unresolved"` into a nonempty package-version string, which is exactly the P38 divergence above. It launders the unresolved owner predicate through a shape check.

This is a proposed research choice only. `formal_closure_ids` remains `[]`; no finding is closed by a passing command, by this v2 report, or by an author’s earlier disposition.

## Minimal v2 contract

Keep the existing strict v1 schema intact. Add `policyos.e02.execution_environment_observation.v2` as a separately typed observation with these load-bearing sections:

- `candidate_source` and `source_freeze`: exact commit/tree/parents, complete source census, source-input manifest and frozen-input manifest refs, each status derived by Git/object and manifest recomputation. No commit/tree or manifest supplied by an author can self-establish completeness.
- `command_runs`: one row per selected command, exact argv or command text, cwd, actual status, output refs and hashes, runtime capture PID, configured sidecar base, PID-derived output path, and exact output-inventory hash ref. Where the wrapper reports both `module_origin_assertion.receipts` and `command_output_inventory_before_metadata.regular_files`, the validator must reconcile their path, PID, and digest to the configured base’s PID-derived path and the reread file bytes. A retained file without a command output digest remains `not_established` as a persisted command output.
- `runtime`, `platform`, and `environment_settings`: observations from the same process that ran the command; keep unset allowlisted values explicit. Runtime platform and settings from a wrapper or a preflight are not substitutes.
- `loaded_origins` and `runtime_inputs`: generic row sets derived from the process capture. Use explicit origin kinds such as `candidate_source`, `distribution_file`, `runtime_file`, `namespace_container`, `stdlib_or_builtin`, `nonfilesystem`, and `unclassified`. A source module binds to the candidate tree; a distribution file binds to exact installed-file/RECORD ownership and package metadata. A loaded bootstrap/runtime file becomes a content-addressed runtime input with its captured path, digest, size, and capture status; its package owner/version may stay `not_established` and must never be replaced by a made-up version string. A namespace container is a non-executable directory observation with search locations and actual per-child module-origin observations; the directory itself is not credited as executable content. A non-filesystem row preserves the observed module identity and unresolved provenance rather than labeling it builtin. Unknown/unobserved children remain explicit.
- `distribution_inventory` and `import_scope`: inventory status/counts and the exact source pointers used to derive completeness. The `complete` state is computed over every root and every loaded child; it cannot be set by copying the plugin’s status field.
- `selected_inputs`: sorted identity/hash rows projected from the frozen source and fixture manifests, with unavailable inputs typed as unavailable and null-hash. Do not conflate that denominator with the larger set of runtime imports.
- `observation_status`: `complete` only if source tree, full selected-input denominator, every command/output, and every relevant import origin resolve; otherwise `partial` or `not_established`, with exact unresolved pointers/reasons. A partial observation is useful evidence but never a complete backend profile.

The current capture can populate its captured process/runtime/platform/settings values, 865 first-party modules plus the product-root assertion, 100 external-root rows by pointer, 248-distribution inventory counts, 268/99 standard/builtin name counts, 62 non-filesystem names by pointer, 13 JUnit outcomes, and the two unresolved-root details above. `_virtualenv.py` has a content digest in the process capture, but without a same-command output inventory its digest is only reported by the sidecar, not bound to the command. It cannot populate a complete selected-input denominator, whole-tree freeze, per-child namespace origins, or a command-output digest for this V5 sidecar. Those fields stay unresolved until the final wrapper/capture adds the missing evidence.

The smallest next capture change is to extend the existing process plugin’s origin inventory, not add a new service: preserve source-module origins against the frozen tree; retain exact distribution-file/RECORD/version checks; record content-addressed loaded runtime/bootstrap files without inventing an owning package; classify a namespace container only from its `ModuleSpec` search locations and capture each loaded child’s origin separately; record `built-in`/`frozen` as such; and, for other non-filesystem modules, ask the already-loaded loader for a filename when available, otherwise retain `unresolved`. Then cross-bind the resulting sidecar’s PID/path/hash to the wrapper’s complete output inventory and command source identity. A child with no file/origin/owner remains unresolved; it must not inherit the namespace root’s or another child’s owner.

Migration is a reader-dispatch extension: keep strict v1 parsing for existing complete profiles, introduce v2 for typed partial/complete observations, and add handoff v3 with an explicit union between a complete v1 backend profile and a v2 observation reference. Do not manufacture `environment_sha256` or required profile strings from a partial observation. Occurrence evaluation v4 already has `UNAVAILABLE_INPUT`, `BOUNDED_LIMITATION`, and `OPEN_ACTION` states for cases whose original property depends on unresolved runtime evidence; v2 should only supply a source-bound ref and status, not auto-select the row’s outcome.
