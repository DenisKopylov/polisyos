## Existing input path and required join

Use the existing `policyos.e02.occurrence_evaluations.v4` import accepted by `LOCAL/emit_proposals.py`, not a task-level status bridge or a new parallel outcome format. The evaluation key is the exact pair `(occurrence_pointer, sha256)` from the original coverage criterion occurrence. Keep every row distinct even when IDs, routes, source text, or test selectors repeat. Validate the evaluation keys as a multiset against the full original denominator before emitting; the final report may show only evaluated rows, but its denominator and `UNRUN` count must still be stated against all 291 occurrences.

Only add a row when the actual run produced occurrence-relevant evidence. Its `candidate_source` must equal the root-supplied frozen commit/tree. Its frozen context must bind `/source_boundary/source_freeze/source_change_census` and the exact digest of that complete census. The final input has the registered top-level fields `schema`, `frozen_context`, and `evaluations`; each evaluation has the required fields `occurrence_pointer`, `sha256`, `candidate_source`, `state`, `result_summary`, `boundary`, `execution_context`, `evidence_refs`, `attempts`, `next_check`, and `review_escape`. Use the schema’s conditional fields only when applicable: `proposal_disposition`, `limitation`, `falsifier`, `missing_input`, and `new_defining_property_counterexample`.

Map evidence from a command to an occurrence only after reading its exact criterion, candidate property, actual consumer, and discriminator. A single actual test run may support multiple occurrence rows, but each row needs its own property/consumer mapping and criterion-specific evidence. A command PASS, a task PASS, a historical closure, an author proposal, an old selector, or an exit code alone never populates an evaluation. Keep exact `PASS`, `FAIL`, `ERROR`, `SKIP`, and `UNRUN` attempt outcomes, with the actual deciding stdout/stderr and other required artifacts bound by their own validated refs. Do not add an unvalidated `junit_ref` or treat a test count as proof.

For each evaluated occurrence, bind the same frozen source, its applicable typed slice receipt(s), source/configuration/lock scope, selected-input state and consumed-input refs, actual backend/profile, current consumer surface, and occurrence-specific decision research. The typed receipt must establish the real producer → persisted artifact → bridge → consumer route. Record actual positive, actual-consumer, and negative evidence for a `VERIFIED` result. Use `BOUNDED_LIMITATION` only with the exact scope, limitation, and an executed falsifier; use `UNAVAILABLE_INPUT` only for a specific unavailable input with its source/authority/permission/context/verification basis; and use `OPEN_ACTION` only with completed attempts and a runnable next action. Preserve `not_established` input scope as not established, never as verified. A missing or malformed supplied value is not absence and cannot be defaulted into a positive.

## Whole-property and next-check fields in the final report

The current crosswalk supplies exact original criterion locators and owner crosswalk references, but that is not a complete current-candidate property/consumer result. In a complete walk of `finding-proposals.json` (282 findings, 291 occurrence rows), 190 occurrences have `owner_property_boundary_state = not_established_by_author_crosswalk`; 55 occurrences have only `acceptance_boundary_state = original_source_span_only`. The six A–F assessment JSON files contain richer source-specific property and consumer references, but they still do not constitute final frozen-source execution. The final report should link each occurrence to its exact A–F assessment row and render, for the candidate actually exercised:

- the original acceptance property and any separate runtime predicate, without narrowing one to the other;
- the current candidate property and the property-versus-proxy boundary;
- the actual producer/artifact/bridge and real consumer surface/selector;
- selected input and backend/profile context, including unavailability or uncertainty;
- the positive, negative, and discriminator that distinguish the property;
- the evaluation state, attempt outcomes, exact evidence refs, and any residual limitation.

Use the v4 `result_summary`, `boundary`, and role-qualified `evidence_refs` for the evaluation input; preserve the source-specific locator rather than copying entire assessment rows into the report. The report view should label the occurrence by its exact pointer and hash, not by ID alone.

All 291 current `candidate_evaluation.state` values are `UNRUN`; all 282 `candidate_proposal` values are null; all rows remain at `source_qualified_author_review_pending_final_candidate_freeze`. The 291 current `next_check.action` values have 14 distinct prefixes, but every action also carries the same generic instruction to compare against the final source/config/lock/input/backend/profile/consumer and then perform the owner or G action. This is a useful pending-work prompt, not a completed next check. After evaluation, replace it with the row’s exact next step: the remaining discriminator and executable command/consumer, the named missing input and owner, the bounded limitation’s falsifier, or the separate G adjudication still needed. Do not copy a generic action forward as evidence that the next check ran.

## Proposal aggregation and final readback

Keep the final report occurrence-first. An occurrence with no explicit evaluation row stays `UNRUN`. Do not infer an outcome for the other occurrences of the same finding. The canonical emitter constructs a finding-level candidate proposal only when explicit occurrence dispositions cover every occurrence for that finding; mixed dispositions remain mixed. It permits `closed` proposals only for VERIFIED occurrences with occurrence-specific positive, actual-consumer, and negative evidence. Even then, the result is a candidate proposal, not formal G closure. If B198 is reopened by a candidate proposal, preserve its historical fields and provide the emitter-required new defining-property counterexample for its exact occurrence.

After the source freeze, build the explicit v4 input at the registered `LOCAL/crosswalk/occurrence-evaluations.json` path. Run the canonical emitter with the exact frozen commit and tree, e.g. `python3 -B policy-engine/docs/research/e02-cloud-test-plan/implementation-handoffs/LOCAL/emit_proposals.py --frozen-commit <frozen-commit> --frozen-tree <frozen-tree> --evaluations policy-engine/docs/research/e02-cloud-test-plan/implementation-handoffs/LOCAL/crosswalk/occurrence-evaluations.json`. Retain and hash the full command outputs and read back the regenerated proposal ledger and receipt. Reconcile their exact original occurrence-key multiset, report the evaluated and still-UNRUN counts, and verify `formal_closure_ids` remains empty. The provisional `LOCAL/crosswalk/receipt.json` and its old source checkpoint are not a final freeze or a candidate result.

This input contract closes a P38/P35 reporting gap by requiring the whole criterion-specific property, real consumer, and complete occurrence-key join rather than task labels or aggregate counts. It preserves P40 by classifying results per occurrence and carrying any new same-class escape into a structural resolution or an explicit bounded residual; it creates no new law or closure authority.
