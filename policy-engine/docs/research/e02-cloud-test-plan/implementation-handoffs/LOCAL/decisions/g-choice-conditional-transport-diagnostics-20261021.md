## Proposed contract and migration

**Proposed reuse-first design:** add optional strict/frozen `candidate_diagnostics: TransportabilityCandidateDiagnosticV1 | None` to the existing `TransportabilityResult`. Its own `schema_version` is `1.0`; its data describes only a conditional candidate and binds the solver output to its graph/query/context inputs and algorithm parameters. The existing top-level PAG scalar may remain a backward-compatible mirror, but when the typed diagnostic exists it must agree with it and must never drive authority, readiness, approval, or publication. Preserve outer `status`, `transport_mode`, `feasible`, refusal code, and review requirement unchanged.

The current version surface is split: the model default and ABI snapshot are 2.1, the CAS writer manifest default is 1.0, the migration registry registers 1.0 and 2.0, and the R1 persisted failure payload reports 2.0. Close that mismatch as part of the rollout, rather than treating any one of those numbers as the authoritative version.

Publish the result **payload and CAS manifest as `ir.transportability_result@2.2`**. Keep contract ID `ir.transportability_result.v2` because the outer result/authority semantics do not change. Update the model default and ABI snapshot to 2.2. Extend the migration registry with an explicit 2.1 predecessor and a 2.2 reader for known versions 1.0, 2.0, and 2.1; normalize those old payloads with `candidate_diagnostics=None`, preserve existing 1.0 aliases, and set canonical version 2.2. Keep the registry, `normalize_payload`, model validation, and artifact manifest checks aligned; do not silently strip unknown fields or accept an unknown future version by pattern alone.

Because the typed subobject is nested inside `CausalEffectReport.transport_result`, publish **report payload and CAS manifest as `ir.causal_effect_report@1.1`**, keeping contract ID `ir.causal_effect_report.v1`. New readers accept report 1.0 and 1.1, normalizing the absent candidate field in 1.0 to `None`; they reject unknown future report versions fail-closed. New writers emit 1.1 only after all in-tree consumers have been upgraded. Explicitly update `governance_gate_requests.py`, which currently rejects any report `schema_version` other than 1.0. Older strict readers cannot consume result 2.2/report 1.1; version negotiation or rejection must fail closed, never drop the new nested value. Coordinate consumer deployment before either writer starts emitting the new versions.

Update `ir/api.py` and both public lazy-facade maps, `schemas/abi_models/catalog.py`, generated result/report schema snapshots and `_manifest.json`, `docs/reference/schemas.md`, the generated IR schema catalog, and the IR public-surface reference. ## Alternatives, acceptance, and boundary

1. **Keep the gate before all math.** Legally safe, but the accepted candidate PAG criterion stays unavailable. This is the current behavior and the remaining red.
2. **Recommended — compute a content-bound candidate and retain the outer refusal.** Reuses the existing solver, transport result, report, CAS, and public summary; adds an explicitly typed interpretation channel and coordinated schema migration.
3. **Move/relax the legal gate or accept caller Boolean/graph metadata as permission.** Rejected. No legal relation producer, artifact, independent verifier, or permitted positive evidence class is present; that would widen authority without evidence.
4. **Create a separate candidate artifact family.** Possible, but it adds another artifact/ref/state/API bridge and consumer lifecycle. The optional nested DTO is narrower while the existing result/report bridge is already used.

The decisive falsifier is a full integrated run where the candidate solver is removed while its marker fields remain: it must fail the positive candidate assertion. Conversely, a marker/ref with mismatched content, a different graph/context, or a caller Boolean must not change the refusal or make consumers pass. The same persisted report must expose both the typed conditional candidate and the unchanged legal refusal. No legal positive may be constructed from a manual SCM fixture.

Relevant patterns: P05 (authority/status boundary), P32 (resolve + content-bind + verifier provenance), P37 (classify candidate inputs as recomputed only relative to supplied content; graph authority/legal relation remain `not_established`), P38 (test the property, not marker presence), and P40 (repair the class once). The R1 boundary is the same candidate-versus-authority class, not a new B33 fix. The R2 source-frame/criterion mismatch was a decision-record provenance error and is corrected here at every dependent binding. Current capability labels remain `bridge_missing` for candidate diagnostics under declared legal unknown; `producer_missing`, `artifact_missing`, and `verification_missing` for a positive legal relation; and `bridge_missing` for the B33 named-model/identification-plan route.

No product source/test patch, test run, formal G decision, legal-positive relation, source-trained GCM, B33 closure, or E02 criterion closure is claimed by this packet.
