## What exists today

1. `GenerationCycleController` installs `CanonicalN9PromotionPort`. The port evaluates each current `CandidateSummary` against the canonical N9 owner sequence. For every returned receipt, `_run_n9_promotion_port_batch` preserves the input order and includes its candidate ID in `certified_candidate_ids` when that receipt is production-lane, promoted, and `consumer_promotable`. The observation carries the receipt mappings themselves. It is a **set of certified candidate IDs**, not a one-winner decision. See `runtime/quality/generation_cycle.py:1650,1707,6714` and `runtime/quality/promotion_sequence.py:2385,3762,4027,4180–4235` in the source binding.

2. N6 stores the `PromotionPortObservation` in `GenerationCycleRun` (current schema through v6). `_apply_promotion_to_summaries` uses the certified-ID set together with the latest current occurrence, the receipt/currentness checks, and other gates before moving a summary into the decision front. Its history validator is append-only and version-aware, but `validate_generation_cycle_run_history` explicitly replays intrinsic history without checking deployment currentness. `eligible_n9_source_for_run` admits only the exact current typed N6 schema and blocks historical N6 records as current N9 sources. See `generation_cycle.py:2284,2488,2642–2703,11012–11035,14839–14880`.

3. The natural-language control-job publisher serializes the compiled recursive run, including its leaf N6 runs and N9 receipts, into one Core CAS artifact with kind `runtime.compiled_recursive_generation_cycle`, schema name `polisyos.runtime.CompiledRecursiveGenerationCycleRun`, and manifest schema version `1.0`. When the execution scope is established, the write includes tenant/cell context. The returned `ArtifactRef` (including the exact store-selected manifest profile) is saved both in the completed job progress and the Core run manifest. This is the physical persisted N9 history source; the receipt is not separately written as a standalone CAS object by the N9 port. See `runtime/http/services/control/job_nl_publication.py:37–118`, `run_lifecycle.py:3216–3243`, and `control/generation_cycle.py:845–900`.

4. There are authentic fresh consumers of that source, but they serve other properties. Evaluation Safety selects a completed job by run and kind, binds the payload tenant/cell/run, resolves the exact completed Core attempt, requires exactly one compiled artifact matching the progress `ArtifactRef`, verifies bytes/manifest/schema/profile, then traverses the typed recursive run, candidate, and N9 receipt. It uses the selected N9 receipt to replay safety evidence; it does not call `ChampionRegistry`. The N5/public-export paths also resolve compiled source and consume N9 for their own typed projections. `GET /control/jobs/{job_id}` exposes `progress` as an untyped projection and the CAS reference; that is not a typed N9 admission or a Champion call. See `runtime/http/services/control/evaluation_safety.py:562–620,644–760`, `runtime/http/routes/control.py:558–573`, `core/contracts/control.py:1675–1715`, `runtime/http/routes/runs.py:1120–1195`, and `runtime/http/services/control/generation_cycle.py:2679–2720`.

5. The available Champion consumer has a different contract. `SearchLoopRunner._evaluate_candidate` creates and persists an actual `MutationArtifact` and a `BenchmarkEvaluation`, then calls `ChampionRegistry.consider_promotion` with the candidate, evaluation, promotion policy, and suite. The registry loads a typed `BenchmarkEvaluation` from the selected artifact and checks candidate/evaluation/suite binding and comparable basis before a pointer can be written. An N9 receipt contains no `BenchmarkEvaluation` or benchmark-suite reference and does not define an evaluation-to-metric/split mapping. It cannot honestly be adapted by inventing those values. `ChampionPointer` is a single loop pointer; N9 can certify several candidates in the same batch.

6. The source explicitly preserves this separation. The `promotion_sequence.py` module describes N9 as the single N6/N9 sequence, “not a second champion or G4 engine.” `LegacyPromotionStrangleReceipt` checks that the legacy policy-champion path is not live for N9. The allowed old `PolicyPromotionCoordinator` path returns `promoted=False` with `canonical_n9_promotion_sequence_required`; it does not supply the missing N9-to-Champion bridge. The AST census finds one `.consider_promotion` call site in canonical production package source: `scientist/methods/autotune/runtime.py:2528`, inside `SearchLoopRunner._evaluate_candidate`. The separate `judge_stack.py:2223` call writes metadata onto an existing pointer; it is not the N9 selection path.

7. The N9 receipt trace's `output_artifact_ref` is a logical trace locator (`pdc://n9/{candidate_id}`) whose content hash is the candidate summary hash. It is not the CAS identity of the serialized receipt. Do not use this trace locator as a fake persisted receipt reference. The physical receipt bytes are part of the compiled N6 artifact above. See `promotion_sequence.py:6874–6915`.

## The decisive falsifier

The current N9 source can produce a batch in which two distinct candidates, A and B, both have production-lane receipts with `promoted=true` and `consumer_promotable=true`; the N9 batch then emits both IDs in `certified_candidate_ids`, and N6 can mark both current summaries for the decision front. This is represented directly by the actual batch comprehension and `_apply_promotion_to_summaries`, not a constructor-only test. No current source rule orders A versus B into a singular Champion. If a bridge selects the first row, reversing the source order can change the pointer without changing the certified set. If it sorts IDs, it invents a selection rule. If it passes either raw N9 receipt to `ChampionRegistry`, the existing consumer asks for a bound `BenchmarkEvaluation` and suite and rejects the type/basis mismatch. If a source removal leaves `consumer_promotable` markers in the projection but removes the receipt/source binding, the candidate must remain non-promotable.

A real implementation falsifier after a G decision is: run the ordinary N9 producer on a controlled, valid source; persist the compiled run through the ordinary control publisher; fresh-read the exact job-owned Core manifest/CAS `ArtifactRef`; then perform the selected candidate/Champion operation and read back the exact pointer. Repeat with two valid N9 candidates and permuted input order; a forged candidate ID/content hash; a stale or wrong-profile/schema manifest; duplicate or missing receipt; a v7/v2 history receipt; and a pointer race. The bridge must preserve candidate occurrence identity and source profile, reject stale/malformed bytes, and never treat an N9 certification as external permission, law, publication authority, or a benchmark measurement. The R1161 assignment did not run this product path; this is a concrete falsifier, not a claimed PASS.

## Decision alternatives for G

**Reuse — recommended default:** keep N9's output as a versioned certified-candidate set. Reuse the existing compiled-run CAS write, exact `ArtifactRef`/manifest profile, current N9 reader, and existing `SearchLoopRunner`/`BenchmarkEvaluation` path. A later Search run may independently evaluate a candidate with its actual suite and then use the existing `ChampionRegistry`. Do not write a Champion directly from an N9 receipt. No history migration is needed; N9 v2–v7 receipts stay readable only as historical records and current eligibility remains v8/current-owner replay. This preserves the source's “not a second champion” contract and avoids adding a new pointer.

**Extend — if a technical N9 Champion is genuinely required:** G must authorize a distinct typed N9 candidate-selection/pointer contract and its exact owner. At minimum decide whether the target is still a set or a single candidate; the key/scope (design problem, run, occurrence, tenant/cell and epoch); the winner/tie/empty-set rule for multiple certified candidates; how fresh currentness and stale/reissue invalidation replace a historical receipt; how source `ArtifactRef`, manifest profile, receipt schema, candidate content hash, occurrence identity, ledger head, and predecessor pointer are bound; and whether this is a separate registry or a typed branch of the existing owner. Preserve the existing benchmark Champion schema and requirements. Use new versioned artifacts; do not backfill older N9 v2–v7 or profileless records into current authority.

**Consolidate:** a common source-bound leadership owner could unify N9-candidate and benchmark-based entries, but it changes the current single `ChampionPointer` contract and migration/read paths. It would need a typed evidence-basis discriminator and per-basis verifier; a generic `metadata` field is not enough. The scope is materially broader than the E02 missing bridge and has higher compatibility cost than Extend.

**Build new:** a second N9-specific Champion registry is technically possible but duplicates the pointer owner and creates competing current state. It should be rejected unless G can show a distinct resource domain and consistency boundary that the existing owner cannot represent.

**Narrow proposal:** select Reuse now. Keep the N9→Champion bridge as `bridge_missing` pending the explicit G choice; expose no pointer claim. If G instead chooses Extend, issue a new owner contract plus versioned pointer/event and fresh reader. `consumer_promotable=true` remains an N9-internal candidate status, not an external issuer/permission/currentness receipt.
