# G decision packet: N9 selected-source binding and bridge body version

**Decision requested from G:** Should the N9 source's selected manifest profile remain an exact CAS-manifest input to the existing v3 bridge, or should a future bridge schema bind a typed selected source reference inside its content? This packet records a bounded proposal, not G acceptance or formal closure.

## Evidence and current source choice

N9 emits a v3 bridge body unchanged and places one fixed-role `n9_promotion_evidence_source` edge, including the exact selected source profile, in the CAS manifest. The consumer selects that manifest view, checks the single edge's role and content ID, and reads the source through the typed ref. The N9 effect and independence source writers share the existing `_persist_model` path; the current source contract therefore also checks the exact default owner-manifest projection (including an empty input list), which rejects a same-content-ID alternate profile with substituted lineage. Duplicate bridge edges remain refused by the generic one-edge check.

The MeasurementRoot envelope is emitted by its current producer with the selected profile returned by the write. N7 passes that value into the route CAS ref, compares the resulting typed ref with DataSnapshot and registry lineage, and reads the registry's MeasurementRoot source through that exact ref. Missing selector stays a refusal; the reader never derives a selected profile from an artifact ID.

## Alternatives

1. **Reuse v3 body plus exact selected CAS manifest edge (current proposal).** This keeps the existing bridge body and historical parse behavior. Currentness requires the typed bridge ref and its selected manifest; the consumer rejects absent, duplicated, wrongly scoped, or producer-contract-inconsistent source edges. Old profileless bytes remain parseable but not current evidence. This makes the selector a property of the selected CAS view, not a claim about external authority or freshness.
2. **Extend the bridge body to v4 with a typed selected source ref.** This puts the source profile into the bridge content hash and gives downstream export/import paths a self-contained semantic reference. It changes canonical bridge bytes and requires v4 reader/writer coexistence, generated/private schema updates, migration policy, and a decision about when v3 stops being current. Existing v3 bytes cannot be backfilled.
3. **Add an optional selector to the v3 body.** This reduces initial versioning work but creates mixed semantics: old v3 bodies omit the field, while new v3 bodies may carry it. A currentness rule still has to reject absent selectors, and the content hash changes for new writes without an explicit schema boundary. This is weaker than either complete v3 manifest selection or a versioned v4 contract.

## Narrow recommendation and tradeoff

Keep v3 for this candidate and defer any v4 decision to G. The exact CAS profile is already represented by the shared typed reference and manifest input APIs; the prototype exercises selected reads and binds the source edge to the existing producer contract. A v4 body should be adopted only if G requires bridge content hashes to be independently portable without retaining the exact selected CAS manifest reference.

If G chooses v4, the narrow migration is: add a strict typed source ref to v4, make current writers emit v4, let readers continue parsing v1-v3 as historical/not-established, and never synthesize missing selectors. This requires regenerated schema/export artifacts only if G also promotes the currently internal `polisyos.pdc` surface. The current repository contract says any unlisted `polisyos.*` entrypoint is internal; the candidate release fragment classifies the field accordingly and makes no generated-client compatibility promise.
