## Reuse, extension, and closure check

Reuse the existing tenant scope only when startup is genuinely composed for that one known tenant. Selecting `tenant-fixture`, a first tenant, or a caller-provided tenant string for process-global startup would transfer shared verifier provenance into that tenant's ownership and would be wrong for the general API.

The smallest possible extension is a deployment-issued, typed bootstrap-owner capability for this fixed runtime-internal purpose, accepted by the CAS owner boundary and shared by both verifier producers and consumers. Its exact principal and cross-tenant read semantics require an explicit design decision; they are not implied by fixed bytes, `classification="public"`, a missing manifest tenant field, or the current shared-CAS name. If that owner contract is not authorized, retain the explicit fail-closed startup refusal for a conflicting tenant claim. Do not disable ownership checks or invent a tenant identity.

P40 classification: this is the **same owner-scope class one level deeper**. The fixture patch closes the construction/lifespan boundary for one declared tenant; process-global bootstrap still lacks an owner model for neutral verifier artifacts. Stop adding per-writer or per-artifact tenant scopes. Either widen Core ownership to a typed bootstrap principal under an approved contract, or keep this bounded residual explicit.
