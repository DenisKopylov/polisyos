# V3 DataNeed intake: actual fixture prototype and scope falsifier

**Status: G-pending research prototype; no source/API change, no accepted route, no closure.** This addendum narrows `v3-valid-input-alternatives-20261010.md` to an actual DataForge/DataNeed execution. It uses only the committed Slice-0 catalog fixture generated under this ignored `LOCAL/raw` folder. It does not contact a connector or read the production catalog.

## Actual execution

The read-only runner used the real `DataNeed`, `DataResolveRequest`, `RetrievalService.resolve`, DataForge `build_slice0_fixture_catalog_graph`, `DatasetCatalogGraph.resolve_metric_bindings`, `data_state_substrate.l1_dcat_variable_availability`, and `l1_variable_availability_requirement_gap` APIs. It requested `msme_credit_access` for `DEU`, 2025, annual, purpose `effect_grounding` against the actual Slice-0 fixture.

The fixture's first three bindings for that metric all identify Ukrainian (`UA`) catalog datasets whose metadata ends by 2024. The real resolver nevertheless returned a fetch plan for date 2025, with `filters: {}`, plus three candidates for the UA datasets. It did not enforce the supplied geography or check the requested year against catalog coverage. The L1 owner then returned `status=available`, `dataset_count=6`, `metric_binding_count=6`, `observation_count=0`. Its `coverage_ref` still names the default production-data path even though this process routed the owner to the portable fixture. Calling the actual L1-to-gap helper with this result refused with `l1_variable_is_not_an_acquisition_gap`.

A second typed need for `government.balance`, DEU/2025, returned zero plans and zero candidates. The fixture L1 owner returned `unavailable` with zero counts, but that only means the synthetic fixture has no matching row. It is not evidence of a scoped DEU/2025 absence. Its `coverage_ref` is likewise the hardcoded production-style locator. The canonical cost schedule has no `government.balance` row; it has an `administrative_tax_receipts` row, which is unrelated to the requested variable.

This is the discriminating result: a request-scope mismatch is currently projected as catalog candidates and then as global `available`, despite zero observation rows. An empty resolver result is also not an absence proof. The existing code therefore provides no valid scope-bound `AcquisitionRequirementGap` for either case. The N7 planner and cost producer were deliberately not called, and no N7/cost artifacts were written to CAS. A candidate-only gap synthesized from these global counts would be a false source claim, not a prototype of a lawful route.

## Contract boundary and reuse choice

The strict `NaturalLanguageRunRequest` (`control.py:440`) has no `DataNeed` field. The existing DataNeed and DataResolve contracts (`control.py:554,724`) are used by the separate retrieval path. `nl_pipeline.py:5393` extracts/constructs DataNeeds from its ProblemFrame and later resolves them (`:5658`), but the served recursive generation path does not pass those needs into N7. The request's `DataSourceBinding` names snapshot/binding/data-view refs; it is not a missingness declaration. `DesignProblem.EvidenceNeed.source_hint` remains a candidate hint, not a source-owner measurement.

Reuse-first G option: if G chooses to allow an ordinary data-need request on the candidate path, carry the existing strict `DataNeed` (or its content-addressed request ref) from the served request into the same recursive run. Bind it to the exact request/candidate, and use a source owner that recomputes availability over the requested canonical metric, geography, time, granularity, and selected catalog profile. The current L1 API does not meet that contract: it counts global dataset/binding metadata as availability, accepts no geography/time, and reports available with zero observations. `DataNeed.metric` is also not proven by this route to be the canonical variable identity consumed by the L1 gap helper. The design must join the metric binding to an exact source/variable contract, not equate a catalog candidate with observations.

If G selects this extension, the public contract companions include the NL request DTO and route/job handoff, recursive-cycle typed input/owner bridge, generated OpenAPI/API clients, and served producer/consumer tests. The existing separate `nl_pipeline.py` extractor is reusable only if its request-bound DataNeed, profile, and lifecycle are carried into the same recursive candidate and preserved in fresh readers; copying its `data_needs` payload into arbitrary `context` is not that bridge.

The availability result must carry the recomputed requested scope, source/catalog/profile identity, exact canonical metric binding, query/rule version, and source content identity needed to distinguish `available`, `unavailable`, and `unknown`. The existing L1 gap contract carries candidate/problem and global variable counts but not the DataNeed scope or its source/profile binding. If no scope-complete source record exists, the result stays unknown and no N7 gap/cost route is emitted. A DataNeed states intent; it does not supply absence, CGF disposition, acquisition approval, currentness, or causal authority. If a candidate-only N7 planning route is eventually selected, it must keep N5 `candidate_scenario_n5_only` / N8 pending, preserve grounding/admissibility unknown, and never project the cost artifact as acquired evidence.

The other safe G option is to keep this N5 path uncosted until the existing N8/CGF route has a genuine disposition and scoped source-owner gap. The current N7 planner consumes a typed `AcquisitionRequirementGap` only after `ACQUISITION_REQUIRED`; the same N5 candidate handoff currently stops at `value_pending_n8`. A generic schedule row or N5 model is not a substitute for the missing owner contract. No candidate-only CGF or authorization semantics were inferred here.

## Acceptance discriminator for a G-approved implementation

- **Positive:** actual served NL request with one strict `DataNeed(metric=..., geography='DEU', time_start='2025', time_end='2025', granularity='annual', purpose='effect_grounding')`; an owned fixture where exactly that requested scope is absent; producer emits a content-bound scoped availability result; the same candidate/run binds it into a typed gap; N7 plan and exact canonical cost row are persisted; fresh CAS readers validate the selected scope, candidate, profile, gap, plan, and cost. Candidate status/admissibility/currentness remain unchanged.
- **Available elsewhere control:** three catalog rows for the same metric only at another geography/period must not resolve DEU/2025 or create an absence/presence claim for DEU/2025. The current resolver/L1 path fails this control as described above.
- **Observed-value control:** metadata bindings with zero observations are not proof of observed data. A future owner must distinguish plan availability from observations/coverage rather than reusing the global count.
- **No-need control:** leave the same source hints and N5 markers but omit the typed need; no need-bound N7 route/cost record appears.
- **Exact-cost control:** `government.balance` cannot borrow the unrelated `administrative_tax_receipts` schedule row; missing exact cost basis yields no costed pair.
- **Mismatch control:** corrupt geography/year, metric binding, profile, or need ref while leaving markers unchanged; fresh consumer must reject rather than select a first/nearest source.

P40 bucket: **SAME_CLASS_DEEPER**—this widens the same served request → need/availability producer → typed gap → N7/cost artifact → fresh consumer property. Widen the complete scope/metric/source/profile join once; do not patch one field or fixture at a time. Current labels for this served property remain `contract_only` (DataNeed exists separately), `bridge_missing` (request/need to scoped source gap), and `verification_missing` (no fresh costed route from this producer). No closure is claimed.
