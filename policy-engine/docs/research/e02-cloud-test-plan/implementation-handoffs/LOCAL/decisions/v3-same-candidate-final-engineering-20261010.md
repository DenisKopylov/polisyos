## What the current implementation can represent

The current identity design already separates a stable candidate subject from an immutable N4 source occurrence. `candidate_scenario_semantic_identity_hash` hashes the stable subject, the complete Trinity proposal and selected intervention, and profile-selection semantics; it deliberately excludes only the profile’s `baseline_state` from N5 semantics (`generation_source.py:1008–1059`, current SHA-256 `8b399470e10afe538b87f8616b64bbf2bc512327f83c7c4483478f23c233c6bd`). `N4CandidateScenarioSourceRecordV3` stores `stable_subject_ref`, `semantic_identity_hash`, `candidate_occurrence_hash`, `profile_selection_ref`, and an immutable typed `origin_source_ref`; its reader recomputes the semantic hash and checks candidate/profile continuity while requiring a different occurrence hash and WMR hash (`generation_source.py:1063–1109, 1660–1695`). That is the right reuse-first contract for “same candidate, new world occurrence.” It must not be weakened or changed in place.

The surrounding cycle contracts already retain occurrence identity. `CandidateSummary` has both `candidate_id` and content hash; `_candidate_occurrence_key` is `(candidate_id, content_hash, cycle_index)`, while `_current_candidate_summaries` preserves history and selects the latest occurrence for the current front (`generation_cycle.py:1484–1502, 12746–12778`, current SHA-256 `327825cd2cfffac7578b4dc36792c06bb6b672027b0d8f5d6e84732d589ea3dc`). The N7 controlled re-entry helper rebinds the same candidate ID to a new world-model reference, recomputes the atom hash, and runs the existing N5/N8 dependent nodes (`generation_cycle.py:7550–7707`). It is explicitly restricted to `authority_scope == "contract_testing"`; the comment sends native admission through `AcquisitionWorldGrowthBridge` instead. This is a controlled witness, not the canonical served producer.

The canonical served bridge validates run/problem/cycle and admitted-observation bindings, then calls `_run_cycle` with `previous_cycle`, the source N4 ref, and the stable design-problem ref (`generation_cycle.py:6130–6171`; bridge `_validate_reentry` in `acquisition_world_growth.py:1150–1167`, SHA-256 `04e5c70d450b297a50ad8936f72d5bf526b5a2520ee6de60fc92bbb1a1fd8bcf`). That `_run_cycle` executes the generation node again. `_candidate_scenario_proposal_result` emits the same candidate ID and links `origin_source_ref` only when the regenerated proposal, selected profile, stable subject, and semantic identity match the prior V3 source (`generation_cycle.py:7709–7717, 7785–7813`). This supports same-candidate re-entry when the semantics match, but re-running N4 does not guarantee that it will.

`CandidateSimulationN5InputV5` already carries `original_candidate_id`, occurrence hash, N4 source ref, context/profile refs, and run/job/tenant/cell (`candidate_simulation.py:693+`, SHA-256 `993866948d5cd9aac4fe89edf51d2365e647ae6d17df4316ccddd0cef31e8c24`). The N4 source ref map is keyed by `(candidate_id, atom.content_hash)` (`generation_cycle.py:5505, 7884`), so distinct occurrences do not alias. Core `ArtifactRef` has the typed artifact ID/kind/media type/selected profile; `artifact_ref_identity_key` compares all four (`core/artifacts/manifest.py:241–295`, SHA-256 `a84690d4f683a107a51afffd655e7a8b9e2550aceb0ca0ce406cf56b1393bc3c`). Preserve this full-ref comparison.

## Why the retained V3 served positive is not same-candidate evidence

The served integration fixture creates `candidate_generation_mode = [False]` at `tests/integration/core_runtime/test_acquisition_authority_served.py:606` (current worktree SHA-256 `73991b22a09d76f0135a5b1f87f039430e4af2e13a92cf0364acc807df9927c4`). The test itself asserts both `source_record.origin_source_ref is None` at line 1257 and the projected history `origin_source_ref is None` at line 1335. These are explicit signals that the fixture changes source identity between the first candidate and re-entry.

The retained V3 artifact diagnosis records the resulting controlled source chain: source candidate `candidate_cgf_shadow`, re-entry candidate `candidate_123b27397979d0b7`, new N4 source ref `sha256:a226a8487e31a44f7ccd6184d2c5417eb23aeed09812700e49984e8e74fa43bf`, and N5 input `sha256:ffab35cbeff4c4b666588f359fe8e06059c056fd429e63d33486ac645c540049`. Its two latest action heads bind the same route, run, source job, and compiled output; the gen-2 terminal outcome is `reentry_completed`. See `LOCAL/decisions/r3-v3-patch-verification-diagnosis-20261010-v2.md` SHA-256 `6dec94dfc001a6dfcf4b93bccca4d1e14dfb3064084119a220bd1d17890d698c`. The retained run’s fresh GET was not a valid positive: the first captured version stopped at missing bearer auth (`v3-history-auth-companion-diagnosis.md`, SHA-256 `9106c1e169c2b8779765ebc655941552acc9a68c47b4d73607aa7eb1bba91672`); a later retained diagnosis also records an unexplained empty projection. Thus the durable producer evidence proves a new candidate was re-entered, not that the same candidate was re-evaluated and surfaced.

The current GET resolver does independently resolve old and new N5/V3 source records and checks their run/job/tenant/cell/profile bindings (`routes/runs.py:295–495, 623–693`, SHA-256 `2d0bec815342d2cd32a2c59e8e1e9a3c28149238c0934210776a3413f0786bd1`). It does not compare the old selected N4 source ref to `new_source.origin_source_ref`, nor require semantic-identity equality when old and new IDs match. The DTO exposes IDs, new source ref, and origin ref but no derived proof status (`core/contracts/runtime.py:2058–2115`, SHA-256 `11659fd0ddde5d675699bcca77338a7bc1fd9c7ae359d1aac36ffb2a348f311d`). The consumer currently reports a generic completed re-entry, so it cannot distinguish a same-candidate refresh from a new candidate after acquisition.

The capability state for the narrow criterion is `implemented_but_not_orchestrated` for the controlled same-candidate rebind and `verification_missing` for the canonical served producer→immutable source occurrence→fresh GET chain. `currentness_status` remains `not_established`; purpose remains `candidate_observation_only`; `publication_authority` remains false. The controlled WMR and synthetic candidate profile also remain limited and carry measurement/coupling blockers. A matching candidate ID is not a currentness or authority claim.

## Smallest controlled discriminator and required companions

The smallest useful V3 fixture change is to seed the first action with the **same** recorded N4 scenario input that is replayed for re-entry: set `candidate_generation_mode[0] = True` before the first `make_wdi_port_case` at `test_acquisition_authority_served.py:606`, retaining the existing `served_n4_recording`, explicit `profile_selection_ref`, and owner-built controlled WMR. `tests/_helpers/acquisition_chain.py:14–52, 58–185` (current SHA-256 `0181432ff573222c7960a45ca57d3547d64a745030c9f2065212e4f5a2aabe28`) already selects recording `gy_n4_cgf_decisive_capture_1_20260704_092222_049411`, rewrites the same candidate action deterministically, and replays it through the ordinary N4 source producer on each restarted worker. The first route may remain quarantined for missing appointment; the second action must still traverse the real admitted owner/overlay path. No production source should be seeded by hand.

The positive is discriminating only if the test captures and proves all of these along the actual producer and authenticated fresh consumer:

1. First N4 source V3 and re-entry N4 source V3 have the same `stable_subject_ref`, recomputed `semantic_identity_hash`, `profile_selection_ref`, and `candidate_id`; the re-entry receipt’s `source_candidate_ref` equals `new_cycle.selected_candidate_ref`.
2. The N4 source artifact refs are different immutable occurrences. The new V3 `origin_source_ref` equals the old source ref by full `artifact_ref_identity_key`; `candidate_occurrence_hash` and `world_model_record_hash` differ. The new N5 V5 input names the same candidate ID, binds the new occurrence hash/source ref/context/WMR, and its actual simulation result is produced from that selected input.
3. The content difference is the admitted owner observation, not a changed URL, timestamp, generated ID, or hand-authored marker. Read the exact admission/overlay receipt and selected WMR/N5 refs from the existing owned source path; retain enough selected ref/hash evidence to show the changed content reached the WMR and the fresh N5 consumer.
4. Keep the two same-run/source-job action heads and the authenticated fresh GET. The GET must resolve the old and new source records, recompute their semantic identity, and bind the new source’s `origin_source_ref` to the old N4 source ref when reporting the same-candidate case. Preserve the corruption→empty history plus typed integrity limitation control.

The companion change belongs in `routes/runs.py::_candidate_acquisition_history_projection`: after resolving the old and new V3 source records, use full typed ref equality and recompute both semantic hashes. For a same-candidate row require same stable subject, semantic identity, candidate ID, and profile selection; require the exact old source ref as the new occurrence’s origin, a changed occurrence hash and WMR hash, and V5 inputs bound to their respective source occurrences. Do not infer continuity from `old_candidate_id == new_candidate_id` alone. Keep the generic new-candidate re-entry path representable; if identities differ, it is not this same-candidate positive and must not be narrated as one.

For one re-entry, the existing V3 source and history DTO have enough typed refs; no DTO expansion or identifier rewrite is required if the GET resolver verifies and returns both `new_candidate_source_ref` and `origin_source_ref`. Keep immutable V1/V2/V3 sources unchanged. If a later requirement needs every successive occurrence to link to its immediate predecessor, the current V3 reader intentionally permits only a root origin (`origin.origin_source_ref is None`); introduce an additive versioned source schema for direct occurrence history rather than overwriting V3. The run’s `(candidate_id, content_hash, cycle_index)` summaries remain the occurrence history, and the latest-front projection remains by stable candidate ID.

Required negative controls are: (a) identical admitted content presented under a new URL/receipt timestamp/UUID must not change WMR content or create a reissue loop; (b) changed semantic intervention, explicit profile, subject, population, or model must not be linked as the same candidate or inherit old evidence; (c) tampered/mismatched source/origin refs still return the typed integrity limitation. The existing `test_candidate_scenario_identity_separates_semantics_from_refreshed_baseline` proves the hash-level baseline-versus-semantic distinction but is not an acquisition producer/GET proof. Keep the separate LA-046 REQ-01 compiler acceptance intact.

Widen the complete affected path—N4 seed/refresh, source V3 lineage, native N7 admission, new N5 execution, persisted cycle occurrence, and fresh GET verification—rather than patching only the served test assertion or forcing an ID field. If the unchanged recorded proposal/profile still fails to yield the same semantic ID, stop and identify which semantic input changed; do not stamp the old ID onto a different proposal. The existing identity and lineage semantics are sufficient for the controlled criterion, so no external-issuer or production-currentness G decision is needed. No currentness, live institutional authority, or publishability is established by this controlled witness.
