# V3: valid input and owner alternatives for a costed acquisition route

**Status: research only; no G choice or capability closure.** Read-only review of the current 9194 candidate snapshot. This packet supplements `LOCAL/decisions/v3-costed-route-actual-zero-gap-diagnosis-20261010.md`; it does not replace that actual-artifact finding or claim a post-fix replay.

## Finding

The current `/api/v1/control/runs/nl` contract has no typed data-need field. `NaturalLanguageRunRequest` is strict (`extra="forbid"`) and carries `request`, arbitrary `context`, `data_source`, optional `target_world_scope_profile_id`, and ordinary run controls. `DataSourceBinding` contains only snapshot, input-binding, or data-view-request refs. The queued worker passes `request` and `context` to the DesignProblem compiler and the target-world profile to the recursive cycle; it does not pass the serialized `data_source` into that cycle. Thus a top-level `data_needs` or `data_requirement_specs` payload is outside the current NL DTO; putting one under `context` makes it untyped candidate context, not an admitted N7 request.

A separate existing `DataNeed`/`DataResolveRequest` path is real and typed, with metric, geography, time range, granularity, quality floor, purpose, and optional `CatalogRunProfile`. Its `/api/v1/control/data/resolve` response is fetch plans, candidates, and warnings. It does not emit an `AcquisitionRequirementGap`, call N7, or persist an acquisition-cost basis for the NL run. The `DataNeedSpec` in `scientist.agent.protocols` is another type and is not carried by this served NL worker.

The current candidate profile is explicitly `synthetic_candidate_scenario`, with mandatory `scenario_only`, real-profile/time-not-established, grounding-not-established, S8-blocked, and N9-not-admitted limitations. With a `CandidateSimulationContextHandoff`, N6 runs the configured N5 scenario and hard-codes `value_pending_n8` / `candidate_scenario_n5_only`; it does not invoke the normal N8 value owner. That is the intended boundary for this profile. Consequently, the real `RealValueOwnerGateway` path that calls `l1_dcat_variable_availability()` cannot produce an N8 missing-data gap under the same candidate handoff.

N7 itself already has a typed route, but it is gated by a cycle-terminal `ACQUISITION_REQUIRED` plus an `acquisition_request` containing a typed requirement. Cost-basis emission additionally needs exactly one owner-carried missing distribution and an exact row in the canonical acquisition cost schedule. The generic `grounding_coverage_requirement_gap` only says `grounding_relation_or_owner_lever:<candidate>`; it does not name an exact distribution. The `PolicyGroundingPort` also returns `grounding_unavailable/cgf_disposition_missing` when the candidate has no matching N4 CGF disposition. The actual retained POST completed with `a_spec_gap`, no requirement, no routing report/cost record, and zero costed pairs as recorded in the preceding diagnosis.

## Reuse-first design choice for G

**Recommended prototype, pending G decision:** reuse the existing strict `DataNeed` contract as an explicit candidate request input to the served NL run (either an optional typed `data_needs` collection on `NaturalLanguageRunRequest`, or a content-addressed request ref). Do not treat the declaration as proof. Bind each selected need to an exact request span and the current `DesignProblem`/candidate; recompute availability through a source owner over the same scope, including geography and time; then reuse `l1_variable_availability_requirement_gap`, the existing cycle `ACQUISITION_REQUIRED` route, N7 planner, and cost-basis producer. Emit the pair only when the owner has an exact scoped absence and the canonical schedule contains that exact distribution. Keep the synthetic N5 profile, candidate status, and N8/S8 limitations unchanged. A route report/cost basis is a costing/planning artifact, not acquired evidence or causal authority.

The minimal proposed fixture input for this fiscal request is one explicit need for `government.balance`, geography `UKR`, start/end `2024`, annual granularity, and purpose `effect_grounding`, alongside the already request-grounded candidate request and the same profile-selection ref. This is **not accepted by the current NL DTO**; it describes a G-approved extension prototype only. The current L1 helper has no geography/time arguments, so the existing global-count result is insufficient for this scope. A scoped catalog query and a persisted source/profile identity are prerequisites; otherwise the result must remain a typed refusal/unknown, with no costed route.

Alternatives for G:

1. **Reuse + extend (recommended to prototype):** accept existing `DataNeed` in the NL request, verify its candidate binding, extend the L1 owner/query to the declared scope, and reuse existing N7/cost contracts. This changes the public NL request schema and the served bridge, so generated/API surfaces and fresh consumer tests are mandatory.
2. **Reuse current `EvidenceNeed`:** preserve the compiler's request-grounded need as candidate input, but extend a typed owner bridge that resolves its variable/scope and computes actual scoped availability. `source_hint` alone remains a hint. This avoids a new public field but depends on compiler output and exact request-span reconciliation.
3. **Reuse current N8 path:** only when a real, admitted WMR/EvalSafety/value context is available. That changes the source/profile condition and cannot be presented as the same candidate-simulation profile path.
4. **Build a new acquisition-intent DTO/route:** not preferred while `DataNeed`, `EvidenceNeed`, `DataRequirementSpec`, L1 availability, N7 gaps, and cost records already exist. Consider only if G determines their contracts cannot express the required provenance/scope join.

The semantic choice for G is whether an explicitly requested, source-recomputed missing distribution may create a candidate-only N7 route while N5 is still `candidate_scenario_n5_only`, without promoting N8/S8 status. The data-need declaration is user-supplied intent; availability must be `recomputed` by the scoped owner; cost basis must come from the existing exact canonical schedule. No field name, LLM `source_hint`, or empty retrieval result may stand in for either predicate.

## First discriminating falsifiers

Run after source/API decision and final freeze, not in this read-only task:

- **Positive:** actual NL POST with the one typed need, same N4 candidate/profile, and a controlled current catalog whose source owner recomputes the exact UKR/2024 absence. Freshly load the compiled cycle and route; require the exact candidate/problem/need/source/profile binding, one persisted N7 report, one exact schedule-backed cost record, and one fresh route closure. Keep the cycle's N8/S8 candidate-only status.
- **No-marker control:** remove the typed need but leave the same LLM `EvidenceNeed.source_hint` and candidate-profile markers; no N7 route/cost record may appear.
- **Available/scope-mismatch control:** same need with data present at the requested scope, or an owner result for a different geography/time, must not route the target gap.
- **Cost control:** exact absence without an exact canonical schedule row yields no costed pair; it must not borrow the WDI helper's synthetic `government.balance` row or fall back to a default amount.
- **Ambiguity control:** two selected needs/costed gaps must not satisfy the strict one-pair resolver by selecting the first.

P40 classification is **SAME_CLASS_DEEPER**: this is another edge in the same served request → producer-bound requirement → persisted N7/cost → strict route-reader property, not a new example class. Widen the source/need/availability/cost join once; do not patch each field or use `context` as a proxy. Current capability labels for this input are `producer_missing` (no served producer emits the exact scoped requirement) and `bridge_missing` (typed need is not connected to N7). No closure is claimed.
