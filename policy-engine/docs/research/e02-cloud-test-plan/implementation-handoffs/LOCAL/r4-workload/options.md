# R4 shared MethodJob admission: implementable options

Status: **Option A is implemented as a candidate Runtime process profile; production authority is not established**. The implementation reuses the existing process-shared `common.async_tools` executor and routes actual `MethodBackend` dispatches through it. A configured capacity/profile revision is immutable for the process lifetime; absent Runtime fields preserve the legacy host-derived fallback. The prior C01 path lease does not constrain the investigation. This does not change the separate conclusion that the current production resource profile/cap is `not_established`.

## The property and route

The property to exercise is: across all competing MethodJobs in one configured Runtime process scope, at most `cap` actual method dispatches are active at once; admitted waiters resume, no job or fold is lost, and changing only the admission cap preserves numerical and uncertainty output for a stable input roster. For the TMLE witness, each job is one dispatch and its fold policy must remain serial (`effective_fold_workers == 1`); otherwise a MethodJob slot is not a bound on simultaneous fold fits.

The canonical route to preserve is:

`ControlWorker.dispatch_once` → `ControlPlaneService._process_control_job` / `_run_legacy_scientist_workflow` → `scientist.api.run_experiment` → `orchestration.workflows.builder.run_selected_workflow` → `run_causal_full_workflow` → synchronous `WorkflowExecutor` → `RunCausalEvaluationNode` → `_run_primary_causal_job` → `scientist.compute.runner.run_job` → `MethodBackend.run` → `MethodDispatcher.dispatch` → TMLE fold fitter.

The cleanest common choke point is `MethodBackend.run` around `MethodDispatcher.dispatch`: it is inside the canonical route after `run_job` has chosen method execution and before the real method call. A wiring test must begin at `run_experiment` through the existing ControlWorker handler path after the interface is selected; a direct `run_job` witness alone is not the Runtime bridge.

## Option A — reuse `common.async_tools` shared executor capacity (recommended to prototype first)

**Owner and unit.** The existing process-shared `_SharedExecutor` in `common/async_tools.py` now exposes a synchronous helper that executes one MethodJob dispatch on that same executor. One occupied physical executor worker equals one active MethodJob dispatch. The cap is the configured executor `max_workers` for the Runtime process, not `WorkflowRunnerConfig.max_parallelism`, a test-local worker count, or a declared `ResourceRequirements` field.

**Bridge paths.** A typed helper and same-worker inline safety check in `common/async_tools.py` are called only for `MethodDispatcher.dispatch` in `scientist/compute/runner.py::MethodBackend.run`. Runtime app/container composition resolves one optional capacity and profile revision before the embedded `ControlWorker` starts, retaining one process-wide executor identity for all Runtime calls. A conflicting second capacity in the same process fails configuration rather than creating a second pool. No `JobSpec`, workflow schema, fold scheduler, or second queue was added.

**Context and liveness.** `_SharedExecutor.submit` copies the caller's `contextvars`; the helper preserves that behavior. If the caller is already one of this executor's workers, dispatch runs inline on that worker instead of submitting and waiting on the same pool. External callers submit once and await the future. The existing saturated nested-submit guard remains fail-fast (`SharedExecutorReentrancyError`). A running Python method is cooperative and cannot be forcibly stopped; cancellation retains its physical slot until the callable returns. ThreadPoolExecutor does not promise fairness; the finite-roster witness measures resume/completion, not starvation-freedom.

**Migration and limits.** Runtime composition accepts a typed positive capacity and explicit profile revision. The profile is candidate-only and frozen for the service lifetime; absent settings use the host-derived fallback and do not establish a deployed cap. Library callers may continue using the existing fallback. The limit is process-local; multiple OS processes need an external shared owner or an explicitly bounded per-process deployment claim.

**Distinctive risk.** This couples CPU MethodJob throughput to the generic executor already used by `TaskRunner`, sync-over-async bridges, and timeout execution. That is a real reuse benefit, but noisy unrelated work can occupy the physical workers. The cap is then correct for this shared process pool, while compute-specific availability is not guaranteed.

## Option B — make the Runtime `ControlPlaneService` own a typed method-admission permit

**Owner and unit.** Extend the existing Runtime service/composition owner with one app-scoped, thread-safe `MethodComputeAdmission(capacity=...)`. One permit covers one `MethodDispatcher.dispatch`; the configured unit is active MethodJobs. Do not give each `WorkflowExecutor`, `ControlWorker`, or call its own permit: those owners are reconstructed per workflow or can coexist, which would recreate the same-scope escape.

**Bridge paths.** `RuntimeContainer` supplies a typed capacity when it builds `ControlPlaneService`; that service retains the single permit before it starts `ControlWorker`. Thread the same object explicitly through `ControlPlaneService._run_legacy_scientist_workflow` → `scientist.api.run_experiment` → `builder.run_selected_workflow` / `run_causal_full_workflow` → `build_execution_context` → `ExecutionContext` → `RunCausalEvaluationNode._run_primary_causal_job` → `run_job` → `MethodBackend.run`. `MethodBackend.run` acquires immediately around dispatch and releases in `finally`. Existing direct library callers without a Runtime permit remain out of the Runtime capability claim; no serialized state or candidate-controlled parameter may supply the permit.

**Context and liveness.** The explicit object travels with `ExecutionContext` across sync and async workflow execution; it does not depend on ambient context inheritance or reconstructing an owner in worker threads. A `Condition`-backed FIFO permit can keep bounded active count and allow queued jobs to resume. Same-thread nested acquisition must fail fast as reentrancy instead of deadlocking. A waiting synchronous caller consumes its workflow thread but not an active permit; Runtime lease heartbeats continue on their existing separate thread. On method failure, cancellation, or exception, `finally` releases exactly once. A single Runtime instance's workers share one queue; cross-process enforcement is still out of scope unless a distributed owner is supplied.

**Migration and limits.** The Runtime config must provide a required positive capacity and immutable revision. Missing capacity cannot be replaced with a guessed default if R4 is presented as configured admission; the service must decline that authority-grade run or explicitly keep its result candidate/limited. Tests instantiate one synthetic Runtime owner with cap 1 or 2. The number of source paths is larger than Option A because the owner is explicit across workflow boundaries, but provenance and scope are reviewable as typed dependencies.

**Distinctive risk.** It introduces a new admission primitive in the Runtime service even though `common.async_tools` already owns bounded physical workers. It can also block executor threads when used by asynchronous callers unless acquisition is made async there. This option is appropriate only if the shared executor cannot safely serve synchronous MethodJobs or its generic capacity is not the Runtime's intended resource unit.

## Falsifier, evidence, and decision boundary

Use a portable synthetic profile named in the test (for example `r4-local-method-cap-v1`, cap 1 then 2) and two stable synthetic studies, not production data. Each study uses distinct stable data seeds, TMLE seed 18, 3 folds × 2 repeats, and serial fold execution. Instrument the actual `MethodDispatcher.dispatch` and `tmle_core._fit_crossfit_fold`; derive the executed denominator from observed `(study, repeat, fold)` call identities. Require the observed set to equal the complete expected set, every result to reopen from CAS, measured active dispatches never to exceed the one configured owner cap, the queued study to resume, and point estimate/SE/interval/report output to agree across caps. This stays below the deferred four-study numerical run.

The gate measures active calls at the actual dispatch boundary and counts executed folds from the real fitter. `executor._max_workers`, a configured roster declaration, an exit code, or `effective_fold_workers` by itself is not the property. The full-route integration test uses two independent Runtime instances sharing one process profile and records each worker future before the outer result assertion. Its cap-1, cap-2, and bridge-removal children observed dispatch peaks 1, 2, and 2, each completed both jobs and all 12 folds, and matched saved numerical/report/envelope outputs across caps. Fresh tenant-enforced reads confirmed result/evidence ownership. The pre-fix outer route still failed when it rejected a current tracked `ArtifactRef` subclass against the emitted base reference. A targeted fix now compares complete canonical artifact identities; a branch-state positive and wrong-kind/media/profile/foreign-ref negatives pass. The cap-1 native confirmation has not yet been rerun against this fix. These falsifiers catch per-call pools and marker-only checks.

`P02`: canonical MethodJob execution is currently not bridged to aggregate admission. `P13`: do not add a fold pool or another job scheduler. `P37`: synthetic capacity/roster is explicit and candidate-grade; production config revision remains `not_established`. `P38`: property is aggregate live MethodJob dispatches ≤ configured cap; a test that checks only executor capacity is a proxy if actual TMLE dispatch can bypass it. `P40`: a second escape from the same aggregate-scope class widens the one owner to all composing Runtime calls or becomes a named bounded residual, not another pool. `P41`: no baseline numerical failure is asserted; the source/candidate and existing peer edits remain separately pinned.

**Disposition:** Option A is selected and implemented. The candidate test exercises the actual ControlWorker → Scientist workflow → TMLE path, verifies the physical cap and fold set, confirms result/evidence owner readback, and includes a bridge-removal negative. The remaining R4 acceptance gap is a passing full output/consumer projection after the canonical identity fix; the single cap-1 confirmation is pending independent root review. Neither this implementation nor the synthetic profile establishes the deployed cap or closes B56: production profile authority and roster are still `not_established`, and B56 `closure_now` remains `not_adjudicated`.
