## Source and composition findings

- On Darwin, `retry._timeout_worker_start_method()` routes timed work to `spawn`; `retry._SPAWN_TIMEOUT_NODE_IDS` admits only `scientist.node_resolve_parameters@1.0.0`. `_build_spawn_timeout_task()` resolves the builtin registry without entry points/dev scanning and requires the exact canonical node type and equality, no pre-existing mutation journal, and an empty params payload. Other platforms retain the fork supervisor path when available.
- Spawn context admission is a strict closed profile in `serialize_timeout_context()`: exact `ExecutionContext`, `FileSystemCAS`, `RunContext`, `RunManifest`, and `JsonlTraceSink`; no audit/access scope and no optional context ports; signing config, run/store ownership, ambient tenant, CAS-root/trace-path relationship, and run identity are checked. Unsupported node/context cases raise typed `node.timeout_worker_unsupported` before starting a process and do not fall back to a thread.
- The worker reconstitutes the context, checks `run_manifest.run_id == state.run_id`, installs `_AttemptAuthority(shared_active, deadline)`, and discovers builtins only. The authority checks both the shared active bit and monotonic deadline for wrapped writes. The process has no nested timeout; the parent owns the compute deadline, terminates the worker on timeout/caller exit, and revokes the shared authority in `finally`.
- Spawn creates a session before setting `group_ready`. The parent accepts a process group only when `pgid == worker pid` and it differs from the parent group. Cleanup signals that validated group, joins/kills the worker, and reports incomplete/unknown when the group handshake is absent; it does not convert an unverified process-handle-only cleanup into success. The admitted timed replay asserted the worker group died and no active child remained. macOS does not have the Linux subreaper path; the evidence covers the worker's validated process group, not a hostile descendant that deliberately detaches into another session. The source also explicitly says the authority wrapper is not a process sandbox.
- Parent success admission decodes the pipe payload through the versioned typed outcome envelope and `deserialize_outcome()` / `decode_node_outcome()`, validating the Pydantic outcome/state and replayable mutation sidecar before returning it. Worker error payloads validate their category/code/message and any failed-spend projection's run ID. The local pipe frame is length-prefixed JSON/base64, not cryptographically authenticated; this is a same-host worker transport, not an untrusted remote-worker trust claim. The successful outcome path does not independently compare its `state.run_id` with the parent's expected ID; for this canonical node, the context/state identities are checked before execution and state writes are restricted to declared ResolveParameters paths.
- The real consumer witness is `test_real_workflow_selector_replays_saved_source_with_current_live_replacement`: it runs `ResolveParametersNode` against a retained SKG read after replacing the live database, then checks the resolved parameter came from the retained source, input/state immutability, manifest binding, and hash of the materialized selected snapshot. The timed and async cases on Darwin verify spawn rather than fork plus group/child cleanup.
