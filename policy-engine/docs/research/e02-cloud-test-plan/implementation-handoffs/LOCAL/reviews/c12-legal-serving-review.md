## Findings

The Legal producer-to-HTTP path is behaviorally complete for a client that supplies the exact immutable selected-generation intent and a runtime-composed encoder provider. The producer encodes with a loaded model and passes that same model to the generation builder; the builder recomputes the identity. The request DTO is frozen and rejects extras. The runtime parser distinguishes absent intent from empty or malformed-present intent. A fresh served graph recomputes selected generation/member basis, matrix-to-HNSW correspondence, and encoder asset identity before returning vector-enabled hybrid results. Provider absence and stale/malformed requests retain real text results with typed refusal. The selected producer, fresh reader, native HNSW, and real HTTP-route witness is in `test_producer_generation_reaches_native_http_with_typed_vector_modes`.

I found two caller-surface limits that should bound any closure claim:

1. **The dashboard is typed but does not originate or display Legal vector intent/status.** Its current page sends `query`, `top_k`, and `output_dir`; it neither sets `query_generation_intent` nor displays `search_mode` / `vector_refusal_code`. A complete source census over 1,117 dashboard `.ts/.tsx` files found query-intent references only in generated types, the validator/schema and its tests. The receipt `LOCAL/i4-c12/runtime-dashboard-api.md` explicitly leaves local browser/runtime display out of scope, so classify that first-party path as `surface_out_of_scope` and the dashboard profile-emitter bridge as absent; do not claim dashboard vector search is enabled. The API accepts a valid external immutable profile, but the source census across 2,709 production Python files found no production constructor of `LegalQueryGenerationIntentV1` or `LegalQueryProfile.from_generation`; only the DTO and HTTP intake refer to that request field. The API profile-emission bridge for a first-party client remains `bridge_missing` unless an external client owns it. Root-generated `types.ts` now contains the field; the earlier dashboard receipt sentence saying it was not edited is stale and should be refreshed.

2. **Catalog's refusal reaches the graph but is lost at result and artifact projections.** The current typed fields are `QueryMetrics.vector_search_refusal: str | None` and optional `DatasetSearchResult.search_explanation: dict[str, object] | None`; the graph attaches the refusal only when `explain=True`, and `search_datasets` returns only `list[DatasetSearchResult]`. I reproduced the mismatch with a real temporary Catalog generation, then mutated a projected member while leaving the generation selector unchanged. Through the actual `KnowledgeToolkit.search_datasets` call (`explain=False`), the text fallback returned `ds-currentness` with `search_explanation=None` while the graph's metric held `catalog_material_basis_mismatch`. The registered `search_datasets` tool serializes that model result without a refusal or explanation field before the tool loop injects it as a role=tool message. The deciding output is `catalog-toolkit-refusal-probe.log` and `catalog-caller-projection-probe.log`.

The other direct production consumers are `MeasurementRootProducer.produce_from_catalog` and the workspace loop; both request `explain=True`, but `canonical_catalog_result_for_workspace_loop` explicitly removes `search_explanation` before the selected Catalog result enters the quality payload. The same probe demonstrates that this projection drops the actual mismatch reason. Thus the Catalog selected-generation/member checks may refuse vector ranking correctly, while the downstream consumer or persisted artifact has no retained mode/refusal fact. This is a `P03` status-surface gap (`surface_missing`) across the Catalog result contract, toolkit/LLM adapter, and workspace artifact bridge; it affects the consumer and audit/provenance criteria, not the graph's currentness check. The complete source census records all five `last_query_metrics` references within the graph implementation and no production metric consumer.

The LLM path is conditional, not currently wired with a Catalog instance: the tool adapter exposes `search_datasets`, but `_default_scientist_tool_registry()` constructs `KnowledgeToolkit()` without `dataset_catalog`, and AST inspection of all 2,709 production Python files found zero `KnowledgeToolkit` calls with a `dataset_catalog` argument. Do not claim that the current default LLM runtime searches this Catalog. `format_dataset_context` also omits result explanations and has no production call site in this source set. The production workspace/measurement consumers are the concrete current surfaces above.

**P40: SAME class** as consumer-side loss of typed fallback status, one level deeper than the graph receipt. The closure should be one typed result/mode/refusal projection carried through the canonical Catalog result owner, toolkit/tool serializer, and workspace payload, not separate call-site patches. The falsifier is a stale selected generation through each real consumer: the row may remain available as text fallback, but the returned tool/audit payload must preserve `search_mode="text"` and the typed refusal. Removing that propagation while keeping marker fields must make the consumer test fail. That caller-level property is not present in this candidate.

The API route is tenant-permission guarded, but `LexSearchRequest.output_dir` is client-controlled and the service uses it directly to construct the DuckDB and index paths. This review did not establish a tenant-to-path binding. The positive HTTP test intentionally disables security middleware and is a compatibility witness only; it proves neither tenant isolation nor deployed provider configuration. Treat path confinement and deployment ownership as `not_established` at this boundary, not as a property of this test.

## Currentness, authority, and P40

For Legal and Catalog, the tested material predicates are recomputed from the selected complete generation and current projected rows; the HNSW/matrix comparison uses the shared vector correspondence helper. The live encoder asset identity is recomputed from the loaded encoder. Those predicates support retrieval compatibility only; neither response grants legal authority, production model authority, or model-quality evidence.

**P40: SAME class for executable-encoder identity.** A static asset digest does not prove the behavior of an arbitrary `encode` callable. The same-assets callable-swap test passes while showing this residual; the Legal README and C12 receipt already state it. The smallest absent capability is a trusted executable/code identity bound to the loaded encoder. The falsifier is the existing `test_runtime_asset_provider_cannot_detect_same_asset_query_callable_swap`. No second per-provider repair is proposed.

The response value `search_mode="vector"` means the vector-enabled **hybrid** path completed without a refusal; `LegalKnowledgeGraph.hybrid_search` still fuses text and vector results. The positive HTTP test verifies actual vector admission and ranking in that mode. Consumers should not interpret it as vector-only results.
