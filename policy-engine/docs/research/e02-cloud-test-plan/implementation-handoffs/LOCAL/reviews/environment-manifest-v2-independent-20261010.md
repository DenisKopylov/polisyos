## Material findings and limits

1. **Medium — wrapper plugin readback can be labeled resolved after source drift.** In _validate_command_capture (adapter lines 636–664), the wrapper branch reads before/after source identities and computes readback_equal, but plugin_content_bound explicitly substitutes True for that predicate when wrapper_receipt is true. A wrapper receipt whose before/after identities differ or whose identity status is failed can still yield plugin_source_binding.status: resolved if pytest_origin_plugin_sha256 equals the current plugin file. The separate source_readback field can say mismatch/not-established while the plugin binding says resolved; the top-level reason list only checks the latter. The current V5 non-wrapper receipt has matching four-path before/after maps, so this is not the observed V5 state. Smallest direction: require the wrapper’s source identities to be PASS and equal for this component too, or keep the plugin binding not_established. The source-freeze barrier still prevents a complete observation today, so this is not evidence of a v1-admission bypass.

2. **Medium — the external completeness predicate covers roots, not all loaded child origins.** The process plugin documents one observed origin per top-level root and stores child module names, but selects one origin at plugin lines 418–425 and emits only that origin plus names at lines 493–510. It computes external_complete from those root rows at lines 514–519. The adapter’s _capture_summary then checks root status triplets and the plugin aggregate status (adapter lines 329–414); it has no per-child origin evidence to reconcile. A loaded child whose origin/owner differs from its parent can therefore remain unexamined while a root row is resolved. V5 itself avoids a false complete state because the namespace root is unresolved and the sidecar lists non-filesystem modules, but this capture shape cannot satisfy the note’s required “every root and every loaded child” completeness rule. Keep child-level completeness not_established until the producer emits per-module origins and the consumer checks them; do not promote a parent’s owner to its children.

3. **Bounded current-result limitation — V5’s PASS is not a fully command-bound result.** The command output includes argv with a JUnit path and the adapter reads/hashes the referenced JUnit file, but this legacy metadata has no JUnit hash or output inventory. The adapter validates command stdout/stderr hashes and parses JUnit (lines 527–552, 633–635), yet cannot reconcile the JUnit bytes to that command. A final wrapper receipt does include junit_sha256 when present, which this adapter checks; the V5 observation predates that receipt form. Until the current wrapper positive binds JUnit and all other outputs, retain the test outcome as partial evidence rather than a complete command result.

The adapter cannot emit a complete observation by construction: source_freeze_status is assigned only bound_pending_git_recomputation or not_established (lines 932–937), and every non-resolved source-freeze state adds a refusal reason (lines 938–940). Thus observation_status cannot become complete, and strict v1 projection cannot become a candidate. This is a safe prototype boundary, not an accidental green. The source/frozen manifests are self-digest checked and cross-compared, then projected as reconciled_manifest_projection; the adapter does not read each listed file or recompute completeness against Git. It correctly stops short of calling that a resolved freeze. A final admission component still must recompute the candidate tree/parents/source census, all source and fixture input bytes and denominator, command-output inventory, and runtime/profile relationship.

The v2 backend_profile field is copied from an optional handoff and labeled bound_by_handoff (lines 974–979); no handoff schema or actual-runtime/profile equivalence is validated there. V5 has no handoff and correctly reports profile IDs as null/not established. A future handoff value is a selected-profile claim, not proof that the observed executable, version, platform, package set, and settings satisfy that profile. Keep that distinction explicit until a source-bound profile rule compares them.
