## What the admission artifacts can carry

The current emitter is `LOCAL/emit_proposals.py` (SHA-256 `2114e764d98afa1663d367614704f0403a8e6a7aa680b64d3c3c1ad674ea7c5b`). The v2 handoff can bind exact base/candidate commit and tree, ordered candidate parents, changed and selected unchanged paths with Git blob and content SHA, inputs, backend/profile, commands and stdout/stderr refs, producer/artifact/bridge/consumer, controls, limitations, exact occurrence triples, and per-occurrence decision refs. Validation resolves the Git commit/tree/parent objects, checks ordered parents and base ancestry, reconciles footprint rows to the complete candidate census, and checks referenced source/output bytes and hashes. `proposal_occurrences` requires exactly `{finding_id, occurrence_pointer, criterion_sha256}`; every bound occurrence must have a distinct, occurrence-covered decision record. `UNRUN` commands need a reason; completed command rows need both output refs. Ignored raw output is validated from local bytes, including path, ignore rule, symlink, and digest checks. A handoff cannot self-claim formal closures.

The v4 evaluation shape separately binds the frozen candidate, full-footprint SHA, exact `(occurrence_pointer, sha256)` key, execution context, evidence refs, attempts, next check, and P40 classification. For selected inputs the validator checks an explicit input denominator and per-identity selected/unavailable, authority, permission, context, and verification refs; missing or unestablished inputs cannot support `VERIFIED`. It also requires a named backend/profile, consumer surface, a typed receipt, and occurrence-specific decision research. Omitted occurrence rows remain `UNRUN`, as intended.

Two semantic validator gaps must be resolved before treating the guide’s criteria as mechanically enforced:

- **`VERIFIED` is weaker in code than in the guide.** `validate_typed_slice_receipt` only requires some command status `PASS` for `state == "VERIFIED"`. The required `property_positive`, `actual_consumer`, and `negative` evidence-role set is enforced only when `proposal_disposition == "closed"`. Consequently, a `VERIFIED` evaluation with no disposition (or a non-closed proposal) can pass without those three roles, despite the guide saying every `VERIFIED` result requires them. Require the three roles for every `VERIFIED` evaluation, not only a proposed closure; retain the existing extra G boundary.
- **Environment binding is a format check, not a recomputation.** The handoff validates `backend_id` and `profile_id` as nonempty and `environment_sha256` as 64 lowercase hex. It does not resolve a canonical environment-manifest ref and recompute that digest. The guide requires the digest to name the exact environment manifest, including runtime/platform, backend/profile recipe, lock/config hashes, loaded import origins, relevant environment settings, command, and fixture/input identities. Bind that manifest as source-backed evidence and compare the digest; also make the backend-profile evidence pointer identify the actual `backend_profile` object.

The command schema preserves argv or command text, status, and full output refs/hashes (or an explicit unrun reason), but it does not require cwd, exit code, elapsed time, or RSS fields. The execution plan requires relevant timing/RSS and installed-consumer evidence. Preserve these as separately hash-bound, validated evidence artifacts where required; a command status string alone cannot prove its execution context. Likewise, the typed full-tree census is complete, but each selected slice must still enumerate the source, test, config, lock, generated, fixture, and consumer companions that actually govern its criterion.
