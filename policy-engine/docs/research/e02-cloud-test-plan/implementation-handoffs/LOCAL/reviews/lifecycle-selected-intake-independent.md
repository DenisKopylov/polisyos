## Proof/readback boundary (P29/P38; P40: same class, deeper witness)

`_finalize_workspace_loop_run_proof` documents that it performs a control-store read, not an HTTP receipt. It reads `current_execution_completed_job_record()`, records `read_method="ControlPlaneStore.get_job"`, uses the passed POST endpoint `/api/v1/control/runs` as `surface`, and appends the tokens `control_job_status` and `runs_readback` (`workspace_loop_transition.py:871-943`; called after worker completion in `job_scope_admission.py:879-905`). The served GET is performed after dispatch in the integration test; it does not write a route receipt into the already-finalized proof. Existing assertions call the store observation a `runs_readback` and assert its surface is the POST path (`test_workspace_loop_transition.py:499-511, 2344-2371`).

The implementation is explicit about its measured property (completed store state), and the separate GET test is real. The divergence only matters if the proof/release language is used as evidence that the actual served GET was witnessed. A falsifier is to omit the GET while retaining worker completion and proof markers: the persisted proof/readback remains present. The smallest closure is either (a) keep the durable proof explicitly store-read-only and narrow the claim, or (b) add a separately emitted route witness bound to the job/request and have the consumer verify that witness; field names alone cannot establish a GET. Because this is the second occurrence of the proof-vs-served-route witness class in this review chain, I record it as a bounded residual with this falsifier rather than proposing a local repair.

The release fragment `release-fragments/unreleased/2026-10-10-e02-production-case-selected-intake.toml` correctly says the route is candidate-only and leaves the public-surface inventory unreviewed. Its API sentence says a fresh CAS reader recomputes admission “before the completed-job proof/readback is accepted”; that is true of the test’s later fresh-store assertion, but not a serving gate in GET or the proof writer. Narrow that temporal/acceptance implication before treating the fragment as evidence of a route-bound proof. The fragment correctly marks client compatibility `requires_regeneration`.
