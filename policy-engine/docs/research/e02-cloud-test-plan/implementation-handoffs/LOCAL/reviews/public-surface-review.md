## Findings

1. **The 2026-08-27 Lex ownership fragment matches the live Lex surface; its removals predate this candidate.** On the live interpreter, all 51 names in `polisyos.lex.__all__` resolve. `HierarchicalPolicySearchAdapter`, `TemporalInterventionSequenceCompiler`, and `TemporalInterventionSequenceCompileResult` are absent from both `polisyos.lex.__all__` and root attribute lookup. They resolve only from their Scientist implementation modules and are absent from those modules' `__all__` and the Scientist package facades. `CompiledLexIntervention` resolves from `polisyos.ir`; `TemporalInterventionSequencer` resolves from Lex but has no `to_dynamic_treatment` method. The public ownership change is therefore applied as described. The Lex facade and intervention source blobs are byte-identical between G `93d6` and candidate `077a`, so this review found no new removal against G.

   `docs/reference/public-surface.md` and `architecture/public_surface/inventory.json` still mark the Lex and Core export counts as unknown because the static resolver stops at `from __future__ import annotations`. The reference page also lists 51 source-declared Lex candidates. This is a bounded static-resolution result, not evidence that either facade has zero exports. The candidate inventory should remain with root's planned canonical regeneration; I did not run it.

2. **The 2026-09-13 Native chronology API is preserved at the declared Core root and requires persisted custody.** `NativeChronologyQualified` appears in `polisyos.core.__all__`, and live imports from `polisyos.core`, `polisyos.core.contracts`, and `polisyos.core.contracts.chronology` resolve to the same class object. Its `projection_receipt` model field is required; the validator binds the receipt statement to the same reconciliation and verified proof. The Core root and chronology source blobs are unchanged from G `93d6`; the persisted-custody semantics are already present in that pinned baseline.

   Current runtime-quality documentation says the native projection is persisted and reopened before qualification, and that empty owner/policy slots refuse. The runtime-services README says the dashboard's nongenerated acquisition adapter accepts the strict negative/positive wire union, while the generated client remains unchanged. The current adapter source contains the separate pending/activated arms and keeps positive native qualification distinct from action authority. These agree with the release fragment's migration boundary.

   One **inherited** facade defect is visible: explicit `polisyos.core.contracts.NativeChronologyQualified` import works, but the symbol is absent from that module's `__all__`; `from polisyos.core.contracts import *` currently raises `AttributeError` for the literal `*_CHRONOLOGY_EXPORTS`. The same literal is in G `93d6`'s module source, so this is not a regression from the 09-13 change. The stable `polisyos.core` root export remains functional. Keep this separate from the acquisition fragment unless the compatibility promise is intended to include wildcard import through the subpackage facade.

   The generated reference page lists `NativeChronologyQualified` among Core's source-declared candidates but explicitly marks native export resolution incomplete. It does not document the custody semantics in that generated inventory; the runtime-quality and runtime-services READMEs plus the release fragment do. No absence claim follows from the inventory's `unknown` count.

3. **The first-party Legal dashboard is an existing caller, so its whole surface cannot be called out of scope solely because the prior author slice did not change or test it.** Original I4 requires an actual request → typed profile → encoded query → fresh reader path, with wrong/missing profile refusal (`TASKS.json` lines 455–472; connected plan `tasks.json` lines 117–127). The delivery plan says HTTP/NL callers send a typed profile, and the current next action explicitly says to preserve refusal code and truthful text fallback (`03-delivery-plan.md` line 26; `TASKS.json` line 471). These criteria do not name a browser requirement, so the dashboard's required status is not established by I4 alone. But the old `runtime-dashboard-api.md` receipt's statement that browser display was not changed/tested is a test-scope statement, not an adjudication that the live first-party consumer is out of product scope.

   The live `LexKnowledgeGraphPage` calls `useLexSearch`, which POSTs `/api/v1/control/lex/search` and parses `lexSearchResponseSchema`. The request schema accepts a strict `query_generation_intent`; the response schema has `search_mode` and nullable `vector_refusal_code`. A runtime comparison found exact current field parity: `LegalFactResult` has 49 fields, the Zod item schema has 49, and neither set has missing or extra fields. The generated request/response types also contain the typed profile and result-mode fields.

   The page's actual request body only sets `query`, `top_k`, and `output_dir`; it never sets `query_generation_intent`. It also never reads or renders `search_mode` or `vector_refusal_code`. The hook preserves the parsed fields, but the component drops them. Thus this page is currently a text-only caller that cannot show whether the result is vector or fallback text, or why vector admission refused. The request can legitimately use the supported no-intent fallback, but the page does not project the typed mode/refusal that the API returns. If this first-party UI is in scope, the accurate labels are `producer_missing` for its selected-profile emitter and `consumer_missing` for its mode/refusal projection. If the UI remains text-only/out of scope, that needs an explicit scope decision and bounded limitation; the existing author receipt is not enough to label it `surface_out_of_scope`.

   P40: this is the same hidden-consumer-surface-loss class already noted in the earlier C12 review, one level deeper than the Zod response contract. I did not propose a per-field patch. The smallest closing capability is one page-level selected-profile flow plus visible mode/refusal projection, with a UI test proving both a matched vector result and a typed refusal/text fallback. If root keeps it out of scope, record that as the bounded residual and falsify the claimed text-only boundary by checking this existing route's actual request/response path.

   A small contract precision delta remains: both Pydantic response DTOs default `search_mode` and `vector_refusal_code`, so their JSON Schema does not mark either field required. Generated `types.ts` requires `search_mode` but marks `vector_refusal_code` optional; the dashboard Zod response validator requires both, including an explicit nullable refusal key. The live server path populates the mode/refusal fields, so this is a requiredness/schema-alignment issue rather than a missing DTO field. Reconcile it if the external contract intentionally requires both keys.
