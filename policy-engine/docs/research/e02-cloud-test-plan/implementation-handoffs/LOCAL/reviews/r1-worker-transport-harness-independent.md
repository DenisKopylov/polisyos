The node checks exact Decimal type and tuple preservation before returning a typed `NodeOutcome`; the parent checks the serialized typed outcome and observed process ancestry. Linux retains the fork-backed timed custom-node route. I found no modification to the production timeout allowlist or timeout admission path.

The registry override is a test fixture for injecting the custom node into this worker invocation. It means this test demonstrates the transport and worker execution path, not production component discovery or worker admission. On Darwin, `timeout_s=None` intentionally exercises the untimed generic worker path; this test does not establish that a custom node is admitted to the closed spawn-timeout path.

**Runtime evidence is still required.** I did not run tests or start processes, as requested. The cited pre-change macOS run records 85 passed and two failures, both at `parent.poll(10.0)`, along with Python's multithreaded-fork warning; it does not prove a lock or establish the new child's startup time. The new 10-second result bound is therefore unmeasured. One portability boundary remains: the non-Linux branch selects `spawn`, but the ancestry helper uses `ps` when `/proc` is absent. That is suitable for the macOS target; it is not a portable Windows ancestry implementation. The note's “other non-Linux hosts” wording should be read as Unix-like hosts with `ps` unless Windows support is separately added and tested. The repository evidence inspected here does not establish Windows as a supported test host.
