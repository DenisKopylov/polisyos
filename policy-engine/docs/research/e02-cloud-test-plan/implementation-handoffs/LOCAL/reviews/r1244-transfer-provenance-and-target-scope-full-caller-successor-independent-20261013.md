## Blocking findings

1. **The controller supplies a synthetic `unknown` run ID as an explicit target declaration, then conflicts with the real search ID.** In virtual `transfer_context.py` lines 612–617, `resolve_transfer_context(candidate=candidate)` returns a `TransferContext` with `run_id=str(resolved_run_id)`; absent a supplied run or fallback, that value is `"unknown"`. Because the constructor receives `run_id`, it is in `model_fields_set`. The virtual controller at `controller.py:2449` calls the resolver without a run ID or fallback. `ParetoRegistry.update` at `pareto_registry.py:432–438` then resolves that context while declaring the actual `loop_id` as `run_id`; the strict field reconciliation sees explicit `"unknown"` versus the controller-owned search ID and refuses the update. The existing controller control in the virtual test file (`test_phase_b_policy_runtime.py:2287–2334`) uses a generator returning only `{"candidate_id": "candidate_b"}` with `initial_context={}` and expects a persisted Pareto projection, so it reaches this path without a candidate run ID. The controller companion only forwards the context to the two reads after `update`; it cannot repair the failed write. **Effect:** ordinary typed policy searches that use this controller/registry path can fail before persisting the frontier. **Smallest direction:** bind the controller-owned current search ID as the resolver fallback/target declaration before constructing the context; retain refusal for a genuinely conflicting supplied declaration. Do not downgrade the shared mismatch check.

2. **A source-domain query is applied again to the transformed destination domain.** The candidate’s own comment in `lessons.py:563–565` says query task/domain/run fields select source cards and `target_context` is the destination. `find_transfer_candidates` applies `_entry_matches(entry, query)` before materialization (`:660–665`), and `_revalidate_transfer` checks the original card before mutation (`:766–771`, `:1286–1295`). Cross-domain transfer is intentionally allowed by the default `TransferPolicy` (`allow_cross_domain=True`) and uses the destination domain when constructing the materialized card (`:778–800`). The final `_matches_query(materialized, query)` at `:800–801` then compares `query.domain` against that overwritten destination field (`:1117–1120`). A `LessonQuery(domain="fiscal")` that correctly selects a fiscal source card is therefore discarded when the explicit target context is `domain="labor"`. The new source-run separation test (`test_lesson_transfer.py:1420–1491`) uses fiscal source/labor target but omits `query.domain`; the other cross-domain positive control (`:1236–1277`) also omits it. Neither catches this divergence. **Effect:** valid cross-domain candidates disappear when callers use the documented source-domain selector. **Smallest direction:** keep source-only selectors bound to the source record and reapply only predicates whose fields remain semantically unchanged on the materialized target; add source-domain→different-target-domain and conflicting/negative controls through the same write/materialize/fresh-read path.

These are two escapes in the same source-versus-target context class, not a new class. Under P40, stop per-case repair and widen the shared mechanism so source selectors, destination fields, and controller-owned run identity remain distinct through lookup, materialization, update, and reread. The existing contract already has a place to express this distinction; the missing capability is to carry it consistently across the whole reader/writer/controller path.
