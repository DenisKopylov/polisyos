## Property review

The test is an actual producer-to-CAS-to-fresh-reader scenario. `run()` invokes `run_stress_test(..., cas=store)` and obtains the persisted report reference; the producer persists the selected plan and basis, resolves them to derive the score, then persists the report (`adversarial.py`, around lines 794–886). The test reads the selected basis and plan back from CAS and creates wrong-profile refs from those stored values. For the wrong-plan case, it keeps the plan body from the selected producer ref, writes it under `wrong.AdversarialPlan` with the same kind/media, and checks equal content-addressed artifact IDs but differing manifest-profile hashes. `FileSystemCAS.put_bytes` derives the artifact ID from SHA-256 of canonical payload bytes (`core/artifacts/store.py`, lines 2618–2647); this is a content-addressed same-body control, although this wrong-plan branch does not also call `get_bytes` for an explicit byte-for-byte assertion. The later wrong-basis control does retain explicit `get_bytes` equality for its unchanged payload.

The source has two distinct valid diagnostics. The lower component resolver checks the selected plan schema and returns `invalid / adversarial_plan_unreadable` for that rejected plan (`stress_report.py`, lines 311–326). The outer report resolver calls the component resolver; when a report still claims `score_status == "available"` or has a non-null score, it deliberately rewrites any failed inner result to `invalid / score_claim_without_resolved_basis` and clears the score (`stress_report.py`, lines 625–637). R1285 correctly adds a direct component-resolution assertion for the wrong-plan case, then expects the outer report resolution to carry the broader claimed-score refusal. That two-layer expectation matches the source.

The candidate does not apply that distinction to the remaining selected-report cases later in this same test:

- Wrong basis schema: `resolve_stress_report_artifact` is still expected to expose `outcome_basis_unreadable` (current test lines 936–942), but the report still claims an available score, so the outer guard returns `score_claim_without_resolved_basis`.
- Missing plan profile: the test expects outer `unbound / adversarial_plan_profile_missing` (lines 960–966), but the same available-score guard changes this to `invalid / score_claim_without_resolved_basis`.
- Forged outcome roster: the test expects `plan_outcome_roster_mismatch` from the outer resolver (lines 1004–1008), but the outer guard again replaces that inner diagnostic with `score_claim_without_resolved_basis`.

Thus, after the R1285 wrong-plan assertion is corrected, the next wrong-basis assertion is the first remaining failure; the stale-profile and forged-roster assertions remain unreachable until that is corrected. This follows directly from the candidate postimage plus the source guard and does not require executing tests. The existing partial-basis control is different by design: its report claims `partial` and has no score, so the outer available-score rewrite does not apply; the test preserves the genuine `partial / expected_occurrence_rows_incomplete` result (lines 1010–1052). A replacement should retain that control and avoid weakening the no-score invariant.

The divergent examples are wrong schema, missing selected profile, or forged roster behind an available-score report: outer output is `score_claim_without_resolved_basis`, score cleared. The two-level R1285 wrong-plan case is a sound example, but not yet a complete test oracle for the siblings.
