## What the source and tests establish

The raw response normalizer distinguishes missing, reported, estimated, and invalid cost evidence. Exact reported zero stays zero. Explicit null or malformed presence does not fall through to a later alias or an estimate. JSON number/string/bool/null/array/object values, negative and malformed values, alias shadowing, `usage.cost`, and values that underflow or overflow binary floating-point are exercised through the raw Gateway → Traced → durable-ledger path. Invalid or pending evidence yields unknown/null totals rather than a fabricated zero.

Configured route/model identity and pricing basis come from the server-selected client/producer intent. Raw response `provider` and `model` labels are not admitted as authority. The falsifier changes those self-labels while leaving the selected client configuration intact; the persisted event and estimate remain bound to the configured route/model. An estimate is explicitly an estimate, not a reported provider amount.

Producer settlement is backed by a durable begin and terminal event. On a lost acknowledgement the reader resolves the exact event; if settlement is still pending, the event remains pending/unknown and the observer does not emit a contradictory terminal claim. Cache cancellation and reuse retain separate local event semantics: the owner call settles, while admitted reuse has a separate zero-cost event. Scope-admission tests vary seed, instruction, snapshot, tenant, scope, purpose, epoch, and independence; distinct admissible requests do not join one flight. The PI same-content test exercises two distinct `create_problem_frame` and `decompose_task` operations through the actual PI and cache wrapper; the controlled provider returns separate outputs and both calls are made because the operations are not cache-authorized. These are local accounting semantics, not external charge counts.

The route witness is an actual NL POST through job/outbox/worker dispatch to a simulated provider producer, followed by reopened app-ledger read and a fresh `/agents` GET. The GET owner is resolved from the persisted completed job and its created-event/outbox relation, execution scope, profile, run derivation, and attempt. The updated Insights fixture uses that owner-bound route setup. A `control_job_id` marker or ledger-shaped DTO row alone does not establish ownership. Fresh GET carries a durable begin-only event as pending/unknown, with null aggregate cost. The pending case is a controlled persisted-boundary fixture; it is not an actual killed-process recovery test.

The P38 property-removal probe kept the persisted run evidence and binding but removed the ledger reader’s event rows. GET then refused with HTTP 400 `agent_pipeline_cost_event_ledger_reconciliation_failed`. This is the expected negative control: the consumer turns on exact ledger reconciliation, not DTO markers.
