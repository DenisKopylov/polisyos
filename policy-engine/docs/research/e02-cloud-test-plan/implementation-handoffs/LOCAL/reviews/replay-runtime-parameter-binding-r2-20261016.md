## Review findings

R2 correctly separates two properties. R1's real temporary-CAS consumer probe proves an actual candidate A/B mismatch: the outer owner admits A, but `_resolve_candidate` selects same-byte/same-ID B when the runtime parameter points to B, whose selected manifest profile differs. R1's separate profileless control shows that resolver can use the default manifest view. Neither is evidence that a complete 37-node run currently passes replay or promotion; R2 keeps that question `UNRUN / NOT_ESTABLISHED`.

R2 also accurately diagnoses the R1 raw-snapshot origin falsifier. A snapshot-derived B and B's current manifest edges were accepted by the R1 prototype after it was labeled `producer_typed`; that established only consistency with caller-supplied data. R5 removes the binding factory and authority-like labels. Its comparison checks the exact JSON Pointer, full `ArtifactRef` identity (including selected profile), selected manifest identity, physical store verification, and expected lineage edges. Controlled A vs A yields only `IDENTITY_AND_SELECTED_VIEW_CONSISTENT_ONLY`; B vs independently held A refuses, including nested and list members. Crucially, raw B compared to itself still passes that limited consistency check, while the prototype reports source provenance and semantic admission as `NOT_ESTABLISHED`. That is the correct treatment of the falsifier: R5 repairs the claim boundary, not the missing source receipt.

There is one useful existing reuse candidate omitted from R2's explicit inventory. `RunProvenanceDAG` (`run_dag.py`, SHA-256 `720a5e32ea0362580a31c7c54f239a8f8c401b68994d303274f3fa4f1dbb8853`) can produce a persisted `scientist.provenance.run_dag` artifact when an executor is given it. `record_node_execution` records run/node/alias and times, a generic `params` map, dependency-output input edges, and actual node output refs. It is not sufficient as currently written: `AsyncWorkflowExecutor` and `WorkflowExecutor` receive this as an optional argument; the standard builder calls `_maybe_create_provenance_dag(state.run_id)` but discards its return and constructs `WorkflowExecutor` without `provenance_dag`. Where directly wired, the recorded `params` are static `NodeInvocation.params`, and input edges come from upstream `_node_outputs`; neither records the actual runtime `ExperimentState.params` value selected at a specific JSON Pointer and consumer role. Thus this is a concrete reuse/extension option, not present evidence and not a reason to build a new provenance subsystem by default. R2's general “extend existing run/event/node output boundary” option can cover it, but its source inventory should name it and its current wiring gap.

The other inspected reuse surfaces support R2's boundary:

- `RunContext` and `RunManifest` are durable run owners, but manifest `inputs`/`outputs` are unkeyed lists. `TraceRecord` has run/phase/event plus `TraceRefs(inputs, outputs)`; `RunContext.emit` does not encode a parameter pointer, invocation role, or source precedence. Current async node start events carry no refs, and node completion events carry outputs, not the runtime inputs consumed from `state.params`. Extending this event path is viable only if the actual trusted intake/consumer emits a typed selection record at the selection point.
- `ExperimentState` has typed input/artifact/report maps, while `params` remains JSON. `NodeOutcome.artifacts` and `_pin_cross_layer_input_ref` can preserve existing explicit typed outputs/inputs on routes that use them; `_pin_cross_layer_input_ref` does not cover the 37-route fallback denominator. `policy_blueprint_runtime_reporting.py` serializes `session.candidate_ref` into params, but that JSON dump is not a durable original-run path/role record.
- The cited C10/C11 materials correctly describe separate capabilities: C10 supplies the fresh ValuePort/S10 producer-reader bridge; C11 owns the Level 2/search consumer, with C07 shared DTO/schema/ref/facade support. These are relevant examples of source-bound producer/consumer composition, but their own owner labels or receipts do not prove which ref a Scientist workflow selected at an original runtime parameter path.

The requested origin rule and conditional legacy policy are appropriately narrow. A serialized ref, manifest/profile hash, current CAS verification, producer string, or origin enum alone cannot establish original selection. Eligibility must depend on the actually consumed ref set and its actual source precedence. A no-params-ref route can retain existing snapshot/archive behavior; a route fully supplied by typed refs can remain eligible only when the actual consumer resolves the same complete selected identity/profile and its content/lineage checks, not merely the same artifact ID or payload. If a params fallback is actually consumed and the original selection is not durably recorded, semantic replay is `not_established` for that route while archive/snapshot inspection remains available. This is consistent with the A/B same-ID, different-profile falsifier and avoids a version-only v1.0 ban.

The three G choices are concrete: (1) ratify that origin evidence must be captured at the original typed intake/producer transition, with run, invocation, exact JSON Pointer, consumer role/source precedence, full selected ref/profile, and content-bound lineage; persisted labels cannot self-authenticate; (2) choose reuse/extension of an existing run/event/node artifact versus a versioned replay-basis receipt; and (3) ratify conditional legacy eligibility and the `not_established` result when a consumed fallback lacks that evidence. The decision does not invent issuer, law, calibration, currentness, or external authority. The S/M/L bands (1–2 days after an exact record is found; several days for a bounded owner alias; more than a week/multi-owner for the 36 mapped routes) are explicitly provisional engineering planning bands, not measured commitments. Full workflow grade/promotion remains unrun.
