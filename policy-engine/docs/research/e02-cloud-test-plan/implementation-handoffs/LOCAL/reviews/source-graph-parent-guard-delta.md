## P38 and P40: source graph depends on Git’s view

The property is “the declared parent headers and ancestry are those of the pinned Git objects.” The implementation reads with ordinary `git cat-file`, `rev-parse`, and `merge-base`; it does not set `--no-replace-objects` / `GIT_NO_REPLACE_OBJECTS` or reject grafts. Git documents that replacement refs are used by default by Git commands and that `--no-replace-objects` disables them; the repository-layout docs describe `info/grafts` as fake commit ancestry ([git-replace](https://git-scm.com/docs/git-replace), [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout)). A repo with a `refs/replace/<candidate>` entry pointing to a same-tree commit with a different parent list is a concrete divergent case: the ordinary `cat-file` view can report the replacement’s parents while the SHA still names the original object. An `info/grafts` overlay can alter ancestry traversal. The current worktree has no replacement refs, is not shallow, and has no `info/grafts` file, so this is an environment-sensitive residual, not an observed false acceptance in the current run. I did not create such refs or grafts because Git mutation was prohibited.

**P40 bucket: `SAME_CLASS_DEEPER`.** This is the same source-graph binding class one level below comparing a supplied parent list: the Git view itself may be overlaid while the declared SHA remains fixed. Widen the graph-resolution mechanism once by forcing raw-object mode for all relevant commands and refusing graft overlays, or record this exact overlay scenario as a bounded residual and retain its falsifier. Do not patch a per-receipt instance or describe the current standard-repository pass as universal.

## Partial-object and unavailable-object behavior

`parse_git_commit_header` rejects a missing header/body separator, malformed tree or parent IDs, and duplicate tree headers. The actual source check also type-resolves the candidate and each parent as commits. The parser is narrower than full Git object validation: synthetic minimal headers containing a tree line and a header/body separator, with or without a parent line, are accepted without author/committer fields. No partial commit object was placed in Git’s object store. This review therefore establishes extraction of tree/parent fields from the actual 9e02 object, not full `git fsck` validity for arbitrary imported commit objects; Git’s fsck documentation lists missing author/committer as object errors ([git-fsck](https://git-scm.com/docs/git-fsck)).

A mocked failure resolving an actual parent is caught and converted to `ValueError` (`actual Git parent is unavailable`). A genuinely missing candidate object fails closed too, but `validate_candidate_source` lets `subprocess.CalledProcessError` escape through `git_text`; missing typed-receipt `git show` reads likewise use the unwrapped `git_bytes` helper. This is a diagnostic/error-shape gap, not an acceptance path. The missing-object probe also surfaced Git’s stderr warning `garbage found: /Users/deniskopylov/polisyos/.git/worktrees/polisyos9/refs`; no cleanup or metadata change was attempted.
