## Material findings

1. **The actual-child success selector necessarily includes the deliberately failing child.** In the added `record_admission` path, a child whose controlled profile initially does not match any actual candidate lever is rewritten to the first actual lever, and its `child_declaration` is then set to `None`. The later `successful_refs` predicate checks only whether the resulting profile rule matches any candidate lever. That predicate is therefore true for the rewritten failed child as well as for a matching child, so `assert len(successful_refs) == 1` fails when the fixture has the intended one completed and one failed branch. The child decision must use an explicit outcome discriminator; in this fixture, declaration presence can distinguish the injected N5 child from the no-model failure branch, provided the test also asserts exactly one declaration-bearing child. The synthetic declaration remains a controlled fixture input and must not be presented as authority.

2. **The partial-run node denominator includes the root.** The added assertion expects exactly two `recursive_payload["nodes"]` and compares their node refs to only `sibling_node_refs`. The unchanged `derive_recursive_design_graph` sets `node_refs=[design_ref, *modules]`, and `_build_sibling_failed_recursive_run_v3` emits one row for every graph node. On the intended two-child graph, the payload therefore has three rows: the root (pending in a partial run), followed by the completed and failed children. Assert the root row and both child refs, rather than omitting the root from the denominator.

3. **The changed failure message conflicts with the existing fresh-GET checkpoint assertion.** The patch changes the injected exception message to `later actual child failed after its earlier sibling completed`, while the existing fresh-GET test still asserts the exact persisted message `controlled_second_sibling_failure: later child failed after its earlier sibling completed`. `GenerationCycleError` formats `str(error)` as `"{code}: {message}"`, and the partial checkpoint retains that string. Keep the existing message or update the checkpoint expectation to the new exact value; preserving the old message avoids unrelated fixture churn.

These are direct source contradictions in the proposed test delta, not inferred runtime failures. I did not execute the test because this review task explicitly prohibited tests.

The optional `root_n4_generation_client` is passed to the existing `N4GenerationPort` constructor's `llm_client` seam in the internal root-source branch; a distinct `RecordedGenerationReplayClient` provides an independent replay cursor for that call. It routes each exact child problem through `ConfiguredCandidateSimulationContextAdmissionOwner`, stores per-child context/profile handoffs with matching design-problem and profile-selection refs, and binds the successful child's N5 input/source refs to the selected context, profile, model declaration, materialization, and resolved source.

The separate `/api/v1/runs/{core_run_id}` request is a real fresh HTTP consumer over the persisted producer artifact. Existing `_lineage_projection` resolves the N5 input from CAS, checks tenant/cell/run/job scope and source/context/profile refs, and for child nodes compares those refs against the compiled child handoff. The test retains the tampered-N5 negative control and checks that the failed-branch checkpoint survives corruption. The patch also keeps candidate limitations and `publication_authority=False`; this controlled recorded fixture does not establish authentic production-profile admission, real-time currentness, external causal grounding, or publication authority.

The new Python parameter is confined to the internal generation function and does not alter an HTTP DTO or generated client. `N4GenerationPort.__init__` already accepts `llm_client: object | None`; the default `None` behavior is preserved. No lifecycle or production caller change is included, so this patch should be described as a controlled root-source producer witness, not a new production-client configuration surface.
