### Distinguishing report-shape control

`_reported_output_statuses()` chooses `/summary/status` only when that value is a string; otherwise it falls back to a root `/status` string (`run_policy_design_case_local_validation_ladder.py:1157–1166`). I ran the real `execute_command()` with exit 0 and a fresh JSON payload `{"summary":{"status":7},"status":"pass"}`. It returned `status="pass"`, `fresh=true`, and no error. All current declared report producers use a nested `summary.status` contract, including the local probe (`_payload()` / `_summary()`), so this payload has an invalid canonical status plus a contradictory fallback. This is a current P38 divergence: the requirement is a fresh valid status from the declared producer report; the generic reader tests for *some* nonempty status string and accepts a malformed canonical report. Bind the path/schema to the four current output producers or reject malformed/contradictory summaries. The full result is in `status-boundary-probe.stdout.txt` (SHA-256 `dba3a49b9c3a5b7826985d4c318a2eee65a5764242d3f645bffdef892b0daa8f`).

Ordinary controls in that same run all behaved as intended: fresh `summary.status="pass"` passed; fresh `warn` with exit 0 failed; missing file, invalid JSON, array payload, missing status, and empty status all failed; unchanged prior `pass` failed freshness. The tests themselves directly exercise the warning and stale branches. This is not a reason to add a list of special malformed cases: define the expected status contract for each declared report and validate it generically.

### Missing-family boundary and source truthfulness

`run_production_data_static_check()` computes missing families by suppressing the source report's list whenever `resolver_executed` or any construct blocker is truthy (`local_prod_debug_probe.py:1317–1326`). It then derives check status from remaining issues (`1334–1351`). The tested positive blocker originates from an injected dictionary, not a loaded resolver result or a content-bound physical-family receipt. `_construct_capability_report()` treats any embedded `metadata.capability_binding` mapping as a `status="pass"` report with `resolver_executed=false`, without validating its status/source (`1440–1456`). Although this is labelled `compiled_data_requirement_spec_metadata`, a status marker alone does not establish that the physical family exists. Current code does **not** claim a direct hash, but it hides the known absent family in details. The bounded correction direction is to preserve the missing-family finding and ensure the child’s structured status remains warning/limited unless a producer-backed resolution is independently established; no hardcoded family/hash or fake producer should be introduced.

The synthetic real-index control passes through `ProductionDataContractIndex` and correctly reports the two absent families plus `production_data_construct_capability_evidence_missing` (`test_local_prod_debug_probe.py:1151–1188`). This supports the distinction between source-family compatibility projection and source authority. The current source/test paths do not provide a physical production snapshot for this review.
