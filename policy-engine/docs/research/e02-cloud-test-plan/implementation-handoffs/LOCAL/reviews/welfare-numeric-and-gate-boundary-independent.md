## Welfare numeric admission

The current `welfare_context.py` widens the numeric boundary across the whole response/weight/sensitivity surface rather than adding per-field boolean checks. `_coerce_welfare_numeric_scalar()` admits finite `numbers.Real` and `Decimal`, rejects Python and NumPy booleans before float conversion, and rejects non-finite values. The mapping and sequence adapters apply that rule to every supplied entry. Response mappings validate all values before selecting `metric_order`; weights do the same before projection to requested labels. Thus an invalid value hidden under an unselected mapping key cannot be silently ignored. Sensitivity requires nonempty mappings, known response labels, nonempty parameter names, and finite numeric coefficients; a missing sensitivity key alone uses the identity default.

The fallback boundary is also explicit. A present response must be a mapping or nonempty list/tuple and malformed values fail with `ERROR_WELFARE_DIMENSION_MISMATCH`; they do not fall back to simulation metrics. A present malformed `metric_order` fails. If response is absent, explicit metric order or mapping weight keys select metric names, followed by the existing named-metric priority and the single-numeric-metric fallback. A missing weights field defaults to `[1.0]` only for a single response label; present `None`, empty weights, wrong shape, and multi-label weights omission fail. Present sensitivity is not treated as the absent-key identity default.

The `Metrics` contract is `dict[str, float | int | str]` (`core/contracts/foundry.py:1599-1605`). The implementation keeps that compatibility: numeric floats/ints and parseable numeric strings are eligible welfare metrics; descriptive strings remain nonnumeric and are omitted from the numeric projection. The numeric-string allowance is limited to Metrics, not response/weight/sensitivity parameters. A direct typed control preserved the float, int, and string runtime variants and projected `1.25`, `2`, and `"3.5"` to numeric values while excluding a qualitative string: `LOCAL/raw/welfare-numeric-gate-independent/metrics-union-control.txt@sha256:39b344573393720e79f8d55a1d9d1598caff79a6a359cffe6a4dca73bcc0271e`.

## Gate malformed-input identity and default selector

Two distinct malformed-present Trinity ref payloads are reduced to the same `invalid_refs["trinity_bundle_ref"] = "malformed_ref"`; the typed selected-ref map omits the key, so the request contexts and IDs are identical. Retained output: `LOCAL/raw/gate-selected-view-independent/malformed-ref-identity-control.json@sha256:c39fef8c513661c9df1533ccad2a2f3f5af2fa26b22fe5d9ec35afe35ab7ca76`.

This is a **same P38 class one level deeper (P40)**. It is technically fixable without deciding what a human approval authorizes: add a stable, typed identity/fingerprint for each malformed-present replay input to the request context (or its typed invalid-ref summary), hashing a canonical safe representation of JSON-compatible malformed values. The request ID already fingerprints the full serialized context, and cache admission recomputes that ID from current state. A changed invalid input would then force a new request and discard the old approval. If a value cannot be safely canonicalized, fail closed from cache reuse rather than use a type-name or generic `malformed_ref` proxy. This changes only what the request binds; it does not make the artifact valid or upgrade readiness. It is consistent with the current 1.2 request-context design, subject to ABI version ownership if the schema has already frozen.

## Gate malformed-input identity delta

This delta reviews the later uncommitted source bytes at the same shared checkpoint (`HEAD=4699fdf8419dd2c89609f68a3edf5f3bfb7c851a`, tree `741784521d909f775d50863a29deec63cde300cd`). It supersedes the earlier `governance_gate_requests.py` hash above for this Gate finding only; it is not a final source freeze.

The malformed-present identity defect is addressed structurally for JSON-valued replay inputs. `_gate_replay_summary()` adds an `invalid_input_digests` mapping only when replay refs are invalid. `_invalid_replay_input_digests()` sorts the input keys and hashes a canonical JSON object that binds the invalid-ref scope, GateRequest schema version, canonicalization version, input key, and complete canonical value. The digest is carried through `GateContext.replay_summary`, which `HumanGateProtocol` includes in its deterministic request fingerprint. Thus two different malformed JSON objects no longer share the prior `malformed_ref` identity proxy, while key-order-only changes keep the same request ID. A value that cannot be represented is refused before a request can be issued; the implementation does not replace it with a type name or generic digest.

The human-gate consumer test observes the whole request/admission consequence. It first persists a request with a malformed-present Trinity ref and confirms that the ref is recorded as invalid, is not listed as missing, and has one digest. Reversing the object key order preserves the request ID. Changing the nested reported hash changes the digest and request ID. With an approval still supplied against the old request, `_handle_initial_gate_request()` cannot admit the persisted request against the new context, issues a replacement, removes the old approval, and records `gate.request.unverified`. This is evidence for cached-request binding and stale-approval rejection; it does not establish a policy about what a valid human `approve` authorizes when readiness is incomplete.

The serializer distinguishes JSON booleans, integers, and floats (`true`, `1`, and `1.0` produce different digests), requires string object keys, rejects cycles and non-finite numbers, and refuses unsupported raw objects. A direct helper probe confirmed those cases. It accepts Python `Sequence` values as JSON arrays, so a tuple and list with the same members intentionally canonicalize identically. That matches the declared `json-sorted-keys-v1` semantics; if the requirement were identity of pre-serialization Python runtime types, tuple/list equivalence would remain a bounded limitation. No collision was observed for JSON values in this review.

This is the **same P38 proxy-identity class one level deeper (P40)** as the previous finding, not a new class. The candidate widens the identity mechanism to cover the complete JSON value for each invalid-present replay input, instead of patching an example ref or adding a per-field exception. The accepted field remains inside the existing `GateContext.replay_summary: dict[str, Any]`; no Gate DTO field or generated schema shape changes in this delta. G approval semantics remain held and no formal closure is proposed.
