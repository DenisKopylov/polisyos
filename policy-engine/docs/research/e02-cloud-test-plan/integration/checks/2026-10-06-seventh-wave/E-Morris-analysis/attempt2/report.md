# Attempt 2: native Morris analysis row-count discriminator

**Result: confirmed bounded analysis-count discrepancy on candidate 70c4.** The native candidate API accepted four valid Morris rows (two full trajectories) under a plan that declares one trajectory, estimates two runs, and sets `max_estimated_runs=2`. Its result truthfully reports `total_runs=4` / `effective_run_count=4`, while the same result retains `estimated_runs=2` and `n_trajectories=1`. This confirms the analysis entrypoint does not bind supplied Morris row count to the plan's declared cap/count. It does not establish that the sampler generates too many rows, nor close any broader B99 criterion by itself.

The healthy control was accepted with two rows and returned native `mu_star[x]=2.0` for `y=2*x`, `total_runs=2`, `estimated_runs=2`, `n_trajectories=1`. The excess case used `[[0, 2/3], [1/3, 1]]` in one dimension, which forms two complete four-level Morris grid trajectories; SALib 1.5.2 returned `mu_star[x]=2.0`, `total_runs=4`, `successful_runs=4`, `estimated_runs=2`, `n_trajectories=1`. Both calls used the actual candidate `analyze_sensitivity` path and unmocked SALib analyzer. No analyzer resampling argument was changed; the native API default was used. The one-trajectory control emits expected degrees-of-freedom/invalid-divide warnings for its dispersion statistic, and `sigma` is NaN there; this witness supports only the point estimate and admission/count behavior.
