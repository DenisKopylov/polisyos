### Cross-lane F/Gini boundary that the C receipt does not test

The exact F source freeze is `4128879c3cec37dcb2bd1e7f91a1da5e4f51d2d3` / tree `134aca5ad6bac87da8d2f3d18a4be0ab20652251` (its receipt/doc commit is `e84acb04fbe1fbebdfa5a54f87ff0fc72640a4ef`). F's `compute_gini_hard` now raises on nonfinite or negative active values. The C freeze is based on old base `198076…`; its existing passing training receipt therefore does **not** exercise the strict F implementation.

At C `a452011…`, `_EconomicsTemporalConsumptionMechanism.apply` calls `_native_to_composite` before the policy action and again immediately after it. That projection constructs `EconomicState`, whose `_compute_distributions` calls `compute_gini_hard` for wealth and income. It then calls `CompositeExecutor.step`; the Economics plugin order is LaborMarket -> Taxation -> Transfers -> Consumption -> Savings, while the C training bridge deliberately removes plugin Consumption because the native policy seam performs that action. `CompositeExecutor.step` calls `update_aggregates()` after mechanisms, which recomputes distributions. Thus, once C is combined with F's strict Gini, it can reject negative values during the pre/post projection or at end-of-step refresh; this is on the training/evaluation path, not a dashboard-only metric.

The boundary is not settled by admission today. `EconomicsTrainingAdapter.assess` checks one-domain/config/plugin types but does not validate state numeric support or run `EconomicState.validate`. That validator returns false for negative wealth, yet Taxation subtracts income tax directly from wealth without a nonnegative floor, and the normal CompositeExecutor does not call the validator. The F reviewer supplied a deterministic positive pre-state (10 active agents, wealth 1, income/wage 20,000, employed, default tax/transfer rates): labor can preserve the 20,000 income, tax is 2,500, means-tested transfer is 2,000, leaving wealth -499 before distribution refresh. This is evidence that a current transition can leave the validator's domain; it is not authority to declare signed wealth valid or invalid, and no full C adapter training run on the F source freeze is present.

**Required owner decision before claiming compatibility:** F/Foundry must adjudicate the Economics wealth domain and what to do when a classical Gini is undefined. If signed wealth/debt is a supported state, expose the missing inequality statistic as typed unavailable or adopt an owner-ratified signed-resource measure; do not let one unsupported statistic abort an otherwise admitted training profile without declaring that scope. If negative wealth is forbidden, the profile/mechanism contract must say so and prove transitions preserve it; do not invent a clamp, floor, wealth normalization, or hidden assumption in this bridge. Until then record `not_established` for combined C/F behavior and keep the C/F boundary limited/held; rerun only the exact affected consumer/property after the canonical contract changes, with a receipt at that combined SHA.

## Public surface, retirement, and closure actions

The plugin release fragment calls `polisy train` behavior `public_stable` and correctly describes the new nonzero exit for `bridge_pending`. However it explicitly has `public_surface_inventory_reviewed = false`, `migration_docs = []`, and `runbook_docs = []`. The `polisyos.foundry` inventory currently lists only the stable facade entrypoints and not `polisyos.foundry.plugins`; the README calls plugins a legacy compatibility surface and retains the old entry-point group, but provides no dated sunset. Before accepting a public-surface completion claim, reconcile the CLI/legacy-plugin scope with the public-surface inventory owner, document migration/automation impact and chosen support/sunset status, and regenerate/review the inventory. Do not remove discovery routes or ABI just because the new code is deterministic.

The existing code-level capability labels are not “complete”: plugin owner-issued verification/admission remains `verification_missing` (LA-022); the public `.train` one-call scope, typed checkpoint/resume contract, and other-profile `bridge_pending` semantics remain unresolved for LA-023; cross-F negative-wealth/Gini composition is `not_established`. The present product slice does not establish verification authority, cross-call recovery, GPU support, historical reward persistence, general third-party plugin trust, or LA-003/LA-004 equivalence. These limits are part of the acceptance result, not reasons to duplicate F's canonical loss or mutate profile semantics locally.
