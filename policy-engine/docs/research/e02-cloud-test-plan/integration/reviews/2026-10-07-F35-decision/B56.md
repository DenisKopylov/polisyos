# B56: решение по исходному критерию и текущему остатку

## Вердикт

F уже реализовал корректную локальную защиту от вложенной параллельности: один Scientist job последовательно выполняет весь свой план folds/repeats, а параллельность допускается на внешнем уровне задач. Это достаточный минимальный механизм для случая, когда все конкурирующие fits действительно проходят через один общий admitted worker pool. Не надо возвращать внутренний `ThreadPoolExecutor` или создавать второй общий scheduler в TMLE.

B56 в целом пока **не закрыт**. Остаётся доказать, что канонический Runtime-путь использует один фактический ресурсный admission для конкурирующих study jobs, и получить полный локальный входной пакет для этой проверки. Это граница Runtime/Scientist admission и отсутствующий вход, а не новая математическая работа F. Кодовая мера F может считаться готовой к интеграции отдельно от finding closure.

Приёмка требует ограничить общим ресурсом допущенную работу, не терять folds/repeats, сохранять численный результат и provenance и измерить время, RSS, активные workers и ожидание. ## Что показывает существующая архитектура

- `LocalWorkerPool(max_workers=...)` уже может быть общим ограничителем **числа активных NodeTask slots**. Его `_can_start` сравнивает `active_tasks` с `max_workers`; это пригодный существующий механизм, если канонический путь помещает каждый fit job в один общий экземпляр pool.
- `NodeTask.resource_requirements` задаёт `cpu_cores` и `memory_mb`, но текущий `LocalWorkerPool` admission ими не взвешивает. `TaskRouter` выбирает пул преимущественно по GPU/idle capacity. Поэтому существующие типы не являются доказательством общего CPU/RSS бюджета.
- В исследованном Runtime-пути `RunLifecycle` вызывает `run_experiment` напрямую. Его публичная сигнатура принимает store, quota, observability и отдельные authority contexts, но не общий worker pool/resource permit. `ExecutionContext` тоже не несёт такой permit. `ControlWorker` синхронно обрабатывает один leased job на экземпляр; это само по себе не задаёт общий лимит между всеми экземплярами/репликами.
- Имеющиеся `BudgetState`/`BudgetLedger` учитывают денежный `max_usd`, а Foundry `CostBudget` — оценку времени/памяти для cost gating. Их нельзя переименовать в ресурсный admission: первое ограничивает spend, второе не является активной общей reservation.

Итак, уже существует локальный slot-cap primitive, но его соединение с реальной Study/Runtime admission не доказано. Если actual path пользуется одним таким пулом, достаточно переиспользовать его. Если admission должна быть общей между несколькими Runtime workers/processes и это не покрывает существующий путь, B/Runtime owner должен согласовать минимальный typed permit/lease в каноническом job context и использовать существующую очередь/ledger там, где она действительно поддерживает эти единицы. F только читает выданную границу и исполняет folds; он не объявляет общую квоту.

## Владельцы и границы решения

1. **F — TMLE/fold core:** оставить serial-fold policy как безопасный default при удерживаемом внешнем worker permit; сохранять весь fold/repeat/seed plan и честно возвращать `effective_fold_workers=1`. Если `max_parallel_folds` далее должен разрешать >1 fold, это возможно только через permit из того же admission, иначе параметр остаётся запросом, а не фактически выделенным ресурсом. Не добавлять новый scheduler внутри estimator.
2. **B/Runtime + Scientist worker-pool owner — bridge/admission:** дать source-bound ответ, каким общим admission пользуется `run_experiment → sync_run_causal_full` и какая единица/лимит допускается; провести реальные concurrent study jobs через этот же контур. Переиспользовать `LocalWorkerPool` worker slots только если все конкурирующие jobs действительно делят один pool. Не подменять общий лимит числом ControlWorker lease или тестовым `max_workers`.
3. **Владелец фактического study input:** до локального replay предоставить ссылки/идентичность текущих read-only входов и полный workload roster (models, folds, repeats, seeds, competing jobs), не копируя production data в cloud. F-пакет явно оставляет эти refs и команду неизвестными.
4. **G — verifier:** после появления этого пакета проверить точную frozen source/runtime admission на локальных read-only данных и сохранить полные deciding outputs. До этого кодовая приёмка не превращается в закрытие B56.

## Триггер возобновления и достаточная приёмка

Возобновлять локальную общую проверку, когда Runtime/admission owner выдаст пакет с точным source SHA/tree, runnable command/profile, полной идентичностью входов и jobs, общей admission-сессией/лимитом, списком всех моделей/folds/repeats/seeds и доступом к свежему CAS readback. Если текущий production путь не имеет общей admission-сессии, сначала назначить этому мосту B/Runtime owner и подключить канонический путь; отсутствие такого моста не лечится повтором теста на вручную созданном pool.

На одном frozen каноническом пути при admission caps 1 и 2 проверить, что число одновременно активных fits/folds не превышает именно лимит admission, ожидающие jobs запускаются после освобождения slot, каждый запланированный fold/repeat/seed исполняется ровно один раз, output и provenance читаются из CAS, а результаты соответствуют serial reference в объявленном tolerance. Зафиксировать полный numerator/denominator, очередь и wait, active peak, wall и peak RSS. Если область общего лимита проходит через несколько pool instances/processes, включить параллельный контроль через эти instances; иначе не расширять область утверждения сверх одного canonical admission scope. Missing/corrupt admission input должен оставить решение ограниченным, а не заменить его заданным тестом лимитом.

## Pattern pass

- `P01/P02`: TMLE producer и локальная pool test есть, но реальный Runtime-to-pool bridge для admitted study пока `bridge_missing`/не доказан; acceptance сигнал — actual consumer path использует shared permit и свежий output readback.
- `P13`: новый универсальный scheduler здесь создаст лишнюю подсистему; сначала переиспользовать существующий worker-slot cap.
- `P37`: в тесте budget задан test harness-ом; происхождение фактического production cap пока `not_established`.
- `P38`: свойство — число совокупно активных fits в admitted scope ≤ действительный cap; текущий тест проверяет `max_workers` одного созданного в тесте pool. Divergent case: несколько отдельных pool instances, каждый зелёный при cap `c`, могут вместе разрешить >`c` активных fits; другой divergent case — фактический direct Runtime path, который не вызывает тестовый pool. Решающий тест должен проходить через установленный canonical shared admission.

Проверки и тесты в этом задании не запускались; выполнен только read-only разбор pinned source, исходной карточки, F evidence pack и текущих runtime/resource contracts.
