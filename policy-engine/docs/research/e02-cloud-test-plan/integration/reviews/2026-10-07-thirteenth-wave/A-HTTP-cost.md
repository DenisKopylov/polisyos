## Monetary producer, consumer, and surface

The new `response_shapes.py@1590` is materially safer than the earlier scalar projection: cost requires typed status **and** origin; an event missing both becomes `legacy_untyped`, `missing`, and `unknown`, not `$0`; mixed unknown cost does not form a partial total; Decimal nonzero-underflow is rejected when Decimal reaches this layer (`#L238-L358`, `#L361-L420`, `#L104-L115`). `nl_pipeline.py@1590` advances budget only for an explicitly known reported/estimated/reuse amount or an explicitly marked no-provider-call zero (`#L1551-L1594`, `#L1662-L1690`). Candidate tests cover unknown-vs-zero, mixed totals, estimates, reuse, prefix mutation, and tiny `1e-10` values (`tests/unit/runtime/http/services/test_e02_monetary_usage_projection.py` and `tests/unit/runtime/http/services/control/test_nl_pipeline_cost_projection.py`). This source corrects the prior `None → 0.0` behavior in the A projection; do not carry the old B66 consumer FAIL onto this changed source as if it were a current result.

There is still a concrete producer/consumer gap. The actual default path passes `call_events.append` as the observer (`nl_pipeline.py@1590#L5337-L5345` → `factory.py@1590#L149-L175`). `TracedLLMClient._record_tokens` emits amounts, `usage_origin`, `provider_call`, `cache_hit`, and estimate fields, then sends that event directly to the observer, but does not emit `cost_status`, `cost_origin`, or `usage_status` (`core/llm/traced_client.py@1590#L322-L348`, `#L403-L405`). The strict consumer consequently classifies this normal event as legacy/untyped and leaves cost/usage unknown; it cannot budget from provider-reported cost or the local estimate. That is conservative, but the standard producer does not yet establish the typed cost path. The existing cost tests construct already-typed event dictionaries and do not exercise `TracedLLMClient → call observer → _sum_call_events → NL budget/persisted summary`. Smallest closure: have the canonical LLM producer/adapter emit the typed event contract, preserving reported, estimated, reuse, and unknown semantics; then add one bridge test through the actual event callback and NL consumer. Do not infer status from scalar fields in a parallel A decoder. Coordinate with the canonical LLM/B owner, then rerun the affected A consumer check on the composed source.

Numerical boundary: on this A candidate, `gateway_client.py@1590#L506-L509` uses default `json.loads` float parsing and `core/llm/response.py@1590#L140-L153` converts values to `float`; a raw positive lexeme such as `1e-1000` can become `0.0` before the Decimal-aware A projection can reject it. The A helper test’s `1e-10` does not distinguish this. The same `_as_float` also clamps a parsed negative amount to `0.0`, so malformed negative provider cost can become indistinguishable from a real reported zero if typed downstream. Use the canonical decoder/typed event boundary owned with the LLM adapter (and reuse the B decoder work if it is in the composed candidate); reject/refuse underflow and negative lexemes there rather than adding an out-of-band parser. The A-only candidate has no receipt testing these raw-lexeme paths.

The per-run `run_performance_summary` preserves `cost_status`, `cost_origin`, estimate, and basis (`nl_pipeline.py@1590#L1814-L1867`), but other consumers are not interchangeable: `scientist/api.py@1590#L104-L128` computes an SLO metric from scalar cost fields and may sum available variants when others are unknown; `run_evaluator.py@1590#L208-L221` treats missing `run_cost_usd` as zero for its remaining-budget ratio. This review found no receipt binding either helper to the ordinary A HTTP path or proving a monetary authorization effect; route those consumers to their own exact owner/criterion rather than using them to reject the bounded HTTP code review. Also keep B66 durable settlement separate from A’s original bounded low-value/informative-check criterion; this audit does not require a new ledger or external invoice reconciliation.
