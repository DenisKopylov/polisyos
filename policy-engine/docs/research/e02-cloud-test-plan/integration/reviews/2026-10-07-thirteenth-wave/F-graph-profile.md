# F graph-profile gate: independent source review

**Decision: HOLD the full profile-gate claim; GO only for the narrow declared-enum refusal.** The guard correctly refuses inputs whose `graph_type` is `MGRAPH`, `PAG`, or `CPDAG` before reconciliation rewrites and before node persistence. The candidate also contains a positive producer/CAS test that accepts a known MGraph payload after changing only `graph_type` to `admg`, and an existing PAG consumer silently turns the new refusal into a successful no-op. These are concrete boundary/consumer effects, not a request for a universal graph classifier.

## What the candidate gate establishes

`graph_reconciliation.py::_validate_reconciliation_profile` admits only `GraphType.DAG`/`GraphType.ADMG`, then calls the existing static endpoint/lag validator. `ReconcileCausalGraph.pure_step` invokes it before filtering, confidence merge, or cycle rewrite (around line 1011). `ComposeSCMFragments.pure_step` applies the same guard to every input fragment graph (around 1323). The node's typed graph-ref resolver uses it (around `reconcile_causal_graph.py:203–208`), and the node validates its output again before CAS persistence (`:1070–1085`). The exact-candidate wheel and native runs now establish the prior direct `GraphType.MGRAPH` refusal at the producer/Node boundary, including registered dispatch, CAS preservation, and selected method-result/cache controls. The same guard also iterates fragment graphs in `ComposeSCMFragments.pure_step`; that composition refusal has source/unit coverage, but was not part of the installed 16-case or native 9-case selector wave.

This is a gate over the *declared enum* plus the existing static resolved-endpoint/lag shape. It does not derive semantic family from graph content. `_validate_static_admg` checks lag and endpoint marks; it does not reconcile MGraph metadata or exclude R/proxy nodes. That distinction is acceptable as a bounded declared-profile boundary only if the admitted artifact's declarations are internally coherent.

## Blocking divergent cases

1. **Known MGraph metadata is accepted under the ADMG label.** In the exact candidate's `test_graph_intake_current_content.py:108–119, 148–157`, the test builds a valid MGraph with `build_mgraph` (`R_X`, `X_star`, substantive variables, and serialized `MGraphMetadata`), changes only `value["graph_type"]` to `"admg"`, and expects the producer, node, CAS write, and fresh reader to succeed while preserving `metadata["mgraph"]`. This is not an arbitrary naming heuristic: `MGraphMetadata` is documented as semantic metadata for a `CausalGraphModel` with `graph_type=MGRAPH` (`ir/analytics/mgraph.py:73–80`), and `extract_mgraph_metadata` explicitly rejects any other `graph_type` (`:124–143`). `GraphType.ADMG` is documented as bidirected-only with no R-nodes (`ir/analytics/causal_graph.py:19–26`), while the candidate's `_validate_static_admg` does not check that known MGraph contract. The exact-candidate runtime diagnostic in `native-F/results/mgraph-extraction-diagnostic/summary.md` confirms this path: `build_mgraph`, retag-only, registered producer/`MethodJob`, Node, CAS, and fresh reader complete successfully (retagged artifact `sha256:dbb7233ea3ab79fbf52c3abe9f29c41827134fd7e3e2d47066cb5cd603139302`); the artifact is `ADMG` while retaining valid MGraph metadata. **The extractor refusal alone is not the discriminator:** the canonical `extract_mgraph_metadata` also correctly refuses a clean ADMG with no MGraph metadata, because that API is reserved for `graph_type=MGRAPH`. The diagnostic's corrected clean bidirected-ADMG control (artifact `sha256:9d2c83f1ebf6efbac5e3bec04a4d38f2555628665a41aac471438ff46d653619`) succeeds with no MGraph metadata and receives the same expected extractor refusal. The distinguishing counterexample is specifically that the retagged output preserves a valid, typed `metadata["mgraph"]` (including R-node/proxy declarations) under the ADMG label; the clean ADMG does not. This is the known profile-consistency boundary, not a claim that every ADMG must be consumable by the MGraph extractor. The existing positive retag test would make this mismatch green by construction.

   **P40 bucket:** same class as the prior MGraph→ADMG type-erasure finding, one level deeper. The new guard fixes the correctly typed MGRAPH case but accepts the same known MGraph content after a tag change. This does not justify an unbounded classifier. Minimum closure: make this explicit known contradiction refuse at the reconciliation boundary (or require a real, semantics-preserving conversion that removes/rebinds the MGraph contract before declaring ADMG), and replace the current positive test with a negative that proves no result/CAS artifact is emitted. Keep a clean ADMG positive control. Unknown node-name conventions with no typed MGraph metadata remain a declared limitation, not a new classifier requirement.

2. **The existing PAG discovery consumer silently degrades.** `discovery_pipeline.py::_maybe_reconcile` documents that it runs when a literature prior or LLM hints are supplied, constructs `GraphReconciliationData(data_graph=pag, ...)`, and calls `ReconcileCausalGraph.pure_step` (`:752–784`). The new profile gate rejects this `GraphType.PAG` input. A broad `except Exception` then returns the original PAG (`:785–786`); the caller at `:1356–1367` validates that returned PAG but adds no warning when it remains valid. Thus the optional prior/hint reconciliation is skipped without a typed limitation or warning. The contract change is understandable for a PAG consumer, but the current caller presents the feature as active and hides its refusal.

   Minimum closure: make the PAG path's out-of-scope/deferred result visible in the `DiscoveryPipelineReport` (or explicitly branch before the call and document a typed no-op), and add a consumer test with a valid PAG plus prior/hint that asserts both the retained graph and the surfaced limitation. Do not coerce PAG to DAG/ADMG merely to pass this gate.
