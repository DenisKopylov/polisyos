## Findings by class

1. **P38/P10 — identification payload is not typed or read by the relation.** The `identification_ref` parameter is generic `ArtifactRefModel`. `_value_subject_for_artifact` verifies its bytes/hash and manifest lineage, but never validates the bytes as `ValueOuterSet` (nor restricts the kind to an admitted identification artifact). The fixture itself uses `synthetic.identification_set`; its fresh-child test loads `ValueOuterSet` separately after relation loading. Divergent case: an arbitrary JSON payload with a valid CAS manifest and matching declared roster can pass `resolve_value_subject_relation` while containing no identification set. Bound this API/documentation strictly to lineage/content agreement, or have the canonical A/C10 owner validate the actual supported identification payload before any consumer uses the join. This blocks claiming the relation alone proves the identification channel; it need not force C07 to duplicate A's canonical reader.
2. **P37/P32 — “complete” is complete relative to a producer declaration, not the actual producer basis.** `value_subject_producer_inputs` derives expected dependencies from `ValueArtifactSubject`; the reader compares the stored manifest back to that same declared object. The missing/extra/duplicate tests prove roster equality to the declaration, not that a real method's entire consumed basis was declared. Falsifier: the producer consumes an additional source/contrast input but writes the same subject and omits that dependency from its manifest; these checks remain green. Thus CAS bytes/manifest equality is `recomputed`, while actual producer-basis completeness, meaning of population/time/source/model, and currentness are `not_established` until independently reconciled to the actual producer. The serialized `predicate_basis: "recomputed"` / `verifier_provenance` literal must never be consumed as scientific or non-producer verifier authority; keep `production_value_eligible=false` enforced at the downstream boundary.
3. **P08/P37 — selected manifest-view loss is a live dependency, not closed by this source.** `C06-selected-view-producer-loss.json` records an actual same-bytes/different-lineage Core result: Core returned a nondefault `manifest_profile_sha256` automatically, but the IR adapter returned the unprofiled default and resolved the old subject.
