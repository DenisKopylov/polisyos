## What needs to scale

PolicyOS models domains as regions of a causal variable graph. The meaning of a state edit depends on the selected model and its resolution. A growing system needs to discover, compose, compare and retire variable bindings across thousands of independently named constructs, measurements and executable models. The acquisition decision depends on which missing input could change the decision, so the system must retain the role and purpose of each requirement from compilation through execution and readback. [North Star, sections 2–5](../system-design-decisions/policy-design-causal-operating-system-north-star.md#2-everything-reduces-to-data--but-the-causal-structure-is-not-data) · [Organizing rules and extension conditions](../system-design-decisions/universal-policy-design-system-vision-and-organizing-rules.md#11-how-to-extend-the-system-conformance-conditions)

Research should establish which of these identities must stay distinct and where their relationships live.

| Layer | Identity question |
| --- | --- |
| Human language and discovery | Which names, translations, aliases and provider codes point to candidate meanings, and within which namespace and epoch? |
| Semantic variable | What construct is measured or manipulated, at what entity grain, with which definition, units or dimension, stock/flow or parameter semantics, and version? |
| Observation | Which exact series, release, geography, population, valid period, observation time, base or denominator, method, uncertainty and provenance produced the value? |
| Executable model | Which model version, variable resolution, state path and slot type consume or produce this variable? Which unit, time and population transformations are admitted? |
| Task and causal role | In this model and request, is it an intervention target, required input, observed outcome, proxy, confounder, calibration target or derived quantity? Which producer establishes that obligation? |

Roles are contextual. A tax rate can be an input to one model, an intervention in another and an observed outcome in a third. A label change can preserve meaning. A new population, denominator, definition or measurement method can change what a result justifies even when the string and scalar stay the same. Rule 12 separates discoverable, executable and admitted authority. A discovery result or LLM proposal may suggest a binding. A protected action or published claim needs a resolved, purpose-scoped binding with verifiable provenance. Unknown or ambiguous bindings must survive as typed limitations, with candidate work and retention governed by the existing status and authority lattice. [Free growth and the authority boundary](../system-design-decisions/universal-policy-design-system-vision-and-organizing-rules.md#5-organizing-rules-the-laws)

## Architecture questions for research

Existing records delimit the starting point. `SlotSpec` carries an executable slot ID, scope, value type, unit, kind, merge rule and optional state path. `VariableAlignment` carries dataset-local and canonical labels, match method, confidence, evidence and proxy state. `CanonicalAcquisitionObservation` already binds dataset, variable, geography, time and provenance. The runtime canonical name registry also defines existing names and synonyms. Research should preserve these distinctions and identify where a versioned, scope-qualified bridge belongs. A name match or alignment score can rank candidates. Verifying equivalence, unit transformation and authority requires the corresponding scoped evidence. [IR slot contract](../../src/polisyos/ir/kernel/slots.py#L50) · [Catalog alignment records](../../src/polisyos/data_forge/domains/catalog/knowledge/variable_alignment.py#L28) · [Scoped observation](../../src/polisyos/data_forge/domains/catalog/knowledge/overlay.py#L638) · [Canonical name registry](../../src/polisyos/data_forge/domains/academic/knowledge/runtime_canonical_registry.py#L9)

1. **Identity and ownership.** Compare stable namespaced semantic IDs, versioned content identities, and a hybrid with stable IDs plus immutable definition and binding revisions. Specify who owns semantic definitions, display aliases, equivalence and supersession, physical source metadata, and model port bindings. Compare one centrally owned namespace with federated authoring and shared admission. A useful answer explains collision handling, local additions, renames, splits, merges, revocations and performance under partial coverage.
2. **The binding contract.** Specify the smallest join from a typed requirement and role to a semantic variable, scoped source descriptor, exact observation, declared transformation and executable slot. Clarify the equivalence, derivation, proxy and causal-transport relations that can be reused, who validates each, and what limits propagate. Explain when a measurement can enter a new causal model without transferring its evidential or publication authority.
3. **Acquisition from model obligations.** Decide which existing owner should emit a missing input or lever obligation and how it composes with the existing outcome gap, grounding coverage, constraints and method requirements. Decide how the compiler and planner distinguish a valid unsatisfied requirement from no compatible source, an ambiguous descriptor and an unavailable observation. Preserve VOI and budget semantics. A bounded unpriced research run still needs the same valid input binding.
4. **Free-grow operation.** Show how a new source series and a new compatible variable become usable through declared metadata, typed rules and verification. Measure where manual review remains necessary, what makes a cross-domain relation admissible, how competing candidates are ranked and how updates invalidate affected consumers. Include a migration path that keeps existing exact artifact, slot and profile references replayable. Keep closed and current views distinct.
5. **Reuse before adding an owner.** Start with typed IR slots, Catalog alignment and discovery, data requirement compilation, N7 routing, and the existing CAS/history and verification owners. Explain what can be wired or extended, what must be consolidated, and what genuinely requires a new contract. Return a small prototype and a migration sequence with explicit producer, artifact, bridge, consumer and public limitation projection. ## Minimum tests that can disprove the proposal

| Case | Required observation |
| --- | --- |
| Fiscal mismatch | A tax-rate requirement never resolves to balance bytes. A balance ratio does not silently enter a USD stock. Each refusal identifies the exact missing relation. If the model declares a justified balance input, its separate real producer can request it while the outcome remains tax rate. |
| New resource and domain | Two held-out variables with distinct units, time and grain enter through the same declared extension mechanism. The normal request reaches the real compiler, admitted producer, persisted result and fresh consumer. The common Runtime requires no per-variable branch. |
| Ambiguity and change | Same display name across namespaces or conflicting descriptors refuses or exposes candidates. A verified alias preserves identity. A change of definition, denominator, scope, or selected profile creates an explicit new binding and affects only dependent consumers. Old artifacts replay with their historical bindings. |
| Equality versus new evidence | An exact effective-basis repeat retains N4/N5 identity and reruns the required cheap current consequences. A changed dependent input runs actual N5. An independent observation with the same number preserves its separate acquisition, time and measurement identity. It receives only the authority justified by its evidence. |
| Consumer and removal | Fresh API and applicable dashboard or export show the selected variable, role, unit, source, status and limitation. Remove or replace the selected descriptor, transformation, observation or model binding while keeping similar names or the same bytes under another profile. The consumer must refuse or degrade at the affected boundary. |

The first prototype should demonstrate an existing owner path with one valid binding and a close semantic counterexample. It should then admit a previously unseen compatible variable without a code change to the common path. Include lookup cost, ambiguity rate, invalidation scope and the cost of extending metadata. The open capabilities are a producer and bridge for the fiscal model-input obligation and a semantic end-to-end proof for the scalable binding. This follows P05, P10, P27, P31, P32, P37 and P38.
