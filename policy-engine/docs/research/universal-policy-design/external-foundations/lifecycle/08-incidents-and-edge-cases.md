# Инциденты и составные крайние случаи

Исследование от 2026-10-21. Здесь **семь внешних инцидентов I01–I07** из первичных отчётов и **восемь сконструированных атак X01–X08**. Это разные множества: атаки не являются случившимися сбоями PolicyOS. Инциденты мотивируют проект, но не доказывают наличие аналогичного дефекта в нашем runtime. Числа ёмкости чужих платформ не становятся нашими лимитами.

## 1. Что действительно случалось

| ID; событие; публикация | Установленный источником механизм | Вывод для проекта PolicyOS, а не факт о его реализации |
|---|---|---|
| I01 — GitLab, 2017-01-31; отчёт 2017-02-10 | При восстановлении replica удалили primary. Отставание replication/WAL и неработавший backup path осложнили восстановление; несовместимый `pg_dump` и недоставленная почта об ошибке разрушили предположения о защите. [Первичный postmortem](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/) | Backup, replica, alert delivery и восстановление — четыре разные проверяемые способности. Для выбранного root нужны actual restore и fresh reader; «job завершён» недостаточно. |
| I02 — GitHub, 2018-10-21; отчёт 2018-10-30 | Короткий network partition привёл к failover с различающимися записями в двух регионах. Безопасный автоматический failback отсутствовал. Проверка backup procedure не предсказывала стоимость полного восстановления: перенос, распаковка, checksum/load и catch-up конкурировали за ресурсы. [Первичный postmortem](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/) | Source incarnation и reconciliation важнее внешне зелёной replica. План recovery охватывает весь путь и очереди; нельзя обещать RTO из времени одного backup-step. |
| I03 — AWS S3, 2017-02-28; дата публикации на странице не указана | Ошибочный параметр maintenance-команды удалил слишком много capacity index/placement. Полный restart и integrity checks выросшего metadata state заняли больше ожидаемого. Status console также зависела от S3. [Отчёт AWS](https://aws.amazon.com/message/41926/) | Ограничивать blast radius и учитывать metadata/cold restart. Проверить, что recovery и truthful limitation surface доступны при отказе той зависимости, которую они объясняют. |
| I04 — Slack, 2020-05-12; отчёт 2020-06-29, обновлён 2020-07-14 | После performance regression autoscaling расширил fleet. Флаг откатили, но synchronizer HAProxy исчерпал фиксированные slots: пытался добавлять новые hosts до освобождения старых. Позднее scale-in выявил устаревший backend set. [Отчёт Slack](https://slack.engineering/a-terrible-horrible-no-good-very-bad-day-at-slack/) | Rollback причины не откатывает накопившееся состояние. Replacement должен учитывать additions и retirements одной desired generation, сохранять serving constraints и проверять фактический set. Простое «удалить старое первым» тоже может нарушить availability. |
| I05 — Slack, 2021-01-04; отчёт 2021-02-01, обновлён 2021-02-03 | Network degradation увеличила ожидание: CPU и занятость threads дали противоположные scaling signals. Массовое provisioning упёрлось в open-files/quota и тот же degraded network; созданные, но неготовые instances заняли fleet limit. [Отчёт Slack](https://slack.engineering/slacks-outage-on-january-4th-2021/) | QPS, CPU и число запущенных workers не взаимозаменяемы с productive capacity. Downstream admission ограничивает scale-up; common dependency может выключить и рабочий путь, и его диагностику. |
| I06 — Meta, 2021-10-04; отчёт 2021-10-05 | Maintenance-команда отключила backbone; audit tool не остановил её. DNS advertisement и recovery access зависели от потерянной сети. Возврат выполняли постепенно, учитывая surge нагрузки и caches. [Отчёт Meta](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/) | Проверять общую зависимость control/recovery plane. Восстановление требует разрешённого маршрута и staged ramp; это не повод создавать privileged bypass или владеть внешней инфраструктурой. |
| I07 — Cloudflare, 2025-11-18; отчёт в тот же день | Изменение permissions расширило результат metadata query, не ограниченного database. Generated feature file превысил consumer limit; поколения чередовались, а версии consumer отказывали по-разному. После rollback login backlog усилил восстановительную нагрузку. [Отчёт Cloudflare](https://blog.cloudflare.com/18-november-2025-outage/) | Generated output остаётся недоверенным input для следующего owner. Проверять semantics, size и failure behavior producer/reader; rollback пригоден лишь при текущей совместимости и правах. |

Не выводить из этих отчётов, что PolicyOS нужен Kafka, Temporal, HDFS или глобальный control plane. Переносится различающее свойство: готовность после cold start, совместимость actual readers, ограниченная стоимость перехода и отсутствие ложного current/complete результата. Источники не устанавливают требуемый размер deployment.

## 2. Атаки на сочетания переходов

Ниже мысленные трассы. Проверки и removal controls пока **UNRUN**; они уточняют существующие T01–T20 в [плане](06-delivery-and-review.md), а не создают второй тестовый каталог.

| ID | Трасса, которая должна отличать правильный механизм | Требуемая реакция и владельцы |
|---|---|---|
| X01 — revision ABA | Snapshot/restore возвращает прежний offset; новый source incarnation использует те же локальные IDs; consumer cache ещё помнит более поздний мир | Native source incarnation + cut, restore generation и replay-floor reconciliation. Старый cursor не признаётся current. Capture/Claim/DV; T01/T05/T14/T18. |
| X02 — пропавшее отрицание | Claim говорит «исключений нет»; новое matching исключение появляется во время rebuild; точный reverse index его не видит, queue пуста | Owner-scope generation меняется до asynchronous fanout. Неполный index не может исключать dependency; dirty scope сохраняется до fenced assessment. T05/T08/T18. |
| X03 — корректировка вернулась к исходному значению | Correction → запрет use → restoration; coalescer видит одинаковое начальное/конечное value, между ними был публичный claim | Coalesce вычислительные wakeups, сохранить material events и промежуточные опубликованные reactions. Final-state calculation не заменяет action history. T05/T11/T18. |
| X04 — ресурсная смерть перед квитанцией | Decode расширяет маленький archive; global join спиллит; диск заполнен перед outcome commit; lease истекает, retry удваивает работу | Bounded stage admission, enforced decode/operator/spill limits, completion reserve и stable effect IDs. При недоступном store нельзя выдать success; restart reconciles attempted effects. T03/T15/T17/T20. |
| X05 — отменённый writer всё ещё жив | Parent cancelled, lease истекла; native worker продолжает писать derivative; GC/rights change успели пройти | Permission/write fence запрещает late commit; physical resource reservation освобождается только после установленного прекращения/изоляции расхода. Lease и память — разные свойства. T11/T13/T17/T20. |
| X06 — полномочный cache чужого вопроса | Bytes одинаковы, но изменились audience/purpose/population/unit или rights generation; single-flight отдаёт старый результат новому waiter | Переиспользовать только invariant computation; admission и смысл каждого use проверяются отдельно. No-hit и estimate не становятся complete/threshold verdict. T02/T08–T11/T19. |
| X07 — consumer пропустил tombstone | Отставший consumer пережил retention expiry; restore возвращает его cursor и старый allow | Gap detection до current projection; разрешённый current snapshot + retained suffix либо limitation. Raw history нельзя бессрочно удерживать вопреки правам. T05/T12/T14. |
| X08 — recovery заражает себя | Shared config/credentials/catalog ломаются; restore запускает все retries; diagnostics и high-cardinality logs заполняют оставшуюся capacity | Existing control/recovery owner имеет bounded reserve/path; retry budget и ramp учитывают downstream. Last-known-good проверяется на rights/currentness; при недоступном decisive control state — limitation, не cached green. T14/T16/T19/T20. |

Нужны также malformed/hostile inputs внутри X04/X06: decompression/recursive-reference growth, path traversal, parser-triggered network access, Unicode/identity collisions и instruction-like source text. Connector/parser owner ограничивает privileges и expansion; данные не могут выдавать команды, выбирать исполняемый plugin или менять authority. Это требование к существующей trust boundary, не новый универсальный sanitizer, который обещает понять весь контент.

## 3. Какие современные механизмы полезны

Сравнительный выбор — **композиция проверенных механизмов**, не один «самый передовой» движок. Native engine memory arbitration/spill помогает physical execution; source-specific snapshot/change protocols — continuity; owner-local transactional generations — invalidation; versioned immutable roots — повторное использование; permission/currentness fences — protected use. Ни один из них не заменяет остальные.

Для PolicyOS особенно важно разделять цену payload и цену обязательств по нему. Растут не только bytes, но и metadata edges, negative predicates, поддерживаемые claim uses, rights/copy decisions, lag и стоимость recovery. [Ресурсный проект](09-resource-execution-design.md) задаёт bounds и отказ для обеих частей; [финальный red-team](10-adversarial-review-and-delivery.md) проверяет их композицию.

Pattern pass: I/X не новые Pxx. P40 — более глубокие примеры R02/R03/R07–R11 существующего review; P05/P07/P08/P13/P27/P29/P31/P37/P38. Target: owner-bound transition с actual resource/semantic predicate и fresh consumer. До реализации отсутствуют behavioral verification/semantic tests; incident analogy не закрывает этот пробел.
