# C1 candidate graph finalization handoff

The existing academic pipeline owner now exposes
`finalize_extraction_campaign_graph` and `resolve_extraction_campaign_graph`.
They consume complete durable campaign outcomes through the checkpoint owner's
read-only historical API. Original source hashes and execution epochs are not
restamped. The new graph artifact carries its own synthetic ancestry and
candidate-only scope, the old input epoch, complete input/outcome bindings, a
separate current graph implementation projection, and its effective capacities.

Every attempt builds private state at a stable unique path. Only completed
load+synthesis output receives the final manifest. The resolver recomputes
actual input/outcome identities, the complete output artifact set and bytes,
staging usage and the run-emitted graph strangle. Original work, attempt and
input packets are reused without a provider client. Rebuilding a killed private
graph never consumes another extraction attempt.

The strangle's predicate is actual use of the two default disk staging owners
under bound limits. Quantitative namespace writes/batches, actual storage
configuration, and staging file hashes decide it. Migration equivalence remains
the separate complete-table/schema/value release proof; the receipt does not
claim this run compared a historical resident implementation. Serialized limits
are not a hard Python RSS bound: encoding/model-validation temporaries can
multiply a bounded payload. The operational resource profile/watchdog is a
separate requirement.
